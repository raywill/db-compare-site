DuckDB

OLAP #嵌入式 #OLAP #单机 #列存 #向量化执行 #MIT开源 #Python生态 #零运维

"分析型 SQLite"——跑在进程里的单机列存 OLAP 引擎：pip install 即用、向量化执行吃满多核、直接对 Parquet/CSV/S3 做 SQL，把"不够上数仓、pandas 又太慢"的中间地带一口吃掉；代价是单写者、单机天花板，以及所有服务端能力（认证、审计、多用户）一概没有。

The "analytical SQLite" — an in-process, single-node columnar OLAP engine: `pip install` and go, vectorized execution saturating all cores, SQL directly against Parquet/CSV/S3. It devours the middle ground between "not enough for a warehouse, too slow in pandas" — at the cost of a single-writer lock, a single-node ceiling, and zero server-side capabilities (auth, audit, multi-user).

硬维度（14 项）

1 静态加密 / TDE 有

有——v1.4.0 起支持透明加密：ATTACH 'f.db' AS d (ENCRYPTION_KEY '...')，AES-256-GCM（默认）/ AES-CTR-256，覆盖主文件、WAL 和溢出临时文件；密钥丢失则数据不可恢复，不支持原地加密/解密/轮换（需 COPY 到新库）；官方声明尚未达到 NIST 合规要求（跟踪 issue #20162）。证据：官方文档（1.4.0 发布公告、encryption 博客）。

2 TLS / 传输加密 不适用

不适用——进程内嵌入式，无服务端、无网络协议、无监听端口；httpfs 读 S3/HTTPS 是客户端 TLS；云端传输加密是 MotherDuck 托管服务的能力。证据：官方文档（架构）。

3 审计 不适用

不适用——无用户体系、无服务端审计日志；谁拿到文件谁就能读。审计需求由宿主应用自己实现。证据：官方文档（架构）+ 社区共识。

4 认证与权限 不适用

不适用——进程内嵌入式，无服务端/用户体系、无 GRANT 模型；文件系统权限即权限边界。证据：官方文档（架构）。

5 备份恢复 部分支持

部分支持——无在线备份工具、无 WAL 归档、无 PITR。可用方式：EXPORT DATABASE 'dir' (FORMAT PARQUET)（MVCC 一致快照，可在线，是社区推荐默认方式）、COPY FROM DATABASE 跨库拷贝、进程关闭后直接拷贝 .duckdb 文件；打开状态下直接 cp 文件可能损坏社区共识。恢复 = IMPORT DATABASE 或文件替换。证据：官方文档 + 社区共识。

6 大版本升级 部分支持

部分支持——存储格式向后兼容自 v0.10 起是官方目标；格式变化时无原地升级，必须"旧二进制 EXPORT DATABASE + 新二进制 IMPORT DATABASE"（需同时保留两个版本的可执行文件）；回退同理。v1.0–v1.5 默认存储格式 pin 在 v1.0（政策非承诺）；v2.0 将换新默认存储格式。证据：官方文档（storage）。

7 可观测性 部分支持

部分支持——有：EXPLAIN / EXPLAIN ANALYZE、PRAGMA profiling（json 输出可画火焰图）、duckdb_memory()、pragma_database_size()、duckdb_temporary_files()、duckdb_settings()、duckdb_databases()；查证为无：慢查询日志、跨会话查询历史（duckdb_queries()/duckdb_connections() 不存在，社区探针 v1.5.5 实测确认）、PRAGMA integrity_check。证据：官方文档 + 社区实测。

8 连接模型 有

有——进程内连接，创建开销极低；查询自动用满全部 CPU 核心（SET threads 可调）；无网络往返、无连接池概念（不需要）。证据：官方文档 + 社区共识。

9 事务与隔离级别 有

有——ACID；为批量优化的 MVCC（借鉴 HyPer），默认快照隔离（Snapshot Isolation）；进程内多线程写走乐观并发：append 永不冲突，并发 update/delete 同一行后者报冲突失败；跨进程只允许"单进程读写"或"多进程只读"，第二进程写会报文件锁错误；无 SAVEPOINT社区共识。证据：官方文档（concurrency）+ 社区共识。

10 复制与一致性 不适用

不适用——单机进程内引擎，无复制协议、无多副本一致性；"多副本" = 文件拷贝；多机协作靠 DuckLake（对象存储 + 元数据）或 MotherDuck；Quack client-server 协议 2026-05 技术预览、beta 中。证据：官方文档 + 社区共识。

11 扩展方式 部分支持

部分支持——纵向扩展（scale-up）有：多核并行 + 外存溢出，单机吃到 GB~数百 GB；横向扩展（scale-out）查证为无：引擎本身不支持分布式查询，多机方案只有 MotherDuck 托管（serverless ducklings）或应用层分片。证据：官方文档 + 社区共识。

12 兼容性 部分支持

部分支持——SQL 方言对标 PostgreSQL（非 PG 线协议）；扩展可 ATTACH 外部库做联邦查询（postgres/sqlite/mysql 扫描扩展）；Python/R/Arrow/Polars/pandas 零拷贝集成；dbt 有社区适配器 dbt-duckdb；WASM 可跑浏览器。证据：官方文档 + 社区共识。

13 许可证与商业模式 有

有——MIT 全开源，无功能阉割的社区版；DuckDB Foundation（非营利）持有 IP；商业化 = DuckLabs（原 DuckDB Labs）支持/咨询服务 + MotherDuck 独立公司的 serverless 托管（按存储 GB 与计算秒计费，免费层 10GB——厂商口径）。2026-08-26 DuckLabs 宣布加入 AWS，开源项目治理与许可不变（官方口径）。证据：官方 history + AWS 官方博客。

14 中文资料丰富度 部分支持

部分支持——官方文档为英文；中文资料以博客、课程、知乎/CSDN 实践帖为主，体量远小于 MySQL/PG 及国产主流库；出海/英文生态反而是强项。证据：社区共识。

1 Data-at-rest encryption / TDE Supported

Supported — since v1.4.0: ATTACH 'f.db' AS d (ENCRYPTION_KEY '...'), AES-256-GCM (default) / AES-CTR-256, covering the main file, WAL, and spilled temp files; a lost key means unrecoverable data; no in-place encrypt/decrypt/re-key (copy to a new database instead); officially not yet NIST-compliant (tracked in issue #20162). Evidence: official docs (1.4.0 release notes, encryption blog).

2 TLS / transport encryption N/A — in-process e

N/A — in-process embedded library, no server, no network protocol, no listening port; httpfs reading S3/HTTPS is client-side TLS; cloud transport encryption is MotherDuck's managed-service capability. Evidence: official docs (architecture).

3 Auditing N/A — no user mode

N/A — no user model, no server-side audit log; whoever can read the file can read the data. Auditing is the host application's job. Evidence: official docs (architecture) + community consensus.

4 Authentication & authorization N/A — in-process e

N/A — in-process embedded, no server/user system, no GRANT model; filesystem permissions are the permission boundary. Evidence: official docs (architecture).

5 Backup & recovery Partially supported

Partially supported — no online backup tool, no WAL archiving, no PITR. Available: EXPORT DATABASE 'dir' (FORMAT PARQUET) (MVCC-consistent snapshot, online, the community-recommended default), COPY FROM DATABASE for cross-database copies, copying the .duckdb file after the process closes; copying the file while the database is open can corrupt it 社区共识. Restore = IMPORT DATABASE or file replacement. Evidence: official docs + community consensus.

6 Major-version upgrades Partially supported

Partially supported — storage-format backward compatibility is an official goal since v0.10; there is no in-place upgrade when the format changes — the only path is old-binary EXPORT DATABASE + new-binary IMPORT DATABASE (both executables must be kept); rollback works the same way. Default storage format pinned at v1.0 for the v1.0–v1.5 line (policy, not a promise); v2.0 introduces a new default storage format. Evidence: official docs (storage).

7 Observability Partially supported

Partially supported — has EXPLAIN / EXPLAIN ANALYZE, PRAGMA profiling (JSON output, flamegraph-able), duckdb_memory(), pragma_database_size(), duckdb_temporary_files(), duckdb_settings(), duckdb_databases(); verified absent: slow-query log, cross-session query history (duckdb_queries() / duckdb_connections() don't exist, confirmed by a community probe on v1.5.5), PRAGMA integrity_check. Evidence: official docs + community testing.

8 Connection model Supported

Supported — in-process connections with negligible setup cost; queries automatically use all CPU cores (SET threads adjustable); no network round-trips, no connection pooling concept (none needed). Evidence: official docs + community consensus.

9 Transactions & isolation levels Supported

Supported — ACID; batch-optimized MVCC (HyPer-inspired), default snapshot isolation; in-process multi-threaded writes use optimistic concurrency: appends never conflict, concurrent update/delete of the same row fails the later one; cross-process only allows "single process read-write" or "multiple processes read-only" — a second writer gets a file-lock error; no SAVEPOINT 社区共识. Evidence: official docs (concurrency) + community consensus.

10 Replication & consistency N/A — single-node

N/A — single-node in-process engine, no replication protocol, no multi-copy consistency; "more copies" = file copies; multi-node collaboration via DuckLake (object storage + metadata) or MotherDuck; the Quack client-server protocol is in technical preview/beta (May 2026). Evidence: official docs + community consensus.

11 Scaling Partially supported

Partially supported — scale-up supported: multi-core parallelism + out-of-core spilling, single node handles GBs to hundreds of GBs; scale-out verified absent: the engine has no distributed queries; multi-node options are MotherDuck managed (serverless ducklings) or application-level sharding. Evidence: official docs + community consensus.

12 Compatibility Partially supported

Partially supported — SQL dialect targets PostgreSQL (not the PG wire protocol); extensions ATTACH external databases for federated scans (postgres/sqlite/mysql); zero-copy Python/R/Arrow/Polars/pandas integration; community dbt-duckdb adapter; WASM runs in browsers. Evidence: official docs + community consensus.

13 License & business model Supported

Supported — fully MIT open source, no crippled community edition; DuckDB Foundation (non-profit) holds the IP; commercialization = DuckLabs (formerly DuckDB Labs) support/consulting + MotherDuck's independent serverless hosting (per-GB storage and per-second compute, 10GB free tier — vendor claim). On 2026-08-26 DuckLabs announced joining AWS; open-source governance and license unchanged (official statement). Evidence: official history + AWS official blog.

14 Chinese-language resources Partially supported

Partially supported — official docs are English; Chinese material is mostly blogs, courses, and community practice posts, far smaller than for MySQL/PG or major domestic databases; the English/international ecosystem is a strength instead. Evidence: community consensus.

杀手特性

每个特性 = 它是什么 + 为什么是真本事 + 推到边缘会发生什么。

  1. 进程内向量化执行：单机分析性能的第一性原理 真本事：算子一次处理 2048 行的列向量（非逐行火山模型），配合 morsel-driven 并行（Leis 等，SIGMOD 2014）把数据切成 morsel 丢进线程池动态调度，列存 row group（约 12 万行）+ zonemap + 轻量压缩（FSST/ALP/Chimp/字典/RLE/bitpacking）。社区实测：TPC-H SF10（约 11GB）22 条查询 4.3 秒跑完（i7-13700H，嵌入版 v1.5.2）。 边缘真相：快的是"单机多核扫描聚合"；preserve_insertion_order 默认 true 为保序付出代价；小查询有固定开销；TB 级以上或巨型 shuffle 依然是 Spark/数仓的地盘。单机上限是物理定律，不是调优问题。
  2. 零导入查文件：SQL 直接对 Parquet/CSV/S3 真本事：SELECT * FROM 's3://bucket/*.parquet' 即查即走，列裁剪 + 谓词下推 + 分区消除（hive 分区）让几十 GB 文件常常只读几 MB；CSV/JSON 自动嗅探 schema。探索和 ETL 的"先建表再导数"整段消失。 边缘真相：CSV auto-detect 会猜错分隔符/类型/日期（生产管线必须显式关 auto_detect）；远程文件延迟进 P99；同一文件被反复高频查询时，导入成 DuckDB 表更快。以及：这是"读"神器，"写回 Parquet"是另一回事。
  3. 零运维嵌入：pip install 就是部署 真本事：单二进制/单 pip 包，无 server、无端口、无配置，Python/R/Node/Java/Rust/Go/WASM 全语言绑定，DataFrame 零拷贝直查。把分析能力嵌进应用、notebook、CLI、边缘设备的摩擦力趋近于零。 边缘真相：省掉的运维没有消失，只是转移——备份、监控、多用户、权限全部变成应用层的责任（见硬维度：四项不适用）。"免运维"是把 DBA 的工作外包给了写应用的人。
  4. 扩展生态：一个引擎，多种形态 真本事：httpfs（S3/HTTP）、spatial（GIS）、postgres/mysql/sqlite（联邦扫描）、iceberg、aws（凭证链）、json 等官方扩展；外围有 MotherDuck（serverless+混合执行）、DuckLake（开放湖仓格式，v1.0 已发布）、Quack（client-server 协议，v2.0 转正）。 边缘真相：扩展与引擎版本锁定，升级 DuckDB 后必须 UPDATE EXTENSIONS，版本错配会崩；Quack 仍是 beta，并发写线程数有限（社区口径约 8）；DuckLake/Iceberg 写支持等能力在补齐中。生态在爆发，但"稳定版"和"预览版"要分开看。

Each feature = what it is + why it's genuinely strong + the edge truth.

  1. In-process vectorized execution: single-node analytics from first principles Genuinely strong: operators process 2,048-row column vectors (not row-at-a-time volcano), with morsel-driven parallelism (Leis et al., SIGMOD 2014) slicing work into morsels scheduled dynamically across the thread pool; columnar row groups (~120k rows) + zone maps + lightweight compression (FSST/ALP/Chimp/dictionary/RLE/bitpacking). Community measurement: TPC-H SF10 (~11GB), all 22 queries in 4.3s (i7-13700H, embedded v1.5.2). Edge truth: what's fast is "single-node multi-core scan-aggregate"; preserve_insertion_order defaults to true at a real cost; small queries carry fixed overhead; beyond TB scale or giant shuffles it's Spark/warehouse territory. The single-node ceiling is physics, not tuning.
  2. Zero-import file queries: SQL straight at Parquet/CSV/S3 Genuinely strong: SELECT * FROM 's3://bucket/*.parquet' just works; column pruning + predicate pushdown + partition elimination (hive partitioning) mean tens of GB of files often read only a few MB; CSV/JSON schema auto-sniffing. The "create table, then load" ritual disappears for exploration and ETL. Edge truth: CSV auto-detect misfires on production data (delimiters, types, dates) — pin parameters and disable auto_detect in pipelines; remote-file latency lands in your P99; repeatedly hot files are faster imported as DuckDB tables. Also: it's a read superpower; writing back to Parquet is a different story.
  3. Zero-ops embedding: pip install is the deployment Genuinely strong: single binary/package, no server, no ports, no config; bindings for Python/R/Node/Java/Rust/Go/WASM; DataFrames queried in place with zero copies. Friction of embedding analytics into apps, notebooks, CLIs, and edge devices approaches zero. Edge truth: the ops didn't vanish, they moved — backup, monitoring, multi-user, permissions all become the application's job (see hard dimensions: four N/A). "No ops" outsources the DBA's work to whoever writes the app.
  4. Extension ecosystem: one engine, many shapes Genuinely strong: official extensions httpfs (S3/HTTP), spatial (GIS), postgres/mysql/sqlite (federated scans), iceberg, aws (credential chain), json; around it MotherDuck (serverless + hybrid execution), DuckLake (open lakehouse format, v1.0 out), Quack (client-server protocol, goes stable in v2.0). Edge truth: extensions are version-locked to the engine — after upgrading DuckDB you must run UPDATE EXTENSIONS, mismatches crash; Quack is still beta with limited concurrent writers (community claim ~8 threads); DuckLake/Iceberg write support is still maturing. The ecosystem is exploding, but "stable" and "preview" must be read separately.

深水区

深水区一：单写者——刻在架构里的并发天花板（领域：并发模型）

  • 机制：进程内多线程写走 MVCC + 乐观并发（append 永不冲突，同行并发改后者冲突报错）；跨进程靠文件锁二选一：单进程读写，或多进程只读。
  • 推到边缘：第二个进程以写模式打开同一文件直接报 Could not set lock on file；多 worker ETL 并行写同一 .duckdb 文件必须串行化，否则第二个部署直接撞锁——这是"第二个节点上线就炸"的经典生产事故；Docker 里忘记挂 volume，容器一停数据全丢（社区高频坑）。
  • 选型含义：任何"多进程/多机并发写同一文件"的架构，DuckDB 直接出局。标准解法：单写进程 + 其他进程 ATTACH ... (READ_ONLY)，或写时分文件、读时合并；真要多用户读写，上 MotherDuck 或等 Quack 转正。这是选型第一问，答不上来后面都不用谈。
  • 来源：官方文档（concurrency）；社区共识（多独立技术文档）；社区实测（sq/neilotoole 驱动文档）。

深水区二：内存与外存溢出——"能跑 100GB"的账单（领域：资源管理）

  • 机制：统一 buffer manager 掌管进程全部内存（页缓存与算子临时内存动态互借）；memory_limit 默认 80% 系统内存；超限后阻塞算子（分组、join、排序、窗口函数）把中间结果溢出到 temp_directory。
  • 推到边缘：没有 temp_directory（或无 swap）时内存限制执行不下去，进程内存无界增长直到被 OOM killer 干掉（源码级确认）；深嵌套查询的溢出量可达数据集 30 倍且"不总是可靠"社区实测；第三方评测：50GB 输入在 16GB 机器上外存聚合比内存慢约 30 倍——"能跑"和"能用"是两回事；加密库用户若没开 temp_file_encryption，溢出的临时文件是明文（官方实现者文档警示）。
  • 选型含义：生产环境三件套必须配齐：SET memory_limit + SET temp_directory（放 SSD，留足磁盘）+ 容器内存/disk 双限额。把 DuckDB 当"无限内存"用的管线，第一个大促就是 OOM 演练。
  • 来源：官方文档（memory 管理）；社区实测（nlesc 指南、firepanda 评测）；源码注释（temporary_memory_manager.cpp）。

深水区三：存储格式与版本升级——没有"原地升级"这回事（领域：运维/升级）

  • 机制：存储格式向后兼容自 v0.10 起是官方目标；前向兼容仅 best-effort；格式变化时官方迁移路径是旧二进制 EXPORT DATABASE + 新二进制 IMPORT DATABASE。
  • 推到边缘：升级后旧文件可能直接打不开，且必须同时保留新旧两个版本的可执行文件才能迁移——CI 自动升级的单二进制部署没有迁移路径；降级更惨：新格式文件旧版本打不开，只能删库或重导；2026-02/03 曾出现 checkpoint 并发 bug 导致 WAL 回放失败、文件无法打开（后修复，但作者承认修复成立的前提是"checkpoint 期间禁删表"——恢复子系统仍在重构中）；v2.0 将切换新默认存储格式，1.x 用户要提前规划。
  • 选型含义：把"升级 DuckDB"当成一次 ETL 演练来排期：pin 版本、EXPORT/IMPORT 演练、回滚预案。关键报表库建议 pin 住小版本，因为每个补丁版都在修"wrong results"类 bug（v1.5.6 一次修了多个静默错误结果问题）。
  • 来源：官方文档（storage）；官方发布公告（1.5.6）；社区分析（powerbrowser 研究文档，PR #21067/#21285）。

深水区四：备份的诚实边界——快照有，PITR 没有（领域：备份恢复）

  • 机制：EXPORT DATABASE (FORMAT PARQUET) 利用 MVCC 读一致快照，可在线备份，输出为 Parquet 目录 + schema.sql；或关进程后拷文件。
  • 推到边缘：打开状态下直接 cp .duckdb 文件可能拷到写一半的状态，恢复出来是坏的（社区共识：必须先 CHECKPOINT，仍有竞态窗口）；删数据后文件不缩小（VACUUM 只做统计信息/空间复用，缩文件唯一可靠办法是 EXPORT+IMPORT）；无 WAL 归档、无时间点恢复——"删库跑路"的恢复点就是上次导出；真实案例：checkpoint 损坏后靠"只读 ATTACH 逐表 COPY 到新库"救回 60M 行数据（62 秒），但重建后文件从 9.0GB 膨胀到 14.2GB（压缩与插入顺序强相关）。
  • 选型含义：DuckDB 是"分析引擎"不是"交易库"——把它当唯一持久层存关键数据是架构错误；正确姿势是上游 OLTP 库（PG/MySQL）做 PITR，DuckDB 当可重建的派生层。备份策略 = 定时 EXPORT + 版本化 Parquet 目录。
  • 来源：官方文档；社区实测（johngavin 备份方案对比、osmpbudynkiv2 恢复实录）；社区共识。

深水区五：直接查文件的代价账本（领域：查询执行）

  • 机制：读 Parquet 时列裁剪 + 谓词下推 + row group 统计信息剪枝；hive 分区消除；httpfs 范围请求读远程文件。
  • 推到边缘：CSV auto-detect 在生产数据上翻车是常态（分隔符、表头、日期格式猜错），社区建议生产管线一律显式指定参数、关 auto_detect；TIMESTAMP 解析默认按本地时区，跨时区管线会静默错位；反复被查询的热文件每次都要重新解析元数据+走网络，不如 CREATE TABLE AS 导入一次；S3 上的"选择性查询"省 IO，但全表扫描的 egress 费用照付。
  • 选型含义：探索/adhoc/ETL 落地前用"直接查"，高频服务查询用"导入表"；对象存储做热查询前先算 egress 账。这是"快"的另一面：快在计算，慢（贵）在 IO。
  • 来源：官方文档；社区共识（多独立实践指南）；社区实测（DuckDB vs Spark 对比）。

深水区六：加密的合规边界（领域：安全）

  • 机制：v1.4.0+ 的 ENCRYPTION_KEY 做 AES-256-GCM 整文件加密（含 WAL 与溢出临时文件），duckdb_databases() 可查 encrypted/cipher。
  • 推到边缘：官方明确未达 NIST 合规要求（跟踪 issue #20162），强合规行业（金融/医疗）评审会卡住；密钥丢失 = 数据永久不可恢复，无任何后门；不支持原地加解密与轮换，轮换 = COPY 到新库（停机窗口）；加密的只是 .duckdb 文件——COPY TO 导出的 Parquet/CSV 是明文，冷数据要靠卷加密或对象存储 SSE。
  • 选型含义：加密解决了"丢盘/丢文件"的威胁模型，解决不了"能读进程内存/能读密钥的人"；合规 checklist 上它算"有"，但"有"和"够"是两回事，先问审计要什么再选。
  • 来源：官方文档（1.4.0 公告、encryption 博客）；社区实测（efcoreprovider 加密文档）。

Deep dive 1: Single writer — the concurrency ceiling cast into the architecture (Domain: concurrency model)

  • Mechanism: in-process multi-threaded writes use MVCC + optimistic concurrency (appends never conflict; concurrent writes to the same row fail the later one); cross-process is a file-lock binary choice: single read-write process, or multiple read-only processes.
  • At the edge: a second process opening the same file for writes gets Could not set lock on file; multi-worker ETL writing the same .duckdb file must serialize or split files, otherwise the second deployment crashes into the lock — the classic "second node goes live and explodes" production incident; in Docker, forgetting the volume mapping means the data is gone when the container stops (a high-frequency community pitfall).
  • Selection meaning: any architecture with "multi-process/multi-node concurrent writes to one file" rules DuckDB out. Standard patterns: one writer process + ATTACH ... (READ_ONLY) elsewhere, or split files on write and merge on read; for real multi-user read-write, use MotherDuck or wait for Quack GA. This is selection question #1 — if you can't answer it, nothing else matters.
  • Sources: official docs (concurrency); community consensus (multiple independent technical write-ups); community testing (sq/neilotoole driver docs).

Deep dive 2: Memory and spilling — the bill for "it can run 100GB" (Domain: resource management)

  • Mechanism: a unified buffer manager owns all process memory (page cache and operator scratch borrow from each other); memory_limit defaults to 80% of system RAM; when exceeded, blocking operators (group-by, join, sort, window functions) spill intermediates to temp_directory.
  • At the edge: without temp_directory (or swap) the memory limit cannot be enforced — process memory grows unboundedly until the OOM killer takes it (confirmed in source); deeply nested queries can spill 30× the dataset size, "not always reliably" (community measurement); third-party benchmark: 50GB input on a 16GB box made external aggregation ~30× slower than in-memory — "can run" and "usable" are different things; encrypted-database users who leave temp_file_encryption off spill plaintext temp files (warned by the official implementer's docs).
  • Selection meaning: production needs the full triad: SET memory_limit + SET temp_directory (on SSD, with disk headroom) + both memory and disk limits on the container. Pipelines treating DuckDB as "infinite memory" get an OOM drill on the first traffic spike.
  • Sources: official docs (memory management); community testing (nlesc guide, firepanda benchmark); source comments (temporary_memory_manager.cpp).

Deep dive 3: Storage format and upgrades — there is no "in-place upgrade" (Domain: operations/upgrades)

  • Mechanism: backward compatibility of the storage format is an official goal since v0.10; forward compatibility is best-effort only; the official migration path on format changes is old-binary EXPORT DATABASE + new-binary IMPORT DATABASE.
  • At the edge: an old file may simply not open after upgrading, and migration requires keeping both the old and new executables — single-binary CI auto-upgrades have no migration path; downgrades are worse: new-format files don't open on old versions, so it's delete-and-reimport; in Feb/Mar 2026 a checkpoint-concurrency bug broke WAL replay and left files unopenable (later fixed, though the author admits the fix only holds because "dropping tables during checkpoint is currently disallowed" — the recovery subsystem is still being rebuilt); v2.0 switches to a new default storage format, so 1.x users should plan now.
  • Selection meaning: schedule "upgrade DuckDB" as an ETL rehearsal: pin versions, rehearse EXPORT/IMPORT, keep a rollback plan. Pin the patch version for critical reporting — every patch fixes "wrong results" class bugs (v1.5.6 fixed several silent wrong-result issues in one go).
  • Sources: official docs (storage); official release notes (1.5.6); community analysis (powerbrowser research doc, PRs #21067/#21285).

Deep dive 4: The honest boundaries of backup — snapshots yes, PITR no (Domain: backup & restore)

  • Mechanism: EXPORT DATABASE (FORMAT PARQUET) uses an MVCC-consistent snapshot, can run online, and emits a Parquet directory + schema.sql; or copy the file after the process stops.
  • At the edge: cp on an open .duckdb file can capture a half-written state that restores corrupted (community consensus: CHECKPOINT first still leaves a race window); deleted data doesn't shrink the file (VACUUM only does statistics/space reuse — EXPORT+IMPORT is the only reliable shrink); no WAL archiving, no point-in-time recovery — your recovery point is your last export; real case: after checkpoint corruption, a user rescued 60M rows via read-only ATTACH + table-by-table COPY into a new database (62s), but the rebuilt file ballooned from 9.0GB to 14.2GB (compression is strongly tied to insertion order).
  • Selection meaning: DuckDB is an analytics engine, not a transactional store — using it as the sole persistence for critical data is an architecture error. The correct posture: upstream OLTP (PG/MySQL) does PITR, DuckDB is a rebuildable derived layer. Backup strategy = scheduled EXPORTs + versioned Parquet directories.
  • Sources: official docs; community testing (johngavin backup comparison, osmpbudynkiv2 recovery write-up); community consensus.

Deep dive 5: The cost ledger of querying files directly (Domain: query execution)

  • Mechanism: reading Parquet gets column pruning + predicate pushdown + row-group statistics pruning; hive partition elimination; httpfs uses range requests on remote files.
  • At the edge: CSV auto-detect fails routinely on production data (delimiters, headers, date formats) — the community recommendation is explicit parameters and auto_detect off in pipelines; TIMESTAMP parsing defaults to the local timezone, silently shifting cross-timezone pipelines; hot files get re-parsed and re-fetched on every query — CREATE TABLE AS once is faster; on S3, selective queries save I/O but full scans still pay egress.
  • Selection meaning: use "direct query" for exploration/ad-hoc/pre-load ETL, "imported tables" for hot serving queries; price the egress before putting hot queries on object storage. The other side of "fast": compute is fast, I/O is slow (and expensive).
  • Sources: official docs; community consensus (multiple independent practice guides); community testing (DuckDB vs Spark comparison).

Deep dive 6: The compliance boundary of encryption (Domain: security)

  • Mechanism: v1.4.0+ ENCRYPTION_KEY gives AES-256-GCM whole-file encryption (WAL and spilled temp files included); duckdb_databases() exposes encrypted/cipher.
  • At the edge: officially not NIST-compliant (tracked in issue #20162) — regulated industries (finance/healthcare) will stall in review; lost key = permanently unrecoverable data, no backdoor; no in-place encryption/decryption or rotation — rotation means COPY to a new database (a downtime window); only the .duckdb file is encrypted — Parquet/CSV from COPY TO is plaintext, cold data needs volume encryption or object-store SSE.
  • Selection meaning: encryption solves the "lost disk/lost file" threat model, not "someone who can read process memory or the key"; on the compliance checklist it's a "have", but "have" ≠ "enough" — ask the auditor what they need first.
  • Sources: official docs (1.4.0 announcement, encryption blog); community testing (efcoreprovider encryption docs).

用户最买账的 5 点

  1. 单机分析性能，"小机器跑出集群感"
    • 为什么是真的：向量化（2048 行/向量）+ morsel 并行 + 列存剪枝是架构级优势，不是调优技巧；社区实测 TPC-H SF10 22 查询 4.3 秒；i7 级笔记本处理几十 GB 是日常。
    • 边缘与限度：甜蜜点在 GB~数百 GB；TB 级以上、巨型分布式 shuffle、流式，依然是 Spark/数仓的地盘；"比 pandas 快 10~100 倍"的对比成立的前提是"数据已超出内存舒适区"，小数据上 pandas 启动更快。来源：社区实测；观察版本：v1.5.2。
  2. Python/Arrow 零拷贝集成，"pandas 不够大、Spark 太重"之间的答案
    • 为什么是真的：duckdb.sql("SELECT ... FROM df") 直接查 DataFrame，无需 register；Arrow 零拷贝双向流通；Polars 互操作顺滑。数据科学家不用离开 notebook 就有完整 SQL。
    • 边缘与限度：替代的是"数据处理"不是"pandas API"——df.groupby().agg() 链式代码要重写成 SQL（chDB 这类方案才保留链式 API）；UDF/复杂 Python 逻辑下推有限。来源：官方文档 + 社区共识；观察版本：v1.5.x。
  3. SQL 方言好用，"写着爽"
    • 为什么是真的：QUALIFY（窗口函数直接过滤）、PIVOT/UNPIVOT 原生、嵌套类型（LIST/STRUCT/MAP）+ UNNEST、宏、对标 PG 的函数库。分析师从"CTE 套 CTE"里解放。
    • 边缘与限度：方言甜点不等于 PG 兼容——存储过程、触发器等 PG 特性没有；从 PG/MySQL 迁分析负载要过一遍函数差异；VARIANT/GEOMETRY 等新类型在 1.5 仍在打磨（v2.0 重写 VARIANT）。来源：官方文档 + 社区共识；观察版本：v1.5.x。
  4. 部署零摩擦，"pip install duckdb"
    • 为什么是真的：单二进制/单包，无 server、无端口、无配置；WASM 直接跑浏览器；Docker/边缘/CI 里即插即用。把"搭个分析环境"从半天变成一条命令。
    • 边缘与限度：零摩擦的是"跑起来"，生产化（备份、内存配额、版本 pin、多用户）一件都少不了；npm 旧包 duckdb 已废弃，要迁 @duckdb/node-api。来源：官方文档 + 社区共识；观察版本：v1.5.x。
  5. MIT 开源 + 基金会治理，"收购也拿不走"
    • 为什么是真的：MIT 无功能阉割；IP 在独立非营利基金会手里；2026-08 AWS 收购的是 DuckLabs 公司，开源项目治理与许可不变（AWS 官方博客口径）；社区 star 数万、日下载量百万级厂商口径。
    • 边缘与限度：许可是 MIT，路线图话语权仍在核心团队/雇主手里；收购后"技术咨询委员会""开放扩展签名"等承诺尚未交付待验证；生产级支持依然要买服务。来源：官方 history + AWS 官方博客；观察版本：2026-09。
  1. Single-node analytics performance — "cluster feel on a small box"
    • Why it's real: vectorization (2,048 rows/vector) + morsel parallelism + columnar pruning is an architectural advantage, not a tuning trick; community measurement: TPC-H SF10, 22 queries in 4.3s; an i7-class laptop on tens of GBs is routine.
    • Edges: the sweet spot is GBs to hundreds of GBs; beyond TB scale, giant distributed shuffles, and streaming remain Spark/warehouse land; "10–100× faster than pandas" holds when data has outgrown memory comfort — pandas starts faster on small data. Sources: community testing; observed on v1.5.2.
  2. Zero-copy Python/Arrow integration — the answer between "pandas too small, Spark too heavy"
    • Why it's real: duckdb.sql("SELECT ... FROM df") queries DataFrames directly, no registration; zero-copy Arrow in both directions; smooth Polars interop. Data scientists get full SQL without leaving the notebook.
    • Edges: it replaces data processing, not the pandas API — df.groupby().agg() chains must be rewritten as SQL (chDB-style APIs keep chains instead); UDF/complex Python logic pushdown is limited. Sources: official docs + community consensus; observed on v1.5.x.
  3. A SQL dialect that's a joy to write
    • Why it's real: QUALIFY (filter on window functions directly), native PIVOT/UNPIVOT, nested types (LIST/STRUCT/MAP) + UNNEST, macros, a PG-grade function library. Analysts escape the "CTE inside CTE" hell.
    • Edges: dialect sugar ≠ PG compatibility — stored procedures, triggers and other PG features don't exist; moving analytical workloads from PG/MySQL means walking the function diffs; VARIANT/GEOMETRY and other new types were still being refined in 1.5 (v2.0 rewrites VARIANT). Sources: official docs + community consensus; observed on v1.5.x.
  4. Zero-friction deployment — "pip install duckdb"
    • Why it's real: single binary/package, no server, no ports, no config; WASM runs in browsers; drop-in for Docker, edge, CI. "Set up an analytics environment" goes from half a day to one command.
    • Edges: what's frictionless is "getting it running" — productionization (backups, memory quotas, version pinning, multi-user) skips nothing; the old npm duckdb package is deprecated, migrate to @duckdb/node-api. Sources: official docs + community consensus; observed on v1.5.x.
  5. MIT open source + foundation governance — "an acquisition can't take it away"
    • Why it's real: MIT with no feature-crippled edition; IP held by the independent non-profit foundation; in August 2026 AWS acquired the DuckLabs company while open-source governance and licensing stayed unchanged (AWS official blog); community of tens of thousands of stars and million-plus daily downloads 厂商口径.
    • Edges: the license is MIT but roadmap influence still sits with the core team/employer; post-acquisition promises (technical advisory board, open extension signing) are not yet delivered (to verify); production-grade support still means buying services. Sources: official history + AWS official blog; observed September 2026.

判决

  • 适合谁：笔记本/单机上的数据分析与探索；Python 数据科学管线（pandas 瓶颈后的第一升级）；轻量 ETL（CSV/Parquet/S3 落地）；嵌入式分析（应用内、边缘、WASM）；CI/测试里的 OLAP 断言；GB~数百 GB 的交互式分析。
  • 不适合谁：多进程/多用户并发写；OLTP 与高频小事务；需要认证/审计/行列权限的合规系统；TB 级以上分布式分析；7×24 服务端 SLA 场景；把 DuckDB 当唯一持久层存关键数据。
  • 迁移成本：pandas/polars → 低（主要是把链式 API 重写成 SQL）；PG/MySQL 的分析负载 → 低-中（方言差异逐项过，ATTACH 可做联邦过渡）；Spark/数仓 → 中（分布式作业重写 + 数据规模先降到单机装得下）；传统 BI 报表 → 中（报表语义回归 + 版本 pin）。
  • Good for: data analysis and exploration on laptops/single nodes; Python data-science pipelines (the first upgrade past the pandas wall); light ETL (CSV/Parquet/S3 landing); embedded analytics (in-app, edge, WASM); OLAP assertions in CI/tests; interactive analysis on GBs to hundreds of GBs.
  • Not for: multi-process/multi-user concurrent writes; OLTP and high-frequency small transactions; compliance systems needing auth/audit/row-column permissions; distributed analysis beyond TB scale; 7×24 server SLA scenarios; using DuckDB as the sole persistence for critical data.
  • Migration cost: pandas/polars → low (mostly rewriting chained APIs into SQL); analytical workloads from PG/MySQL → low-medium (walk the dialect diffs; ATTACH enables federated transition); Spark/data warehouses → medium (rewrite distributed jobs + first fit data onto one node); traditional BI reporting → medium (report-semantics regression + version pinning).
