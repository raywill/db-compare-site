硬维度（47 项）

1 静态加密 / TDE 部分支持

部分支持——云数据库 OceanBase（托管服务）2021 年起支持 TDE 透明加密（阿里云官方产品动态）；内核有加密基础设施（备份加密 AES-256、密钥存储支持本地文件 / HSM / 云 KMS、微块支持用户指定加解密算法）。自建社区版的完整落盘加密能力边界未找到可靠证据，选型前需对照版本说明书。证据：阿里云官方动态厂商口径+ 社区共识。

2 TLS / 传输加密 部分支持

部分支持——云服务支持 SSL 链路加密；自建版 TLS 配置与默认行为未找到可靠证据。证据：厂商口径 + 待验证。

3 审计 部分支持

部分支持——GV$OB_SQL_AUDIT 提供 SQL 级审计（需 enable_sql_audit=true，环形内存缓冲，滚动覆盖，巡检需带时间窗）；合规级安全审计（DDL/权限变更的长期留存审计）未找到证据，不得与 MySQL Enterprise Audit 等同。证据：社区共识（easydba 巡检手册、mopheus skill）+ 官方文档待复核。

4 认证与权限 部分支持

部分支持——MySQL 模式支持用户/密码认证与 GRANT/REVOKE 权限体系，用户名可携带租户信息；Oracle 模式沿用其权限语义。角色（ROLE）与外部认证（LDAP/Kerberos）支持情况未找到可靠证据。证据：社区实测 + 待验证。

5 备份恢复 有

有——全量备份 → 增量备份 → 归档日志链路；支持按 SCN/时间点恢复（ALTER SYSTEM RESTORE/RECOVER TENANT）。证据：社区共识（mopheus 备份恢复 skill），官方文档待复核。

6 可观测性 部分支持

部分支持——系统视图族（GV$OB_SQL_AUDIT、GV$OB_PROCESSLIST、GV$SYSSTAT 等）+ ODC/OCP 管控平台；第三方巡检手册生态成熟。标准化 APM/慢查询治理能力与社区版边界未找到可靠证据。证据：社区实测 + 厂商口径。

7 连接模型 有

有——支持直连 OBServer（常用 2881），也支持经 OBProxy/ODP 代理接入（ODP 默认监听 2883），用户名可携带租户/集群信息。证据：官方 ODP 文档厂商口径+ 社区共识。

8 事务与隔离级别 有

有——单分区事务经 Paxos 一次提交；跨分区/跨机事务走 2PC；MVCC 多版本读 + GTS 全局一致性读。证据：官方文档（底层引擎材料）+ 社区共识。

9 复制与一致性 有

有——Paxos 多副本，多数派确认即写成功；RPO=0、RTO<8 秒为三地五中心部署下的官方口径（厂商口径，切主非恢复）。证据：官方口径。

10 扩展方式 有

有——原生 scale-out，在线扩缩容不停服；4.0 起单机分布式一体化（同一架构可单机部署）。证据：官方口径。

11 兼容性 有

有——租户级 MySQL 模式 / Oracle 模式双兼容；协议层对 MySQL 客户端友好。深水差异见深水区四。证据：官方口径 + 社区实测。

12 许可证与商业模式 有

有——社区版开源（2021-06 起）；企业版商业授权（订阅制）；OB Cloud 托管服务按云计费。替代 Oracle 可省大额 license 费用为选型口径，非承诺。证据：官方口径。

13 中文资料丰富度 有（丰富）

有（丰富）——官方中文文档、社区、大量 CSDN/博客实践帖。证据：社区共识。

14 性能与延迟特征 有

有（原生分布式；公开 TPC-C 纪录保持者）。

  • 公开 TPC-C/TPC-H 纪录（厂商口径，特定版本与硬件配置）厂商口径。
  • LSM-Tree + 多副本 Paxos：分布式写延迟高于单机 MySQL，读可就近副本 社区共识。
  • 多租户资源隔离，混合负载间互相影响小；单机极限性能不如 MySQL 极致调优 社区共识。

47 热点数据更新能力 有

有（ELR 提前释锁，厂商口径 9000 TPS）。

  • 并发控制原语：行锁加 MVCC；UPDATE 默认对行加隐式互斥锁，事务结束前并发更新同一行的后来者被阻塞，锁等待行为与普通行锁一致 官方文档。
  • ELR 机制：redo log 写入 log buffer 后即释放行锁，不等日志落盘；后续事务可提前拿到同一行的锁，正确性由提交协议保证。参数 enable_early_lock_release，租户级；V2.2.50+ 引入（旧参数 ob_early_lock_release 自 V2.2.30 起废弃），V4.0 起默认 True，ALTER SYSTEM SET 立即生效 官方文档。
  • 性能数字厂商口径：v3.1.2 release notes 称热点行并发更新从 3000 提升到 9000 TPS；官方文章称支付宝场景 5–6 倍提升；官方教程称 50 线程单行更新约 8223/s，约为默认关闭时的 4.5 倍——以上均为厂商自测口径，未见独立第三方复现 厂商口径。
  • 衰减形态：ELR 只是提前释放行锁，热点行的流量仍集中在分区 leader 单点，天花板为单分区的串行更新能力；并发继续加压时延迟随排队增长，吞吐不再随并发度提升 社区共识。
  • 内置缓解：官方性能调优指南明确建议热点行场景开启 ELR，将其列为热点行调优手段 官方文档。
  • 缺口与应用层：ELR 与分布式事务 2PC 的交互限制、ELR 专属监控指标、社区正反两面的实测评价，均未找到公开资料；官方也未给出 ELR 之外的热点行应用层模式指导 待验证。

1 Data-at-rest encryption / TDE Partially supported

Partially supported — the managed OceanBase cloud service has supported TDE transparent encryption since 2021 (Alibaba Cloud official product updates); the kernel has encryption infrastructure (AES-256 backup encryption, key storage via local files / HSM / cloud KMS, micro-blocks support user-specified encryption algorithms). No reliable evidence found for the full at-rest encryption boundary of the self-hosted Community Edition — check the edition manual before selecting. Evidence: Alibaba Cloud official updates 厂商口径 + community consensus.

2 TLS / transport encryption Partially supported

Partially supported — the cloud service supports SSL link encryption; no reliable evidence found for the self-hosted edition's TLS configuration and default behavior. Evidence: vendor claim + to-be-verified.

47 Hotspot update handling Supported

Supported(ELR releases locks early; vendor claims 9,000 TPS).

Parameter enable_early_lock_release, tenant-level; introduced in V2.2.50+ (the old ob_early_lock_release parameter deprecated since V2.2.30), default True since V4.0, and ALTER SYSTEM SET takes effect immediately 官方文档.

招牌能力

写法要求：每个特性 = 它是什么 + 为什么是真本事 + 推到边缘会发生什么。只写官方宣传稿的档案没有价值。

  1. 原生分布式 + 单机分布式一体化 真本事：4.0 起同一套代码既跑单机又跑分布式，开发测试用单机、生产切分布式，数据和 SQL 无需改造。 边缘真相：单机模式是"退化"的分布式——Paxos、GTS、多副本机制仍在，单机性能天花板天然低于为单机而生的 MySQL / PG。别指望它单机跑赢 MySQL，一体化的价值在"架构统一"不在"单机更快"。
  2. Paxos 多副本金融级容灾 真本事：RPO=0、RTO<8 秒，三地五中心；出身支付宝核心账务，正确性优先的工程文化是口碑根基。 边缘真相：RTO<8 秒指的是"故障自动切主"，不是"从备份恢复"；多数派写确认意味着跨城部署时每次提交都要等最远的多数派，写延迟与物理距离强相关；网络分区时少数派分区直接拒绝写入——保正确性弃可用，这是 CAP 写在架构里的选择，不是 bug。
  3. MySQL / Oracle 双模式兼容 真本事：租户级切换兼容模式，"去 O"迁移的改造成本在国产库里最低一档。 边缘真相：见下文深水区四——"兼容 90%" 剩下那 10% 往往是核心系统最难迁的部分，兼容性矩阵打勾不等于业务能跑。
  4. 多租户与资源隔离 真本事：单集群多租户，资源池弹性调整，适合"一库多用"的平台型团队做资源整合。 边缘真相：资源单元管的是 CPU / 内存配额，IO 和网络的 noisy neighbor 依然存在；混部 OLTP + OLAP 时，一个租户的大查询能拖慢邻居——逻辑隔离不等于物理隔离，核心业务建议独占资源。
  5. LSM-Tree 高压缩低成本 真本事：编码压缩 + 通用压缩，归档场景存储成本优势明显；4.4 起 TP / AP / AI 一体化，向混合负载延伸。 边缘真相：见下文深水区一——LSM-Tree 的写放大和合并毛刺是写密集型业务必须面对的税，压缩省下来的钱，一部分会以 DBA 调优人力的形式还回去。

Writing rule: each feature = what it is + why it's genuinely good + what happens at the edge. A profile that only repeats the vendor's marketing copy is worthless.

  1. Native distribution + single-node/distributed unification Why it's genuinely good: Since 4.0, the same codebase runs both standalone and distributed — develop and test on a single node, cut over to distributed in production, with no changes to data or SQL. Edge truth: Standalone mode is a "degraded" distributed system — Paxos, GTS, and multi-replica machinery are still there, so its single-node performance ceiling is inherently lower than databases born for single-node, like MySQL / PostgreSQL. Don't expect it to beat MySQL on a single node; the value of unification is "one architecture," not "faster on one node."
  2. Paxos multi-replica disaster recovery for financial-grade availability Why it's genuinely good: RPO=0, RTO<8s, three-geo five-IDC deployment; born in Alipay's core accounting system, its correctness-first engineering culture is the foundation of its reputation. Edge truth: RTO<8s means "automatic primary failover on failure," not "restore from backup"; quorum write acknowledgment means every commit in a cross-city deployment waits for the farthest quorum member, so write latency is strongly correlated with physical distance; during a network partition the minority partition refuses writes outright — choosing consistency over availability is a CAP trade-off baked into the architecture, not a bug.
  3. Dual MySQL / Oracle compatibility modes Why it's genuinely good: Compatibility mode switches at the tenant level; migration cost for "qu-O" (replacing Oracle) projects is among the lowest of domestic databases.   4. 一句话

Under high concurrency on the same row, the row lock is released as soon as the redo log lands in the log buffer (majority acknowledged) — no waiting for commit. The only OLTP database among the 31 with a kernel-level optimization purpose-built for hotspot row updates.
窄场景

机制
传统行更新串行持有行锁直到事务提交；ELR 在 redo log 多数派确认后即释锁，后续事务不必等前一事务提交即可拿锁，锁等待队列大幅缩短。
Traditional row updates hold the row lock serially until commit. With ELR, the lock is released once the redo log reaches majority, so the next transaction can acquire the lock without waiting for the previous transaction to commit — the lock wait queue shrinks dramatically.

内核 Primary Zone 主副本钉选 + 单机事务亲和

一句话
把各分区的 leader 副本钉在指定机房/节点，配合 OBServer 单进程架构与 OBProxy 分区感知路由，让分布式集群里 80%+ 的事务以"单机"方式执行——三副本 Paxos 的高可用，接近单机 MySQL 的延迟。
Leaders are pinned to chosen zones/nodes; combined with the single-process OBServer architecture and partition-aware routing in OBProxy, 80%+ of transactions in a distributed cluster execute "as if single-node" — three-replica Paxos availability with near-single-node MySQL latency.
窄场景
同城多机房、对延迟敏感又要分布式扩展和高可用的 OLTP 业务；从单机 MySQL 起步、不想做分库分表改造的中型团队。
Same-city multi-DC deployments needing low latency plus distributed scale and HA; mid-size teams growing out of single-node MySQL without wanting to hand-shard.
机制
三层叠加缺一不可——Primary Zone 指定 leader 落点，多数派写只付一次跨机房延迟；OBServer 单进程（SQL/存储/事务同一进程），OBProxy 按分区直达数据节点，全在本节点即单机执行；表组（tablegroup）把高频跨机 join 的表绑定同分布。反向证据：度小满实践第一条教训就是"尽量避免跨分区 RPC"，说明机制真实且影响巨大。
Three layers, all required — Primary Zone pins leader placement so majority writes pay cross-DC latency only once; single-process OBServer (SQL/storage/transaction in one process) lets OBProxy route by partition directly to the data node, executing locally when everything is on one node; table groups bind frequently co-joined tables to the same distribution. Reverse evidence: Du Xiaoman's top lesson is "avoid cross-partition RPC" — proof the mechanism is real and performance-critical.
生产验证

深水区

很多能力问题，只有把系统推到边缘才能感知好坏。以下每条都标注了机制、边缘行为和选型含义。

深水区一：LSM-Tree 的转储与合并——写得越猛，欠的债越重

  • 机制：写入先入 MemTable，冻结后转储为 L0 Mini SSTable，再逐层下沉到 L1 / L2 基线；合并分全量 / 增量 / 渐进三种。
  • 推到边缘：
    • 写入洪峰时 memstore 涨得比转储快，会触发非计划合并，极端时直接报 4030 Over tenant memory limits（MemStore 内存超限）——这是 OB 压测和大促前最常见的报错之一，应急手段是限流 + 加租户内存。
    • 合并前会把本 zone 的所有 leader 切到其他 zone（社区实测记录），合并不是免费的后台任务，有 leader 迁移开销。
    • 频繁更新 / 删除后，读要穿越所有版本做融合，读放大导致点查性能肉眼可见下降；应急是手动触发合并，长期靠 Table Mode 自适应（4.x 起 queuing 表改为自适应，无需人工指定）。
    • 快速冻结的墓碑阈值 4.2 是 120s、4.3 起改为 300s——调优参数跨版本会变，照抄旧博客的参数可能适得其反。
  • 选型含义：写入密集型业务必须做合并窗口规划和 4030 预案；DBA 要会看 GV$OB_MEMSTORE。

深水区二：时间是命门——GTS 与 NTP

  • 机制：分布式事务的全局一致性读依赖全局授时（GTS）；Paxos 自身也要求节点间时钟同步。
  • 推到边缘：NTP 不同步，OBServer 直接无法启动（真实故障案例：ntpdate 配置错误导致整节点起不来）；虚拟机时钟漂移是隐形杀手。早期版本社区曾反馈中心化 GTS 在高并发短事务下承压，4.x 持续优化，但"全局授时"这个中心化组件永远是架构评审时最值得追问的单点。
  • 选型含义：机房 NTP 基建是 OB 部署的前置条件，不是可选项；上云时要确认云厂商的时钟同步方案。

深水区三：分布式事务的 2PC 税

  • 机制：单分区事务走 Paxos 一次提交；跨分区 / 跨机事务走两阶段提交。
  • 推到边缘：事务跨越的分区越多，2PC 协调开销越大；热点行上的分布式事务还会放大锁等待。表组（tablegroup）把关联表绑到同一分区，本质是"把分布式事务变回本地事务"——schema 设计直接决定事务成本，这和 MySQL 里"随便跨表"的习惯完全不同。大事务还受 memtable 内存限制，ETL 必须拆批，这是从 MySQL 迁过来最容易踩的坑。
  • 选型含义：POC 时一定要用真实的事务模型压测，不要只测单表点查；秒杀类热点写入场景要单独验证分区打散策略。

深水区四：Oracle 兼容的深水区——"兼容 90%" 的剩下 10%

  • 社区实测差异（4.2.x，flydb / mopheus 实测记录）：
    • DBMS_LOCK.ALLOCATE_UNIQUE 可调用，但 REQUEST / RELEASE 不可用；
    • ALTER TABLE ... MODIFY 不支持只改数值 scale，组合变更（改类型 + 改可空性）可能报 -4007，要拆成两条 DDL；
    • ORA-01451 / ORA-00955 错误码兼容，但触发条件与真 Oracle 不同，不能按 Oracle 经验吞异常；
    • ALTER SESSION SET CURRENT_SCHEMA 不改变 USER_* 视图可见性，查元数据要用 ALL_* + OWNER 过滤；
    • DDL 进异步队列：客户端断开 DDL 可能继续执行，在线 DDL 会暴露 _hidden_ 中间表；
    • 数据类型：LONG / ROWID 部分兼容（ROWID 格式不同），UROWID / XMLTYPE / BFILE / 嵌套表 / VARRAY 不支持。
  • 选型含义：核心系统迁移必须逐项 POC，尤其是存储过程包、触发器、DB Job。另有一方观点（信创选型文章）认为 OB 的 Oracle 兼容弱于金仓 / 达梦这类集中式路线、迁移成本更高——该文有立场，需交叉验证，但"重度 Oracle 依赖选集中式兼容路线"这个判断值得认真对待。

深水区五：运维——概念多不是最贵的，版本差异才是

  • 3.x vs 4.x 系统视图差异大：GV$OB_PROCESSLIST、GV$OB_LOCKS 是 4.x 新增，3.x 只能查内部虚拟表；GV$SYSSTAT 计数器名跨版本不一致，硬编码计数器名的巡检脚本升级就挂。
  • GV$SQL_AUDIT 是环形内存缓冲：巡检 SQL 必须带时间窗 + 租户过滤，否则全表扫描能把业务拖垮；高频巡检建议加 READ_CONSISTENCY(WEAK) 弱一致读降低影响。
  • 选型含义：DBA 的学习成本要按"版本"算；照抄博客巡检 SQL 之前先对版本号。

深水区六：RTO<8s 的真实含义

  • RTO<8s 指故障自动切主；TB 级集群从物理备份恢复是小时级。备份窗口、异地备份、恢复演练一个都不能少——"高可用"不等于"不怕丢"，这是两个预算。

Many capability issues only reveal their good or bad side when the system is pushed to the edge. Each entry below is labeled with mechanism, edge behavior, and selection implications.

Deep Dive 1: LSM-Tree dump and compaction — the harder you write, the heavier the debt

  • Mechanism: Writes go to the MemTable first; once frozen, data is dumped as L0 Mini SSTables, then sinks level by level into the L1 / L2 baselines; compaction comes in three flavors: major / minor / progressive.
  • At the edge:
    • During write floods, the memstore grows faster than dumps can drain it, triggering unplanned compactions; in extreme cases it throws 4030 Over tenant memory limits (MemStore memory exceeded) — one of the most common errors in OB load tests and pre–sales-event drills; the emergency response is throttling + adding tenant memory.
    • Before compaction, all leaders in the local zone are switched to other zones 社区实测 — compaction is not a free background task; it carries leader-migration overhead.
    • After frequent updates / deletes, reads must traverse and merge all versions, and read amplification visibly degrades point-lookup performance; the emergency fix is manual compaction, while the long-term answer is adaptive Table Mode (since 4.x, queuing tables became adaptive — no manual specification needed).
    • The fast-freeze tombstone threshold is 120s in 4.2 and changed to 300s in 4.3+ — tuning parameters change across versions, so copying parameters from old blog posts can backfire.
  • Selection implications: Write-intensive workloads must plan compaction windows and prepare a 4030 runbook; DBAs need to know how to read GV$OB_MEMSTORE.

Deep Dive 2: Time is the jugular — GTS and NTP

  • Mechanism: Globally consistent reads for distributed transactions depend on the Global Timestamp Service (GTS); Paxos itself also requires clock synchronization between nodes.
  • At the edge: If NTP is out of sync, OBServer simply won't start (real incident: an ntpdate misconfiguration kept an entire node from starting); VM clock drift is a silent killer. In early versions the community reported that the centralized GTS struggled under high-concurrency short transactions; 4.x keeps optimizing it, but the "global timestamping" centralized component will always be the single point most worth interrogating in an architecture review.
  • Selection implications: Data-center NTP infrastructure is a prerequisite for OB deployment, not an option; when moving to the cloud, confirm the cloud vendor's clock-synchronization solution.

Deep Dive 3: The 2PC tax on distributed transactions

  • Mechanism: Single-partition transactions commit via Paxos in one round; cross-partition / cross-node transactions go through two-phase commit.
  • At the edge: The more partitions a transaction spans, the higher the 2PC coordination overhead; distributed transactions on hot rows further amplify lock waits. Table groups (tablegroup) colocate related tables in the same partition — essentially "turning distributed transactions back into local ones" — so schema design directly determines transaction cost, a complete departure from MySQL's "join any tables freely" habit. Large transactions are also bound by memtable memory limits, so ETL must be batched — the easiest pitfall when migrating from MySQL.
  • Selection implications: POC load tests must use the real transaction model, not just single-table point lookups; flash-sale-style hot-write scenarios need separate validation of partition-scattering strategies.

Deep Dive 4: The deep waters of Oracle compatibility — the remaining 10% of "90% compatible"

  • Community-tested differences (4.2.x, tested by flydb / mopheus):
    • DBMS_LOCK.ALLOCATE_UNIQUE is callable, but REQUEST / RELEASE are unavailable;
    • ALTER TABLE ... MODIFY doesn't support changing only numeric scale; combined changes (type change + nullability change) may throw -4007 and must be split into two DDL statements;
    • ORA-01451 / ORA-00955 error codes are compatible, but their trigger conditions differ from real Oracle — don't swallow exceptions based on Oracle experience;
    • ALTER SESSION SET CURRENT_SCHEMA doesn't change USER_* view visibility; query metadata with ALL_* + OWNER filters instead;
    • DDL goes into an async queue: DDL may keep executing after the client disconnects, and online DDL exposes _hidden_ intermediate tables;
    • Data types: LONG / ROWID partially compatible (ROWID format differs); UROWID / XMLTYPE / BFILE / nested tables / VARRAY unsupported.
  • Selection implications: Core-system migrations must POC each item, especially stored procedure packages, triggers, and DB jobs. One other viewpoint (a xinchuang selection article) argues OB's Oracle compatibility is weaker than centralized alternatives like Kingbase (金仓) / Dameng (达梦), with higher migration cost — that article has a position and needs cross-verification, but the judgment that "heavy Oracle dependence favors the centralized compatibility route" deserves serious consideration.

Deep Dive 5: Operations — concepts aren't the most expensive part, version differences are

  • System views differ greatly between 3.x and 4.x: GV$OB_PROCESSLIST and GV$OB_LOCKS are new in 4.x; on 3.x you can only query internal virtual tables; GV$SYSSTAT counter names are inconsistent across versions, so inspection scripts with hardcoded counter names break on upgrade.
  • GV$SQL_AUDIT is a ring memory buffer: inspection SQL must include a time window + tenant filter, or a full scan will drag down production; for high-frequency inspections, add READ_CONSISTENCY(WEAK) (weak-consistency read) to reduce impact.
  • Selection implications: DBA learning cost should be counted "per version"; check the version number before copying inspection SQL from blogs.

Deep Dive 6: What RTO<8s really means

  • RTO<8s means automatic primary failover on failure; restoring a TB-scale cluster from physical backup takes hours. Backup windows, off-site backups, and restore drills are all non-negotiable — "high availability" is not the same as "not afraid of losing data"; those are two separate budgets.

  1. 金融级高可用口碑

  2. "去 O"降本
    • 为什么是真的：Oracle 模式租户级兼容 + OMS 迁移工具链成熟；省下的 Oracle license（按 CPU 核数收费）是真金白银，CFO 看得懂。

  3. TPC-C / TPC-H 基准纪录（厂商口径，非判决依据）
    • 为什么被引用：2020 年 TPC-C 7.07 亿 tpmC 等公开基准纪录是厂商宣传的核心论据，用来证明分布式 OLTP 架构没有明显短板。
    • 边缘与限度：TPC 是"实验室上限"，不是"你的业务下限"；跑分用的硬件配置和调优投入普通团队达不到；OLTP 纪录不代表你的混合负载也快。本档案所有判决均不以该数字为依据。benchmark 的价值是"证明架构上限高"，不是"保证你的 SQL 快"——拿跑分成绩单去要求业务性能，是经典误用。
  4. 在线扩缩容
    • 为什么是真的：原生分布式，数据按分区自动均衡，加节点不停服，扩容不再是"半夜停机窗口"。
    • 边缘与限度：扩容时的数据均衡（tablet 迁移）会吃 IO 和网络，业务高峰期扩容等于"给飞行中的飞机换引擎"，要选低峰窗口；缩容更危险，数据迁出耗时更长。以及很多人高估了自己对扩容的需求——"从 3 节点扩到 100 节点"的故事很性感，但大多数业务 3 年都用不满 3 节点，为用不上的扩展性付了运维税。
  5. 中文生态 + 政策红利
    • 为什么是真的：中文文档、社区、原厂服务响应确实对国内团队友好；信创目录是实打实的订单来源。
    • 边缘与限度：政策红利是"入场券"不是"护城河"，目录里有几十家；中文生态强意味着英文生态相对弱，出海或招外籍 DBA 时是短板；对原厂依赖度高，社区版用户遇到深水区问题最终还是要找原厂——"开源"不等于"能自己搞定"。

Writing rule: the good parts need depth too. Each entry = why it's true + edges and limits (how good it is, where it breaks, what it costs).

  1. Financial-grade high-availability reputation
    • Why it's true: Paxos multi-replica + three-geo five-IDC is an architectural capability, not a configuration item; 15 years of Alipay / Singles' Day validation back the RPO=0, RTO<8s claims 官方文档, with public reporting to corroborate.
    • Edges and limits: High availability costs write latency (quorum acknowledgment) and operational complexity; RTO<8s is failover, not recovery; running three replicas for a small workload is "using a cannon to kill a mosquito" — machine and labor costs may exceed the benefit. The reputation holds only if you genuinely need financial-grade — most workloads' real requirement is "don't go down," not "three geos, five IDCs."
  2. "Qu-O" (replacing Oracle) cost reduction
    • Why it's true: Tenant-level Oracle-mode compatibility + a mature OMS (OceanBase Migration Service) toolchain; the Oracle licenses saved (charged per CPU core) are real money that a CFO can understand.
    • Edges and limits: You save on licenses but spend on refactoring, DBA learning, and Enterprise Edition subscriptions; the compatibility pitfalls in Deep Dive 4 mean "cost reduction" has a precondition — passing the POC. TCO math must include 3 years of labor cost; some teams found the saved money went right back into vendor professional services. Cost reduction is the outcome, not the starting point.
  3. TPC-C / TPC-H benchmark records (vendor claim, not a basis for verdicts)
    • Why it's cited: the public benchmark records — e.g., the 2020 TPC-C result of 707 million tpmC — are the centerpiece of the vendor's marketing, cited to show the distributed OLTP architecture has no obvious weak spots.
    • Edges and limits: TPC is a "lab ceiling," not "your workload's floor"; ordinary teams can't match the benchmark's hardware and tuning investment; an OLTP record doesn't mean your mixed workload is fast. No verdict in this profile is based on these numbers. A benchmark's value is "proving the architecture's ceiling is high," not "guaranteeing your SQL is fast" — demanding production performance from a benchmark scorecard is a classic misuse.
  4. Online scaling
    • Why it's true: Natively distributed, data auto-balances by partition, nodes can be added without downtime — scaling is no longer a "midnight maintenance window."
    • Edges and limits: Data rebalancing during scale-out (tablet migration) consumes IO and network; scaling during peak hours is like "changing engines mid-flight" — pick an off-peak window; scaling in is riskier, as data migration-out takes longer. And many teams overestimate their scaling needs — the "from 3 nodes to 100 nodes" story is sexy, but most workloads won't fill 3 nodes in 3 years, and they pay an operations tax for scalability they'll never use.
  5. Chinese-language ecosystem + policy tailwinds
    • Why it's true: Chinese documentation, community, and responsive vendor support are genuinely friendly to domestic teams; the xinchuang (信创, China's IT application innovation) catalog is a real source of orders.
    • Edges and limits: Policy tailwinds are an "entry ticket," not a "moat" — the catalog has dozens of vendors; a strong Chinese ecosystem means a relatively weak English one, a disadvantage when expanding overseas or hiring non-Chinese DBAs; vendor dependence is high — Community Edition users with deep-water problems end up going to the vendor anyway. "Open source" doesn't mean "you can handle it yourself."

判决

  • 适合谁：金融 / 政企核心系统（容灾要求极高）、"去 O"替换 Oracle、数据量大且持续增长需在线扩展、有信创目录要求、一套集群服务多业务线的平台型团队。
  • 不适合谁：初创小团队的单机小库（运维和资源成本不划算）、重度依赖 MySQL 偏门特性且不愿做兼容测试、团队无专职 DBA 又想"装完不管"。
  • 迁移成本：MySQL → 低（协议兼容，OMS 迁移工具成熟，复杂 SQL 需回归）；Oracle → 中（Oracle 模式兼容度高，PL/SQL 高级特性逐项验证）；PostgreSQL → 中高（无原生 PG 兼容，走应用层改造）。
  • Best for: Financial / government core systems (extremely high DR requirements), "qu-O" Oracle replacement, large and growing datasets needing online scaling, xinchuang catalog requirements, platform teams serving multiple business lines from one cluster.
  • Not for: Small startup teams with single-node small databases (ops and resource costs don't pay off), heavy reliance on obscure MySQL features without willingness to compatibility-test, teams with no dedicated DBA hoping to "install and forget."
  • Migration cost: MySQL → low (protocol-compatible, mature OMS migration toolchain, regression-test complex SQL); Oracle → medium (high Oracle-mode compatibility, verify advanced PL/SQL features item by item); PostgreSQL → medium-high (no native PG compatibility, application-layer rework).
