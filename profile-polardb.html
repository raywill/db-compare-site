PolarDB

关系型 OLTP #云原生 #存算分离 #共享存储 #一写多读 #MySQL兼容 #PostgreSQL兼容 #Oracle兼容 #托管服务 #Serverless #PolarProxy

阿里云自研的云原生关系型数据库，云上托管、对标 AWS Aurora 路线：计算与存储彻底分离（共享存储一写多读），三引擎（MySQL / PostgreSQL / Oracle 兼容）共用同一套 PolarStore 分布式存储底座；2017 年公测，"云原生存算分离"在国内云厂商中最早规模商用的实践者之一。

Alibaba Cloud's self-developed cloud-native relational database, a managed cloud offering on the same track as AWS Aurora: complete compute-storage separation (shared storage, single-writer/multi-reader), with three engines (MySQL / PostgreSQL / Oracle-compatible) sharing the same PolarStore distributed storage foundation; public beta in 2017 — one of the earliest large-scale commercial practices of "cloud-native compute-storage separation" among Chinese cloud vendors.

硬维度（46 项）

1 静态加密 / TDE 有

有官方文档。MySQL 版：实例级 TDE（控制台/API UpdateDBInstanceTDE 开启），8.0 引擎自 8.0.1.1.15 起支持"新建表自动加密"；一表空间级透明加密，密钥由阿里云 KMS 产生和管理，应用无感，开启后数据文件落盘加密、读入内存解密，不改变数据文件大小。PG/Oracle 版：仅支持创建集群时开启，开通后无法关闭；对数据文件执行实时 I/O 加密；KMS 密钥管理，支持阿里云自动生成密钥，也支持 BYOK（自带密钥材料再授权 PolarDB 使用）。限制：源 RDS 若开启 TDE/SSL 则无法使用"一键升级至 PolarDB"（官方文档前提条件）。待验证：MySQL 版 BYOK 支持情况（未找到证据）；WAL/redo、临时文件、备份文件的加密范围（未找到官方证据）；PG 版 I/O 密集场景性能影响（官方注意事项有提及，量化待验证）。

2 TLS / 传输加密 有

MySQL 有官方文档——2020-02-11 起主地址支持 SSL 加密传输，可按需开启；开启会增加网络连接响应时间（官方说明）；API UpdateDBInstanceSSL。PG 有（官方 API 文档）——ModifyDBClusterSSL 支持设置集群 SSL 的开通/关闭/更新 CA 证书。Oracle 版：未找到证据——没查到 PolarDB-O 的 SSL 设置文档，待验证。

3 审计 有

有官方文档。三引擎通用 SQL 审计功能：EnableSqlAudit / DisableSqlAudit / DescribeSqlAuditInfo，审计日志可接入阿里云日志服务 SLS（CheckSqlAuditSlsStatus 校验接入状态）；控制台开启后，SQL 审计日志写入 SLS 的 Project/Logstore，可检索分析。MySQL 8.0.1.1.3 起"支持新版本的审计日志格式，增加了 VIP 信息"（官方内核发布说明）；社区笔记提及内置 POLARDB_AUDIT_LOG（社区共识，待官方文档交叉验证）。

4 认证与权限 有

有（官方文档 + 社区实测）。分层机制：① 云管控层：RAM 子账号授权、IP 白名单、安全组/VPC 隔离；② 数据库层：高权限账号（一个实例仅一个）与普通账号（CreateAccount/ModifyAccountPrivilege），MySQL 8.0 增强密码管理（官方发布说明）；③ PG/Oracle 版有专属权限参数：社区实测 PolarFlex（PolarDB-PG 轻量版）内核存在大量 polar_* 专属参数（含 polar_acl_* 权限安全），原生 PG 没有；④ 支持三权分立开关（官方 API EnableRightsSeparation，适用引擎版本待验证）。

5 备份恢复 有

有官方文档。机制：① 数据备份（快照，存于 PolarDB 分布式存储，一级备份）：默认开启不可关闭，保留 3 天～730 天；二级备份（存于 OSS）：默认关闭，保留 30 天～7300 天（标准版集群仅支持一级备份，不支持二级备份）；② 日志备份：Redo 日志实时并行上传 OSS，默认开启同地域、不可关闭，保留 3 天～7300 天，支持跨地域备份；③ PITR：全量快照 + 日志备份可恢复到任意时间点；MySQL 5.7（5.7.1.0.8+）/8.0 支持库表级恢复（按备份集恢复、按时间点恢复）。恢复速度：官方口径——应用 Redo 日志的恢复速度约 20~70 秒/GB厂商口径，总恢复时间 = 快照恢复 + 日志应用。备份系统具 WORM 不可篡改特性（防篡改）；自动备份不可完全删除（最低保留 3 天、每周至少 2 次）。注意：官方文档实锤的坑——二级备份转存失败时，到期的下一个一级备份会被直接删除而不是转存，大库用户可能无声丢失备份链。社区实测（PG 版）：PITR 以"全备份 + 重做日志"恢复到新集群，不覆盖原集群，且恢复集群不携带源集群参数设置。

6 可观测性 有

有官方文档。① 控制台监控：CPU/内存/IOPS/连接数/复制延迟等指标（云监控集成）；② DAS（数据库自治服务）：性能洞察、慢 SQL 明细查询（API DescribeSlowLogRecords、DescribeDBNodePerformance）；③ 慢日志控制台查询、show processlist；④ 事件与运维任务（DescribeEvents、DescribeActiveOperationTasks）；⑤ 复制链路健康检查（CreateRplInspectionTask）。MySQL 5.6/8.0 支持语句并发控制（Statement Concurrency Control）限流问题 SQL（官方 FAQ）。

7 连接模型 有

有（官方文档 + 社区共识）。三种地址：主地址（读写）、集群地址（PolarProxy 自动读写分离：写→主节点、读→按负载分发到主/只读节点）、自定义集群地址（可隔离业务）；集群地址支持会话级连接池（官方 FAQ：高并发 PHP 短连接可在集群地址开启会话级连接池优化）；社区/官方一致建议应用侧仍使用连接池（社区共识：长连接 + 合理池大小）。注意：PolarProxy 代理层连接≠后端直连，故障切换时旧主节点主动断开所有连接（官方文档明确为预期行为），应用需重连。

8 事务与隔离级别 有

有官方文档 社区共识。MySQL：继承 InnoDB 事务模型：ACID、MVCC、4 种标准隔离级别；8.0 支持原子 DDL 等原生特性。PG：标准 PG MVCC 事务模型与隔离级别。Oracle：Oracle 兼容事务语义，支持 PL/SQL 存储过程/函数/触发器异常处理（开发者社区文章）；具体隔离级别映射细节待验证。集群地址支持一致性级别设置（会话一致性/全局一致性/最终一致性，官方文档）。

9 复制与一致性 有

有官方文档。共享存储（Shared Everything）+ 物理复制：所有计算节点共享同一份 PolarStore/PolarFS 分布式存储（三副本，RPO=0 为厂商口径）；主从节点间只需同步 Redo 日志元数据（MySQL）/ WAL（PG），只读节点应用物理日志，复制延迟通常为毫秒级社区共识；故障时只读节点快速提升为主，RTO<60 秒为厂商口径。读一致性通过 MVCC 跨节点保证。部分待验证：跨地域 GDN（全球数据库网络）的复制协议细节未深入查证。

10 扩展方式 有

有官方文档。纵向：计算节点规格升降配在线进行（分钟级）；存储按实际用量自动扩容，无需预置（PG/Oracle 版默认最高 500TB，可扩展至 PB 级，厂商口径）。横向：只读节点秒级添加（共享存储，无需数据拷贝），一写多读最多 15 个只读节点厂商口径。横向写扩展：集中式三引擎为单主写，写扩展需走 PolarDB-X（见文末澄清）。

11 兼容性 有

有（官方文档 + 社区实测）。MySQL：完全兼容 MySQL 5.6/5.7/8.0 协议与语法；迁移工具：DTS（全量+增量）、RDS 一键升级；PolarDB 8.0 要求客户端驱动升级到 8.0 系列（官方兼容性说明）。PG：高度兼容 PG（从 PG 11 起，现支持 PG 14/15/16/17；PG 18 已白名单开放，厂商/社区口径）；社区实测实例含 189 个可用扩展（含 pgvector 0.8.3.1）；自带列存索引 IMCI、Ganos 时空等；官方提供 PolarDB-Tools（psql/pg_dump/pg_restore 客户端）。Oracle：官方相关口径称支持 95%+ Oracle SQL 与 PL/SQL（厂商相关口径）；支持存储过程/函数/触发器/分区表/序列/同义词；迁移用 DTS + ADAM 评估；部分 Oracle 专有包（如 UTL_FILE）需调整（社区文章）。生态工具：DTS、DMS、ADAM 迁移评估、PolarDB-Tools；MySQL 生态工具（Navicat/JDBC 等）直接可用，PG 生态驱动直接可用。

12 许可证与商业模式 查证为无

MySQL 版查证为无开源证据（社区共识：仅 PG 版开源，MySQL/Oracle 版只能在阿里云使用）；PG 版有（2021 年开源，Apache 2.0）；Oracle 版查证为无开源证据；PolarDB-X 有（2021 年 10 月正式开源）；PolarDB for AI 未找到开源证据（商业产品）。商业版形态：集群版/企业版 vs 标准版（如标准版不支持二级备份、企业版支持删除集群前长期保留备份）；Serverless 形态（敏态 Serverless、Agentic Database）。计费（官方文档，只写计费模型）：包年包月 / 按量付费（集群版固定规格）；Serverless 按 PCU（PolarDB Capacity Unit）实际用量按秒计费、按小时出账（0~8 PCU，0.5 PCU 粒度），无负载时计算不收费；存储按实际用量计费（另有存储包资源包可抵扣）。授权坑：PolarDB-PG 轻量版（PolarFlex 栈）商用需 License，未授权只有 30 天免费试用、之后限流社区实测；"开源印象"不等于免费商用。

13 中文资料丰富度 丰富

丰富。官方中文文档齐全（help.aliyun.com/polardb 三引擎独立文档体系 + API 参考）；阿里云开发者社区大量官方/用户文章；CSDN/掘金/知乎/墨天轮有大量实践帖与迁移踩坑记录（如 RDS PG→PolarDB PG 万字迁移实录）；官方开设 PolarDB for PostgreSQL 开源训练营/知识竞赛。英文资料相对少，以 alibabacloud.com 英文文档和 VLDB 论文为主；国际站英文文档存在版本滞后（如 Oracle 兼容英文开发者指南停留在 2022 年文档版本）。

14 性能与延迟特征 有

有（云原生一写多读；读扩展秒级）。

  • 单机性能接近社区 MySQL/PG；写上限为单主规格 社区共识。
  • PolarDB-X（分布式版）提供水平写扩展 官方文档。

18 生态工具链 有

22 CDC 与下游同步 有

26 跨地域多活 有

27 高可用架构与 RTO/RPO 有

有（一写多读快速切换）。

  • 共享存储一写多读，主故障只读节点快速提升，RTO 秒级 官方文档。

  • 切换对长连接有闪断，应用需重连 社区共识。

28 行级安全与数据脱敏 部分支持

部分支持（继承PG/MySQL生态；云上管控增强）。

  • PolarDB PostgreSQL 版继承 PG 原生 RLS；MySQL 版与 MySQL 企业版脱敏组件的对应关系需按版本确认 官方文档

1 Data-at-rest encryption / TDE Supported

Supported 官方文档. MySQL edition: instance-level TDE (enabled via console/API UpdateDBInstanceTDE); the 8.0 engine supports "auto-encryption for newly created tables" from 8.0.1.1.15; per-tablespace transparent encryption, keys generated and managed by Alibaba Cloud KMS, transparent to applications — data files are encrypted on disk and decrypted when read into memory, with no change to data file size. PG/Oracle edition: can only be enabled when the cluster is created and cannot be disabled afterward; performs real-time I/O encryption on data files; KMS key management, supports both Alibaba Cloud auto-generated keys and BYOK (bring your own key material, then authorize PolarDB to use it). Limitation: source RDS instances with TDE/SSL enabled cannot use "one-click upgrade to PolarDB" (official docs prerequisite). To-be-verified: BYOK support for the MySQL edition (no evidence found); encryption scope for WAL/redo, temp files, and backup files (no official evidence found); performance impact on I/O-intensive PG workloads (official notes mention it, quantification to-be-verified).

2 TLS / transport encryption supported

MySQL supported 官方文档 — SSL encrypted transport supported on the primary endpoint since 2020-02-11, optional; enabling it increases network connection response time (official statement); API UpdateDBInstanceSSL. PG supported (official API docs) — ModifyDBClusterSSL supports enabling/disabling cluster SSL and updating the CA certificate. Oracle edition: no evidence found — no SSL configuration docs found for PolarDB-O, to-be-verified.

3 Auditing Supported

Supported 官方文档. SQL auditing available across all three engines: EnableSqlAudit / DisableSqlAudit / DescribeSqlAuditInfo; audit logs can be shipped to Alibaba Cloud Log Service (SLS) (CheckSqlAuditSlsStatus verifies SLS integration); once enabled in the console, SQL audit logs are written to an SLS Project/Logstore for search and analysis. MySQL 8.0.1.1.3+ "supports a new audit log format with VIP information added" (official kernel release notes); community notes mention a built-in POLARDB_AUDIT_LOG (community consensus, pending cross-verification against official docs).

4 Authentication & authorization Supported

Supported (official docs + community-tested). Layered mechanism: ① cloud control plane: RAM sub-account authorization, IP whitelists, security groups/VPC isolation; ② database layer: privileged accounts (one per instance) and standard accounts (CreateAccount/ModifyAccountPrivilege), enhanced password management in MySQL 8.0 (official release notes); ③ PG/Oracle editions have dedicated permission parameters: community testing found that the PolarFlex (lightweight PolarDB-PG edition) kernel contains many polar_*-specific parameters (including polar_acl_* permission/security ones) not present in vanilla PG; ④ supports a separation-of-duties switch (official API EnableRightsSeparation, applicable engine versions to-be-verified).

5 Backup & recovery Supported

Supported 官方文档. Mechanism: ① Data backups (snapshots stored on PolarDB distributed storage, Level-1 backups): enabled by default and cannot be disabled, retained 3 days–730 days; Level-2 backups (stored on OSS): disabled by default, retained 30 days–7300 days (Standard Edition clusters support only Level-1 backups, not Level-2); ② Log backups: redo logs uploaded to OSS in real time and in parallel, enabled by default in the same region, cannot be disabled, retained 3 days–7300 days, supports cross-region backup; ③ PITR: full snapshots + log backups can restore to any point in time; MySQL 5.7 (5.7.1.0.8+) / 8.0 support database/table-level restore (restore from backup set, restore to a point in time). Recovery speed: official statement — applying redo logs recovers at about 20–70 seconds/GB 厂商口径; total recovery time = snapshot restore + log apply. The backup system has WORM immutability (tamper-proof); automatic backups cannot be fully deleted (minimum 3-day retention, at least twice per week). Note: a documented-in-official-docs pitfall — when a Level-2 backup transfer fails, the expiring next Level-1 backup is deleted directly instead of being transferred, so large-database users may silently lose their backup chain. Community-tested (PG edition): PITR restores via "full backup + redo logs" to a new cluster, never overwriting the original cluster, and the restored cluster does not inherit the source cluster's parameter settings.

6 Observability Supported

Supported 官方文档. ① Console monitoring: CPU/memory/IOPS/connections/replication lag and other metrics (integrated with CloudMonitor); ② DAS (Database Autonomy Service): performance insights, slow-SQL detail queries (APIs DescribeSlowLogRecords, DescribeDBNodePerformance); ③ slow-log console queries, show processlist; ④ events and ops tasks (DescribeEvents, DescribeActiveOperationTasks); ⑤ replication-link health checks (CreateRplInspectionTask). 7 Connection model Supported

Supported (official docs + community consensus). Three endpoint types: primary endpoint (read-write), cluster endpoint (PolarProxy automatic read/write splitting: writes → primary, reads → distributed across primary/read-only nodes by load), custom cluster endpoints (isolate workloads); the cluster endpoint supports session-level connection pooling (official FAQ: high-concurrency PHP short-connection workloads can enable session-level connection pooling on the cluster endpoint for optimization); community and official guidance agree apps should still use their own connection pools (community consensus: long-lived connections + sane pool sizing). Note: PolarProxy-layer connections ≠ direct backend connections — during failover the old primary actively disconnects all connections (official docs state this is expected behavior), applications must reconnect.

8 Transactions & isolation levels Supported

Supported (official docs / community consensus). MySQL: inherits the InnoDB transaction model — ACID, MVCC, 4 standard isolation levels; 8.0 supports atomic DDL and other native features. PG: standard PG MVCC transaction model and isolation levels. Oracle: Oracle-compatible transaction semantics, supports PL/SQL stored procedures/functions/trigger exception handling (Alibaba Cloud developer community articles); exact isolation-level mapping details to-be-verified. 9 Replication & consistency Supported

Supported 官方文档. Shared storage (shared-everything) + physical replication: all compute nodes share the same PolarStore/PolarFS distributed storage (3 replicas, RPO=0 is a vendor claim); primary and secondary nodes only need to sync redo log metadata (MySQL) / WAL (PG); read-only nodes apply physical logs, replication lag is typically millisecond-level 社区共识; on failure a read-only node is promoted to primary quickly, RTO<60 seconds is a vendor claim. Read consistency is guaranteed via MVCC across nodes. Partially to-be-verified: replication protocol details for cross-region GDN (Global Database Network) were not deeply verified.

  1. 共享存储 + 物理复制的一写多读：加读节点不搬数据 真本事：计算与存储分离，所有节点（含 15 个只读节点）挂载同一份 PolarStore 分布式存储；节点间同步走 redo 物理复制而非 binlog/WAL 逻辑复制。相对 RDS（加从库=全量复制数据+逻辑回放，TB 级要小时级），PolarDB 加只读节点不复制数据，只需拉元数据+追增量 redo，这是"分钟级加读"的机制根因；毫秒级复制延迟让"读写分离读到旧数据"的窗口比 RDS 主从小一个数量级。 边缘真相：①只读节点是"无状态计算节点"，不是"数据副本"——真正的数据冗余在存储层三副本；节点故障切换快，但存储层出问题是另一套故障域，别把"节点秒级恢复"理解成"数据丢不了"。②写洪峰下 redo 产生速度 > 只读节点回放速度，延迟放大，"毫秒级"是稳态值不是承诺值。③读扩展≠写扩展，写天花板永远是单主——这是 Aurora 路线共同的原罪，选型时最容易误判的一点。 证据与版本：官方 FAQ（只读节点上线、毫秒级延迟口径）；社区压测共识；适用 PolarDB for MySQL 8.0 / PG 14+ 全版本。
  2. PolarProxy：把读写分离、连接池、一致性级别做进基础设施层 真本事：集群强制经过的透明代理，自动做读写分离、语句级/事务级连接复用、按一致性级别路由（全局一致/会话一致/最终一致，PG 版用 CSN 构建强一致读视图）。相对自建 PG（要自己搭 pgbouncer + 读写分离中间件 + 一致性策略），PolarDB 把这三件事做成开箱即用的基础设施。真实压测证据：同等压力下 PolarDB-PG 内存显著低于原生 PG，就是代理截断连接风暴的直接效果——这是用户"零改造拿到 PG 连接池+读写分离"的体感来源。 边缘真相：①代理是必经之路，多一跳延迟，且代理自身的版本升级=连接闪断（见吐槽清单）；②代理对 SQL 的解析有边界，复杂协议特性/大对象/特定管理命令可能需要绕过代理直连，应用要保留直连主地址的逃生通道；③DBA 的可观测性被代理隔了一层，慢 SQL 归因、连接查杀都要重建方法论——"透明"的代价是"黑盒"。 证据与版本：CSDN 真实迁移案例（2025）；官方一致性级别文档；适用全版本，PG 版连接池红利最明显。
  3. 存储层 ROW 快照备份：秒级备份 + 强制开启的一级备份 真本事：备份在 PolarStore 存储层做 Redirect-on-Write 快照，不复制数据；一级备份（3~730 天保留）默认开启且无法关闭，二级备份压缩转存离线存储（OSS）。相对自建 MySQL 的逻辑备份（锁表/慢/恢复更慢）和 RDS 的备份窗口，PolarDB 的备份是"无感知的存储层操作"，库再大也是秒级。这是存算分离架构附赠的、传统架构做不到的能力。 边缘真相：①"无法关闭"=备份存储强制计费，备份策略没有"不备"这个选项；②二级备份转存失败时到期的备份会被直接删除（官方文档实锤），大库用户可能无声丢失备份链；③恢复是"拉起新集群"（不覆盖原集群、不携带源集群参数设置），厂商口径 10 分钟级恢复与数据量强相关，别当成 RTO 承诺。 证据与版本：官方《备份与恢复》文档（help.aliyun.com）；适用 PolarDB for MySQL / PG 全版本。
  4. Serverless 弹性计费（PCU 模型）：计算按秒、存储按量 真本事：计算资源以 PCU 为单位按秒计费、按小时出账，闲时可缩到 0~1 PCU（PG Agentic Database 支持 Scale to Zero）；存储按实际用量独立计费。相对 RDS"按规格买断"的计费模型，这是 PolarDB 真正的商业模式差异点——潮汐业务（大促、夜间闲置的 SaaS）不用为峰值买单。注意这是"计费模型创新"不是"技术创新"，但对 CTO 的预算表是真实差异。 边缘真相：①弹性滞后：秒级探测+拉起，应对不了分钟级以下的尖刺，前排请求可能被限流；②各形态有 PCU 上下限（如 0~8 PCU），超限业务用不了 Serverless；③负载平稳的业务实测可能贵于包年包月，且账单不可预测是财务侧真实抱怨；④"降本 35%"是厂商口径，成立前提是"你的负载真有潮汐"——没有潮汐的业务用 Serverless 是反向优化；⑤自动暂停的触发条件细节（无流量持续多久、哪些状态阻止暂停如只读节点/长连接/定时任务）在公开文档中未找到确切条款——待验证；有长连接的应用可能永远触发不了自动暂停。 证据与版本：官方 PolarDB-PG 形态对比与计费文档（2026）；社区选型共识；适用 MySQL Serverless、PG 敏态 Serverless。
  1. Shared storage + physical replication single-writer/multi-reader: adding read nodes moves no data What it's really good at: compute-storage separation — all nodes (including up to 15 read-only nodes) mount the same PolarStore distributed storage; inter-node sync uses redo physical replication rather than binlog/WAL logical replication. Compared to RDS (adding a replica = full data copy + logical replay, hours at TB scale), PolarDB adds read-only nodes without copying data — it only pulls metadata and catches up on incremental redo. That is the mechanistic root cause of "minute-level read scaling"; millisecond-level replication lag shrinks the "read stale data under read/write splitting" window by an order of magnitude versus RDS primary-replica setups. Edge truth: ① A read-only node is a "stateless compute node", not a "data replica" — the real data redundancy lives in the storage layer's 3 replicas; node failover is fast, but a storage-layer problem is a different failure domain — don't mistake "second-level node recovery" for "data can't be lost". ② Under a write burst, redo generation speed > read-only node replay speed, lag blows up — "millisecond-level" is a steady-state value, not a commitment. ③ Read scaling ≠ write scaling — the write ceiling is always the single primary. This is the original sin shared by the whole Aurora lineage and the easiest thing to misjudge in selection. Evidence & versions: official FAQ (read-only node onboarding, millisecond-level lag statement); community load-test consensus; applies to PolarDB for MySQL 8.0 / PG 14+ all versions.
  2. PolarProxy: read/write splitting, connection pooling, and consistency levels built into the infrastructure layer What it's really good at: a mandatory transparent proxy for the cluster that automatically does read/write splitting, statement-level/transaction-level connection multiplexing, and routing by consistency level (global/session/eventual consistency; the PG edition builds strongly consistent read views with CSN). Compared to self-hosted PG (where you have to assemble pgbouncer + a read/write-splitting middleware + consistency policies yourself), PolarDB turns all three into out-of-the-box infrastructure. Real load-test evidence: under equal pressure, PolarDB-PG memory was significantly lower than native PG — the direct effect of the proxy absorbing connection storms. This is the source of users' "zero-change access to a PG connection pool + read/write splitting" experience. Edge truth: ① The proxy is on the mandatory path — one extra network hop, and a proxy version upgrade = connection blips (see complaints table); ② the proxy's SQL parsing has boundaries — complex protocol features / large objects / certain admin commands may need to bypass the proxy and connect directly, so applications should keep a direct-to-primary escape hatch; ③ the DBA's observability is one layer removed behind the proxy — slow-SQL attribution and connection killing both need a rebuilt methodology — the cost of "transparent" is "black box". Evidence & versions: CSDN real migration case (2025); official consistency-level docs; applies to all versions, connection-pool benefits most pronounced on the PG edition.
  3. Storage-layer ROW snapshot backup: second-level backups + mandatory Level-1 backups What it's really good at: backups happen at the PolarStore storage layer as Redirect-on-Write snapshots, copying no data; Level-1 backups (3–730 day retention) are enabled by default and cannot be disabled; Level-2 backups are compressed and transferred to offline storage (OSS). Compared to self-hosted MySQL logical backups (table locks / slow / even slower restore) and RDS backup windows, PolarDB backups are "unperceived storage-layer operations" — second-level regardless of database size. This is a capability the compute-storage separation architecture gets for free and traditional architectures cannot match. Edge truth: ① "Cannot be disabled" = forced backup storage billing — there is no "don't back up" option in the backup policy; ② when a Level-2 backup transfer fails, expiring backups are deleted directly (verified in official docs) — large-database users may silently lose their backup chain; ③ recovery means "spin up a new cluster" (does not overwrite the original cluster, does not inherit source cluster parameter settings); the vendor's 10-minute-level recovery statement is strongly correlated with data volume — don't treat it as an RTO commitment. Evidence & versions: official Backup and Recovery docs (help.aliyun.com); applies to PolarDB for MySQL / PG all versions.
  4. Serverless elastic billing (PCU model): compute per second, storage by usage What it's really good at: compute resources billed per second in PCU units and settled hourly, scaling down to 0–1 PCU when idle (PG Agentic Database supports Scale to Zero); storage billed independently by actual usage. Compared to RDS's "buy specs on subscription" pricing model, this is PolarDB's genuine business-model differentiator — spiky businesses (promotions, SaaS idle overnight) don't pay for peak capacity. Note this is a "billing model innovation", not a "technology innovation", but it's a real difference on a CTO's budget sheet. Edge truth: ① Elasticity lags: second-level detection + spin-up can't handle sub-minute spikes — the first requests may get throttled; ② each form has PCU lower/upper bounds (e.g., 0–8 PCU) — workloads exceeding them can't use Serverless; ③ steady-load businesses may find actual bills higher than subscription pricing, and unpredictable bills are a genuine finance-team complaint; ④ the "35% cost reduction" is a vendor claim — it holds only if "your load really is spiky" — Serverless without spikiness is reverse optimization; ⑤ the exact terms for auto-pause triggers (how long without traffic, which states block pausing such as read-only nodes / long connections / scheduled jobs) were not found in public docs — to-be-verified; applications with long-lived connections may never trigger auto-pause. Evidence & versions: official PolarDB-PG form-comparison and billing docs (2026); community selection consensus; applies to MySQL Serverless, PG nimble Serverless.

深水区

深水区一（存算分离架构）：PolarFS / PolarStore——"数据复制"换成了"存储层是逻辑单点"

  • 机制：计算节点与存储彻底分离，存储层是阿里自研的分布式文件系统 PolarFS 跑在三副本 PolarStore 上；集群内所有计算节点（1 主 + 最多 15 只读）共享同一份物理数据，只读节点不复制数据，只需从共享存储读 redo 并同步内存元数据，靠 MVCC 保证跨节点读一致性（官方文档 / 开发者社区）。
  • 推到边缘：① 主节点故障真实过程：备节点接管不需要搬数据——切换本质是"redo 所有权 + 主角色"的转移，RPO=0 的机制基础是 redo 落盘三副本后事务才算提交（官方口径）。但真实代价有三层：切换时旧主主动断开所有存量连接（官方文档明确为预期行为），应用看到的是 Communications link failure，不是透明漂移；新主的 Buffer Pool 是空的，冷启动预热期查询延迟可达平时的 2–5 倍、持续数分钟（社区运维文章引阿里内部实践经验，社区共识）；故障转移本身厂商口径"30 秒内"，但业务体感中断常被应用层放大到 1–3 分钟（连接池死连接 + 羊群重连，社区实测案例）。② 存储层抖动/脑裂时计算层表现：工程化防护包括网卡 Flapping 用 Multi-path 多链路 + RTT 选路快速绕行、多对多 Incast 拥塞用计算侧 PolarSwitch 限 I/O 深度 + 存储侧反压（官方 TPC-C 技术揭秘文章）。双主写不可能发生——写必须经存储层仲裁（redo 三副本多数派确认），被网络隔离的旧主写不进存储、自然失去主资格；但计算层网络分区时，只读节点仍可提供读服务，读到的是分区前的旧数据——一致性级别选了"最终一致"就是这个代价。公开渠道几乎没有 PolarDB 存储层脑裂的真实故障复盘，存储抖动传导到计算层的量化行为标待验证。③ "加只读节点不搬数据"的代价：加节点约 5 分钟、数据立即可见，但新节点内存是冷的，预热前读性能打折；只读节点 replay redo 本身消耗 CPU，官方 FAQ 原话承认：只读节点负载过高会"抢占原本属于应用 redo 日志的资源"，直接导致复制延迟增大——读节点不是免费的，它和主库共享同一份存储 I/O 与 redo 带宽预算；主节点写吞吐的天花板从"本地盘"变成了"共享存储的 IOPS/带宽"，热点小写密集场景下存储层是新的瓶颈点（机制推导，待验证）。
  • 选型含义：存算分离把"数据复制"问题换成了"存储层是强依赖单点（逻辑上）"问题——架构评审时要问的不是"主备延迟多少"，而是"存储层抖动的 blast radius 有多大、管控面能否观测到 PolarFS 延迟"。写密集型业务做 POC 时必须压存储 IOPS 而不只是 CPU；只读节点数量规划要留 redo replay 的 CPU 余量，不能按"纯读 QPS"线性外推。MySQL 与 PG 引擎在此架构行为一致；PolarDB-O 继承 PG 引擎的同一套机制。
  • 来源：机制与加节点/复制延迟增大条件——官方文档 FAQ官方文档；切换断连为预期行为、冷启动 2–5 倍延迟——阿里云开发者社区运维实测文章（社区实测，2026）；PolarStore 抗抖动设计——官方 TPC-C 技术揭秘（官方文档，厂商口径成分已剥离，只取机制描述）；脑裂行为——机制推导 + 公开故障复盘缺失待验证

深水区二（Oracle 兼容）：PolarDB-O 的真实覆盖度——"语法跑通"≠"语义等价"

  • 机制：PolarDB-O 是 PG 内核的 Oracle 语法兼容层（SPL 过程语言、Oracle 字典视图、数据类型映射），公有云版本为 Oracle 2.0（基于 PG 11，官方国际站文档），内核闭源；另有基于 PG 14 的商业内核仅通过特殊企业版定制提供（Pigsty 社区 2026 年记录），公有云标准版拿不到。
  • 推到边缘（官方文档白纸黑字的"兼容但不一致"）：① PL/SQL（SPL）：基础语法、游标、包/存储过程/函数、触发器、序列、同义词官方宣称支持。但官方英文《Developer Guide for Oracle Compatibility》明确列出行为差异：自治事务（PRAGMA AUTONOMOUS_TRANSACTION）每个消耗一个连接槽，单会话最多嵌套 16 层，不支持并行查询；"与 Oracle 不完全兼容"：SPL 块结束时若存在未提交事务，PolarDB-O 不报错（Oracle 会报错）——静默吞掉本该暴露的逻辑 bug；包函数支持 STRICT/LEAKPROOF/COST 等 PG 扩展关键字，Oracle 反而不认——从 PolarDB-O 迁回 Oracle 或做双写时是反向坑。② DATE/数据类型：DATE 类型默认是 PG 行为（不带时间部分），必须把参数 polar_comp_redwood_date 设为 true 才与 Oracle 一致——默认值就是个坑（开发者社区教程）。③ DBLINK：官方文档与兼容性指南中未找到原生 DBLINK 支持证据待验证；社区实践走 oracle_fdw/dblink FDW 做外部连接，跨库分布式事务语义与 Oracle DBLINK 不对等。④ 分区表全局索引：官方国际站文档列出硬限制——不能对非分区表建全局索引、不支持表达式索引键、分区键列不能做索引键。
  • 选型含义：PolarDB-O 的兼容是"语法跑通"级别，不是"语义等价"级别。选型测试必须包含：自治事务的连接槽耗尽压测、异常处理路径（尤其依赖 Oracle 报错语义的代码）、DATE 类型参数检查、DBLINK 替代方案验证。把它当"免改代码的 Oracle"会翻车，当"会说 Oracle 方言的 PG"则预期正确。事实差异参考：EDB Postgres Advanced Server 是可私有化部署、跨云的软件产品、跟踪较新 PG 大版本，PolarDB-O 是阿里云托管服务、内核闭源、公有云停在 PG 11 的 Oracle 2.0；OceanBase Oracle 模式是原生分布式多租户架构（Paxos 多副本、租户级双模式），PolarDB-O 是单机 PG 内核 + 存算分离（一写多读、非分片）——"集中式兼容 vs 分布式兼容"的路线选择。
  • 来源：兼容特性清单——官方文档与开发者社区官方文档；自治事务限制与"不完全兼容"声明——官方英文 SPL 开发者指南 PDF官方文档；DATE 参数——开发者社区教程社区实测；PG14 商业内核仅企业版定制——Pigsty 文档（社区实测，2026-08）；EDB/OceanBase 差异——产品形态公开事实（官方文档 + 社区共识）；DBLINK 原生支持情况待验证

深水区三（一写多读与代理）：PolarProxy / 集群地址——收益取决于"能拆出多少无事务纯读流量"

  • 机制：PolarProxy 是集群自带的代理层，解析 SQL 后把写发往主节点、读分发到只读节点；对外三种地址：主地址（只连主）、集群地址（自动读写分离）、只读地址（只读）；一致性三档可选：全局一致性（强）、会话一致性、最终一致性（官方 FAQ）。
  • 推到边缘：① 读延迟真实量级：官方口径"毫秒级"。延迟增大的三个官方承认条件（FAQ 原话）：主节点写入产生过多 redo 导致只读节点"来不及应用"；只读节点负载过高抢占 replay 资源；I/O 瓶颈导致 redo 读写过慢。大促级写入洪峰下，毫秒级口径会破，选了最终一致性的读业务会读到秒级旧数据——这是架构内建的 trade-off，不是故障。② 事务/临时表/会话变量的坑：一旦连接开启事务、建临时表、设置会话变量，PolarProxy 会把该连接粘滞到主节点（事务粘性），后续读也走主——读写分离名存实亡。框架（如 Spring 的 @Transactional）默认给所有方法加事务的业务，上了集群地址可能发现只读节点零流量、主库被读打爆，这是社区最高频的 PolarDB 读写分离翻车模式社区共识。临时表只在主节点会话可见，跨节点的"写临时表、读临时表"在只读节点直接报错。③ 连接行为：连接数上限跟随节点规格的 max_connections官方文档；PolarProxy 本身做连接复用。主备切换时旧主主动断开全部连接，长连接应用若用 HikariCP 默认 maxLifetime=30 分钟，死连接可在池里滞留 10 分钟，叠加"羊群重连"可把刚接管的新主瞬间打垮（社区实测案例：某电商大促切换后连接池持续报错 3 分钟）。官方 FAQ 冷知识：新增只读节点后，已建立的读写分离连接不会自动把流量发到新节点，必须断开重建（如重启应用）——弹性扩容对长连接应用不是即时生效的。④ 引擎差异：MySQL 引擎支持线程池参数（loose_thread_pool_*，8.0.1.1.19+ 支持 proxy 感知的 bypass 配置）；PG 引擎的 PolarProxy 实现为 MaxScale 组合方案（社区 PolarFlex 实测：代理端口 12369）；PolarDB-O 继承 PG 引擎行为。
  • 选型含义：先审计应用的事务边界和会话变量使用，再决定只读节点数量，否则加节点等于加摆设。连接池参数（maxLifetime < 数据库 wait_timeout、显式 socketTimeout 5–10 秒、故障演练）是 PolarDB 选型的必答题，不是可选项。自定义集群地址按业务拆分（读写隔离、权重差不超 3 倍）是生产标配（社区运维经验）。

深水区四（计费与弹性）：Serverless——"为波动付费"不是"为便宜付费"

  • 机制：PolarDB MySQL 版 Serverless 以 RCU 为计算单元按实际消耗自动伸缩、支持自动启停，暂停后只收存储费；PG 版走"敏态 Serverless"，按 PCU 计费（1 PCU 起、0.5 PCU 粒度）；2026 年新推的 PG Agentic Database 支持缩容到 0（0~8 PCU，无负载时计算不收费）（官方帮助中心 + 社区计费拆解）。
  • 推到边缘：① 冷启动/缩容到 0 的真实行为：PG Agentic 版官方明确支持 Scale to Zero / Scale from Zero，有请求时快速恢复官方文档。MySQL Serverless 版支持自动启停、暂停只收存储费（社区计费教程引官方规则）。但自动暂停的触发条件细节（无流量持续多久、哪些状态阻止暂停如存在只读节点/长连接/定时任务）在公开文档中未找到确切条款——待验证；有长连接的应用可能永远触发不了自动暂停，这是 Serverless 省钱的头号隐形杀手（机制推导）。② "按量付费反而更贵"的负载画像：按量单价天然高于包年包月摊销单价。7×24 小时稳定高水位运行的实例，Serverless 按实际 RCU/PCU 累计的账单会超过同规格包年包月；Serverless 赢的场景是波峰波谷差 5–10 倍以上的潮汐负载、开发测试环境、夜间几乎零请求的业务（社区计费拆解文章的选型建议，机制性结论）。另外存储与计算分开计费：存储按实际用量按小时收，计算暂停了存储费照收——"缩容到 0"不等于"账单到 0"，TB 级数据的存储费是固定支出。③ 计费拆分细节：计算（RCU/PCU）+ 存储（GB/小时）+ 增值项（只读节点、SQL 审计、跨地域备份、备份超额）各自计费；包年包月不含只读节点与备份超额（社区计费避坑文章）。RDS 侧有"存储包不能抵扣 Serverless 存储"的规则，PolarDB Serverless 是否同样——待验证。

Deep dive 1 (compute-storage separation architecture): PolarFS / PolarStore — "data replication" replaced by "the storage layer is a logical single point"

  • Mechanism: compute nodes are fully separated from storage; the storage layer is Alibaba's self-developed distributed filesystem PolarFS running on 3-replica PolarStore; all compute nodes in a cluster (1 primary + up to 15 read-only) share the same physical data; read-only nodes replicate no data — they only read redo from shared storage and sync in-memory metadata, with MVCC guaranteeing cross-node read consistency (official docs / developer community).
  • Pushed to the edge: ① The real primary-failure process: replica takeover moves no data — failover is essentially the transfer of "redo ownership + primary role", and the mechanistic basis for RPO=0 is that a transaction only commits after redo lands on 3 replicas (official statement). But the real costs come in three layers: at failover the old primary actively disconnects all existing connections (official docs state this is expected behavior) — applications see Communications link failure, not a transparent drift; the new primary's Buffer Pool is empty, and during the cold-start warm-up, query latency can reach 2–5× normal for several minutes (community ops articles citing Alibaba internal practice, community consensus); failover itself is a vendor claim of "within 30 seconds", but business-perceived interruption is often amplified by the application layer to 1–3 minutes (dead connections in pools + herd reconnection, community-tested cases). ② Compute-layer behavior under storage-layer jitter/split-brain: engineering protections include Multi-path links + RTT-based routing for NIC flapping, and compute-side PolarSwitch I/O-depth limiting + storage-side backpressure for many-to-many Incast congestion (official TPC-C technical deep-dive article). Dual-primary writes cannot happen — writes must be arbitrated by the storage layer (redo 3-replica majority confirmation); a network-isolated old primary can't write to storage and naturally loses primary eligibility; but during a compute-layer network partition, read-only nodes can still serve reads — reads see pre-partition stale data — that's the cost of choosing "eventual consistency". There are virtually no real-world postmortems of PolarDB storage-layer split-brain in public channels; the quantitative behavior of storage jitter propagating to the compute layer is marked 待验证. ③ The cost of "adding read nodes moves no data": adding a node takes ~5 minutes with data immediately visible, but the new node's memory is cold — read performance is discounted before warm-up; read-only node redo replay itself consumes CPU, and the official FAQ states verbatim: an overloaded read-only node "steals resources that belong to the application's redo logs", directly increasing replication lag — a read node is not free; it shares the same storage I/O and redo bandwidth budget as the primary; the primary's write-throughput ceiling moves from "local disks" to "shared storage IOPS/bandwidth" — the storage layer becomes the new bottleneck in hotspot small-write-intensive scenarios (mechanism derivation, to-be-verified).
  • Selection implication: compute-storage separation trades the "data replication" problem for a "storage layer is a (logically) strong-dependency single point" problem — the architecture-review question is not "how much primary-replica lag", but "how large is the storage layer's jitter blast radius, and can the control plane observe PolarFS latency". Write-intensive businesses must stress storage IOPS in the POC, not just CPU; read-only node count planning must reserve CPU headroom for redo replay — don't linearly extrapolate from "pure-read QPS". The MySQL and PG engines behave identically in this architecture; PolarDB-O inherits the same mechanism from the PG engine.
  • Sources: mechanism and node-addition/replication-lag-increase conditions — official docs FAQ 官方文档; disconnection-on-failover as expected behavior, 2–5× cold-start latency — Alibaba Cloud developer community ops field-testing articles (community-tested, 2026); PolarStore anti-jitter design — official TPC-C technical deep-dive (official docs, vendor-claim components stripped, mechanism descriptions only); split-brain behavior — mechanism derivation + absence of public postmortems 待验证

Deep dive 2 (Oracle compatibility): PolarDB-O's real coverage — "syntax runs" ≠ "semantics equivalent"

  • Mechanism: PolarDB-O is an Oracle-syntax compatibility layer on the PG kernel (SPL procedural language, Oracle dictionary views, data-type mappings); the public-cloud version is Oracle 2.0 (based on PG 11, official international-site docs), kernel closed-source; a separate PG 14-based commercial kernel is only available through special enterprise-edition customization (Pigsty community records, 2026), not obtainable in the public-cloud standard edition.
  • Pushed to the edge (the "compatible but inconsistent" items documented in official docs): ① PL/SQL (SPL): basic syntax, cursors, packages/stored procedures/functions, triggers, sequences, synonyms are officially claimed as supported. But the official English Developer Guide for Oracle Compatibility explicitly lists behavioral differences: autonomous transactions (PRAGMA AUTONOMOUS_TRANSACTION) each consume one connection slot, at most 16 nested levels per session, parallel queries not supported; "not fully compatible with Oracle": if an SPL block ends with an uncommitted transaction, PolarDB-O does not raise an error (Oracle does) — silently swallowing a logic bug that should have surfaced; package functions support STRICT/LEAKPROOF/COST and other PG extension keywords that Oracle doesn't recognize — a reverse pitfall when migrating back from PolarDB-O to Oracle or running dual-write. ② DATE/data types: the DATE type defaults to PG behavior (no time component) — the parameter polar_comp_redwood_date must be set to true to match Oracle — the default is itself a pitfall (developer community tutorial). ③ DBLINK: no native DBLINK support evidence found in official docs or compatibility guides 待验证; community practice uses oracle_fdw/dblink FDWs for external connections, and cross-database distributed transaction semantics are not equivalent to Oracle DBLINK. ④ Partitioned-table global indexes: the official international-site docs list hard limits — no global indexes on non-partitioned tables, no expression index keys, partition-key columns can't be index keys.
  • Selection implication: PolarDB-O compatibility is "syntax runs" level, not "semantics equivalent" level. Selection testing must include: connection-slot-exhaustion stress tests for autonomous transactions, exception-handling paths (especially code depending on Oracle error semantics), DATE-type parameter checks, and DBLINK alternative validation. Treating it as "Oracle without code changes" will blow up; treating it as "PG that speaks Oracle dialect" sets expectations correctly. Factual difference reference: EDB Postgres Advanced Server is a privately deployable, cross-cloud software product tracking newer PG major versions; PolarDB-O is an Alibaba Cloud managed service, kernel closed-source, public cloud stuck at Oracle 2.0 on PG 11; OceanBase's Oracle mode is a natively distributed multi-tenant architecture (Paxos multi-replica, tenant-level dual mode); PolarDB-O is a single-machine PG kernel + compute-storage separation (single-writer/multi-reader, non-sharded) — the route choice of "centralized compatibility vs distributed compatibility".
  • Sources: compatibility feature list — official docs and developer community 官方文档; autonomous-transaction limits and "not fully compatible" statement — official English SPL developer guide PDF 官方文档; DATE parameter — developer community tutorial 社区实测; PG 14 commercial kernel only via enterprise customization — Pigsty docs (community-tested, 2026-08); EDB/OceanBase differences — public product-form facts (official docs + community consensus); native DBLINK support status 待验证

Deep dive 3 (single-writer/multi-reader and proxy): PolarProxy / cluster endpoint — returns depend on "how much transaction-free pure-read traffic you can split off"

  • Mechanism: PolarProxy is the cluster's built-in proxy layer — it parses SQL, sends writes to the primary and distributes reads to read-only nodes; three endpoint types: primary endpoint (primary only), cluster endpoint (automatic read/write splitting), read-only endpoint (reads only); three consistency levels: global consistency (strong), session consistency, eventual consistency (official FAQ).
  • Pushed to the edge: ① Real read-lag magnitude: official statement is "millisecond-level". The three officially acknowledged lag-increase conditions (FAQ verbatim): the primary generates so much redo that read-only nodes "can't keep up applying it"; read-only nodes overloaded, stealing replay resources; I/O bottlenecks slowing redo reads/writes. Under promotion-level write bursts the millisecond-level statement breaks; read workloads on eventual consistency will read second-level stale data — this is an architecture-inherent trade-off, not a failure. ② Transaction/temp-table/session-variable pitfalls: once a connection opens a transaction, creates a temp table, or sets session variables, PolarProxy pins that connection to the primary (transaction stickiness) — subsequent reads go to the primary too, making read/write splitting nominal. Frameworks (like Spring's @Transactional) that put transactions on every method by default can end up with zero traffic on read-only nodes and the primary hammered by reads — the most frequent PolarDB read/write-splitting failure mode in the community 社区共识. Temp tables are only visible in the primary-node session; "write temp table, read temp table" across nodes errors out directly on read-only nodes. ③ Connection behavior: connection limits follow each node spec's max_connections 官方文档; PolarProxy itself multiplexes connections. On primary/secondary failover the old primary actively disconnects all connections; for long-lived-connection apps using HikariCP's default maxLifetime=30 minutes, dead connections can linger in the pool for 10 minutes, and combined with "herd reconnection" can instantly crush the newly promoted primary (community-tested case: an e-commerce promotion saw connection-pool errors persist for 3 minutes after failover). A cold fact from the official FAQ: after adding a read-only node, already-established read/write-splitting connections will not automatically route requests to the new node — connections must be dropped and rebuilt (e.g., restart the app) — elastic scale-out is not immediately effective for long-connection applications. ④ Engine differences: the MySQL engine supports thread-pool parameters (loose_thread_pool_*; 8.0.1.1.19+ supports proxy-aware bypass config); the PG engine's PolarProxy is implemented as a MaxScale-based combo (community PolarFlex testing: proxy port 12369); PolarDB-O inherits the PG engine's behavior.
  • Selection implication: audit the application's transaction boundaries and session-variable usage before deciding how many read-only nodes to add — otherwise added nodes are decorations. Connection-pool parameters (maxLifetime < database wait_timeout, explicit socketTimeout 5–10 seconds, failover drills) are required answers in PolarDB selection, not optional. Custom cluster endpoints split by business (read/write isolation, weight ratios within 3×) are the production standard (community ops experience).
  • Sources: three endpoint types and three consistency levels, replication-lag conditions and causes, new nodes requiring connection rebuild — official docs FAQ 官方文档; failover disconnections/cold starts/connection-pool herd effects/address mixing — developer community field-testing articles (community-tested, 2026); transaction stickiness causing zero traffic on read-only nodes — community consensus (consistent with official read/write-splitting docs at the mechanism level); PG engine MaxScale proxy — Pigsty/PolarFlex community testing 社区实测

Deep dive 4 (billing & elasticity): Serverless — "pay for fluctuation", not "pay for cheap"

  • Mechanism: PolarDB MySQL Serverless auto-scales on RCU compute units with actual consumption and supports auto start/stop — after pausing, only storage is billed; the PG edition uses "nimble Serverless" billed on PCU (starting at 1 PCU, 0.5 PCU granularity); the 2026 PG Agentic Database supports scaling to 0 (0–8 PCU, no compute charge when idle) (official help center + community billing breakdowns).
  • Pushed to the edge: ① Real cold-start/scale-to-zero behavior: the PG Agentic edition officially supports Scale to Zero / Scale from Zero with fast recovery on requests 官方文档. The MySQL Serverless edition supports auto start/stop with only storage billed when paused (community billing tutorials citing official rules). But the exact auto-pause trigger conditions (how long without traffic, which states block pausing such as read-only nodes / long connections / scheduled jobs) were not found in public docs — 待验证; applications with long-lived connections may never trigger auto-pause — the #1 hidden killer of Serverless savings (mechanism derivation). ② The "pay-as-you-go is actually more expensive" load profile: pay-as-you-go unit prices are naturally higher than amortized subscription prices. For instances running 7×24 at stable high water marks, Serverless bills accumulated on actual RCU/PCU will exceed subscription pricing for the same spec; Serverless wins for tidal loads with 5–10× peak-to-valley ratios, dev/test environments, and businesses with near-zero requests at night (community billing breakdown articles' selection advice, a mechanistic conclusion). Note that storage and compute are billed separately: storage is billed per GB per hour by actual usage — compute pausing doesn't stop storage charges — "scaling to 0" ≠ "bill to 0"; TB-scale data incurs fixed storage spend. ③ Billing breakdown details: compute (RCU/PCU) + storage (GB/hour) + add-ons (read-only nodes, SQL auditing, cross-region backup, backup overage) are billed separately; subscription doesn't cover read-only nodes and backup overage (community billing pitfall articles). On the RDS side there's a rule that "storage plans can't offset Serverless storage" — whether the same applies to PolarDB Serverless — 待验证.
  • Selection implication: before selecting, draw the 24-hour load curve: peak-to-average ratio < 2 → go subscription directly; only talk Serverless with real valleys. Also confirm auto-pause conditions and long-connection behavior — otherwise a "Serverless" instance becomes the most expensive 7×24 pay-as-you-go form. Model storage charges separately — for large data volumes, storage charges can exceed compute charges.

用户最买账的 5 点

  1. 只读节点秒级扩容，加读能力不搬数据（MySQL / PG 通用）
    • 为什么是真的：存算分离下只读节点挂载同一份 PolarStore 共享存储，通过 redo 物理复制追主，没有 RDS 加从库时的"全量数据复制"阶段。官方口径新增只读节点约 5 分钟，社区实测和用户案例普遍认可"加读节点快一个数量级"是真实机制红利。
    • 边缘与限度：①"秒级/分钟级"是节点启动上线，不是流量生效——官方 FAQ 实锤：新增只读节点前已建立的读写分离连接不会自动把请求转发到新节点，必须断开重连；②写密集时 redo 产生速度超过只读节点回放速度，延迟从毫秒级放大；③每个只读节点都是独立计费的计算节点；④加只读节点只扩展读，写吞吐天花板永远是单主节点。
    • 来源：阿里云官方 FAQ官方文档；社区共识（CSDN/掘金选型帖，2026）。观察版本：PolarDB for MySQL 8.0、PolarDB-PG 14/15/16
  2. PolarProxy 把读写分离和连接池做进基础设施（PG 版口碑最突出）
    • 为什么是真的：强制走代理（集群地址），自动做读写分离、一致性级别路由，PG 版还有 statement 级连接复用。真实用户压测记录：同等压力下原生 PG 内存打到 80%+，PolarDB-PG 只有 60% 不到——代理截断了连接风暴，相当于白送一个调优过的 pgbouncer + 读写分离中间件。
    • 边缘与限度：①代理是所有流量的必经之路，多一跳网络延迟，代理故障/误判路由就是单点风险；②打乱 DBA 运维习惯：pg_stat_activity 看到的是代理后端连接，查杀连接、慢 SQL 定位都要区分"连代理"还是"直连节点"，有用户为此建"运维代理"和"应用代理"两套；③代理对 SQL 的解析有边界，特殊协议特性/大对象场景可能需要绕过代理直连（细节待验证）。
    • 来源：CSDN liuhuayang《PolarDB for PG 查杀连接》迁移系列（2025，真实迁移记录）；CSDN 压测对比（2025）。观察版本：PolarDB for PostgreSQL 14（机制适用于全版本）
  3. 快照备份体系：秒级备份、一级备份强制开启（MySQL/PG 通用）
    • 为什么是真的：基于存储层 ROW 快照，一级备份不真正复制数据，无论库多大都是秒级；官方文档实锤"一级备份默认开启，无法关闭"。用户买账的点是"备份这件事不用操心了"。
    • 边缘与限度：①备份功能免费，但备份占用的存储空间计费（超免费额度后），"无法关闭" = 强制消费存储；②一级备份保留期只有 3~14 天（数据备份最长可配 730 天，默认较短），长期归档靠二级备份（默认关闭）；③二级备份转存失败时到期的备份会被直接删除（官方文档实锤）；④恢复是"恢复成一个新集群"，不是原地回滚。
    • 来源：阿里云官方《备份与恢复》文档；社区共识。观察版本：MySQL / PG 集群版全版本
  4. Serverless 弹性：潮汐业务的"用多少付多少"（MySQL 版 + PG 敏态 Serverless）
    • 为什么是真的：计算（PCU）按秒计费按小时出账 + 存储按实际用量，闲时可缩到 0~1 PCU。相对 RDS"按规格包年包月买断"，业务有明显波峰波谷时避免了为峰值买单。
    • 边缘与限度：①弹性有滞后：负载探测+拉起是秒级不是瞬时，突发尖刺的前几十秒可能先被限流；②各形态有 PCU 上下限（如 0~8 PCU）；③负载平稳的业务可能比包年包月更贵，账单可预测性差是财务侧真实抱怨；④小团队选型帖共识：体量小、用不明白 PolarDB 特性的团队，RDS 更省心。
    • 来源：官方 PolarDB-PG 形态对比文档（2026）；CSDN 选型帖（2025）。观察版本：MySQL Serverless、PG 敏态 Serverless（2026）
  5. Oracle 兼容模式：去 O 降本的迁移跳板（PolarDB-O / PG ora 模式）
    • 为什么是真的：同一 PG 内核通过兼容模式提供 Oracle 语法兼容，厂商口径"95% 以上 Oracle SQL/PLSQL 兼容"。相对 RDS（无 Oracle 兼容）和自建 PG，这是阿里云生态内"去 Oracle 授权费"的低改造成本路径之一，对被 Oracle license 绑定的政企用户是真金白银的吸引力。
    • 边缘与限度：①95% 是厂商口径，剩下的 5% 往往是存储过程包、高级特性——UTL_FILE 等包需调整，管理命令和系统视图名称与原生 Oracle 不同（官方开发者社区 FAQ）；②兼容模式在安装时选定，事后切换成本高，选错模式=重建；③重度 Oracle 依赖（复杂 PL/SQL、DB Job）的系统仍需逐项 POC，"免改代码"是营销话术，真实是"少改代码"。
    • 来源：阿里云开发者社区 FAQ（2026）；官方《Oracle 兼容性用户指南》PDF。观察版本：PolarDB for PostgreSQL（Oracle 兼容模式）
  1. Second-level read-node scale-out, adding read capacity moves no data (MySQL / PG)
    • Why it's true: under compute-storage separation, read-only nodes mount the same PolarStore shared storage and catch up with the primary via redo physical replication — no "full data copy" phase like adding an RDS replica. Official statement: adding a read-only node takes ~5 minutes; community field tests and user cases widely recognize "read-node addition an order of magnitude faster" as a genuine mechanistic dividend.
    • Edges and limits: ① "Second/minute-level" is node startup and going live, not traffic taking effect — the official FAQ confirms: read/write-splitting connections established before a new read-only node is added will not automatically forward requests to the new node; they must be dropped and rebuilt; ② under write intensity, redo generation speed exceeds read-only node replay speed and lag blows up from millisecond-level; ③ each read-only node is an independently billed compute node; ④ adding read-only nodes only scales reads — the write-throughput ceiling is always the single primary.
    • Sources: Alibaba Cloud official FAQ 官方文档; community consensus (CSDN/Juejin selection posts, 2026). Observed versions: PolarDB for MySQL 8.0, PolarDB-PG 14/15/16
  2. PolarProxy builds read/write splitting and connection pooling into the infrastructure (strongest reputation on the PG edition)
    • Why it's true: the mandatory proxy (cluster endpoint) automatically does read/write splitting and consistency-level routing, with statement-level connection multiplexing on the PG edition. Real user load-test records: under equal pressure native PG memory hit 80%+ while PolarDB-PG stayed under 60% — the proxy absorbing connection storms, equivalent to a tuned pgbouncer + read/write-splitting middleware for free.
    • Edges and limits: ① The proxy is on the mandatory path for all traffic — one extra network hop, and proxy failures/mis-routed queries are a single-point risk; ② it disrupts DBA operational habits: pg_stat_activity shows proxy backend connections, so killing connections and locating slow SQL both require distinguishing "connected to proxy" vs "connected directly to node" — some users were forced to build two sets: "ops proxy" + "app proxy"; ③ the proxy's SQL parsing has boundaries — special protocol features / large-object scenarios may need to bypass the proxy and connect directly (details to-be-verified).
    • Sources: CSDN liuhuayang's Kill connections on PolarDB for PG migration series (2025, real migration records); CSDN load-test comparisons (2025). Observed versions: PolarDB for PostgreSQL 14 (mechanism applies to all versions)
  3. Snapshot backup system: second-level backups, mandatory Level-1 backups (MySQL/PG)
    • Why it's true: based on storage-layer ROW snapshots, Level-1 backups copy no real data — second-level regardless of database size; official docs confirm "Level-1 backups are enabled by default and cannot be disabled". What users love is "not having to worry about backups anymore".
    • Edges and limits: ① The backup feature is free, but backup storage space is billed (beyond the free quota) — "cannot be disabled" = forced storage spend; ② Level-1 backup retention is only 3–14 days (data backups configurable up to 730 days, shorter by default); long-term archiving relies on Level-2 backups (disabled by default); ③ when a Level-2 backup transfer fails, expired backups are deleted directly (verified in official docs); ④ recovery means "restore into a new cluster", not in-place rollback.
    • Sources: Alibaba Cloud official Backup and Recovery docs; community consensus. Observed versions: MySQL / PG Cluster edition all versions
  4. Serverless elasticity: "pay for what you use" for tidal businesses (MySQL edition + PG nimble Serverless)
    • Why it's true: compute (PCU) billed per second and settled hourly + storage by actual usage, scaling down to 0–1 PCU when idle. Compared to RDS's "buy specs on subscription", businesses with clear peaks and valleys avoid paying for peak capacity.
    • Edges and limits: ① Elasticity lags: load detection + spin-up is second-level, not instant — the first tens of seconds of a sudden spike may get throttled; ② each form has PCU lower/upper bounds (e.g., 0–8 PCU); ③ steady-load businesses may pay more than subscription, and unpredictable bills are a genuine finance-side complaint; ④ small-team selection-post consensus: teams too small to fully use PolarDB's features find RDS more worry-free.
    • Sources: official PolarDB-PG form-comparison docs (2026); CSDN selection posts (2025). Observed versions: MySQL Serverless, PG nimble Serverless (2026)
  5. Oracle compatibility mode: a migration springboard for de-Oracle cost reduction (PolarDB-O / PG ora mode)
    • Why it's true: the same PG kernel provides Oracle syntax compatibility via compatibility mode, with a vendor statement of "95%+ Oracle SQL/PLSQL compatibility". Compared to RDS (no Oracle compatibility) and self-hosted PG, this is one of the lower-cost "Oracle license removal" paths within the Alibaba Cloud ecosystem — genuinely attractive to government/enterprise users bound by Oracle licenses.
    • Edges and limits: ① 95% is a vendor statement — the remaining 5% is usually stored-procedure packages and advanced features — packages like UTL_FILE need adjustments, and admin command and system view names differ from native Oracle (official developer community FAQ); ② the compatibility mode is chosen at installation time — switching later is costly; choosing the wrong mode = rebuild; ③ systems with heavy Oracle dependencies (complex PL/SQL, DB Jobs) still need item-by-item POCs — "zero code changes" is marketing speak; the reality is "fewer code changes".
    • Sources: Alibaba Cloud developer community FAQ (2026); official Oracle Compatibility User Guide PDF. Observed versions: PolarDB for PostgreSQL (Oracle compatibility mode)

判决

  • 一句话定位：想用 Aurora 路线的"存算分离 + 一写多读"，但业务长在阿里云生态、要中文支持和国内合规的团队，PolarDB 是当前最顺手的选择——但你要接受它是闭源托管服务这个事实：单主写天花板、代理心智成本、版本跟随阿里云节奏，一个都躲不掉。
  • 适合谁：已深度使用阿里云（RDS→PolarDB 一键升级成本最低）的业务；一写多读、读扩展需求强的 OLTP；负载有明显波峰波谷的潮汐业务（Serverless PCU 模型）；被 Oracle 授权费绑定的政企用户走 PolarDB-O 做去 O 跳板（先逐项 POC）；需要 PG 生态 + 连接池/读写分离开箱即用的团队。
  • 不适合谁：非阿里云/多云环境（MySQL、Oracle 版闭源，只能在阿里云上开）；写密集型且需要水平写扩展的业务（单主是架构原罪，加只读节点无解，只能升主规格或走 PolarDB-X）；重度依赖 MySQL 高级特性/原生生态工具（pt-osc 等）的 DBA 团队；预算敏感的小业务（同等规格贵于 RDS，特性用不满=反向付费，"先 RDS"）；要求最新 PG 大版本即时跟进的团队（PG 18 需白名单，版本跟随阿里云节奏）；出海且主要用欧美地域的团队（国际站地域覆盖与功能节奏滞后）。
  • 迁移成本：RDS MySQL/PG → 低（一键升级/DTS，支持回滚，停机<10 分钟为官方口径，社区实测跨版本一键迁移可行）；自建 MySQL/PG → 低-中（协议高度兼容，DTS 全量+增量；注意驱动版本、pt-osc 等生态工具限制、事务粘性导致的读写分离失效要提前审计应用）；Oracle → 中（PolarDB-O 兼容模式是"少改代码"不是"免改代码"：自治事务、DATE 类型、DBLINK、分区全局索引逐项 POC；安装时选定兼容模式，选错=重建）。
  • One-sentence positioning: For teams that want the Aurora-track "compute-storage separation + single-writer/multi-reader" but whose business lives in the Alibaba Cloud ecosystem and needs Chinese-language support and domestic compliance, PolarDB is the most natural choice today — but you must accept the fact that it's a closed-source managed service: the single-primary write ceiling, the proxy cognitive cost, and versioning following Alibaba Cloud's cadence — none of them can be avoided.
  • Good for: businesses deeply invested in Alibaba Cloud (RDS→PolarDB one-click upgrade is the cheapest path); write-heavy/multi-reader OLTP with strong read-scaling needs; tidal businesses with clear peaks and valleys (Serverless PCU model); government/enterprise users bound by Oracle licensing fees using PolarDB-O as a de-Oracle springboard (item-by-item POCs first); teams wanting PG ecosystem + out-of-the-box connection pooling/read-write splitting.
  • Not for: non-Alibaba Cloud / multi-cloud environments (MySQL and Oracle editions closed-source, only available on Alibaba Cloud); write-intensive businesses needing horizontal write scaling (single-primary is the architectural original sin — adding read-only nodes doesn't help, only primary spec upgrades or PolarDB-X); DBA teams heavily dependent on MySQL advanced features / native ecosystem tools (pt-osc, etc.); budget-sensitive small businesses (costs more than RDS at equivalent specs; paying for unused features = reverse payment, "start with RDS"); teams requiring immediate tracking of the latest PG major versions (PG 18 needs allowlist, versions follow Alibaba Cloud's cadence); overseas teams primarily serving Europe/US regions (international-site region coverage and feature cadence lag).
  • Migration cost: RDS MySQL/PG → Low (one-click upgrade/DTS, supports rollback, downtime <10 minutes per official statement, community-tested cross-version one-click migration works); self-hosted MySQL/PG → Low–Medium (highly protocol-compatible, DTS full+incremental; watch driver versions, pt-osc and other ecosystem tool limits, and audit the app's transaction stickiness that can silently defeat read/write splitting); Oracle → Medium (PolarDB-O compatibility mode is "fewer code changes", not "zero code changes": autonomous transactions, DATE types, DBLINK, partitioned global indexes each need POCs; the compatibility mode is chosen at installation — wrong choice = rebuild).
