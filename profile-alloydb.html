Google AlloyDB（AlloyDB for PostgreSQL）

关系型 OLTP #云原生 #PG兼容 #HTAP #存算分离 #列存 #GCP #Omni

Google Cloud 的 PG 兼容云原生数据库：计算存储分离 + 行存列存双引擎，定位是"GCP 上的 Aurora，但只做 PostgreSQL 且带 HTAP"；另有可下载的 AlloyDB Omni 版本跑在任意环境。

Google Cloud's PostgreSQL-compatible cloud-native database: disaggregated compute and storage + dual row-store/column-store engines, positioned as "Aurora on GCP, but PostgreSQL-only with HTAP"; also available as a downloadable AlloyDB Omni edition that runs in any environment.

硬维度（14 项）

1 静态加密 / TDE 有

有官方文档。托管版数据默认由 Google 管理的密钥加密落盘；支持 CMEK——密钥存于 Cloud KMS（软件密钥或 Cloud HSM 硬件密钥），另支持 Cloud EKM 外部密钥管理与 KMS Autokey；加密覆盖数据库与备份。Omni 侧：Kubernetes operator 1.8.0（2026-07-15）TDE GA，加密数据文件、备份与缓存溢出到磁盘的数据；容器版 18.1.0 TDE 为 Preview。注意托管版官方口径不称"TDE"，但落盘加密+CMEK 的实质等价。

2 TLS / 传输加密 有

有官方文档。AlloyDB Auth Proxy 可把非 TLS 连接透明升级为 TLS 1.3；语言连接器（Language Connectors）使用 mTLS；支持 VPC 私有连接。

3 审计 有

有官方文档。两层：① pgAudit 扩展做 SQL 级会话/对象审计，需开 alloydb.enable_pgaudit flag（实例重启生效），日志摄入速率上限 4MB/s，超限可能导致磁盘打满甚至丢审计日志；② Cloud Audit Logs 记录管理面操作（Admin Activity / Data Access / System Event）。

4 认证与权限 有

有官方文档。支持 IAM 数据库认证（短时令牌，替代静态密码）与传统 PG 密码用户（BUILT_IN）并存；另支持无密码认证选项；Omni 容器版 17.5.0 起支持 AD 组授权（GA）。

5 备份恢复 有

有官方文档。连续备份+PITR 默认开启，保留窗口 1–35 天可配，每日增量备份，微秒级时间点恢复厂商口径；支持按需全量备份、计划自动备份、升级前后自动生成的系统备份。关键限制：恢复永远生成一个新集群，不支持原地回滚社区实测。

6 大版本升级 部分支持

部分支持官方文档。支持原地大版本升级：总耗时 40 分钟–48 小时（随库大小增长，128TB 约 22 小时），主库停机典型 20 分钟–1 小时；升级前有预检，失败可在读池升级阶段前回滚（系统备份作为回滚点）。PG 18 Preview 暂不支持原地升级。Omni 自行负责，用标准 pg_upgrade 流程。

7 可观测性 有

有官方文档。Cloud Monitoring 指标（CPU/存储/网络/内存/连接数）、Query Insights、pg_stat_statements、auto_explain flag；Omni 支持日志轮转（默认 200MB 轮转、归档保留 7 天）。

8 连接模型 有

有官方文档。默认 max_connections=1000，可调至 240,000；官方建议每 vCPU 不超过 4 个并发查询；托管版提供内置托管连接池（默认 transaction 模式，默认池 50/库-用户对，最大客户端连接默认 5000）；短连接场景官方仍建议应用侧连接池（HikariCP/c3p0）或 PgBouncer；Omni Kubernetes 版提供 PgBouncer CRD。

9 事务与隔离级别 有

有。与社区 PG 相同的 MVCC 事务模型官方文档。来源等级：官方文档

10 复制与一致性 有

有。区域内基于日志的分布式存储层同步复制；跨区为异步 secondary cluster 复制。来源等级：官方文档

11 扩展方式 纵向为主 + 读横向扩展

纵向为主 + 读横向扩展。主实例纵向扩缩（官方称近乎无中断）；读扩展靠 read pool（全集群最多 20 个读节点，共享同一份存储，读副本不产生额外存储费用）；写扩展上限为主实例规格——不是 Spanner 式的无上限水平写扩展。来源等级：官方文档

12 兼容性 PostgreSQL 线协议/S

PostgreSQL 线协议/SQL 全兼容（官方口径"100% PG compatible"）；50+ 扩展（含 PostGIS、pgvector、自研 alloydb_scann、google_ml_integration、google_columnar_engine）；标准 PG 驱动/psql 即插即用。来源等级：官方口径

13 许可证与商业模式 无 I/O 费用

商业云服务 + Omni 商业软件订阅。按 vCPU + 内存 + 实际使用存储计费，无 I/O 费用（官方定价策略，厂商口径）；读副本不收存储费；1/3 年 committed use discount；Omni 生产按 vCPU 订阅、非生产免费。只描述模型，不引用具体标价。来源等级：官方口径

14 中文资料丰富度 中等

中等。官方文档提供中文版；中文社区实战文章少于 Cloud SQL社区共识。来源等级：官方文档 + 社区共识

1 Data-at-rest encryption / TDE Yes

Yes 官方文档. Managed edition data is encrypted at rest by default with Google-managed keys; CMEK supported — keys stored in Cloud KMS (software keys or Cloud HSM hardware keys), plus Cloud EKM external key management and KMS Autokey; encryption covers databases and backups. Omni side: Kubernetes operator 1.8.0 (2026-07-15) TDE is GA, encrypting data files, backups, and data spilled to disk from caches; container edition 18.1.0 TDE is Preview. Note the managed edition's official documentation does not use the term "TDE", but encryption at rest + CMEK is the substantive equivalent.

2 TLS / transport encryption Yes

Yes 官方文档. AlloyDB Auth Proxy can transparently upgrade non-TLS connections to TLS 1.3; Language Connectors use mTLS; VPC private connectivity supported.

3 Auditing Yes

Yes 官方文档. Two layers: ① the pgAudit extension for SQL-level session/object auditing, requires the alloydb.enable_pgaudit flag (takes effect after instance restart), with a log ingestion rate cap of 4MB/s — exceeding it can fill the disk or even lose audit logs; ② Cloud Audit Logs record control-plane operations (Admin Activity / Data Access / System Event).

4 Authentication & authorization Yes

Yes 官方文档. Supports IAM database authentication (short-lived tokens replacing static passwords) coexisting with traditional PostgreSQL password users (BUILT_IN); passwordless authentication option also supported; Omni container edition supports AD group authorization (GA) from 17.5.0.

5 Backup & recovery Yes

Yes 官方文档. Continuous backup + PITR enabled by default, configurable retention window of 1–35 days, daily incremental backups, microsecond-level point-in-time recovery; on-demand full backups, scheduled automatic backups, and system backups auto-generated before/after upgrades supported. Key limitation: recovery always creates a new cluster; in-place rollback is not supported 社区实测.

6 Major-version upgrades Partially supported

Partially supported 官方文档. Supports in-place major version upgrades: total duration 40 minutes–48 hours (grows with database size; ~22 hours for 128TB), typical primary downtime 20 minutes–1 hour; pre-upgrade checks available, rollback possible before the read-pool upgrade phase (system backups serve as rollback points). PG 18 Preview does not support in-place upgrades. Omni is self-managed with the standard pg_upgrade process.

7 Observability Yes

Yes 官方文档. Cloud Monitoring metrics (CPU/storage/network/memory/connections), Query Insights, pg_stat_statements, auto_explain flag; Omni supports log rotation (default 200MB rotation, 7-day archive retention).

8 Connection model Yes

Yes 官方文档. Default max_connections=1000, adjustable up to 240,000; official recommendation of no more than 4 concurrent queries per vCPU; the managed edition provides a built-in managed connection pool (default transaction mode, default pool 50 per database-user pair, default max client connections 5000); for short-lived connection workloads the official guidance still recommends application-side pooling (HikariCP/c3p0) or PgBouncer; the Omni Kubernetes edition provides a PgBouncer CRD.

9 Transactions & isolation levels Yes

Yes. Same MVCC transaction model as community PostgreSQL 官方文档. Source level: official docs

10 Replication & consistency Yes

Yes. Log-based distributed storage-layer synchronous replication within a region; asynchronous secondary cluster replication across regions. Source level: official docs

11 Scaling Primarily vertical

Primarily vertical + read scale-out. Primary instance vertical scaling (officially described as near-zero-downtime); read scaling via read pools (up to 20 read nodes per cluster, sharing the same storage; read replicas incur no additional storage charges); write scaling ceiling is the primary instance size — not the unbounded horizontal write scaling of Spanner. Source level: official docs

12 Compatibility PostgreSQL wire pr

PostgreSQL wire protocol/SQL fully compatible (official statement: "100% PG compatible"); 50+ extensions (including PostGIS, pgvector, in-house alloydb_scann, google_ml_integration, google_columnar_engine); standard PG drivers/psql work out of the box. Source level: official statement

13 License & business model no I/O charges

Commercial cloud service + Omni commercial software subscription. Billed on vCPU + memory + actual storage used, no I/O charges (official pricing policy, vendor claim); read replicas incur no storage charges; 1/3-year committed use discounts; Omni production billed per vCPU subscription, non-production free. Model described only, no absolute prices cited. Source level: official statement

14 Chinese-language resources Moderate

Moderate. Official documentation available in Chinese; fewer Chinese community hands-on articles than Cloud SQL 社区共识. Source level: official docs + community consensus

杀手特性

  1. 分离式日志型存储：故障恢复与库大小无关 真本事：计算与存储分离，WAL 日志处理下沉到区域级分布式存储层，计算节点只管执行。这带来两个结构性结果：读池节点共享同一份存储（加读节点不搬数据、不收存储费）、故障切换不 replay 本地 WAL。官方口径 60 秒内恢复且与库大小无关。 边缘真相：这是"区域内"的故事——跨区 secondary 是另一套异步复制机制，RPO 不再是 0；存储层是黑盒，单集群默认 16TiB 配额，超了要走配额流程；存储层自身的抖动你看不见也调不了，只能开 ticket。
  2. 列存引擎：同一份数据的 HTAP 真本事：内存列存 + 列式查询规划/执行器，与行存并存；auto-columnarization 按工作负载自动挑选热列入库；读池可单独开列存并做透明查询转发。OLTP 写入的同时跑分析查询，不用 ETL 到数仓。 边缘真相：见深水区一——列存是"最终新鲜"不是实时；频繁更新的表列存收益会被失效稀释；查询引用的列必须全部在列存里，缺一列就整体回退行存，优化器不会告诉你它"差点就用了列存"。
  3. 自治运维：adaptive autovacuum + index advisor 真本事：自适应 autovacuum 按实时负载自动调节 vacuum 的 CPU/IO/进程数/内存，主动防事务 ID 回卷（wraparound），还能检测长事务、孤儿 prepared 事务、孤儿复制槽并告警；index advisor 按真实查询负载推荐索引。PG 最经典的两个运维坑（vacuum 调优、索引拍脑袋）被产品化了。 边缘真相：见深水区二——自治的前提是"它比你更懂你的负载"，极端场景（超大单表、DDL 频繁）下自动策略可能与业务预期打架；关掉（enable_google_adaptive_autovacuum=off）就退回社区 PG 手动调优，等于为这个特性付了它本应省掉的钱。
  4. 无 I/O 账单的计费模型 真本事：只按 vCPU+内存+存储收费，不收 I/O 费用。官方原话是"不透明的 I/O 费用可占到账单 60%"厂商口径——把 I/O 风险留给自己，对 I/O 密集型负载这是实打实的成本可预测性。 边缘真相：见深水区五——没有 I/O 账单不等于便宜：按 vCPU 持续计费、无 serverless（截至 2026-09），低利用率实例的"空转税"可能超过省下的 I/O 钱；计费模型是"可预测"，不是"便宜"。
  5. Omni：可下载的反锁定版本 真本事：同一套引擎打包成容器/K8s/RPM 可下载版本，跑在本地、笔记本、任意云，PG 驱动和扩展照常工作。这是 Aurora/Cosmos DB 们都没有的官方"逃生舱"：先在 GCP 跑托管版，合规要求来了可以整体搬到本地，应用不用改。 边缘真相：见深水区四——Omni 容器版用的是标准 PG 文件系统接口，没有托管版的分布式存储层，等于"只有引擎、没有云底座"；HA、备份、跨区都要自己搭（RPM 编排版/K8s operator 只是脚手架）；生产还要按 vCPU 买订阅，"免费下载≠免费使用"。
  1. Disaggregated log-structured storage: failover time independent of database size Why it's real: compute and storage are separated; WAL log processing is pushed down into the region-level distributed storage layer, and compute nodes only execute. This yields two structural results: read-pool nodes share the same storage (adding read nodes moves no data and incurs no storage charges), and failover does not replay local WAL. Official statement: recovery within 60 seconds, independent of database size. Edge truth: that's the "within one region" story — cross-region secondary is a separate asynchronous replication mechanism, and RPO is no longer 0; the storage layer is a black box with a default 16TiB quota per cluster, exceeding it requires a quota request; storage-layer jitter is invisible and untunable — all you can do is open a ticket.
  2. Columnar engine: HTAP on the same data Why it's real: in-memory columnar storage + columnar query planner/executor coexisting with the row store; auto-columnarization automatically selects hot columns into the column store based on workload; read pools can enable the columnar engine separately with transparent query routing. Run analytics queries alongside OLTP writes without an ETL pipeline to a data warehouse. Edge truth: see Deep Water #1 — the columnar engine is "eventually fresh", not real-time; frequently updated tables see columnar speedups diluted by invalidation; every column referenced by a query must be in the columnar store — one missing column and the whole query falls back to row-store execution, and the optimizer won't tell you it "almost used the columnar engine".
  3. Autonomous operations: adaptive autovacuum + index advisor Why it's real: adaptive autovacuum automatically tunes vacuum's CPU/IO/process/memory based on live load, proactively prevents transaction ID wraparound, and can detect long transactions, orphaned prepared transactions, and orphaned replication slots with alerts; the index advisor recommends indexes based on real query load. PostgreSQL's two classic operational pain points (vacuum tuning, index guesswork) are productized. Edge truth: see Deep Water #2 — autonomy assumes "it knows your workload better than you do"; in extreme scenarios (huge single tables, frequent DDL) automatic policies can fight business expectations; turning it off (enable_google_adaptive_autovacuum=off) reverts to manual community-PostgreSQL tuning — i.e., you paid for a feature to do the work it was supposed to save you from.
  4. A billing model with no I/O line item Why it's real: billed only on vCPU + memory + storage, no I/O charges. The official line is that "opaque I/O charges can account for 60% of the bill" 厂商口径 — Google absorbs the I/O risk, which is genuine cost predictability for I/O-intensive workloads. Edge truth: see Deep Water #5 — no I/O line item doesn't mean cheap: per-vCPU continuous billing with no serverless (as of 2026-09); the "idle tax" on low-utilization instances can exceed the I/O savings; the billing model is "predictable", not "cheap".
  5. Omni: a downloadable anti-lock-in edition Why it's real: the same engine packaged as container/K8s/RPM downloadable editions, running on-prem, on a laptop, or on any cloud, with PG drivers and extensions working as usual. This is an official "escape hatch" that Aurora and Cosmos DB don't offer: start on the GCP managed edition, and if compliance requirements arrive, move everything on-prem with no application changes. Edge truth: see Deep Water #4 — the Omni container edition uses the standard PostgreSQL filesystem interface with no distributed storage layer, i.e., "the engine without the cloud substrate"; HA, backups, and cross-region replication must all be built yourself (the RPM-orchestrated edition / K8s operator is just scaffolding); production still requires a per-vCPU subscription — "free download ≠ free use".

深水区

深水区一：列存引擎——"100x"的三个前提与失效条件（domain：存储引擎）

  • 机制：列存是内存中的一份列式副本，默认占实例内存 30%（Omni 默认 1GB），可调至最高 70%（推荐上限 50%）；超配额部分自动溢出到实例缓存层；auto-columnarization 每小时评估一次按查询热度增删列；写入不直接更新列存，而是把受影响块标记失效，后台按"50% 内容失效"阈值刷新（可调，可手动 google_columnar_engine_refresh()）。
  • 推到边缘：① 高频更新的表：失效块堆积，列存加速比持续衰减，直到后台刷新追上——HTAP 在"写多读也多"的表上是 T+分钟级新鲜，不是实时；② 查询引用的列只要有一列不在列存里，整个查询回退行存执行（官方文档明确），且优化器对"有索引的列"可能主动选行存；③ 分区表只支持叶子分区逐个入库、非叶子分区表/外部表/5000 行以下小表直接不支持、不支持的数据类型静默忽略——schema 设计不适配，列存等于不存在。
  • 选型含义：列存最适合"写入低频、分析高频"的大宽表；写入洪峰型业务先看失效-刷新比（g_columnar_relations 的 invalid_block_count），别信 100x（厂商口径，第三方实测未能复现）。
  • 来源：官方文档（columnar engine about/configure/freshness 三篇），benchant.com 第三方实测

深水区二：自适应 autovacuum——自治的边界（domain：运维/自治）

  • 机制：默认开启的 adaptive autovacuum 替代社区 PG 的固定阈值策略，实时感知负载自动调节 vacuum 资源；监控事务 ID 消耗速度，必要时全库 vacuum 以阻止 wraparound；自动检测三类"vacuum 杀手"（长事务、孤儿 prepared 事务、孤儿复制槽）并在日志告警。
  • 推到边缘：社区实测（hardbyte/awa，2026-09）发现 PG 17 的 AlloyDB 上，维护循环的 ACCESS EXCLUSIVE 锁（ring-rotation）会让 AccessShareLock 等待者排队，4 vCPU 实例吞吐被硬限制在约 2000 jobs/s，原地升级到 PG 18 后限制消失、吞吐回到与 Cloud SQL PG 18 相同的约 5000 jobs/s。这说明"自适应"不等于"无干扰"——维护任务与业务负载的锁竞争在特定版本真实存在，且与底层 PG 大版本行为耦合。
  • 选型含义：把 vacuum 交给自治是省心的，但版本升级（尤其 PG 大版本）后要重新验证维护窗口行为；超高频小事务场景建议做混沌/压测验证。
  • 来源：官方文档（adaptive autovacuum），社区实测（hardbyte/awa deploying-on-managed-postgres.md，2026-09）

深水区三：与 Cloud SQL、Spanner 的定位三角（domain：定位与选型）

  • 机制：Google Cloud 官方自己把三者并排：Cloud SQL = 标准开源 PG/MySQL/SQL Server 全托管（最便宜、lift-and-shift 最容易）；AlloyDB = PG only，高性能 + HTAP（官方口径 4x 事务、100x 分析）；Spanner = 无限水平扩展 + 全球强一致 + 99.999% SLA。
  • 推到边缘：选错的代价是结构性的——① 小规模 PG 负载上 AlloyDB：按 vCPU 持续计费且无 serverless，账单可能数倍于 Cloud SQL，性能优势在低负载下感知为零；② 需要全球多写/超 16TiB 单库/无限扩展：AlloyDB 写扩展天花板是主实例规格，跨区是异步，硬上等于用错工具，这时 Spanner 才是答案；③ MySQL/SQL Server 团队：AlloyDB 是 PG only，没有退路，Cloud SQL 才是同构选项。
  • 选型含义：三选一的决策树应该是"先定引擎（PG/MySQL）→ 再定规模（单机够/要弹性读/要全球写）→ 最后定要不要 HTAP"，而不是"哪个新用哪个"。
  • 来源：官方产品页对比表，社区共识（HN、readmedium 对比长文）

深水区四：Omni——"同一引擎"是真的，"同一服务"是假的（domain：部署形态）

  • 机制：Omni 与托管版共享核心引擎和扩展（ScaNN、google_ml_integration、列存），但容器版走标准 PG 文件系统接口，没有分布式存储层；HA 靠 RPM 编排版的三节点同步流复制 + etcd + HAProxy（官方口径 zone 级故障 near-zero RPO/RTO，厂商口径），或 K8s operator；备份/PITR、低停机维护、TDE 在 operator 1.8.0（2026-07）才 GA。
  • 推到边缘：① 托管版的招牌能力（60 秒故障恢复与库大小无关、读池零存储成本、跨区 secondary）是存储层给的，Omni 没有存储层，这些能力全部要自己重建；② 版本节奏不同步：托管版 PG 17 GA 于 2025-09，Omni PG 17 GA 于 2025-12，Omni 容器版各版本功能有差异（如 TDE 在容器版长期 Preview）；③ 生产授权是按 vCPU 订阅，operator 会上报遥测（可关闭），合规审计时要把"Google 的遥测 agent"纳入评估。
  • 选型含义：Omni 适合"要 AlloyDB 引擎但数据不能上 GCP"的合规/多云场景，以及开发测试；把它当"免费的托管版平替"是误解——省的是云账单，花的是运维人力。
  • 来源：官方文档（Omni overview、release notes、RPM 编排版架构页）

深水区五：计费模型——"无 I/O 账单"的另一面（domain：成本）

  • 机制：计费三要素 vCPU + 内存 + 实际存储；无 I/O 费用；读副本不收存储费；1/3 年 committed use discount；存储自动增长按用量收。
  • 推到边缘：① 无 serverless（截至 2026-09，托管版按配置持续计费），潮汐型负载低谷期的空转成本是纯支出——HN 社区把这列为相对 Aurora 的明确短板；② 2026-09 Google 推出"PostgreSQL for agents"新架构预览，agent 实例可缩容到零（dbta 报道，Preview，待验证实际计费细则），说明 Google 自己也意识到持续计费是短板，但 GA 时间未知；③ 列存默认吃掉 30% 实例内存——为分析能力付的内存费，在纯 OLTP 负载上是浪费，关掉列存才能把钱花在刀刃上。
  • 选型含义：成本建模时按"峰值 vCPU × 24h"估算，不要按平均负载；I/O 密集型选 AlloyDB 省心，低利用率型先算 Cloud SQL 的账。
  • 来源：官方产品页/定价策略，社区共识（HN），dbta 新闻（2026-09-26，Preview）

深水区六：PG 大版本跟进滞后（domain：兼容/升级）

  • 机制：AlloyDB 的 PG 大版本 GA 明显晚于社区：PG 15 社区 2022-10 → AlloyDB GA 2024-01；PG 16 社区 2023-09 → 2024-10；PG 17 社区 2024-09 → 2025-09-22（约 12 个月）；PG 18 社区 2025-09 → 截至 2026-09 仍为 Preview（AlloyDB 18.1），且 Preview 不支持逻辑复制/DMS/原地升级。
  • 推到边缘：社区 PG 新特性的红利（PG 17/18 的 vacuum、I/O、锁改进——深水区二的实测案例正是 PG 18 修了 PG 17 的问题）在 AlloyDB 上要等约一年；原地大版本升级主库停机 20 分钟–1 小时、大库总耗时可达 22 小时（128TB，官方文档），升级窗口本身就是一次小型停机演练；Preview 版本功能残缺（无逻辑复制），生产无法提前验证。
  • 选型含义：把"AlloyDB 的 PG 版本"当作独立的产品版本来跟踪，而不是"PG 17 出了 = 我能用 PG 17"；依赖新版本特性的规划至少留 12 个月缓冲。
  • 来源：官方文档（db-version-policies 时间表），社区实测（awa PG17→18 对比）

Deep Water #1: The columnar engine — the three prerequisites and failure conditions behind "100x" (domain: storage engine)

  • Mechanism: the columnar store is an in-memory columnar copy of data, defaulting to 30% of instance memory (Omni default 1GB), adjustable up to 70% (recommended cap 50%); over-quota portions spill automatically to the instance cache layer; auto-columnarization evaluates query heat hourly to add/remove columns; writes don't update the columnar store directly — affected blocks are marked invalid and refreshed in the background once the "50% content invalid" threshold is hit (tunable, or manual google_columnar_engine_refresh()).
  • Pushed to the edge: ① frequently updated tables: invalid blocks accumulate, columnar speedup decays until background refresh catches up — HTAP on "write-heavy and read-heavy" tables is T+minutes freshness, not real-time; ② if any column referenced by a query is missing from the columnar store, the entire query falls back to row-store execution (explicit in official docs), and the optimizer may actively choose row-store for "columns with indexes"; ③ partitioned tables only support loading leaf partitions individually; non-leaf partitioned tables, foreign tables, and tables under 5000 rows are not supported at all; unsupported data types are silently ignored — if the schema isn't designed to fit, the columnar engine effectively doesn't exist.
  • Selection implication: the columnar engine fits "low-write, high-analytics" wide tables best; for write-burst workloads, check the invalidation-to-refresh ratio first (invalid_block_count in g_columnar_relations) and don't believe 100x (vendor claim, not reproduced in third-party tests).
  • Sources: official docs (three columnar-engine articles: about/configure/freshness), benchant.com third-party test

Deep Water #2: Adaptive autovacuum — the limits of autonomy (domain: operations/autonomy)

  • Mechanism: adaptive autovacuum (on by default) replaces community PostgreSQL's fixed-threshold policy, sensing live load to tune vacuum resources in real time; monitors transaction ID consumption rate and runs full-database vacuum when necessary to prevent wraparound; automatically detects three "vacuum killers" (long transactions, orphaned prepared transactions, orphaned replication slots) and alerts in logs.
  • Pushed to the edge: community testing (hardbyte/awa, 2026-09) found that on PG 17 AlloyDB, the maintenance cycle's ACCESS EXCLUSIVE lock (ring-rotation) makes AccessShareLock waiters queue up, hard-capping a 4-vCPU instance at ~2000 jobs/s; after an in-place upgrade to PG 18 the cap disappeared and throughput returned to ~5000 jobs/s — the same as Cloud SQL PG 18. This shows "adaptive" doesn't mean "non-intrusive" — lock contention between maintenance tasks and business load is real in specific versions and coupled to the underlying PG major-version behavior.
  • Selection implication: handing vacuum to autonomy is convenient, but maintenance-window behavior must be re-validated after version upgrades (especially PG major versions); ultra-high-frequency small-transaction workloads warrant chaos/stress testing.
  • Sources: official docs (adaptive autovacuum), community test (hardbyte/awa deploying-on-managed-postgres.md, 2026-09)

Deep Water #3: The positioning triangle with Cloud SQL and Spanner (domain: positioning & selection)

  • Mechanism: Google Cloud itself places the three side by side: Cloud SQL = standard open-source PG/MySQL/SQL Server fully managed (cheapest, easiest lift-and-shift); AlloyDB = PG only, high performance + HTAP (official statement: 4x transactions, 100x analytics); Spanner = infinite horizontal scaling + global strong consistency + 99.999% SLA.
  • Pushed to the edge: picking wrong is structural — ① small PG workloads on AlloyDB: continuous per-vCPU billing with no serverless means the bill can be several times Cloud SQL's while the performance advantage is imperceptible at low load; ② workloads needing global multi-write / single databases over 16TiB / unbounded scaling: AlloyDB's write ceiling is the primary instance size and cross-region is asynchronous — forcing it means using the wrong tool, and Spanner is the right answer; ③ MySQL/SQL Server teams: AlloyDB is PG only with no way back — Cloud SQL is the like-for-like option.
  • Selection implication: the three-way decision tree should be "first pick the engine (PG/MySQL) → then pick the scale (single node enough / need elastic reads / need global writes) → finally decide whether HTAP is needed" — not "whichever is newest".
  • Sources: official product page comparison table, community consensus (Hacker News, readmedium comparison long-form)

Deep Water #4: Omni — "same engine" is real, "same service" is not (domain: deployment form factor)

  • Mechanism: Omni shares the core engine and extensions with the managed edition (ScaNN, google_ml_integration, columnar engine), but the container edition uses the standard PostgreSQL filesystem interface with no distributed storage layer; HA relies on the RPM-orchestrated edition's three-node synchronous streaming replication + etcd + HAProxy (official statement: near-zero RPO/RTO for zone-level failures — vendor claim), or the K8s operator; backup/PITR, low-downtime maintenance, and TDE only went GA in operator 1.8.0 (2026-07).
  • Pushed to the edge: ① the managed edition's signature capabilities (failover in 60 seconds independent of database size, zero-storage-cost read pools, cross-region secondary) come from the storage layer — Omni has no storage layer, so all of them must be rebuilt by you; ② version cadence is out of sync: managed PG 17 went GA 2025-09, Omni PG 17 went GA 2025-12, and feature sets differ across Omni container editions (e.g., TDE long in Preview on the container edition); ③ production licensing is a per-vCPU subscription, and the operator reports telemetry (can be disabled) — compliance audits must account for "Google's telemetry agent".
  • Selection implication: Omni fits compliance/multi-cloud scenarios where "AlloyDB's engine is wanted but data can't go to GCP", plus dev/test; treating it as a "free managed-edition substitute" is a misunderstanding — you save the cloud bill and spend the operational headcount.
  • Sources: official docs (Omni overview, release notes, RPM-orchestrated edition architecture page)

Deep Water #5: The billing model — the other side of "no I/O bill" (domain: cost)

  • Mechanism: three billing dimensions — vCPU + memory + actual storage; no I/O charges; read replicas incur no storage charges; 1/3-year committed use discounts; auto-growing storage billed by usage.
  • Pushed to the edge: ① no serverless (as of 2026-09, the managed edition bills continuously on provisioned capacity) — low-trough idle cost for tidal workloads is pure spend; Hacker News lists this as a clear weakness relative to Aurora; ② in 2026-09 Google launched the "PostgreSQL for agents" preview, where agent instances can scale to zero (dbta report, Preview, actual billing details to-be-verified) — Google itself recognizes continuous billing as a weakness, but GA timing is unknown; ③ the columnar engine eats 30% of instance memory by default — memory paid for analytics capability is wasted on pure-OLTP workloads; only by disabling the columnar engine can you spend the money where it matters.
  • Selection implication: model costs on "peak vCPU × 24h", not average load; I/O-intensive workloads are at ease on AlloyDB, low-utilization workloads should price Cloud SQL first.
  • Sources: official product/pricing pages, community consensus (Hacker News), dbta news (2026-09-26, Preview)

Deep Water #6: PG major-version lag (domain: compatibility/upgrades)

  • Mechanism: AlloyDB's PG major-version GA lags community significantly: PG 15 community 2022-10 → AlloyDB GA 2024-01; PG 16 community 2023-09 → 2024-10; PG 17 community 2024-09 → 2025-09-22 (~12 months); PG 18 community 2025-09 → still Preview as of 2026-09 (AlloyDB 18.1), and Preview doesn't support logical replication/DMS/in-place upgrades.
  • Pushed to the edge: community PostgreSQL's new-version dividends (PG 17/18 vacuum, I/O, and lock improvements — the Deep Water #2 test case is exactly a PG 18 fix for a PG 17 problem) take about a year to arrive on AlloyDB; in-place major-version upgrades bring 20 minutes–1 hour of primary downtime, with total duration up to ~22 hours for large databases (128TB, official docs) — the upgrade window is itself a small downtime drill; Preview versions have incomplete features (no logical replication), so production can't validate ahead of time.
  • Selection implication: track "AlloyDB's PG version" as its own product version, not as "PG 17 is out = I can use PG 17"; plans depending on new-version features should leave at least a 12-month buffer.
  • Sources: official docs (db-version-policies timeline), community test (awa PG17→18 comparison)

用户最买账的 5 点

  1. PG 兼容到"零改代码"迁移 为什么是真的：线协议与 SQL 全兼容，psql、JDBC、ORM、PostGIS/pgvector 等 50+ 扩展即插即用；Database Migration Service 做 PG→AlloyDB 持续迁移，表级 dump 锁<10 秒、CDC 追增量，停机主要是最后的停写切换窗口。 边缘与限度：兼容的是 PG，不是 Oracle/MySQL——异构迁移仍要改写；PG 大版本滞后（深水区六）意味着"社区 PG 已 GA 的特性"我这没有；DMS 对无主键表的 CDC 只复制 INSERT，UPDATE/DELETE 要手工补。 来源：官方文档（DMS 迁移页），社区共识。观察版本：PG 17
  2. 读扩展是真的"加节点就行" 为什么是真的：读池节点共享同一份分布式存储，加节点不复制数据、不收存储费，全集群最多 20 个读节点；还可对读池单独开列存 + 透明查询转发，把 BI 流量物理隔离到读池。 边缘与限度：写扩展没有这回事——天花板是主实例规格；20 个节点是全集群上限（含所有读池实例）；跨区读要靠 secondary cluster，那是异步复制不是读池。 来源：官方文档（sizing/read pool），社区 skill 文档共识。观察版本：PG 17
  3. 备份与 PITR 默认开启、不用求人 为什么是真的：连续备份+PITR 默认开（1–35 天可配），每日增量、微秒级时间点恢复；升级前后自动打系统备份当回滚点。对比自建 PG"备份脚本是 DBA 的祖传手艺"，这是开箱即用的省心。 边缘与限度：恢复只能生成新集群——想"回滚到 10 分钟前"意味着要切流量到新集群，没有原地 rewind；PITR 必须在事发前就开着，事后开救不了历史。 来源：官方文档（backup overview），社区实测（nullstone-modules）。观察版本：PG 17
  4. vacuum 和索引有人管了 为什么是真的：adaptive autovacuum 自动调优、防 wraparound、自动揪出长事务/孤儿复制槽；index advisor 按真实负载推荐索引。PG DBA 两大心病被产品化。 边缘与限度：自治策略与业务预期的冲突只能靠 flag 关掉再手动调（等于退回社区 PG）；维护循环的锁竞争问题真实存在过（深水区二）；index advisor 的推荐仍需人工评审，建错索引的代价它不承担。 来源：官方文档，社区实测（awa）。观察版本：PG 17
  5. Omni 给了"不上 GCP 也能用"的退路 为什么是真的：同一引擎可下载，跑在本地/K8s/其他云，开发测试免费；对数据驻留合规、多云战略的团队，这是 Aurora/Cosmos DB 给不了的官方逃生舱。 边缘与限度：逃的是"云锁定"，不是"运维"——HA/备份/跨区全得自己搭；生产按 vCPU 订阅，"免费下载"有授权边界；容器版没有分布式存储层，托管版的核心优势带不走。 来源：官方文档（Omni license/production 页），社区共识。观察版本：Omni 18.1.0 / operator 1.8.0
  1. PG compatibility to "zero-code-change" migration Why it's real: wire-protocol and SQL fully compatible; psql, JDBC, ORMs, PostGIS/pgvector and 50+ other extensions work out of the box; Database Migration Service does continuous PG→AlloyDB migration with table-level dump locks under 10 seconds and CDC catch-up — downtime is mostly the final write-stop cutover window. Edge and limits: what's compatible is PG, not Oracle/MySQL — heterogeneous migrations still require rewrites; PG major-version lag (Deep Water #6) means "features GA in community PG" aren't here yet; DMS's CDC for tables without primary keys only replicates INSERTs — UPDATE/DELETE must be backfilled manually. Sources: official docs (DMS migration page), community consensus. Observed version: PG 17
  2. Read scaling that really is "just add nodes" Why it's real: read-pool nodes share the same distributed storage — adding nodes copies no data and incurs no storage charges, up to 20 read nodes per cluster; read pools can also enable the columnar engine separately with transparent query routing, physically isolating BI traffic to the read pool. Edge and limits: there's no such thing for writes — the ceiling is the primary instance size; 20 nodes is the whole-cluster cap (including all read-pool instances); cross-region reads rely on secondary clusters, which are asynchronous replication, not read pools. Sources: official docs (sizing/read pool), community skill-doc consensus. Observed version: PG 17
  3. Backups and PITR on by default, no DBA required Why it's real: continuous backup + PITR on by default (1–35 days configurable), daily incrementals, microsecond-level point-in-time recovery; system backups are auto-taken before/after upgrades as rollback points. Compared to self-managed PostgreSQL's "backup scripts are the DBA's inherited craft", this is out-of-the-box peace of mind. Edge and limits: recovery can only create a new cluster — "rolling back to 10 minutes ago" means cutting traffic to the new cluster; there's no in-place rewind; PITR must have been on before the incident — enabling it afterwards doesn't save history. Sources: official docs (backup overview), community test (nullstone-modules). Observed version: PG 17
  4. Vacuum and indexes are taken care of Why it's real: adaptive autovacuum auto-tunes, prevents wraparound, and automatically catches long transactions/orphaned replication slots; the index advisor recommends indexes from real workload. The two biggest PostgreSQL DBA headaches are productized. Edge and limits: conflicts between autonomous policies and business expectations can only be resolved by flipping the flag off and tuning manually (back to community PG); the maintenance-cycle lock contention issue genuinely happened (Deep Water #2); index advisor recommendations still need human review — it doesn't pay for wrongly built indexes. Sources: official docs, community test (awa). Observed version: PG 17
  5. Omni offers an "off-GCP" exit Why it's real: the same engine is downloadable, running on-prem/K8s/other clouds, free for dev/test; for teams with data-residency compliance or multi-cloud strategies, this is an official escape hatch Aurora/Cosmos DB can't provide. Edge and limits: what you escape is "cloud lock-in", not "operations" — HA/backups/cross-region all must be built yourself; production is per-vCPU subscription, so "free download" has licensing boundaries; the container edition has no distributed storage layer, so the managed edition's core advantages don't come along. Sources: official docs (Omni license/production pages), community consensus. Observed version: Omni 18.1.0 / operator 1.8.0

判决

  • 一句话定位：GCP 上"又要 PG 兼容、又要性能、还要实时分析"的答案；但它是 PG only 的高端托管，不是万能数据库，规模和成本的上限要先算清楚。
  • 适合谁：
    • GCP 上的核心 OLTP 系统，PG 单机性能到顶、想无改代码上云原生架构的团队
    • 需要在同一套 PG 上同时跑交易和分析（实时风控、用户实时看板、推荐特征），想砍掉 T+1 ETL 链路的团队
    • 以 PG/向量检索为底座构建 RAG/Agent 应用的团队（ScaNN + Vertex AI 集成）
    • 数据不能出本地但想要 AlloyDB 引擎的合规/多云团队（走 Omni，但接受自运维）
  • 不适合谁：
    • MySQL / SQL Server 技术栈的团队（AlloyDB 是 PG only）
    • 小规模、低利用率、对成本敏感的负载（Cloud SQL for PostgreSQL 更便宜、更简单）
    • 需要全球多写、无限水平写扩展、99.999% 的超大规模 OLTP（Spanner 才是对应工具）
    • 指望 serverless 按量付费的潮汐型负载（截至 2026-09 未 GA）
  • 迁移成本：
    • PostgreSQL → 低：线协议兼容，DMS 支持低停机持续迁移；注意无主键表的 CDC 限制与 PG 大版本对齐问题
    • MySQL → 中高：需先过 PG 方言关（无 MySQL 协议兼容），DMS + Gemini 可辅助异构迁移与代码转换
    • Oracle → 高：AlloyDB 无 Oracle 兼容层（不像 EDB/OceanBase），PL/SQL、包、专有语法需重写；适合借迁移机会彻底 PG 化、不适合"零改动替换 Oracle"的诉求
  • One-line positioning: the answer on GCP for "PG compatibility + performance + real-time analytics"; but it's a premium PG-only managed database, not a universal one — compute the scale and cost ceilings first.
  • Good for:
    • Core OLTP systems on GCP where standalone PG performance has topped out and teams want to move to a cloud-native architecture without code changes
    • Teams needing to run transactions and analytics on the same PG (real-time risk control, real-time user dashboards, recommendation features) wanting to kill the T+1 ETL pipeline
    • Teams building RAG/agent applications on PG/vector search (ScaNN + Vertex AI integration)
    • Compliance/multi-cloud teams that can't take data off-prem but want the AlloyDB engine (via Omni, accepting self-operation)
  • Not good for:
    • MySQL / SQL Server technology stacks (AlloyDB is PG only)
    • Small-scale, low-utilization, cost-sensitive workloads (Cloud SQL for PostgreSQL is cheaper and simpler)
    • Hyperscale OLTP needing global multi-write, unbounded horizontal write scaling, 99.999% (Spanner is the corresponding tool)
    • Tidal workloads expecting serverless pay-per-use (not GA as of 2026-09)
  • Migration cost:
    • PostgreSQL → Low: wire-protocol compatible; DMS supports low-downtime continuous migration; note the no-primary-key CDC limitation and PG major-version alignment issues
    • MySQL → Medium-high: must first clear the PG dialect hurdle (no MySQL protocol compatibility); DMS + Gemini can assist heterogeneous migration and code conversion
    • Oracle → High: AlloyDB has no Oracle compatibility layer (unlike EDB/OceanBase); PL/SQL, packages, and proprietary syntax need rewrites; fits teams that want to use the migration to go all-in on PG, not teams wanting "zero-change Oracle replacement"
