StarRocks

OLAP #OLAP #MPP #实时数仓 #MySQL协议 #存算分离 #湖仓一体 #向量化引擎 #开源

源自百度 Palo / Doris 代码基的极速 MPP 分析型数据库——为"多表关联的实时报表 + 湖仓一体"而生：全向量化执行引擎配 Cascades 风格 CBO，主键模型做实时 upsert，存算分离做弹性；代价是 FE 中心化元数据、tablet 规划和主键内存这些"建表第一天就写好"的约束。

A blazing-fast MPP analytical database with roots in the Baidu Palo / Doris codebase — built for "real-time reporting over many joined tables plus lakehouse in one engine": a fully vectorized execution engine with a Cascades-style CBO, a primary-key model for real-time upserts, and shared-data storage for elasticity; the price is front-loading constraints like FE-centralized metadata, tablet planning, and primary-key memory — decisions made on day one of table design.

硬维度（46 项）

1 静态加密 / TDE 有

有——enable_transparent_data_encryption（BE 静态参数，v3.3.1 / v3.4.0 / v3.5.0 / v4.0.0 起引入）：开启后新写入的存储对象（segment、delete/update 文件、lake SST、persistent index 等）落盘加密，密钥经 KEK / KeyCache 管理。边缘：默认关闭；必须在部署前开启、运行期不可动态修改；FE 与 BE 的加密开关必须一致，否则 BE 在心跳时直接 abort（LOG(FATAL)）；仅覆盖"开启后新写入"的对象，老数据需重写才加密；WAL / 临时文件 / 备份的覆盖边界未找到明确证据。证据：官方文档（BE 参数文档）。

2 TLS / 传输加密 有

有——v3.4 起支持 MySQL 协议链路的 SSL（fe.conf ssl_force_secure_transport=true 可强制，客户端不用加密会被 5205 拒绝）；Stream Load 可走 HTTPS。证据：官方文档（v3.4 release notes、SSL 配置文档）。

3 审计 有

有——FE fe.audit.log 记录全量 SQL、用户、客户端、执行时间与结果；可按模块过滤（audit_log_modules=slow_query,query,load,stream_load）、JSON 格式、默认保留 30 天、可压缩归档。边缘：文件型审计日志，合规场景需外部采集（ELK 等）做集中留存与防篡改；细粒度"谁看了哪列"需配合脱敏策略与 secure view。证据：官方文档（logs.md、FE 配置文档）。

4 认证与权限 有

有——MySQL 兼容的用户 / 密码 / 角色 / GRANT-REVOKE 权限体系；支持 LDAP 外部认证、SSL 客户端认证；v3.4 起支持 secure view（防越权穿透基表）；列级脱敏 masking policy 在社区资料中有完整语法示例，官方文档待复核。行级安全策略、Kerberos 未找到证据。证据：官方文档 + 社区资料。

5 备份恢复 有

有——CREATE REPOSITORY（S3 / HDFS via broker）+ BACKUP SNAPSHOT / RESTORE SNAPSHOT，支持分区 / 表 / 库三级粒度，异步执行；恢复可改副本数、可跨集群；v3.4 起 shared-data 集群支持自动快照用于集群恢复。边缘：同一时间只允许一个备份任务；恢复是"搭新表再导数据"式的重建，大库恢复耗时与写入吞吐强相关，恢复窗口要实测。证据：官方文档。

6 可观测性 有

有——Prometheus 指标 + 官方 Grafana 看板；information_schema 暴露运维表（如 be_cloud_native_compactions 可审计 shared-data compaction 历史）；慢查询日志、审计日志、EXPLAIN ANALYZE 与 query profile。边缘：shared-data 的关键指标（DataCache 命中率、lake_publish_tablet_version_queuing_count、compaction score）需要 DBA 主动看，默认看板不一定覆盖；v3.5 新增 txn_max_committed_pending_publish_ms 专门诊断版本发布卡住。证据：官方文档 + 社区共识。

7 连接模型 有

有——FE 经 MySQL 协议（9030 端口）接入，兼容 MySQL 客户端与 BI 工具；Stream Load 走 FE/BE 的 HTTP（8030）；v3.5 起支持 Arrow Flight SQL 高速通道。连接池靠应用侧或外部代理，FE 本身是查询协调器而非连接池。证据：官方文档 + 社区共识。

8 事务与隔离级别 部分支持

部分支持——OLAP 定位，无通用 OLTP 事务；写入侧有单库事务能力：Stream Load 事务接口（预提交 + 提交两阶段，对 Flink 保证 exactly-once），v4.0 起支持单库多表事务（多库多表开发中），label 机制做去重（at-most-once 语义），idle_transaction_timeout 超时自动回滚；另有 Group Commit 合并高频小批量写入。跨库事务、多语句交互式事务查证为无；"快照隔离"级别的严谨表述待验证。证据：官方文档（Stream Load 事务接口文档）。

9 复制与一致性 有

有——默认 3 副本（replication_num=3），tablet 多副本分布；v3.4 起写入按"多数派副本成功即成功"（此前曾因单副本找不到而整体失败）；读走版本化可见性（visible version），单批次写入原子可见。边缘：一致性是"单表版本级"而非跨表分布式强一致；shared-data 下 FE leader 切换曾导致在途事务丢失（见深水区一）。证据：官方文档 + 社区共识。

10 扩展方式 有

有——原生 scale-out。shared-nothing：加 BE 节点，tablet 自动均衡（需数据重分布，吃 IO/网络）；shared-data：CN 计算节点无状态、秒级弹性（K8s HPA），Warehouse 实现多负载物理隔离。硬约束：两种模式不可混部、不可互转（官方文档明确）；shared-data 要求 CN 硬件同构。证据：官方文档。

1 Data-at-rest encryption / TDE Supported

Supported — enable_transparent_data_encryption (static BE parameter, introduced in v3.3.1 / v3.4.0 / v3.5.0 / v4.0.0): when enabled, newly written storage objects (segments, delete/update files, lake SSTs, persistent indexes, etc.) are encrypted at rest, with keys managed via KEK / KeyCache. Edges: off by default; must be enabled before deployment, cannot be changed dynamically at runtime; FE and BE flags must match or the BE aborts at heartbeat (LOG(FATAL)); only covers objects written after enabling — old data stays unencrypted until rewritten; coverage of WAL / temp files / backups has no evidence found. Evidence: official docs (BE parameter reference).

2 TLS / transport encryption Supported

Supported — MySQL-protocol SSL since v3.4 (ssl_force_secure_transport=true in fe.conf enforces it; unencrypted clients are rejected with error 5205); Stream Load can run over HTTPS. Evidence: official docs (v3.4 release notes, SSL configuration docs).

3 Auditing Supported

Supported — FE fe.audit.log records all SQL, users, clients, execution times and results; filterable by module (audit_log_modules=slow_query,query,load,stream_load), JSON format, 30-day default retention, compressible archives. Edges: file-based audit logs — compliance scenarios need external collection (ELK etc.) for centralized retention and tamper protection; "who saw which column" granularity requires masking policies plus secure views. Evidence: official docs (logs.md, FE configuration docs).

4 Authentication & authorization Supported

Supported — MySQL-compatible user / password / role / GRANT-REVOKE privilege system; external LDAP authentication, SSL client authentication; secure views since v3.4 (prevents privilege escalation through base tables); column masking policy syntax exists in community materials, official docs pending verification. 杀手特性

写法要求：每个特性 = 它是什么 + 为什么是真本事 + 推到边缘会发生什么。

  1. 全面向量化执行引擎 + CBO + Pipeline 真本事：C++ 向量化引擎（SIMD）配 Cascades 风格 CBO 与 Pipeline 并行执行，多表 Join 场景下优化器自动选 Join 顺序与策略（broadcast / shuffle / colocate），这是它相对 ClickHouse（Join 历史短板）的结构性差异，也是"多表关联实时报表"口碑的技术根基。 边缘真相：CBO 的"智能"完全依赖统计信息——ANALYZE 没跑或过期，Join 顺序和策略就可能选错；外表（湖上数据）统计信息天然弱，湖上复杂查询的计划质量要打折；v3.5 灰度升级时官方曾要求手动关闭低基数优化（cbo_enable_low_cardinality_optimize=false），说明优化器新特性与升级存在耦合风险。见深水区六。
  2. 主键模型（Primary Key）：列存上的真 upsert 真本事：把随机更新转化为"追加新版本 + 主键索引去重"，保留列存批量写入优势的同时做到秒级可见，部分列更新（column mode）进一步降低写入放大。这是实时数仓 CDC 场景选它的核心理由——对比 ClickHouse 的 ReplacingMergeTree（后台异步去重、读时仍需处理），StarRocks 的主键模型在"更新频繁 + 查询也要快"的场景更直接。 边缘真相：见深水区二——主键索引是内存税，规划失误直接报 primary key memory usage exceeds the limit；DelVector 带来读时过滤开销；compaction 必须及时清理历史版本，否则读放大。主键模型不是"免费的更新"，是把更新成本从写入时搬到了内存和后台合并。
  3. 异步物化视图 + SPJG 透明改写 真本事：v2.4 引入、v2.5 起支持改写，MV 可跨多表、跨数据源（Hive / Iceberg / Hudi / Paimon）构建，支持分区级增量刷新；查询侧 SPJG 算法自动匹配改写（单表 / Join / 聚合 / Union / 嵌套 MV），业务 SQL 不用改。这是"预聚合加速"口碑的来源。 边缘真相：见深水区三——"刷新"和"改写"是两条独立链路，数据新鲜度和查询能否命中是两个问题；v4.1.1 对 INCREMENTAL / AUTO 类 MV 禁用了查询改写并拒绝 FORCE 刷新（行为变更，升级前必读 release notes）；候选 MV 过多会拖慢优化器本身。
  4. 存算分离（shared-data）：CN 秒级弹性 + Warehouse 隔离 真本事：v3.0 引入，数据下沉对象存储，CN 计算节点无状态，K8s 下可按负载秒级扩缩容；Warehouse 实现"一份数据、多组计算资源"的物理隔离，解决 MPP 时代"ETL 大查询饿死小查询"的资源隔离难题。研发重心明显向该架构倾斜（4.x 新特性多优先 shared-data）。 边缘真相：见深水区一——这是"用运维复杂度换弹性"：DataCache（StarCache）腐蚀 / 驱逐、S3 限流、FE leader 切换丢在途事务、tablet 数量爆炸压垮 FE 元数据；且与 shared-nothing 不可互转，选型时一次定终身。
  5. 湖仓一体：External Catalog 直查 真本事：Hive / Iceberg / Hudi / Paimon / Delta / JDBC 等外部 catalog 一等公民，StarRocks 可直接查询湖上数据并做 MV 加速，"热数据放仓、冷数据放湖"不用搬数据。这是它相对纯数仓引擎的差异化。 边缘真相：外表查询的性能天花板受湖格式与对象存储延迟限制；外表元数据缓存过期会导致"基表是否变化"判断失准，进而影响 MV 刷新正确性；跨引擎写湖（Format SDK / Spark 直写）是较新的能力，生产采用需逐项验证。

Each feature = what it is + why it's genuinely good + what happens at the edge.

  1. Fully vectorized execution engine + CBO + Pipeline The real thing: C++ vectorized engine (SIMD) with a Cascades-style CBO and Pipeline parallel execution — the optimizer automatically picks join order and join strategy (broadcast / shuffle / colocate) for multi-table joins. This is its structural difference versus ClickHouse (whose join capabilities historically lagged) and the technical root of its "real-time reporting over joins" reputation. The edge truth: the CBO's "intelligence" is entirely statistics-dependent — stale or missing ANALYZE statistics and the CBO picks the wrong join order and strategy; external tables (data on the lake) have inherently weak statistics, so query plans over the lake are discounted; gray-upgrading to v3.5 once required manually disabling low-cardinality optimization (cbo_enable_low_cardinality_optimize=false), showing optimizer features are coupled to upgrade risk. See Deep dive 6.
  2. Primary-key model: real upserts on a columnar store The real thing: random updates become "append a new version + primary-index deduplication", keeping columnar bulk-write advantages while achieving second-level visibility; partial updates (column mode) further reduce write amplification. This is the core reason CDC real-time-warehouse scenarios pick it — versus ClickHouse's ReplacingMergeTree (background async dedup, reads still have to cope), StarRocks' primary-key model is more direct for "frequent updates + fast queries". The edge truth: see Deep dive 2 — the primary index is a memory tax, and bad planning fails loudly with primary key memory usage exceeds the limit; DelVector adds read-time filtering overhead; compaction must reclaim old versions promptly or read amplification grows. The primary-key model is not "free updates" — it moves update cost from write time to memory and background merging.
  3. Asynchronous materialized views + SPJG transparent rewrite The real thing: introduced in v2.4, rewrite-capable since v2.5; MVs can span multiple tables and data sources (Hive / Iceberg / Hudi / Paimon), with partition-level incremental refresh; the SPJG algorithm automatically matches and rewrites queries (single-table / join / aggregation / union / nested MV) without changing business SQL. This is the source of its "pre-aggregation acceleration" reputation. The edge truth: see Deep dive 3 — "refresh" and "rewrite" are two independent pipelines; data freshness and whether a query hits the MV are two separate questions; v4.1.1 disabled query rewrite for INCREMENTAL / AUTO MVs and rejected FORCE refresh (a behavior change — read the release notes before upgrading); too many candidate MVs slow down the optimizer itself.
  4. Shared-data: second-level CN elasticity + Warehouse isolation The real thing: introduced in v3.0; data sinks to object storage, CN compute nodes are stateless and scale in seconds on K8s with load; Warehouses give "one dataset, multiple isolated compute groups" physical isolation, solving the classic MPP problem of "big ETL queries starving small queries". R&D emphasis is visibly shifting to this architecture (most 4.x features land there first). The edge truth: see Deep dive 1 — this trades operational complexity for elasticity: DataCache (StarCache) corruption / eviction, S3 throttling, FE leader failover losing in-flight transactions, tablet explosion crushing FE metadata; and it cannot be converted to/from shared-nothing — one choice, for life.
  5. Lakehouse: External Catalogs query the lake directly The real thing: Hive / Iceberg / Hudi / Paimon / Delta / JDBC external catalogs are first-class; StarRocks can query lake data directly and accelerate with MVs — "hot data in the warehouse, cold data in the lake" without moving data. This is its differentiation against pure warehouse engines. The edge truth: external-table performance is capped by lake formats and object-storage latency; stale external-table metadata caches can misjudge "did the base table change", hurting MV refresh correctness; cross-engine lake writes (Format SDK / direct Spark writes) are newer capabilities — verify each one before production use.

深水区

深水区一：存算分离的真实成熟度——弹性是拿运维复杂度换的

  • 领域：存储架构 / 运维
  • 机制一句话：CN 计算节点无状态，数据持久化在对象存储，本地 StarCache（DataCache）做热数据加速，Warehouse 做多租户计算隔离。
  • 推到边缘：
    • DataCache 是第一故障聚集地：缓存块腐蚀（checksum mismatch 导致发布/查询失败）、自动扩缩容驱逐引发 S3 回源、compaction 跟不上时 score 告警——shared-data 排障手册里五大根因有三条与缓存/对象存储相关。
    • S3 侧：multipart 上传失败、503 限流会直接卡住写入与 compaction。
    • FE leader 切换曾导致在途事务丢失（EditLog gap 造成事务重放失败）——"高可用切换"与"数据不丢"在这里是两笔账。
    • tablet 数量失控会压垮 FE：官方 issue 承认单 tablet ~1GB 的推荐值在大规模下导致 FE 元数据（shard/tablet 元数据、GC、RPC）先成为瓶颈，目标是把单 tablet 容量做到 100GB——这是架构级的已知短板，不是调优能解决的。
    • 历史事故：v3.4.1 shared-data 集群在 leader 切换 + 未发布 compaction 事务下发生元数据丢失，该版本被下线，基线至少 v3.4.5 / v3.5。
    • 硬约束：shared-nothing 与 shared-data 不可混部、不可互转；CN 硬件必须同构。
  • 对选型的含义：shared-data 适合"负载波峰波谷明显、能接受 K8s 运维"的团队；选之前先评估团队是否有对象存储 + 缓存排障能力；tablet/分桶规划在 shared-data 下更关键（FE 是单点瓶颈）；新集群直接上最新 patch，老集群迁 shared-data 等于重建。
  • 来源：官方文档（shared-data feature support）；官方 issue #66457（tablet 容量）；社区排障手册（shared-data 五大根因）；社区版本基线记录（v3.4.1 事故）。

深水区二：主键模型的内存税——upsert 不是免费的

  • 领域：存储引擎
  • 机制一句话：随机更新转化为"追加新版本 + 主键索引定位旧版本"，主键索引常驻内存（或 persistent index 落盘），读时用 DelVector 过滤旧行，后台 compaction 清理历史版本。
  • 推到边缘：
    • 规划失误的直接后果是报错 primary key memory usage exceeds the limit（真实案例：Airtable 数据验证系统，7200 个 bucket 下主键内存超限，加载卡住）。
    • 每个 tablet 有独立的 ingest memtable 和主键索引 memtable——tablet 数量 × 单 tablet 索引 = 总内存，tablet 切得越碎，内存税越重（与深水区一的 FE 压力同源）。
    • 导入进度"99% 卡住"是典型症状：LOAD 返回 99% 表示数据写完，生效（版本发布 + 索引构建）才是最后 1%，主键表的大导入这里最容易现形。
    • 部分列更新走 column mode，与 GIN 倒排索引组合曾出现结果损坏（v4.1.4 修复）——新特性的组合路径是 bug 高发区。
    • 缓解手段 enable_persistent_index 把索引放磁盘，是用读放大换内存，点查延迟会涨，不是无代价开关。
  • 对选型的含义：主键表必须做"分区分桶 × 预估行数 × 主键宽度"的内存测算；高频 CDC 场景先压测"写入 + compaction + 查询"三并发，而不是只测写入；把 enable_persistent_index 当作容量规划选项而非事后救火。
  • 来源：官方文档（主键模型、persistent index）；社区实测（Airtable 案例、CSDN 实践）；官方 release notes（v4.1.4 GIN 修复）。

深水区三：物化视图——"刷新"和"改写"是两条独立链路

  • 领域：SQL 层
  • 机制一句话：刷新链路（MVRefreshPartitionSelector 选分区、BaseMVRefreshProcessor 执行、成功后更新 BaseTableVisibleVersionMap）管数据新鲜度；改写链路（MvRewritePreprocessor 收集候选 + SPJG 模式匹配 + 补偿）管查询能否命中，两者在优化器里汇合。
  • 推到边缘：
    • "数据新鲜"不等于"查询能用"：分区映射错误、外表 connector 元数据过期，都会导致"基表是否变化"判断失准，MV 看似新鲜实则过期。
    • 候选 MV 过多拖慢优化器本身：cbo_materialized_view_rewrite_related_mvs_limit 默认 64、optimizer_materialized_view_timelimit 默认 1000ms——MV 建得越多，优化器搜索成本越高，改写可能因超时而放弃。
    • 行为变更风险：v4.1.1 起对 INCREMENTAL / AUTO 类 MV 禁用查询改写、拒绝 FORCE 刷新与分区刷新——依赖这类 MV 的集群升级 4.1 必须先读 release notes。
    • 统计信息过期会让"命中 MV 的计划仍然不优"；嵌套 MV 要限制改写层数防组合爆炸。
  • 对选型的含义：MV 治理（命名、分区对齐、数量上限）是 DBA 的日常工作，不是"建完不管"；升级前逐项核对 MV 行为变更；用 EXPLAIN 验证改写是否真的发生（看是否出现 MV Scan），不要靠"感觉变快了"。
  • 来源：官方文档（MV 文档、v4.1.1 release notes）；社区源码级解析（2026-08 架构深挖）。

深水区四：写入的隐形瓶颈——版本发布（publish）

  • 领域：写入 / 事务
  • 机制一句话：Stream Load 走预提交 + 提交两阶段，数据落盘后还要"发布版本"（publish version）才可见；Group Commit 把高频小批量合并为 fewer 版本；label 机制做去重。
  • 推到边缘：
    • 高频小写入（如逐条 CDC）的版本数会膨胀：版本越多，compaction 压力越大，查询读放越大——这是"实时性"向"查询性能"收的税。
    • 版本发布卡住时，txn_max_committed_pending_publish_ms（v3.5 新增指标）会报警——"已提交但不可见"是 StarRocks 特有的中间态，排障时先看这个指标而不是只看写入 QPS。
    • FE leader 切换在 shared-data 下可能丢在途事务——"exactly-once"是 Flink connector + 事务接口配合达成的，不是存储层无条件保证，链路任一环节（FE 切换、label 去重窗口）出问题语义就降级。
    • 大版本发布延迟会直接放大 HTAP/实时报表的"数据新鲜度"——业务以为的"秒级实时"，可能是"秒级写入 + 分钟级可见"。
  • 对选型的含义：实时数仓 POC 必须同时压"写入吞吐"和"版本发布延迟"，并看 compaction 队列；CDC 链路做端到端语义测试（含 FE 切换演练），不要只看 happy path。
  • 来源：官方文档（Stream Load 事务接口、Group Commit）；官方 release notes（v3.5 新指标）；社区排障手册。

深水区五：tablet / 分桶规划——建表第一天就决定上限

  • 领域：数据分布
  • 机制一句话：表按分区切、分区按分桶（bucket）切成 tablet，tablet 是数据分布、副本、compaction、调度的基本单位。
  • 推到边缘：
    • tablet 太多：每个 tablet 独立 memtable / 索引 / compaction，BE 内存与 CPU 开销随 tablet 数线性涨；FE 要维护海量 shard/tablet 元数据，CPU、内存、GC、RPC 先到瓶颈（官方 issue #66457 明确承认这是架构级短板）。
    • tablet 太少 / 数据倾斜：单个 tablet 的写入与 compaction 是单线程，一个倾斜的 tablet 就是整条链路的瓶颈。
    • 官方推荐单 tablet ~1GB（压缩后），但这是经验值不是自适应的——v4.0 起支持 automatic tablet splitting（自动分裂），成熟度待生产验证。
    • 分桶键选错（如高基数列做 hash 导致倾斜）上线后再改等于重建表。
  • 对选型的含义：建表必须做"数据量 / 分区数 / 分桶数 / tablet 大小"四算；大表优先按时间分区 + 合理分桶；把 tablet 数量纳入日常巡检（FE 元数据压力是慢死不是快死）。
  • 来源：官方文档（Data_distribution，含 MERGE TABLETS / range 分布限制）；官方 issue #66457；社区容量规划口诀。

深水区六：CBO 的强弱项——统计信息是氧气

  • 领域：SQL 层
  • 机制一句话：Cascades 风格 CBO 基于 ANALYZE 收集的基数、直方图等统计信息估算代价，决定 Join 顺序、Join 策略（broadcast / shuffle / colocate）、是否命中 MV。
  • 推到边缘：
    • 统计信息过期或缺失时，CBO 会选错 Join 顺序、把大表 broadcast（内存爆炸）或该 colocate 的走了 shuffle——"查询突然变慢"的第一嫌疑人永远是统计信息。
    • 外表（Hive / Iceberg 等）统计信息天然弱，湖上复杂查询的计划质量系统性低于内表。
    • 新优化特性与升级耦合：v3.5 灰度升级要求先关低基数优化（cbo_enable_low_cardinality_optimize=false），说明优化器行为是版本相关的，升级后要回归核心报表的执行计划。
    • 低基数列优化、Runtime Filter 等好不好使，都依赖统计信息对基数的正确估计。
  • 对选型的含义：把 ANALYZE 做成定时任务写进运维手册（尤其是 ETL 后）；核心报表升级前后做执行计划 diff；湖仓一体场景对"外表查询性能"单独设预期，不要拿内表跑分去要求湖上查询。
  • 来源：官方文档（CBO、统计信息、v3.5 升级说明）；社区共识。

Deep dive 1: Real maturity of shared-data — elasticity bought with operational complexity

  • Domain: storage architecture / operations
  • Mechanism in one sentence: CN compute nodes are stateless, data persists in object storage, a local StarCache (DataCache) accelerates hot data, and Warehouses isolate multi-tenant compute.
  • At the edge:
    • DataCache is the first incident cluster: block corruption (checksum mismatch failing publishes/queries), auto-scaling evictions causing S3 round-trips, compaction falling behind triggering score alarms — three of the five documented shared-data root causes relate to cache/object storage.
    • On the S3 side: failed multipart uploads and 503 throttling directly stall writes and compaction.
    • FE leader failover once caused in-flight transaction loss (EditLog gap breaking transaction replay) — "HA failover" and "no data loss" are two separate ledgers here.
    • Runaway tablet counts crush the FE: the official issue admits the ~1GB-per-tablet guidance creates an FE metadata (shard/tablet metadata, GC, RPC) bottleneck at scale, targeting 100GB per tablet — an architecture-level known weakness, not a tuning problem.
    • Historical incident: v3.4.1 shared-data clusters lost metadata under FE leader switch + un-published compaction transactions; the version was pulled, baseline at least v3.4.5 / v3.5.
    • Hard constraints: shared-nothing and shared-data cannot mix in one cluster or convert into each other; CN hardware must be homogeneous.
  • Selection implication: shared-data suits teams with spiky loads that can handle K8s operations; assess whether the team can debug object storage + cache before adopting; tablet/bucket planning matters more under shared-data (the FE is a single bottleneck); new clusters go straight to the latest patch, moving an old cluster to shared-data equals rebuilding.
  • Sources: official docs (shared-data feature support); official issue #66457 (tablet sizing); community shared-data troubleshooting handbook (five root causes); community version-baseline records (v3.4.1 metadata incident).

Deep dive 2: The primary-key memory tax — upserts are not free

  • Domain: storage engine
  • Mechanism in one sentence: random updates become "append a new version + primary-index lookup of the old version"; the primary index lives in memory (or on disk via persistent index), reads filter old rows with DelVector, and background compaction reclaims old versions.
  • At the edge:
    • The direct consequence of bad planning is the hard error primary key memory usage exceeds the limit (real case: an Airtable data-validation system hit primary-key memory limits with 7,200 buckets and loads stalled).
    • Each tablet has its own ingest memtable and primary-index memtable — tablet count × per-tablet index = total memory; the more fragmented the tablets, the heavier the memory tax (same root as the FE pressure in Deep dive 1).
    • Imports "stuck at 99%" is the classic symptom: LOAD reporting 99% means data is written; taking effect (version publish + index build) is the final 1% — most visible on primary-key tables.
    • Partial updates via column mode combined with GIN inverted indexes once returned corrupted results (fixed in v4.1.4) — new-feature combination paths are bug hotspots.
    • The mitigation enable_persistent_index moves the index to disk — trading memory for read amplification, raising point-lookup latency; not a free switch.
  • Selection implication: primary-key tables require upfront "partitions × buckets × estimated rows × primary-key width" memory math; high-frequency CDC scenarios must load-test "write + compaction + query" together, not writes alone; treat enable_persistent_index as a capacity-planning option, not a fire extinguisher.
  • Sources: official docs (primary-key model, persistent index); community field reports (Airtable primary-key memory case); official v4.1.4 release notes (GIN + column-mode fix).

Deep dive 3: Materialized views — "refresh" and "rewrite" are two independent pipelines

  • Domain: SQL layer
  • Mechanism in one sentence: the refresh pipeline (MVRefreshPartitionSelector picks partitions, BaseMVRefreshProcessor executes, then updates BaseTableVisibleVersionMap) governs data freshness; the rewrite pipeline (MvRewritePreprocessor collects candidates + SPJG pattern matching + compensation) governs whether queries hit the MV; they meet inside the optimizer.
  • At the edge:
    • "Fresh data" ≠ "query can use it": wrong partition mapping or stale external-connector metadata misjudges "did the base table change", leaving MVs looking fresh while actually stale.
    • Too many candidate MVs slow the optimizer itself: cbo_materialized_view_rewrite_related_mvs_limit defaults to 64, optimizer_materialized_view_timelimit to 1000ms — more MVs mean higher optimizer search cost, and rewrite may be abandoned on timeout.
    • Behavior-change risk: since v4.1.1, INCREMENTAL / AUTO MVs have query rewrite disabled and FORCE / partition refreshes rejected — clusters relying on them must read the release notes before upgrading to 4.1.
    • Stale statistics leave "a plan that hit the MV still suboptimal"; nested MVs need rewrite-depth limits against combinatorial explosion.
  • Selection implication: MV governance (naming, partition alignment, count caps) is DBA daily work, not "build and forget"; verify every MV behavior change before upgrading; verify rewrite actually happens with EXPLAIN (look for MV Scan) instead of relying on "it feels faster".
  • Sources: official docs (MV documentation, v4.1.1 release notes); community MV deep-dives (SPJG, rewrite matrix, refresh strategies); community source-level analysis (refresh/rewrite dual pipelines, optimizer cost).

Deep dive 4: The invisible write bottleneck — version publishing

  • Domain: writes / transactions
  • Mechanism in one sentence: Stream Load runs prepare + commit two-phase; data must "publish its version" (publish version) to become visible after landing; Group Commit merges high-frequency small batches into fewer versions; labels provide deduplication.
  • At the edge:
    • High-frequency small writes (e.g. per-row CDC) inflate version counts: more versions → more compaction pressure → higher query read amplification — a tax that "real-time" pays against "query performance".
    • When publishing stalls, txn_max_committed_pending_publish_ms (new in v3.5) raises the alarm — "committed but invisible" is a StarRocks-specific intermediate state; check this metric first, not just write QPS.
    • FE leader failover can lose in-flight transactions under shared-data — "exactly-once" is achieved by the Flink connector + transaction interface together, not an unconditional storage guarantee; any link (FE failover, label-dedup window) degrading the semantics downgrades the guarantee.
    • Publishing lag directly inflates HTAP / real-time-reporting "data freshness" — what the business thinks of as "second-level real-time" may be "second-level writes + minute-level visibility".
  • Selection implication: real-time-warehouse POCs must load-test both write throughput and publish lag, and watch the compaction queue; run end-to-end semantics tests for CDC pipelines (including FE failover drills), not just happy paths.
  • Sources: official docs (Stream Load transaction interface, Group Commit); official release notes (v3.5 new metric); community troubleshooting handbook.

Deep dive 5: Tablet / bucket planning — day-one table design sets the ceiling

  • Domain: data distribution
  • Mechanism in one sentence: tables are cut by partitions, partitions by buckets into tablets; the tablet is the unit of data distribution, replication, compaction, and scheduling.
  • At the edge:
    • Too many tablets: each has an independent memtable / index / compaction; BE memory and CPU scale linearly with tablet count; the FE must maintain vast shard/tablet metadata, hitting CPU, memory, GC, and RPC limits first (official issue #66457 calls this an architecture-level weakness).
    • Too few / skewed tablets: writes and compaction on a single tablet are single-threaded — one skewed tablet bottlenecks the whole pipeline.
    • The official ~1GB-per-tablet (compressed) guidance is an empirical rule, not adaptive — automatic tablet splitting since v4.0, production maturity pending validation.
    • Picking the wrong bucket key (e.g. a high-cardinality column hash that skews) means rebuilding the table later.
  • Selection implication: table design requires "data volume / partition count / bucket count / tablet size" math; large tables prefer time partitioning + sensible bucketing; put tablet counts on the routine patrol checklist (FE metadata pressure dies slowly, not loudly).
  • Sources: official docs (Data_distribution, including MERGE TABLETS / range-distribution limits); official issue #66457; community capacity-planning rules of thumb.

Deep dive 6: The CBO's strengths and weaknesses — statistics are oxygen

  • Domain: SQL layer
  • Mechanism in one sentence: the Cascades-style CBO estimates costs from statistics (cardinality, histograms) collected by ANALYZE to decide join order, join strategy (broadcast / shuffle / colocate), and MV hits.
  • At the edge:
    • Stale or missing statistics make the CBO pick the wrong join order, broadcast a huge table (memory blowup), or shuffle when colocate was right — "the query suddenly got slow" always suspects statistics first.
    • External tables (Hive / Iceberg etc.) have inherently weak statistics; complex queries over the lake are systematically worse-planned than on internal tables.
    • New optimizer features couple to upgrades: gray-upgrading to v3.5 required disabling low-cardinality optimization first (cbo_enable_low_cardinality_optimize=false) — optimizer behavior is version-dependent, so core-report plans need regression checks after upgrades.
    • Low-cardinality optimization, Runtime Filters and friends all depend on correct cardinality estimates from statistics.
  • Selection implication: make ANALYZE a scheduled job in the operations runbook (especially after ETL); diff core-report execution plans before and after upgrades; set separate expectations for external-table query performance in lakehouse scenarios — don't hold lake queries to internal-table benchmarks.
  • Sources: official docs (CBO, statistics, v3.5 upgrade notes); community consensus.

用户最买账的 5 点

好的也要有深度。每条 = 为什么是真的 + 边缘与限度。

  1. 查询快，尤其是多表 Join
    • 为什么是真的：全向量化引擎 + CBO + Pipeline，TPC-H / TPC-DS 这类复杂分析是主场；社区大量"从 Hive / Presto 迁过来查询快一个数量级"的实测（厂商口径的倍数不采信，但"变快"的方向是社区共识）。
    • 边缘与限度：快的前提是统计信息新鲜、tablet 规划合理；单表极限扫描拼不过 ClickHouse（向量化鼻祖 + 更高压缩比）；外表查询受对象存储延迟限制。以及 benchmark 跑的是"调优后的上限"，不是"你建表第一天的下限"。
    • 来源：社区共识；观察版本：v3.5 / v4.1。
  2. MySQL 协议，BI 工具即插即用
    • 为什么是真的：9030 端口 MySQL 协议，Tableau / Superset / PowerBI / DataGrip 直连，分析师零学习成本；JDBC 驱动通用。
    • 边缘与限度：兼容的是"协议和常用查询语法"，不是 MySQL 行为——存储过程、触发器没有，某些函数语义有差异；BI 生成的复杂 SQL 仍可能触发 CBO 选错计划。接入成本低不等于"SQL 随便写都快"。
    • 来源：官方文档；社区共识。观察版本：v4.1。
  3. 实时写入秒级可见，CDC 友好
    • 为什么是真的：Stream Load / Routine Load / Flink connector 链路成熟，主键模型 upsert 秒级可见，Flink 事务接口保证 exactly-once，是实时数仓的主流选型之一。
    • 边缘与限度：见深水区四——"秒级写入"不等于"秒级可见"，版本发布延迟是隐形成本；高频小写入有版本膨胀税；FE 切换等异常下语义降级。实时链路的 SLA 要按"端到端可见延迟"签，不要按"写入成功"签。
    • 来源：官方文档；社区共识。观察版本：v3.5 / v4.1。
  4. 架构简单，无外部依赖
    • 为什么是真的：FE / BE（/ CN）两类角色，元数据内嵌 BDB-JE 复制，不依赖 ZK / HDFS / 外部协调服务；扩容加节点自动均衡。相对 ClickHouse（分片规划 + Keeper）的运维项确实少。
    • 边缘与限度："无外部依赖"不等于"无单点"——FE 的 BDB-JE 元数据集群（3 节点，leader 选举 <3 秒）仍是中心，tablet 爆炸时 FE 先成为瓶颈（深水区一、五）；shared-data 引入对象存储后，"外部依赖"以 S3 的形式回来了（限流、multipart 失败照单全收）。
    • 来源：官方文档；社区共识。观察版本：v4.1。
  5. Apache 2.0 真开源 + 中文生态
    • 为什么是真的：内核 GitHub 全公开（含存算分离），无功能阉割的社区版；中文文档完整、社区响应快，国内团队上手成本低。
    • 边缘与限度：开源的是代码不是运维能力——深水区问题（tablet 规划、主键内存、DataCache 排障）最终靠读源码或买商业支持；云上 Serverless 是按计算用量计费，常驻高负载下自建可能更便宜，成本模型要按自己的负载曲线算。以及 GitHub star 数是流行度不是质量分。
    • 来源：官方口径；社区共识。观察版本：v4.1。

Strengths get depth too. Each = why it's real + its edge and limits.

  1. Fast queries, especially multi-table joins
    • Why it's real: fully vectorized engine + CBO + Pipeline; TPC-H / TPC-DS style complex analytics are its home turf; community field reports of "an order of magnitude faster than Hive / Presto after migration" (vendor-claimed multiples not adopted, but the direction of "faster" is community consensus).
    • Edges and limits: speed assumes fresh statistics and sane tablet planning; it can't beat ClickHouse on single-table scan extremes (the vectorization originator with higher compression); external-table queries are object-storage-latency-bound. And benchmarks show a tuned ceiling, not your day-one floor.
    • Sources: community consensus; observed on v3.5 / v4.1.
  2. MySQL protocol — BI tools plug right in
    • Why it's real: MySQL protocol on port 9030; Tableau / Superset / PowerBI / DataGrip connect directly, zero learning curve for analysts; generic JDBC drivers work.
    • Edges and limits: compatibility covers "protocol and common query syntax", not MySQL behavior — no stored procedures or triggers, some function semantics differ; BI-generated complex SQL can still trigger bad CBO plans. Low connection cost doesn't mean "any SQL runs fast".
    • Sources: official docs; community consensus. Observed on v4.1.
  3. Second-level write visibility, CDC-friendly
    • Why it's real: mature Stream Load / Routine Load / Flink connector pipelines; primary-key upserts visible in seconds; the Flink transaction interface guarantees exactly-once — a mainstream real-time-warehouse pick.
    • Edges and limits: see Deep dive 4 — "second-level writes" ≠ "second-level visibility"; publish lag is the hidden cost; high-frequency small writes pay the version-inflation tax; semantics degrade under anomalies like FE failover. Sign SLAs on "end-to-end visible latency", not "write success".
    • Sources: official docs; community consensus. Observed on v3.5 / v4.1.
  4. Simple architecture, no external dependencies
    • Why it's real: two role types (FE / BE, plus CN), metadata replicated via embedded BDB-JE — no ZooKeeper / HDFS / external coordination; adding nodes rebalances automatically. Genuinely fewer moving parts than ClickHouse (shard planning + Keeper).
    • Edges and limits: "no external dependencies" ≠ "no single point" — the FE's BDB-JE metadata cluster (3 nodes, leader election <3s) is still central, and the FE bottlenecks first on tablet explosion (Deep dives 1 and 5); shared-data brings "external dependencies" back in S3 form (throttling and multipart failures included).
    • Sources: official docs; community consensus. Observed on v4.1.
  5. Genuinely open Apache 2.0 + Chinese ecosystem
    • Why it's real: kernel fully on GitHub (including shared-data), no crippled community edition; complete Chinese docs, responsive Chinese community, low onboarding cost for domestic teams.
    • Edges and limits: open source is code, not operational capability — deep-dive problems (tablet planning, primary-key memory, DataCache debugging) ultimately require reading source or buying commercial support; cloud Serverless bills by compute usage, and self-hosting may be cheaper under sustained high load — model costs against your own load curve. And GitHub stars measure popularity, not quality.
    • Sources: official statements; community consensus. Observed on v4.1.

判决

  • 一句话定位：多表关联实时分析的最优解之一——CBO + 向量化 + 主键模型 + 湖仓一体，代价是把 tablet 规划、主键内存、统计信息运维这些"建表第一天"的约束前置。
  • 适合谁：
    • 多表 Join 的实时报表 / BI（广告、零售、SaaS 用户侧分析），查询模式复杂、并发高；
    • Flink CDC 实时数仓，需要主键 upsert 秒级可见；
    • 湖仓一体：热数据放仓、冷数据放湖，一个引擎统一查询；
    • 负载波峰波谷明显、能接受 K8s 运维，想用存算分离弹性的团队；
    • MySQL / BI 技术栈，希望分析侧"换库不换工具"的团队。
  • 不适合谁：
    • 单表海量日志扫描、追求极限吞吐（ClickHouse 单表聚合仍是标杆）；
    • 需要存储过程 / 触发器的传统系统；
    • "去 O"替换 Oracle 的信创场景（无 Oracle 兼容）；
    • 团队无专职数据工程师、想"装完不管"（tablet 规划、ANALYZE、compaction 观察一个不能少）；
    • 数据量很小（GB 级）且查询简单——单机 DuckDB / MySQL 更省事。
  • 迁移成本：
    • MySQL（分析侧）→ 低：协议兼容，BI 工具直连；主要是把"行存思维"换成"列存 + 分区分桶"建模。
    • ClickHouse → 中：单表扫描逻辑要重写成多表模型能发挥优势的形态；ReplacingMergeTree 的去重习惯要换成主键模型；分片规划换成 tablet 规划。
    • Hive / Spark 数仓 → 中：ETL 链路可保留，查询层迁移；宽表模型可直接沿用，但分区策略要重做。
    • Doris → 低-中：同源架构（FE/BE、9030、三种数据模型、Stream Load）高度相似，上手快；差异在 CBO 调优、MV 体系、存算分离细节，需逐项验证。
  • One-line positioning: One of the best fits for real-time analytics over many joined tables — CBO + vectorization + primary-key model + lakehouse, at the price of front-loading day-one constraints like tablet planning, primary-key memory, and statistics maintenance.
  • Good for:
    • Real-time reporting / BI over multi-table joins (ads, retail, SaaS user-side analytics) with complex query patterns and high concurrency;
    • Flink CDC real-time warehouses needing primary-key upserts with second-level visibility;
    • Lakehouse: hot data in the warehouse, cold data in the lake, one engine querying both;
    • Teams with spiky loads that can handle K8s operations and want shared-data elasticity;
    • MySQL / BI-stack teams wanting "new warehouse, same tools" on the analytics side.
  • Not for:
    • Single-table massive log scans chasing extreme throughput (ClickHouse still sets the single-table bar);
    • Systems needing stored procedures / triggers;
    • "De-O" Oracle-replacement projects (no Oracle compatibility);
    • Teams without dedicated data engineers wanting "install and forget" (tablet planning, ANALYZE, compaction watch are all mandatory);
    • Tiny datasets (GB scale) with simple queries — a single-node DuckDB / MySQL is simpler.
  • Migration cost:
    • MySQL (analytics side) → Low: protocol-compatible, BI tools connect directly; mainly replacing "row-store thinking" with "columnar + partitioning + bucketing" modeling.
    • ClickHouse → Medium: single-table scan logic must be reshaped to exploit multi-table strengths; ReplacingMergeTree dedup habits become the primary-key model; shard planning becomes tablet planning.
    • Hive / Spark warehouses → Medium: ETL pipelines can stay, the query layer migrates; wide-table models carry over, but partitioning strategies need redoing.
    • Doris → Low-medium: same-origin architecture (FE/BE, port 9030, three data models, Stream Load) is highly similar and easy to pick up; differences in CBO tuning, the MV system, and shared-data details need item-by-item verification.
