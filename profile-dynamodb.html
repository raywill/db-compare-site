Amazon DynamoDB

KV · 宽列 · 文档 #serverless #KV #NoSQL #单毫秒延迟 #GlobalTables #按量计费 #AWS锁定

AWS 的 serverless KV/文档数据库：按分区键哈希分片、单毫秒延迟与表规模无关、多 Region 可多活——但"无运维"的代价是把 DBA 的工作换成了容量建模与账单工程，访问模式设计错了比选错数据库更贵。

AWS's serverless KV/document database: sharded by partition-key hash, single-digit-millisecond latency independent of table size, multi-active across regions — but "no ops" comes at the cost of turning the DBA's job into capacity modeling and bill engineering, and designing your access patterns wrong costs more than picking the wrong database.

硬维度（46 项）

1 静态加密 / TDE 有

有官方文档。所有表默认 AES-256 落盘加密；三档：AWS owned key（默认）、AWS managed key（aws/dynamodb）、customer managed KMS key（自带轮换策略、CloudTrail 审计密钥使用）。注意：AWS owned key 无可见性，合规场景必须显式切 CMK。

2 TLS / 传输加密 有

有官方文档。所有 API 走 HTTPS/TLS；SDK 默认；支持 VPC endpoint 私有访问不走公网。

3 审计 部分支持

部分支持官方文档。CloudTrail 记录管理面 API（建表、改容量、改策略）；数据面（GetItem/PutItem/Query）默认无审计，靠 CloudTrail data events（需单独启用、按量收费）或应用层日志。没有 SQL 审计日志式的"谁查了哪行"开箱能力。

4 认证与权限 有

有官方文档。无用户名密码，IAM SigV4 签名；细粒度访问控制（dynamodb:LeadingKeys 行级、dynamodb:Attributes 列级），多租户隔离的标准做法。

5 备份恢复 有

有官方文档。PITR 连续备份（2025-01 起保留期 1–35 天可配）+ 秒级时间点恢复；on-demand 全量备份（可永久保留）；AWS Backup 集成。关键限制：恢复只能生成新表，不支持原地覆盖/回滚官方文档，"回滚到 10 分钟前"意味着切流量到新表。

6 可观测性 有

有官方文档。CloudWatch 指标（ConsumedRCU/WCU、ThrottledRequests、ReplicationLatency、SystemErrors 等）；Contributor Insights 定位热 key/热分区；CloudTrail；DAX 有独立指标。慢查询概念不存在——只有"被节流的请求"。

7 连接模型 有

有官方文档。HTTPS API，无连接、无连接池——连接风暴问题天然不存在；但"连接"换成了"吞吐配额"，突发超 2 倍历史峰值 30 分钟内仍可能被节流（社区技能文档口径）。

8 事务与隔离级别 有

有官方文档。TransactWriteItems（最多 100 项/4MB，2x WCU）、TransactGetItems（最多 100 项/4MB）；ClientRequestToken 幂等；单 Region 内 ACID。限制：事务仅单 Region（MRSC Global Tables 不支持事务）；默认读最终一致，ConsistentRead=True 得强一致（2x RCU）。

9 复制与一致性 有

有官方文档。表内 3 AZ 同步复制；读默认最终一致（通常 <1 秒收敛，厂商口径）；跨 Region Global Tables：MREC（异步，last-writer-wins）或 MRSC（同步 quorum，需 3 Region 固定拓扑）。

10 扩展方式 有，在线

有，在线官方文档。存储驱动自动分区（无感）；吞吐按 on-demand 自动或 provisioned/auto-scaling 调整；无纵向扩展概念。分区是"只增"逻辑，热 key 无法靠加分区解决（见深水区一）。

11 兼容性 部分支持

部分支持官方文档。专有 NoSQL API（GetItem/PutItem/UpdateItem/DeleteItem/Query/Scan/Batch/Transact）+ PartiQL（SQL 方言子集，功能弱于真 SQL）；AWS SDK 全语言；DynamoDB Local 供本地开发。无 MySQL/PG/Oracle 协议，无开源发行版，迁出=重写数据访问层。

12 许可证与商业模式 闭源商业官方文档

闭源商业官方文档。按量付费：on-demand 按读写请求单元、provisioned 按 RCU/WCU-小时、存储 GB-月、PITR、备份存储、Global Tables 复制写（rWCU）、Streams 读取、DAX 另计；Standard-IA 表类降存储费。AWS 锁定是最大商业现实：无他云、无自建。

13 中文资料丰富度 有中文版但部分页面翻译滞后

中等社区共识。官方文档有中文版但部分页面翻译滞后；中文社区实践帖（CSDN/掘金/知乎）不少，但深度建模（单表设计、GSI 成本）内容多为英文。

20 数据接入与摄入 有

21 外部数据访问 部分支持

部分支持（自身无外部表；Athena 可联邦查 DynamoDB）。

  • DynamoDB 无外部表语义 官方文档。
  • Athena DynamoDB 连接器可做联邦查询 官方文档。
  • PartiQL 只能查本表，跨源要在上层做 社区共识。

22 CDC 与下游同步 有

有（DynamoDB Streams：Lambda/Kinesis）。

  • DynamoDB Streams 提供 24 小时变更日志，可接 Lambda/Kinesis Data Streams 官方文档。
  • Kinesis Data Streams for DynamoDB 支持更长保留与多消费者 官方文档。
  • 大写入量下 Stream 分片热点与 Lambda 并发是调优点 社区共识。

23 TTL 与数据生命周期管理 有

有（表级 TTL 属性，后台自动删不耗 WCU）。

  • 表上指定 TTL 属性（epoch 秒），过期项后台自动删，不消耗写容量 官方文档。
  • 删除延迟通常几小时内，不保证精确时刻 官方文档。
  • TTL 删除会产生 DynamoDB Streams 记录，可触发下游清理 官方文档。

24 在线 DDL 与 Schema 演进 不适用

不适用（schemaless，无 DDL 概念）。

  • 无 schema，属性随时增减，无 DDL 痛点 官方文档。
  • 加 GSI 是在线后台构建，大表回填耗时但不阻塞 官方文档。
  • GSI 回填期间写放大，WCU 规划要留余量 社区共识。

25 多租户与资源隔离 部分支持

部分支持（表级吞吐隔离；无集群内多租户）。

  • 租户隔离靠多表/多账号，表级 WCU/按需计费天然隔离 官方文档。
  • 单表内多租户无资源限流，需应用层分区键设计 社区共识。

26 跨地域多活 有

有（Global Tables 多活写）。

  • Global Tables 多区多活写，最终一致，冲突 last-writer-wins 官方文档。
  • 冲突解决粗糙，不适合强一致多写场景 社区共识。
  • 跨区复制延迟通常 1 秒内 官方文档。

27 高可用架构与 RTO/RPO 有

有（托管多 AZ，SLA 99.99%）。

  • 数据多 AZ 同步复制，AZ 故障自动容错 官方文档。
  • Global Tables 另有 99.999% SLA 档 官方文档。
  • RTO/RPO 由平台兜底，用户无感知 社区共识。

28 行级安全与数据脱敏 部分支持

部分支持（IAM条件键做细粒度行级控制）。

  • DynamoDB 无引擎内 RLS，官方推荐用 IAM policy 的 condition keys（如 dynamodb:LeadingKeys）实现按分区键的行级隔离 官方文档
  • 列级控制靠 IAM 属性级权限（特定属性允许 / 拒绝） 官方文档
  • 脱敏无内置能力，靠应用层 社区共识
  • IAM 策略复杂度随租户数膨胀，是主要运维成本 社区实测

29 JSON 与半结构化能力 有

部分支持（存储黑盒；按量计费无调优）。

1 Data-at-rest encryption / TDE Supported

Supported 官方文档. All tables encrypted on disk with AES-256 by default; three tiers: AWS owned key (default), AWS managed key (aws/dynamodb), customer managed KMS key (bring your own rotation policy; key usage audited via CloudTrail). Note: AWS owned keys offer no visibility — compliance scenarios must explicitly switch to a CMK.

2 TLS / transport encryption Supported

Supported 官方文档. All API calls go over HTTPS/TLS; SDK default; VPC endpoints supported for private access without going over the public internet.

3 Auditing Partially supported

Partially supported 官方文档. CloudTrail records management-plane API calls (table creation, capacity changes, policy changes); the data plane (GetItem/PutItem/Query) has no auditing by default — rely on CloudTrail data events (must be enabled separately, metered billing) or application-layer logging. There is no out-of-the-box "who read which row" SQL-audit-log-style capability.

4 Authentication & authorization Supported

Supported 官方文档. No username/password; IAM SigV4 signatures; fine-grained access control (row-level via dynamodb:LeadingKeys, column-level via dynamodb:Attributes) — the standard practice for multi-tenant isolation.

5 Backup & recovery Supported

Supported 官方文档. PITR continuous backups (retention configurable 1–35 days since 2025-01) + second-level point-in-time restore; on-demand full backups (retained indefinitely); AWS Backup integration. Key limitation: recovery only creates a new table — no in-place overwrite/rollback 官方文档. "Roll back to 10 minutes ago" means cutting traffic to a new table.

6 Observability Supported

Supported 官方文档. CloudWatch metrics (ConsumedRCU/WCU, ThrottledRequests, ReplicationLatency, SystemErrors, etc.); Contributor Insights to locate hot keys/hot partitions; CloudTrail; DAX has its own metrics. The concept of "slow queries" doesn't exist — only "throttled requests."

7 Connection model Supported

Supported 官方文档. HTTPS API, no connections, no connection pools — connection storms are a non-issue by construction. But "connections" are replaced by "throughput quotas": bursts exceeding 2x the historical peak can still be throttled within 30 minutes (community skill docs wording).

8 Transactions & isolation levels Supported

Supported 官方文档. TransactWriteItems (max 100 items / 4MB, 2x WCU), TransactGetItems (max 100 items / 4MB); ClientRequestToken for idempotency; ACID within a single region. Limitations: transactions are single-region only (MRSC Global Tables don't support transactions); reads are eventually consistent by default — ConsistentRead=True gets strong consistency (2x RCU).

9 Replication & consistency Supported

Supported 官方文档. 3-AZ synchronous replication within a table; reads default to eventual consistency (usually converging in <1 second — vendor claim); cross-region Global Tables: MREC (async, last-writer-wins) or MRSC (synchronous quorum, requires a fixed 3-region topology).

10 Scaling Supported

Supported, online 官方文档. Storage-driven automatic partitioning (invisible to you); throughput adjusts via on-demand auto or provisioned/auto-scaling; no vertical-scaling concept. Partitions only ever grow — hot keys can't be solved by adding partitions (see Deep-dive 1).

11 Compatibility Partially supported

Partially supported 官方文档. Proprietary NoSQL API (GetItem/PutItem/UpdateItem/DeleteItem/Query/Scan/Batch/Transact) + PartiQL (a SQL-dialect subset, weaker than real SQL); AWS SDKs in all languages; DynamoDB Local for local development. No MySQL/PG/Oracle protocol (confirmed absent), no open-source distribution (confirmed absent) — migrating away = rewriting the data-access layer.

杀手特性

  1. Serverless 零运维：无实例、无补丁、无版本升级 真本事：没有"主从""分片运维""版本升级"这些概念，吞吐与存储自动扩展；这是它相对一切自建/半托管库最硬的差异。 边缘真相：运维工作没有消失，只是换了形态——DBA 变成了"容量建模师 + FinOps"：on-demand 还是 provisioned、GSI 投影、item 大小取整，每一项都直接连着账单。团队里没人懂 RCU/WCU 账，"零运维"会变成"零预警的账单惊魂"。
  2. 规模无关的单毫秒延迟 真本事：分区哈希架构，GetItem/Query 延迟与表是 1GB 还是 100TB 无关（官方口径个位数毫秒）；这是关系型库"数据量涨→索引深→变慢"曲线不存在的地方。 边缘真相：只对"按键访问"成立。Scan 全表、跨分区聚合、GSI 回表是线性成本；强一致读 2x RCU；DAX 能把读压到微秒但只缓存最终一致读，ConsistentRead=True 直接绕过 DAX（配了 DAX 又全走强一致 = 白花钱）。
  3. Global Tables：真正的多 Region 多写 真本事：每个 Region 可读可写，本地延迟写全球；Region 级 DR 与全球化读写的天然方案。 边缘真相：见深水区六——MREC 的 last-writer-wins 会静默丢更新；MRSC 要 3 Region 固定拓扑、无事务、无 TTL，写延迟付跨 Region quorum 税。多活的是"接入"，不是"一致性免费"。
  4. Streams + TTL + PITR 开箱即用 真本事：CDC（Streams→Lambda）、自动过期（TTL 零存储成本）、35 天秒级 PITR 全是第一方开关，不用攒 Debezium/备份脚本。 边缘真相：Streams 只保留 24 小时、每 shard 最多 2 个消费者，高吞吐 CDC 要换 Kinesis Data Streams for DynamoDB；TTL 删除是"48 小时内尽力"，不是准时过期（到期必须不可见的场景应用层还要再过滤）；PITR 恢复只能建新表。
  5. 向量检索（2026-08 GA）：KV 库里的 ANN 真本事：每表最多 5 个向量索引、4096 维、TopK 100，RAG 场景"元数据过滤 + 向量召回"一库搞定。 边缘真相：base 表超 600GB 需 allowlist（待验证细节）；别把它当专用向量库——大规模 ANN 性能与生态（LangChain 集成深度）待实测验证。这是"顺手做向量"，不是"向量数据库"。
  1. Serverless zero-ops: no instances, no patches, no version upgrades Why it's real: there are no concepts of "primary/replica," "shard ops," or "version upgrades" — throughput and storage scale automatically; this is its hardest differentiator against every self-hosted/semi-managed database. Edge truth: the ops work didn't disappear, it changed shape — the DBA became a "capacity modeler + FinOps engineer": on-demand vs. provisioned, GSI projections, item-size rounding — every choice connects directly to the bill. If nobody on the team understands RCU/WCU billing, "zero ops" becomes "bill shock with no early warning."
  2. Single-digit-millisecond latency independent of scale Why it's real: partitioned-hash architecture — GetItem/Query latency doesn't care whether the table is 1GB or 100TB (official docs wording: single-digit milliseconds); this is where the relational-database curve of "more data → deeper indexes → slower" simply doesn't exist. Edge truth: only holds for key-based access. Full-table Scans, cross-partition aggregations, and GSI backfills are linear-cost operations; strong reads cost 2x RCU; DAX can push reads to microseconds but only caches eventually consistent reads — ConsistentRead=True bypasses DAX entirely (configuring DAX then running everything strongly consistent = money down the drain).
  3. Global Tables: genuinely multi-region, multi-write Why it's real: every region is readable and writable with local-latency writes worldwide; the natural solution for region-level DR and global read/write. Edge truth: see Deep-dive 6 — MREC's last-writer-wins silently drops updates; MRSC requires a fixed 3-region topology, no transactions, no TTL, and pays a cross-region quorum tax on write latency. What's multi-active is "access," not "consistency for free."
  4. Streams + TTL + PITR, all out of the box Why it's real: CDC (Streams→Lambda), auto-expiry (TTL at zero storage cost), and 35-day second-level PITR are all first-party toggles — no need to assemble Debezium/backup scripts yourself. Edge truth: Streams retain only 24 hours with at most 2 consumers per shard — high-throughput CDC needs Kinesis Data Streams for DynamoDB instead; TTL deletion is "best effort within 48 hours," not punctual expiry (if expired items must be invisible on time, the application layer still has to filter); PITR restore only creates a new table.
  5. Vector search (GA 2026-08): ANN inside a KV store Why it's real: up to 5 vector indexes per table, 4096 dimensions, TopK 100 — "metadata filtering + vector recall" in one database for RAG scenarios. Edge truth: base tables over 600GB require an allowlist (details to-be-verified); don't treat it as a dedicated vector database — large-scale ANN performance and ecosystem depth (LangChain integration) await production validation. This is "vector search as a convenience," not "a vector database."

深水区

深水区一（存储/性能）：分区是物理上限，热 key 是设计税（domain：存储引擎）

  • 机制：按分区键哈希分布到内部分区；每分区硬上限 3,000 RCU / 1,000 WCU官方文档，provisioned 和 on-demand 都一样；burst capacity 借 300 秒未用额度扛短峰，adaptive capacity 把闲置额度挪给热分区（甚至把热 key 隔离到独立分区）。
  • 推到边缘：adaptive 再能借也借不过分区天花板——单 key 的写入超过 1,000 WCU/s 就是死刑，分区自动分裂只看吞吐不看 key 基数，一个 key 永远分不到两个分区。表级 CloudWatch 显示"只用了 43% 容量"但请求被 ProvisionedThroughputExceededException 打回，是 DynamoDB 最经典的故障现场。唯一解是写分片（user#0…#N 后缀打散），代价是读变 scatter-gather、应用层合并排序。
  • 选型含义：key 设计是 DynamoDB 的第一生产力；POC 必须按真实 key 分布压测，均匀压测是自欺欺人；上线 Contributor Insights，把"热 key 定位"写进 on-call 手册。
  • 来源：官方文档（burst/adaptive capacity）；dev.to 社区解析（2026-08）；社区技能文档（2026-09）

深水区二（成本）：RCU/WCU 的取整税与"方便税"（domain：成本）

  • 机制：写按 1KB 向上取整计 WCU，读按 4KB 向上取整计 RCU；强一致读 2x；事务写 2x；条件表达式失败的写照样收费；on-demand 单价约为满利用 provisioned 的数倍（社区口径 5–7x）。
  • 推到边缘：1.1KB 的 item 按 2KB 收费——JSON 嵌套、时间戳、元数据让"刚好超一点"成为常态，高频写入下隐形附加成本显著（第三方博客测算口径）；"先 on-demand 上线，以后再切 provisioned"的团队，流量起来后账单翻数倍才想起切（第三方博客案例，厂商无关）；Scan 做 admin 看板：大表全表扫一次费用可观（第三方口径），每刷一次看板烧一次。
  • 选型含义：item 设计时把"每 KB 都是钱"刻进 schema 评审；条件写失败率要监控（失败=烧钱无产出）；on-demand 只给"不可预测"负载，流量可预测且有稳定基线就该切 provisioned+auto-scaling（社区经验）；Scan 永远走 S3 导出 + Athena。
  • 来源：hackernoon 第三方成本分析；awslabs startup-advisor 技能文档（2026-09）；社区共识

深水区三（成本/一致性）：GSI 是"第二张账单"，且只给最终一致（domain：索引）

  • 机制：每个 GSI 独立计费——写入含 GSI key 属性的 item，base 表和 GSI 各收一次 WCU（投影 ALL ≈ 写成本翻倍）；GSI 有独立吞吐配额、独立节流；GSI 读永远最终一致；LSI 只能建表时建、共享表吞吐、单分区键值 10GB 上限。
  • 推到边缘：更新 GSI 的 key 属性 = 删旧索引项 + 写新索引项，一次更新收两次 GSI 写；"随手加个索引查 email"的 PR 让月账单显著上升、写延迟 +40%（Medium 社区案例 2025-10）；5 个全投影 GSI = 写账单 ×6；GSI 背压还会拖慢 base 表写入（写入要等索引写）。
  • 选型含义：GSI 是 schema 设计的一部分，不是运维期的"加索引"按钮；投影能少则少（KEYS_ONLY/INCLUDE），稀疏索引（只给部分 item 建 GSI key）是省钱的标准动作；要强一致的第二访问模式只能用 LSI——但 LSI 必须在建表时想好。
  • 来源：官方文档；Medium 社区案例（2025-10）；社区技能文档（2026-09）

深水区四（复制/CDC）：Streams 的 24 小时与 2 消费者天花板（domain：复制与 CDC）

  • 机制：DynamoDB Streams 按 shard 有序推送变更，保留 24 小时；每 shard 最多 2 个消费者；通常接 Lambda。
  • 推到边缘：消费者挂了超过 24 小时没追上——数据永久丢失，没有"从头再消费"的后悔药；第 3 个消费者（审计+缓存失效+搜素同步各要一个）直接被拒，只能换 Kinesis Data Streams for DynamoDB（保留期可达 1 年、5+ 消费者）；每秒 1 万次写入 = 每秒 1 万次 Lambda 调用，Lambda 并发配额和调用费一起爆炸；单个坏 record 会卡住整个 shard 的重试。
  • 选型含义：Streams 是"触发器"，不是"消息队列"；超过 2 个下游或需要回放，先上 Kinesis；Lambda 消费端必须做幂等 + 死信队列，坏 record 不能卡 shard。
  • 来源：官方文档；awslabs startup-advisor（2026-09）；社区技能文档（2026-09）

深水区五（建模）：单表设计——把 join 从数据库赶到人脑（domain：建模/迁移）

  • 机制：DynamoDB 没有 join，"访问模式先行"：所有查询预先设计为分区键+排序键（+GSI），多实体塞一张表、用 key 前缀区分（USER#/ORDER#），一次 Query 取回聚合。
  • 推到边缘：这是 DynamoDB 学习曲线最陡的一段——关系型里"加个 join 就能查"的需求，在这里=加 GSI（加钱）或重做 key 设计（停机迁移）；item 拆分也有讲究：高频变的小属性和静态大属性放同一 item，每次更新按整个 item 大小收 WCU，拆成两个 item 能把计数器更新从 2 WCU 降到 1 WCU；新增访问模式 = 新 GSI = 新账单，老表的"查询灵活性"是事先买好的，不是免费的。
  • 选型含义：团队里必须有人能画出"访问模式→key 设计"矩阵，否则三个月后就是"加表还是加 GSI"的泥潭；创业公司建议"先用 PG 跑通业务，热路径稳定后再迁 DynamoDB"（awslabs 官方 startup 建议），别在需求天天变的阶段玩单表设计。
  • 来源：社区技能文档（2026-09）；awslabs startup-advisor（2026-09）；社区共识

深水区六（复制与一致性）：Global Tables——LWW 静默丢 vs MRSC 的三 Region 笼子（domain：复制与容灾）

  • 机制：MREC（默认）：异步复制（通常 1–2 秒，官方口径），并发写同一 item 用 last-writer-wins 收敛；MRSC（新）：同步 quorum 写，冲突写直接抛 ReplicatedWriteConflictException 让应用重试。
  • 推到边缘：MREC 下两个 Region 同时扣库存，LWW 静默丢掉一笔——没有冲突告警，没有版本向量，"最终一致"一致的是"丢了哪一笔不告诉你"；MRSC 把笼子建得很死：固定 3 Region（含 1 个 witness）拓扑、Region 集合不能跨大区组、事务/TTL 不支持，写延迟 = 跨 Region quorum RTT，账单 = 每 Region 一份 rWCU 写费。以及"多活接入"不等于"用户路由"——DynamoDB 不帮你做流量调度，Route 53/应用层自己来。
  • 选型含义：库存/余额/计数器三类数据，MREC 下必须"写分区 pin Region"或条件写，天然多写 LWW 就是丢数据；MRSC 只给"丢不起但写得少"的核心数据，且先算好延迟和账单；DR 演练要测"Region 挂了流量怎么切"，而不是"数据有没有过去"。
  • 来源：官方文档（Global Tables 原理页）；aws.amazon.com Global Tables FAQ；社区技能文档（2026-09）

Deep-dive 1 (Storage/Performance): Partitions are the physical ceiling; hot keys are a design tax (domain: storage engine)

  • Mechanism: items are distributed to internal partitions by partition-key hash; each partition has a hard cap of 3,000 RCU / 1,000 WCU 官方文档, identical for provisioned and on-demand; burst capacity borrows 300 seconds of unused allowance to absorb short spikes, adaptive capacity moves idle allowance to hot partitions (even isolating hot keys onto dedicated partitions).
  • At the edge: no matter how much adaptive capacity can borrow, it can't borrow past the partition ceiling — a single key written at over 1,000 WCU/s is a death sentence, because automatic partition splitting looks at throughput, not key cardinality: one key can never span two partitions. Table-level CloudWatch shows "only 43% of capacity used" while requests get bounced with ProvisionedThroughputExceededException — DynamoDB's most classic incident scene. The only fix is write sharding (user#0…#N suffix scattering), at the cost of scatter-gather reads and application-layer merge sorting.
  • What it means for selection: key design is DynamoDB's #1 productivity lever; the POC must be load-tested with real key distributions — uniform load tests are self-deception; turn on Contributor Insights and put "hot-key location" in the on-call runbook.
  • Sources: official docs (burst/adaptive capacity); dev.to community analysis (2026-08); community skill docs (2026-09)

Deep-dive 2 (Cost): The RCU/WCU rounding tax and the "convenience tax" (domain: cost)

  • Mechanism: writes are billed per 1KB rounded up to WCU, reads per 4KB rounded up to RCU; strong reads cost 2x; transactional writes cost 2x; writes that fail conditional expressions are still billed; on-demand unit price is several times that of fully-utilized provisioned (community wording: 5–7x).
  • At the edge: a 1.1KB item is billed as 2KB — nested JSON, timestamps, and metadata make "just barely over" the norm, which a third-party blog calculated as a 67% hidden surcharge at 100 million writes/day; teams that "go live on on-demand and switch to provisioned later" only remembered to switch after the bill jumped from $11K to $39K/month (third-party blog case, vendor-neutral); a Scan for an admin dashboard: scanning 100 million items costs about $125 per full scan (third-party source) — every dashboard refresh burns cash.
  • What it means for selection: bake "every KB is money" into schema reviews at item-design time; monitor conditional-write failure rates (failed writes = burning money for nothing); on-demand is only for "unpredictable" loads — if the monthly bill exceeds $100 and traffic is predictable, switch to provisioned + auto-scaling (community rule of thumb); never Scan for analytics — export to S3 and query with Athena.
  • Sources: hackernoon third-party cost analysis; awslabs startup-advisor skill docs (2026-09); community consensus

Deep-dive 3 (Cost/Consistency): The GSI is a "second bill," and it only gives eventual consistency (domain: indexing)

  • Mechanism: each GSI is billed independently — writing an item containing a GSI key attribute charges WCU once on the base table and once per GSI (ALL projection ≈ doubling write cost); GSIs have independent throughput quotas and independent throttling; GSI reads are always eventually consistent; LSIs can only be created at table-creation time, share the table's throughput, and cap at 10GB per partition-key value.
  • At the edge: updating a GSI key attribute = deleting the old index entry + writing a new one, one update billed twice for GSI writes; a "just add an index to look up email" PR raised the monthly bill by $800 and write latency by 40% (Medium community case, 2025-10); 5 fully-projected GSIs = the write bill ×6; GSI backpressure can also slow base-table writes (writes must wait for index writes).
  • What it means for selection: the GSI is part of schema design, not an "add an index" button at ops time; keep projections minimal (KEYS_ONLY/INCLUDE); sparse indexes (only giving some items a GSI key) are the standard cost-saving move; a second access pattern that needs strong consistency can only use an LSI — but the LSI must be planned at table-creation time.
  • Sources: official docs; Medium community case (2025-10); community skill docs (2026-09)

Deep-dive 4 (Replication/CDC): Streams' 24-hour retention and 2-consumer ceiling (domain: replication & CDC)

  • Mechanism: DynamoDB Streams push changes in shard order, retained for 24 hours; at most 2 consumers per shard; typically consumed via Lambda.
  • At the edge: if a consumer falls behind for more than 24 hours, the data is permanently lost — there's no "replay from the beginning" second chance; a third consumer (audit + cache invalidation + search sync each wanting one) gets rejected outright, forcing a move to Kinesis Data Streams for DynamoDB (up to 1 year retention, 5+ consumers); 10,000 writes/second = 10,000 Lambda invocations/second, exploding both the Lambda concurrency quota and the invocation bill; a single poison record blocks retries for the entire shard.
  • What it means for selection: Streams are a "trigger," not a "message queue"; with more than 2 downstream consumers or any replay need, go Kinesis first; Lambda consumers must be idempotent with a dead-letter queue — poison records must not block the shard.
  • Sources: official docs; awslabs startup-advisor (2026-09); community skill docs (2026-09)

Deep-dive 5 (Modeling): Single-table design — moving joins out of the database and into your head (domain: modeling/migration)

  • Mechanism: DynamoDB has no joins — "access patterns first": every query is pre-designed as partition key + sort key (+ GSI), multiple entities stuffed into one table distinguished by key prefixes (USER#/ORDER#), aggregates fetched in a single Query.
  • At the edge: this is the steepest part of DynamoDB's learning curve — a need that in a relational database is "just add a join" becomes here = adding a GSI (more money) or redoing the key design (downtime migration); item splitting also matters: putting a frequently-changing small attribute and a static large attribute in the same item bills every update at the whole item's size — splitting into two items can cut a counter update from 2 WCU to 1 WCU; each new access pattern = a new GSI = a new bill — an old table's "query flexibility" was prepaid, not free.
  • What it means for selection: someone on the team must be able to draw the "access pattern → key design" matrix, otherwise in three months you'll be stuck in the "add a table or add a GSI" swamp; startups are advised to "get the business working on PG first, then migrate stable hot paths to DynamoDB" (awslabs' official startup guidance) — don't play single-table design while requirements change daily.
  • Sources: community skill docs (2026-09); awslabs startup-advisor (2026-09); community consensus

Deep-dive 6 (Replication & Consistency): Global Tables — LWW's silent drops vs. MRSC's three-region cage (domain: replication & disaster recovery)

  • Mechanism: MREC (default): async replication (usually 1–2 seconds — official docs wording), concurrent writes to the same item converge via last-writer-wins; MRSC (new): synchronous quorum writes, conflicting writes throw ReplicatedWriteConflictException directly and let the application retry.
  • At the edge: under MREC, two regions deducting inventory simultaneously means LWW silently drops one transaction — no conflict alert, no version vector; "eventually consistent" is consistent about "which write got dropped, without telling you"; MRSC builds a tight cage: fixed 3-region topology (including 1 witness), the region set can't span region groups, transactions/TTL unsupported, write latency = cross-region quorum RTT, and the bill = one rWCU write charge per region. And "multi-active access" is not "user routing" — DynamoDB doesn't do traffic steering for you; Route 53/application layer handles it.
  • What it means for selection: for inventory/balance/counter data — where one lost write is an incident — under MREC you must pin writes to a region or use conditional writes; multi-writing natively under LWW is data loss by design; MRSC is only for "can't afford to lose but writes little" core data — and only after costing out latency and the bill; DR drills should test "how traffic cuts over when a region dies," not "whether the data arrived."
  • Sources: official docs (Global Tables concepts page); aws.amazon.com Global Tables FAQ; community skill docs (2026-09)

判决

  • 一句话定位：AWS 上"按键访问、读多、规模不确定"的 serverless 状态层最优解；但它是为"访问模式"设计的，不是为"数据模型"设计的——建模错了，账单和重构会教你做人。
  • 适合谁：
    • AWS 上的 serverless/事件驱动架构，需要单毫秒 KV/文档存储（session、购物车、用户画像、设备影子、订单头）
    • 访问模式清晰且稳定、读多写少、key 分布均匀的高并发 OLTP
    • 全球化业务需要多 Region 低延迟读写（MREC + 写分区 pin Region）
    • 流量不可预测的新业务、潮汐负载、开发测试环境（on-demand）
    • 需要开箱 CDC（Streams→Lambda）做事件驱动的团队
  • 不适合谁：
    • 查询模式多变、需要 ad-hoc 查询/聚合/报表（这是 OLAP 或搜索引擎的活）
    • 跨多 item 的复杂事务是常态（100 项/4MB 上限 + 2x 成本是紧箍咒）
    • 库存/余额/计数器类"丢一笔就是事故"的数据，又想多 Region 同时写（LWW 静默丢）
    • 重度关系建模、join 是刚需的业务
    • 多云/信创/要求开源自主可控的组织；预算敏感且不愿做 FinOps 的小团队
  • 迁移成本：
    • MySQL → 高：关系建模→访问模式建模重写，join 拆应用层或 GSI，事务语义重做
    • PostgreSQL → 高：同上；JSONB 用户注意 DynamoDB 文档模型更弱（无 GIN 这类索引）
    • Oracle → 高：无 Oracle 兼容路线，不建议作为"去 O"目标
    • Redis/Cassandra → 中低：KV 心智接近，注意 DynamoDB 无 Lua 脚本/复杂数据结构，Cassandra 宽行要重做 key 设计
  • One-line positioning: On AWS, the best serverless state layer for "key-based access, read-heavy, uncertain scale." But it's designed for "access patterns," not for "data models" — get the modeling wrong, and the bill and the rewrite will teach you a lesson.
  • Best for:
    • Serverless/event-driven architectures on AWS needing single-digit-millisecond KV/document storage (sessions, carts, user profiles, device shadows, order headers)
    • High-concurrency OLTP with clear, stable access patterns, read-heavy, uniformly distributed keys
    • Global businesses needing multi-region low-latency reads/writes (MREC + region-pinned writes)
    • Unpredictable traffic: new businesses, tidal loads, dev/test environments (on-demand)
    • Teams needing out-of-the-box CDC (Streams→Lambda) for event-driven designs
  • Not for:
    • Shifting query patterns, ad-hoc queries/aggregations/reporting (that's OLAP or search-engine work)
    • Multi-item complex transactions as the norm (the 100-item/4MB cap + 2x cost is a tight constraint)
    • Inventory/balance/counter data where "one lost write is an incident," yet multi-region simultaneous writes are desired (LWW silently drops)
    • Heavily relational modeling where joins are a hard requirement
    • Multi-cloud / xìnchuàng (IT localization) / open-source-self-hosting organizations; budget-sensitive small teams unwilling to do FinOps
  • Migration cost:
    • MySQL → High: relational modeling rewritten as access-pattern modeling, joins pushed to the application layer or GSIs, transaction semantics redone
    • PostgreSQL → High: same as above; JSONB users note DynamoDB's document model is weaker (no GIN-style indexes)
    • Oracle → High: no Oracle compatibility path — not recommended as a "de-Oracle" target
    • Redis/Cassandra → Medium-low: KV thinking is close, but note DynamoDB has no Lua scripting/complex data structures, and Cassandra wide rows need key redesign
