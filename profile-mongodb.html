MongoDB

KV · 宽列 · 文档 #文档型 #NoSQL #SSPL #分片 #副本集 #BSON #灵活Schema #WiredTiger #Atlas

文档型数据库的事实标准：BSON 文档 + 灵活 Schema + 原生分片，把"上线快"做到了极致——但"没有 Schema"不等于"不需要数据治理"，SSPL 许可证意味着它早已不是传统意义上的开源数据库。

The de facto standard for document databases: BSON documents + flexible schema + native sharding, taking "time-to-launch" to the extreme — but "no schema" does not mean "no data governance," and the SSPL license means it is long past being an open-source database in the traditional sense.

硬维度（19 项）

1 静态加密 / TDE 部分支持

部分支持。WiredTiger 引擎级静态加密（AES-256-GCM）为 Enterprise 版专属，社区版查证为无（不带 --enableEncryption 相关能力）；密钥管理支持 KMIP（企业版）与本地 keyfile；Atlas 托管默认落盘加密。客户端字段级加密 Queryable Encryption（7.0 起）是客户端侧能力，不分社区/企业（需 crypt_shared 库）。来源等级：官方文档

2 TLS / 传输加密 有

有。TLS/SSL 全链路支持（客户端↔mongos/mongod、副本集内部、备份传输）；自 3.6 起默认仅绑定 localhost，暴露公网需显式配置。来源等级：官方文档

3 审计 部分支持（企业版专属）

部分支持（企业版专属）。审计（auditLog）为 Enterprise Advanced 功能，社区版查证为无原生审计；社区用户只能靠应用层日志或代理层弥补。来源等级：官方文档

4 认证与权限 有

有。SCRAM-SHA-256（默认）、x.509 证书、LDAP（企业版）、Kerberos（企业版）、OIDC（企业版，7.0+ 起能力逐步完善）；RBAC 角色模型（内置角色 + 自定义角色，库/集合级粒度）。来源等级：官方文档

5 备份恢复 有

有。自建：mongodump/mongorestore（逻辑）、文件系统快照（物理，需 journaling + 锁或副本集一致性配合）、mongoexport；Atlas：连续备份 + PITR（时间点恢复）、按需快照。恢复速度取决于数据量与拓扑（分片集群恢复需逐分片协调，官方无统一 RTO 口径——厂商无口径，按自测）。来源等级：官方文档 + 社区共识

6 可观测性 有

有。自建：mongostat/mongotop、Database Profiler（慢查询）、db.currentOp()、FTDC（诊断数据捕获）、官方 MongoDB Cloud Manager / Ops Manager（企业级监控自动化）；Atlas 内置监控、Performance Advisor、慢查询分析。来源等级：官方文档

7 连接模型 有（驱动侧连接池）

有（驱动侧连接池）。无服务端内置连接池中间件概念；各官方驱动自带连接池（maxPoolSize 默认 100 等驱动相关参数），长连接复用；官方建议应用层保持单例 MongoClient。超大规模连接场景靠横向加应用实例或第三方代理（如自研/Proxy），官方无 pgBouncer 式标配。来源等级：官方文档 + 社区共识

8 事务与隔离级别 有（有限制）

有（有限制）。多文档 ACID 事务：副本集 4.0 起、分片集群 4.2 起；隔离级别为快照隔离（snapshot）；默认 transactionLifetimeLimitSeconds=60 秒，超时自动 abort（可调，但调大增加冲突与缓存压力）。单文档写入天然原子。分片事务不支持某些操作（如跨分片的特定 DDL），以官方"事务限制"文档为准。来源等级：官方文档

9 复制与一致性 有

有。副本集主从复制（异步 oplog 拉取，非 Raft/Paxos 共识写，选举用 Raft-like 投票协议）；一致性可调：写关注 w:1（默认单机确认）/w:majority（5.0 起为默认写关注，仲裁节点等拓扑下有例外）/w:all，读关注 local/majority/snapshot/linearizable。强一致需显式 w:majority + readConcern:majority 组合，默认配置不提供线性一致。来源等级：官方文档

10 扩展方式 有

有。纵向（加配置）与横向（分片集群：mongos 路由 + config servers + shards）兼具；分片扩容在线（加分片后 balancer 自动迁移 chunk），但见深水区一：分片键选错则"扩了也白扩"。来源等级：官方文档 + 社区共识

11 兼容性 部分支持

部分支持。协议层面：MongoDB wire protocol 为事实标准，被 FerretDB、Amazon DocumentDB、Azure Cosmos DB（Mongo API）等兼容实现反向兼容；但反过来 MongoDB 不兼容别家 SQL 协议。工具链：官方驱动覆盖主流语言（Apache 2.0）、Compass GUI、MongoDB Connector for BI（SQL 访问）、Mongoose（Node ODM）等生态成熟。SQL 兼容查证为无（非关系型）。来源等级：官方文档 + 社区共识

12 许可证与商业模式 SSPL v1（非 OSI 开源

SSPL v1（非 OSI 开源）。见深水区六专述：2018-10-16 社区版从 AGPL 转 SSPL；SSPL 要求"将本软件作为服务提供"者必须开源整个服务栈（含管理、用户界面、备份、监控等），实质封堵第三方 DBaaS。普通企业自用（内部业务系统）不受影响。商业模式：Enterprise Advanced 订阅（企业版功能：静态加密、审计、LDAP/Kerberos、Ops Manager 等）+ Atlas 托管（按实例规格/存储/数据传输/备份计费，M0 免费、Flex 按量封顶、M10+ 专用集群按小时）。来源等级：官方 LICENSE 文件 + 官方博客 + 第三方分析

1 Data-at-rest encryption / TDE Partial support

Partial support. WiredTiger engine-level data-at-rest encryption (AES-256-GCM) is Enterprise-edition only; the Community edition is (confirmed absent) for this capability (no --enableEncryption-style support); key management supports KMIP (Enterprise) and local keyfile; Atlas enables at-rest encryption by default. Client-side field-level encryption via Queryable Encryption (since 7.0) is a client-side capability not split by Community/Enterprise (requires the crypt_shared library). Evidence level: 官方文档

2 TLS / transport encryption Supported

Supported. Full TLS/SSL support across the stack (client↔mongos/mongod, intra-replica-set, backup transport); since 3.6 it binds to localhost only by default, exposing it to the public internet requires explicit configuration. Evidence level: 官方文档

3 Auditing Partial support

Partial support (Enterprise-only). Auditing (auditLog) is an Enterprise Advanced feature; the Community edition has (confirmed absent) native auditing; Community users can only compensate with application-layer logs or a proxy layer. Evidence level: 官方文档

4 Authentication & authorization Supported

Supported. SCRAM-SHA-256 (default), x.509 certificates, LDAP (Enterprise), Kerberos (Enterprise), OIDC (Enterprise, capabilities progressively improved since 7.0+); RBAC role model (built-in roles + custom roles, database/collection-level granularity). Evidence level: 官方文档

5 Backup & recovery Supported

Supported. Self-hosted: mongodump/mongorestore (logical), filesystem snapshots (physical, requires journaling + locking or replica-set consistency coordination), mongoexport; Atlas: continuous backups + PITR (point-in-time recovery), on-demand snapshots. Recovery speed depends on data size and topology (restoring a sharded cluster requires per-shard coordination; there is no official RTO statement — no vendor position; judge from your own tests). Evidence level: 官方文档 + 社区共识

6 Observability Supported

Supported. Self-hosted: mongostat/mongotop, Database Profiler (slow queries), db.currentOp(), FTDC (full-time diagnostic data capture), official MongoDB Cloud Manager / Ops Manager (enterprise-grade monitoring automation); Atlas has built-in monitoring, Performance Advisor, and slow-query analysis. Evidence level: 官方文档

7 Connection model Supported

Supported (driver-side connection pooling). There is no server-side built-in connection-pool middleware concept; every official driver ships its own connection pool (maxPoolSize defaults to 100 and other driver-specific parameters), with long-lived connection reuse; the official recommendation is to keep a single MongoClient singleton at the application layer. Very large-scale connection scenarios rely on horizontal scaling of application instances or third-party proxies (self-built/proxy), and there is no official pgBouncer-style standard. Evidence level: 官方文档 + 社区共识

8 Transactions & isolation levels Supported

Supported (with limitations). Multi-document ACID transactions: replica sets since 4.0, sharded clusters since 4.2; the isolation level is snapshot isolation; default transactionLifetimeLimitSeconds=60 seconds, timed-out transactions abort automatically (tunable, but raising it increases contention and cache pressure). Single-document writes are naturally atomic. Sharded transactions do not support certain operations (such as specific cross-shard DDL); defer to the official "transaction limitations" documentation. Evidence level: 官方文档

9 Replication & consistency Supported

Supported. Replica-set primary/secondary replication (asynchronous oplog pulling, not Raft/Paxos consensus writes; elections use a Raft-like voting protocol); tunable consistency: write concern w:1 (default single-node acknowledgment) / w:majority (the default write concern since 5.0, with exceptions for topologies such as arbiter nodes) / w:all, read concern local / majority / snapshot / linearizable. Strong consistency requires the explicit w:majority + readConcern:majority combination; the default configuration does not provide linearizability. Evidence level: 官方文档

10 Scaling Supported

Supported. Vertical (bigger machines) and horizontal (sharded clusters: mongos routers + config servers + shards) both; shard scaling is online (the balancer automatically migrates chunks after adding shards) — but see deep-dive 1: if the shard key is chosen wrong, "you scaled for nothing." Evidence level: 官方文档 + 社区共识

11 Compatibility Partial support

Partial support. Protocol level: the MongoDB wire protocol is the de facto standard, wire-protocol-compatible implementations such as FerretDB, Amazon DocumentDB, and Azure Cosmos DB (Mongo API) exist; but MongoDB itself is not compatible with other vendors' SQL protocols. Toolchain: official drivers cover mainstream languages (Apache 2.0), Compass GUI, MongoDB Connector for BI (SQL access), Mongoose (Node ODM), and a mature ecosystem. SQL compatibility is (confirmed absent) (it is not a relational database). Evidence level: 官方文档 + 社区共识

12 License & business model SSPL v1

SSPL v1 (not OSI open source). See deep-dive 6 for details: on 2018-10-16 the Community edition switched from AGPL to SSPL; SSPL requires anyone "offering the software as a service" to open-source their entire service stack (including management software, user interfaces, backup, monitoring, and everything else that makes the service possible), effectively blocking third-party DBaaS offerings. 杀手特性

每个特性 = 它是什么 + 为什么是真本事 + 边缘真相。

  1. BSON 文档模型 + 灵活 Schema 真本事：JSON 式文档天然贴合对象模型，嵌套数组/子文档一次读写搞定"一对多"，省掉 ORM 映射与 join；字段可增减，需求变更时不用先写 migration 脚本——这是 MongoDB 十几年"开发效率"口碑的根。 边缘真相："灵活"是有账期的。无 Schema 约束意味着脏数据、字段类型漂移（同一字段一会是字符串一会是数字）在生产环境真实发生，治理成本从 DBA 转嫁给了应用层；5.x 起的 Schema Validation 是补救，但它是"事后加的缰绳"， adoption 率远低于宣传。见深水区五。
  2. 原生分片（auto-sharding） 真本事：分片集群是官方一等公民——mongos 路由、config server 元数据、balancer 自动迁移 chunk，应用对"数据在哪"无感知；从单机 ReplicaSet 到分片是官方升级路径，不是第三方中间件拼凑。 边缘真相：分片只解决"数据量大"，不解决"分片键选错"。单调递增键（ObjectId/时间戳）把写入钉死在一个 chunk 上，jumbo chunk（超大不可再分）会让 balancer 直接跳过它——集群越扩越不均。分片键是"一选定终身"的设计，选错的代价是重建集合。这是 MongoDB DBA 面试必考题，也是生产事故重灾区。见深水区一。
  3. Change Streams（变更流） 真本事：基于 oplog 的官方 CDC：db.collection.watch() 订阅增删改，带 resume token 断点续传；是"数据库→缓存/搜索/数仓"实时同步的官方答案，不用再 tail oplog 写脏脚本。 边缘真相：resume token 只在 oplog 窗口内有效——token 太旧（消费端宕机太久）会直接报错，应用必须自己实现"全量重扫"兜底；分片集群的 change stream 要汇聚各分片事件，排序与延迟开销更大；它不是 Kafka，别指望它做消息队列的持久化语义。见深水区六。
  4. 聚合管道（Aggregation Framework） 真本事：$match/$group/$lookup/$facet… 一套声明式管道覆盖了大部分"报表/分析"需求，配合索引能跑出不错的 OLAP 能力；是 MongoDB 从"KV 增强版"进化为"通用数据库"的关键。 边缘真相：阻塞式 stage（$group/$sort）默认 100MB 内存上限，超了就报错（allowDiskUse 可转磁盘但那是正确性兜底不是性能方案）；$lookup 本质是"对每条输入文档查一次外集合"，无索引就是 N+1 全表扫描；跨分片聚合要 scatter-gather，分片键不对就是全集群广播。管道写起来爽，执行计划还是要看 explain。
  5. Atlas 托管与生态完整度 真本事：Atlas 是完成度最高的 DBaaS 之一：全球多区域部署、连续备份/PITR、Performance Advisor、Atlas Search（Lucene）、Vector Search、私有终端；驱动/Compass/CLI/Connector for BI 全家桶让"从开发到上线" friction 极低。 边缘真相：Atlas 是"省心税"最贵的选项之一——专用集群按小时+存储+备份+数据传输多项计量，Search/Vector Search 另算；一旦 workload 上去，自建（或搬到云厂商兼容服务）的 TCO 对比会很难看。以及 Atlas 的网络出口/跨区流量是账单刺客，上线前必须做计费影子测试。
  • Queryable Encryption（7.0+，9.0 增强）：客户端字段级加密，服务端只见密文；与 TDE（防"偷硬盘"）正交，防的是"DBA/云厂商能看到明文"。差异点：合规（隐私字段）场景的正规解；代价是可查询能力受限（支持的查询类型随版本扩展，9.0 起字符串前缀/后缀/子串查询 GA）与客户端依赖 crypt_shared 库。来源等级：官方文档 + 驱动 release notes（2026-07）
  • 时序集合（5.0+）：列式桶存储优化的时序类型，写入/压缩/ttl 一体；差异点：IoT/监控场景不用手写 bucket 模式。来源等级：官方文档
  • Atlas Search / Vector Search：托管 Lucene 全文检索 + HNSW 向量索引，RAG 场景"顺手"可用；差异点：别当专用向量库——大规模 ANN 召回性能与生态深度待实测验证。来源等级：官方口径 + 待验证
  • Atlas Stream Processing：流处理（聚合管道跑在流上）；2026 年仍在演进，GA 状态与定价以官方为准，本档案不计入判决依据。来源等级：官方口径 + 待验证

Each feature = what it is + why it is real engineering + the edge truth.

  1. BSON document model + flexible schema Why it's real: JSON-style documents naturally fit object models — nested arrays/sub-documents handle "one-to-many" in a single read/write, eliminating ORM mapping and joins; fields can be added or removed, so changing requirements don't start with a migration script — this is the root of MongoDB's decade-plus "developer productivity" reputation. Edge truth: "Flexibility" is bought on credit. Without schema constraints, dirty data and field type drift (the same field being a string one moment and a number the next) genuinely happen in production, and the governance cost shifts from the DBA to the application layer; Schema Validation (since 5.x) is the remedy, but it is a "rein added after the fact" whose adoption rate is far below the marketing. See deep-dive 5.
  2. Native sharding (auto-sharding) Why it's real: Sharded clusters are a first-class citizen — mongos routing, config server metadata, the balancer automatically migrating chunks, and the application never needs to know where data lives; going from a single-node replica set to sharding is the official upgrade path, not a third-party middleware patchwork. Edge truth: Sharding solves "too much data," not "wrong shard key." A monotonically increasing key (ObjectId/timestamp) pins all writes onto one chunk; jumbo chunks (oversized and unsplittable) make the balancer skip them outright — the more you scale the cluster, the more skewed it gets. The shard key is a "choose once, live with it" design; choosing wrong means rebuilding the collection. This is the must-ask question in every MongoDB DBA interview and a leading cause of production incidents. See deep-dive 1.
  3. Change Streams Why it's real: Official CDC built on the oplog: db.collection.watch() subscribes to inserts/updates/deletes with resume tokens for resume-after-restart; it is the official answer for "database → cache/search/data warehouse" real-time sync — no more dirty scripts tailing the oplog. Edge truth: Resume tokens are only valid within the oplog window — a token that is too old (consumer down for too long) errors out, and the application must implement its own "full rescan" fallback; change streams on sharded clusters must merge events from all shards, with larger ordering and latency overhead; it is not Kafka — don't expect message-queue persistence semantics. See deep-dive 6.
  4. Aggregation Framework Why it's real: $match/$group/$lookup/$facet… — one declarative pipeline covers most "reporting/analytics" needs and can deliver decent OLAP performance with the right indexes; it is the key to MongoDB's evolution from "KV-plus" to "general-purpose database." Edge truth: Blocking stages ($group/$sort) have a default 100MB memory cap — exceed it and the query errors out (allowDiskUse can spill to disk, but that is a correctness backstop, not a performance strategy); $lookup is essentially "query the foreign collection once per input document" — without indexes it is an N+1 full scan; cross-shard aggregation requires scatter-gather, and with the wrong shard key it is a cluster-wide broadcast. Pipelines are fun to write, but you still have to read the explain plan.
  5. Atlas hosting and ecosystem completeness Why it's real: Atlas is one of the most complete DBaaS offerings: global multi-region deployment, continuous backup/PITR, Performance Advisor, Atlas Search (Lucene), Vector Search, private endpoints; the driver/Compass/CLI/Connector-for-BI bundle makes the "dev to production" friction extremely low. Edge truth: Atlas is one of the most expensive "peace-of-mind taxes" — dedicated clusters are metered on hours + storage + backup + data transfer, with Search/Vector Search billed separately; once the workload grows, the TCO comparison against self-hosting (or moving to a cloud vendor's compatible service) gets ugly. And Atlas network egress/cross-region traffic is a bill assassin — you must run a billing shadow test before launch.

深水区

深水区一（扩展/分片）：chunk 迁移救得了容量，救不了分片键

  • 机制：集合按分片键区间切成 chunk（6.0 起默认 128MB，之前 64MB），balancer 在分片间迁移 chunk 均衡数据；jumbo chunk 是"超大且无法再分"（无有效分割点，如低基数分片键）的 chunk，balancer 直接跳过。
  • 推到边缘：① 单调递增分片键（时间戳/ObjectId）→ 所有新写入落到最后一个 chunk → 单分片写热点，集群其余分片空闲，总吞吐封顶，加分片不解决问题；② 低基数分片键（如 status 只有几个值）→ chunk 无法分裂 → jumbo chunk 卡住 balancer，数据倾斜永久化；③ chunk 迁移本身吃 IO/网络，高峰期开 balancer 等于给飞行中的飞机换引擎。分片键一旦选定，修改=重建集合+重导数据。
  • 选型含义：分片不是"以后再说"的运维选项，是上线第一天就要定死的架构决策；POC 必须按真实 key 分布压测写入倾斜，不能只看均匀压测。
  • 来源：官方文档（Sharding / Balancer / Jumbo Chunks 章节）；社区运维共识

深水区二（复制/一致性）：选举、回滚与"默认不强一致"

  • 机制：副本集主从复制走 oplog 异步拉取；主节点故障时剩余节点投票选举（多数派原则，约 10 秒级自动故障转移）；读/写关注分别控制 durability 与可见性。
  • 推到边缘：① w:1（单机确认）的写入在主节点宕机且未复制到从节点时可被回滚——回滚的数据写进 rollback 文件，需人工对账，应用永远无感知；② 默认读关注 local 可能读到随后被回滚的数据；③ 只有 w:majority + readConcern:majority 组合才能获得"不丢已确认写入"的保证，5.0 起默认写关注已是 majority（仲裁节点等拓扑有例外），但读关注默认仍是 local——"默认配置"≠"强一致"，这是 MongoDB 最常见的选型误读；④ PSA（主-从-仲裁）拓扑是耐久性陷阱：一个数据节点宕机后 majority 写即不可用（仲裁节点不存数据），省钱的代价是可用性。
  • 选型含义：凡涉及钱/状态机，显式指定 w:majority + readConcern:majority（或用事务），并做 kill -9 主节点的混沌测试验证 RPO；PSA 拓扑只适合开发测试。
  • 来源：官方文档（Replication / Write Concern / Read Concern / Rollback 章节）；社区 skill 实测总结

深水区三（事务）：60 秒生死线与快照隔离的税

  • 机制：多文档事务基于 WiredTiger 快照隔离 + oplog 时间戳；默认 transactionLifetimeLimitSeconds=60，超时自动 abort；驱动 withTransaction 封装对 TransientTransactionError / UnknownTransactionCommitResult 的重试。
  • 推到边缘：① 60 秒是硬预算——事务里调一次外部 HTTP、做一次大聚合，超时 abort，前功尽弃；② 写冲突时事务 abort 抛给应用，重试是应用的税，且"重试外部副作用"（发短信、调支付）是应用自己的坑；③ 长事务 pin 住 WiredTiger 快照，阻塞历史版本清理，放大缓存压力（早期版本快照历史曾直接放在 WT cache 里，这是 60 秒限制的由来）；④ 分片事务限制更多（部分 DDL/操作不支持），且跨分片 2PC 开销显著高于单副本集事务；⑤ updateMany/deleteMany 不是 retryable write，事务外批量写遇主从切换可能部分执行。
  • 选型含义：事务只装"短平快"的多文档原子操作；长流程用 Saga/ outbox 模式拆；POC 必须测"热点行并发事务的 abort 率"，不能只测无冲突场景。
  • 来源：官方文档（Transactions / Production Considerations）；社区 skill（transaction-performance）

深水区四（存储引擎）：WiredTiger 的缓存淘汰与检查点

  • 机制：WiredTiger 默认缓存为 max(50%×(RAM-1GB), 256MB)；缓存占用达 95% 触发应用线程参与的淘汰（eviction），80% 为后台淘汰目标；检查点默认 60 秒一次（或 journal 达 2GB），保证崩溃恢复点。
  • 推到边缘：① 工作集大于缓存时，应用线程被迫参与淘汰 → 延迟毛刺、p99 抖动，这是"内存明明够、查询偶发慢"的经典根因；② 大文档/大批量写入瞬间撑爆缓存，淘汰风暴直接拖慢全库；③ 检查点期间的 IO 毛刺与压缩（默认 snappy，可选 zstd/zlib）CPU 开销在写入密集型场景叠加；④ 频繁更新产生大量历史版本，长事务/长游标 pin 住它们，缓存被"死版本"占满——"一个忘了关的游标拖慢整库"真实存在。
  • 选型含义：内存配比按"工作集+索引"算，不按数据总量算；监控 wiredTiger.cache 的淘汰计数与检查点耗时，把它们写进容量规划基线。
  • 来源：官方文档（WiredTiger Storage Engine / Cache / Checkpoints）；社区运维共识

深水区五（数据治理）：灵活 Schema 的双刃剑

  • 机制：集合无强制 Schema，文档可异构；5.0 起可用 $jsonSchema 做 Schema Validation（strict/moderate 级别），7.0+ 持续增强。
  • 推到边缘：① 同一字段类型漂移（string vs int vs null）在聚合/排序时产生诡异结果，且错误静默；② 嵌套层级失控、超大数组（16MB 文档上限是硬顶）往往在业务爆发时才暴露，修复=数据迁移；③ Validation 是"事后缰绳"——已有脏数据不会自动变干净，moderate 级别只拦新写入；④ 没有 DDL 评审流程的团队，三年后的集合是考古现场：字段含义靠口口相传。
  • 选型含义："无 Schema"是开发期的效率，不是生产期的免死金牌；上线前定字段规范 + 开 Validation（至少 moderate），把治理成本前置，否则它会在最忙的时候连本带利收回。
  • 来源：官方文档（Schema Validation）；社区共识（类型漂移/16MB 上限为高频生产事故）

深水区六（许可证）：SSPL 的争议实质

  • 机制：2018-10-16 起，4.0.0 及之后所有版本（含旧版本的新补丁）从 AGPL 转为 SSPL v1；SSPL 要求"将本程序作为服务向第三方提供"者，必须以 SSPL 开源整个服务的源码——包括管理软件、用户界面、API、自动化、监控、备份等全部"使服务成为可能"的软件。这比 AGPL（只要求开源修改过的程序本身+通过网络提供时的对应源码）的传染半径大得多。
  • 推到边缘：① 对普通企业自用：无实质影响——内部业务系统使用 MongoDB 不触发 SSPL 的服务条款（MongoDB 官方 FAQ 明确）；② 对云厂商/DBaaS：实质封堵——AWS、阿里云等无法再基于 SSPL 版本提供 MongoDB 托管服务而不开源整个云管栈，这正是 SSPL 的设计目标；③ 对 Linux 发行版/开源生态：出局——Debian/Fedora/Red Hat 均不收录 SSPL 软件，OSI 拒绝承认其为开源，"开源 MongoDB"的叙事在 2018 年已经结束；④ 曾有 2024 年"回归 AGPL"的社区传言与讨论，但截至 2026-09-29，官方仓库 LICENSE 仍为 SSPL v1（AGPL 仅适用于 2018-10-16 之前的版本），以官方仓库为准。
  • 社区分叉现状：FerretDB（2021 年创立，v2.0 于 2025-03 GA，Apache 2.0）走"MongoDB wire protocol 代理 + PostgreSQL（含微软开源的 DocumentDB 扩展，MIT）存储"路线，CRUD/多数聚合可用，但 change streams/oplog 尾随等高级能力有缺口（约 90% 兼容口径，生产替换需逐项 POC）；Amazon DocumentDB / Azure Cosmos DB Mongo API 是云厂商自研的兼容实现（非 MongoDB 内核，兼容边界各自为政）；Percona Server for MongoDB 同样 SSPL（附带企业级功能免费开放），不解决许可证问题。
  • 选型含义：把 MongoDB 当"商业软件"评估：自用免费、托管花钱、二次分发/云服务受限；若组织政策要求 OSI 认可的开源许可证，MongoDB 直接出局，备选是 FerretDB（功能折中）或换赛道（PostgreSQL JSONB / DocumentDB 扩展路线）。
  • 来源：mongodb/mongo 官方仓库 LICENSE/README（SSPL v1）；SSPL 文本 v1；FerretDB 官方博客（v2.0 GA 2025-03）；第三方兼容性分析（dockit、brightcoding，2025-2026）；社区 issue 讨论（Falcone 迁移 epic，2026）

深水区七（运维/安全）：默认配置的坑与历史包袱

  • 机制：3.6 起默认绑定 localhost；访问控制需手动启用（--auth / 配置文件 security.authorization）。
  • 推到边缘：① 历史上大量"裸奔" MongoDB（未开认证、绑 0.0.0.0）被勒索删库（2017 年大规模 MongoDB 勒索事件），"默认安全"是近年的补救，不是与生俱来的；② 社区版无静态加密、无审计——等保/合规要求下，社区版+自建=默认不合规，要么买企业版/Atlas，要么接受差距；③ 分片集群组件多（mongos/config/shard），版本升级、备份恢复、慢查询定位的复杂度是副本集的数倍，"分片一时爽"之后是长期的运维税。
  • 选型含义：安全基线检查（认证、TLS、bind_ip、审计）必须进上线 checklist；合规敏感行业直接按"企业版或 Atlas"的预算立项，不要先按社区版做预算再补窟窿。
  • 来源：官方文档（Security Checklist）；2017 年勒索事件公开报道（历史）；社区共识

Deep-dive 1 (scaling/sharding): chunk migration saves capacity, not shard keys

  • Mechanism: A collection is split by shard-key ranges into chunks (128MB default since 6.0, 64MB before); the balancer migrates chunks between shards to balance data; a jumbo chunk is one that is "oversized and unsplittable" (no valid split point, e.g. a low-cardinality shard key), which the balancer skips outright.
  • At the edge: ① A monotonically increasing shard key (timestamp/ObjectId) → all new writes land on the last chunk → a single-shard write hotspot, the rest of the cluster idle, total throughput capped — adding shards doesn't help; ② A low-cardinality shard key (e.g. status with only a few values) → chunks can't split → jumbo chunks permanently stall the balancer, data skew becomes permanent; ③ Chunk migration itself consumes IO/network — turning on the balancer at peak hours is like changing engines on a plane in flight. Once chosen, changing a shard key means rebuilding the collection + re-importing data.
  • Selection implication: Sharding is not an ops option you defer to "later" — it is an architecture decision locked on day one; the POC must stress write skew against the real key distribution, not just uniform load.
  • Sources: official docs (Sharding / Balancer / Jumbo Chunks chapters); community ops consensus

Deep-dive 2 (replication/consistency): elections, rollbacks, and "not strongly consistent by default"

  • Mechanism: Replica-set primary/secondary replication via asynchronous oplog pulling; when the primary fails, remaining nodes vote in an election (majority rule, automatic failover in roughly 10 seconds); read/write concern control durability and visibility respectively.
  • At the edge: ① Writes with w:1 (single-node acknowledgment) can be rolled back if the primary crashes before replicating to a secondary — rolled-back data is written to rollback files, requiring manual reconciliation, and the application never notices; ② The default read concern local can read data that is later rolled back; ③ Only the w:majority + readConcern:majority combination gives the "no acknowledged write is lost" guarantee — the default write concern has been majority since 5.0 (with exceptions for topologies like arbiter nodes), but the default read concern is still local — "default configuration" ≠ "strong consistency," the most common MongoDB selection misread; ④ PSA (primary-secondary-arbiter) topology is a durability trap: after one data-bearing node fails, majority writes become unavailable (the arbiter stores no data) — the price of saving money is availability.
  • Selection implication: For anything involving money/state machines, explicitly set w:majority + readConcern:majority (or use transactions), and validate RPO by kill -9-ing the primary in a chaos test; PSA topology is for dev/test only.
  • Sources: official docs (Replication / Write Concern / Read Concern / Rollback chapters); community skill hands-on summaries

Deep-dive 3 (transactions): the 60-second deadline and the snapshot-isolation tax

  • Mechanism: Multi-document transactions are built on WiredTiger snapshot isolation + oplog timestamps; the default transactionLifetimeLimitSeconds=60 aborts transactions automatically on timeout; the driver's withTransaction wraps retries for TransientTransactionError / UnknownTransactionCommitResult.
  • At the edge: ① 60 seconds is a hard budget — one external HTTP call inside a transaction, one big aggregation, and the abort wipes out all the work; ② On write conflicts the transaction aborts back to the application, and retrying is the application's tax — and "retrying external side effects" (sending SMS, calling payments) is the application's own pit; ③ Long transactions pin WiredTiger snapshots, blocking historical-version cleanup and amplifying cache pressure (in early versions snapshot history lived directly in the WT cache — the origin of the 60-second limit); ④ Sharded transactions have more restrictions (some DDL/operations unsupported) and cross-shard 2PC costs are significantly higher than single-replica-set transactions; ⑤ updateMany/deleteMany are not retryable writes — bulk writes outside transactions can partially execute on primary failover.
  • Selection implication: Transactions are only for "short and fast" multi-document atomic operations; long flows should be broken up with Saga/outbox patterns; the POC must measure "hot-row concurrent transaction abort rates," not just no-conflict scenarios.
  • Sources: official docs (Transactions / Production Considerations); community skill (transaction-performance)

Deep-dive 4 (storage engine): WiredTiger cache eviction and checkpoints

  • Mechanism: WiredTiger's default cache is max(50%×(RAM-1GB), 256MB); cache occupancy at 95% triggers application-thread-participating eviction, with 80% as the background eviction target; checkpoints run every 60 seconds by default (or when the journal reaches 2GB), guaranteeing crash-recovery points.
  • At the edge: ① When the working set exceeds the cache, application threads are forced into eviction → latency spikes, p99 jitter — the classic root cause of "plenty of memory, occasional slow queries"; ② Big documents/bulk writes can instantly blow through the cache, and an eviction storm drags the whole database down; ③ Checkpoint IO spikes and compression (snappy by default, zstd/zlib optional) CPU costs stack up in write-heavy scenarios; ④ Frequent updates generate many historical versions; long transactions/long cursors pin them, and the cache fills with "dead versions" — "one forgotten cursor slowing the whole database" genuinely happens.
  • Selection implication: Size memory for "working set + indexes," not total data size; monitor wiredTiger.cache eviction counts and checkpoint latency, and write them into the capacity-planning baseline.
  • Sources: official docs (WiredTiger Storage Engine / Cache / Checkpoints); community ops consensus

Deep-dive 5 (data governance): the double-edged sword of flexible schema

  • Mechanism: Collections have no enforced schema; documents can be heterogeneous; since 5.0, $jsonSchema-based Schema Validation is available (strict/moderate levels), continuously enhanced in 7.0+.
  • At the edge: ① Same-field type drift (string vs int vs null) produces bizarre results in aggregations/sorts, and the errors are silent; ② Uncontrolled nesting depth and oversized arrays (the 16MB document limit is a hard ceiling) usually surface only when the business explodes, and fixing them means data migration; ③ Validation is a "rein added after the fact" — existing dirty data doesn't clean itself up, and moderate level only blocks new writes; ④ In a team with no DDL review process, a three-year-old collection is an archaeology site: field meanings survive by word of mouth.
  • Selection implication: "Schema-less" is development-phase efficiency, not a production-phase get-out-of-jail card; establish field conventions and enable Validation (at least moderate) before launch — front-load the governance cost, or it will collect principal plus interest at the busiest moment.
  • Sources: official docs (Schema Validation); community consensus (type drift / the 16MB limit are high-frequency production incidents)

Deep-dive 6 (license): the substance of the SSPL controversy

  • Mechanism: Starting 2018-10-16, all versions 4.0.0 and later (including new patches of old versions) moved from AGPL to SSPL v1; SSPL requires anyone "offering the Program as a service to third parties" to open-source the entire service under SSPL — including management software, user interfaces, APIs, automation, monitoring, backup, and all other software that "makes the service possible." Its viral radius is far larger than AGPL (which only requires open-sourcing the modified program itself plus corresponding source when offered over a network).
  • At the edge: ① For ordinary enterprises using it in-house: no substantive impact — using MongoDB in internal business systems does not trigger the SSPL service terms (MongoDB's official FAQ is explicit); ② For cloud vendors/DBaaS: effectively blocked — AWS, Alibaba Cloud, and others can no longer offer hosted MongoDB based on SSPL versions without open-sourcing their entire cloud management stack, which is precisely the design goal of SSPL; ③ For Linux distros/open-source ecosystem: out — Debian/Fedora/Red Hat all refuse to ship SSPL software, and OSI refuses to recognize it as open source; the "open-source MongoDB" narrative ended in 2018; ④ There were 2024 community rumors and discussions of a "return to AGPL," but as of 2026-09-29, the official repository LICENSE is still SSPL v1 (AGPL applies only to versions before 2018-10-16) — defer to the official repository.
  • Community forks: FerretDB (founded 2021, v2.0 GA in 2025-03, Apache 2.0) takes the "MongoDB wire protocol proxy + PostgreSQL storage (including Microsoft's open-sourced DocumentDB extension, MIT)" route — CRUD/most aggregations work, but advanced capabilities like change streams / oplog tailing have gaps (~90% compatibility claim; production replacement requires item-by-item POC); Amazon DocumentDB / Azure Cosmos DB Mongo API are cloud-vendor-built compatible implementations (not the MongoDB kernel; compatibility boundaries vary by vendor); Percona Server for MongoDB is likewise SSPL (with enterprise-grade features free), which doesn't solve the license problem.
  • Selection implication: Evaluate MongoDB as "commercial software": free for in-house use, paid for hosting, restricted for redistribution/cloud services; if organizational policy requires an OSI-recognized open-source license, MongoDB is out — alternatives are FerretDB (with feature trade-offs) or a different track (PostgreSQL JSONB / the DocumentDB extension route).
  • Sources: mongodb/mongo official repo LICENSE/README (SSPL v1); SSPL text v1; FerretDB official blog (v2.0 GA 2025-03); third-party compatibility analyses (dockit, brightcoding, 2025-2026); community issue discussions (Falcone migration epic, 2026)

Deep-dive 7 (ops/security): default-configuration pitfalls and historical baggage

  • Mechanism: Since 3.6 it binds to localhost by default; access control must be enabled manually (--auth / config-file security.authorization).
  • At the edge: ① Historically, huge numbers of "naked" MongoDB instances (no auth, bound to 0.0.0.0) were ransomware-wiped (the large-scale 2017 MongoDB ransomware incident) — "secure by default" is a recent remediation, not an original trait; ② The Community edition has no data-at-rest encryption and no auditing — under 等保 (classified protection / MLPS) or compliance requirements, Community + self-hosted = non-compliant by default; you either buy Enterprise/Atlas or accept the gap; ③ Sharded clusters have many components (mongos/config/shard), and version upgrades, backup/recovery, and slow-query triage are multiples more complex than replica sets — "sharding is fun for a day" is followed by a long-term ops tax.
  • Selection implication: Security baseline checks (auth, TLS, bind_ip, auditing) must go into the launch checklist; compliance-sensitive industries should budget directly for "Enterprise or Atlas" — don't budget for Community first and patch the gap later.
  • Sources: official docs (Security Checklist); public reporting on the 2017 ransomware incident (historical); community consensus

判决

  • 一句话定位：文档型场景"开发效率"的最优解，原生分片让它能从小跑到大；但它是用 SSPL 商业软件的心态来选型的——自用免费、合规与高级功能花钱、"无 Schema"的债迟早要还。
  • 适合谁：
    • 产品迭代快、数据模型多变的内容/社交/电商/SaaS 业务（文档模型红利最大）
    • 读写模型以"聚合文档整体读写"为主、关联查询少的系统
    • 数据量持续增长、希望用官方分片永远不做"分库分表"的团队
    • 需要 Change Streams 做实时同步（缓存/搜索/数仓）的架构
    • 愿意为 Atlas 付省心税、不想养 Mongo DBA 的团队
  • 不适合谁：
    • 强事务、复杂多表 join 为核心的账务/ERP 类系统（关系型更合适）
    • 组织政策要求 OSI 认可开源许可证（SSPL 直接出局）
    • 合规要求静态加密+审计但预算只够社区版自建（默认不达标）
    • 团队无数据治理纪律、指望"无 Schema"等于"不用设计"的（债会到期）
    • 超大规模写入且分片键天然单调（如纯时间序列）又不愿做分片键设计的（时序集合或专用时序库更合适）
  • 迁移成本：
    • MySQL/PostgreSQL → 中高：数据建模范式完全不同（反范式化、嵌入 vs 引用），不是"换驱动"能解决的；事务语义、join 习惯都要重写；建议按"重构数据模型"立项
    • 从 DocumentDB/Cosmos/FerretDB 迁回官方 → 低-中：wire 协议兼容，但 change streams/事务/高级聚合的边界差异需逐项验证
    • 从 MongoDB 迁出（到 PG JSONB/DocumentDB 扩展）→ 中：BSON 类型细节、聚合语义、驱动行为需逐项对齐
  • One-liner: The best answer for "developer productivity" in document scenarios; native sharding lets it grow from small to large — but evaluate it with a commercial-software mindset: free for in-house use, paid for compliance and advanced features, and the "no schema" debt comes due sooner or later.
  • Best for:
    • Content/social/e-commerce/SaaS businesses with fast product iteration and changing data models (where the document-model dividend is largest)
    • Systems whose read/write patterns are dominated by "read/write whole aggregate documents," with few relational queries
    • Teams with continuously growing data that want official sharding and never want to "shard the database by hand" again
    • Architectures needing Change Streams for real-time sync (cache/search/data warehouse)
    • Teams willing to pay the Atlas peace-of-mind tax and not hire a MongoDB DBA
  • Not for:
    • Billing/ERP-style systems built on strong transactions and complex multi-table joins (a relational database fits better)
    • Organizations whose policy requires an OSI-recognized open-source license (SSPL rules it out directly)
    • Compliance requirements for data-at-rest encryption + auditing on a Community-only self-hosted budget (non-compliant by default)
    • Teams with no data-governance discipline that expect "no schema" to mean "no design" (the debt will come due)
    • Very-high-scale writes with naturally monotonic shard keys (pure time series) unwilling to design shard keys (time-series collections or dedicated time-series databases fit better)
  • Migration costs:
    • MySQL/PostgreSQL → Medium-high: the data-modeling paradigm is completely different (denormalization, embedding vs referencing) — not solvable by "switching drivers"; transaction semantics and join habits must be rewritten; budget it as a "data-model rebuild" project
    • From DocumentDB/Cosmos/FerretDB back to official → Low-medium: wire-protocol compatible, but the boundary differences in change streams/transactions/advanced aggregation need item-by-item verification
    • Out of MongoDB (to PG JSONB / the DocumentDB extension) → Medium: BSON type details, aggregation semantics, and driver behaviors need item-by-item alignment
