关系型 OLTP #分布式 #NewSQL #强一致 #Serializable #多地域 #PG协议兼容 #Raft #商业许可

Cockroach Labs 出品的 Spanner 式强一致分布式 SQL 数据库：默认 Serializable、跨地域多活接入、PostgreSQL 线协议——但"多活接入"不等于"跨洋写本地完成"，"PG 兼容"不等于"PostgreSQL"。

A Spanner-style strongly consistent distributed SQL database from Cockroach Labs: Serializable by default, multi-active access across regions, PostgreSQL wire protocol — but "multi-active access" does not mean "cross-ocean writes complete locally," and "PG compatible" does not mean "PostgreSQL."

硬维度（46 项）

1 静态加密 / TDE 部分支持

部分支持。数据文件落盘加密有引擎内机制（--enterprise-encryption 启动参数，多 store 需逐个配置；存储层 RFC 显示文件状态记录在 COCKROACHDB_REGISTRY）；备份可用 passphrase / KMS 加密。但 WAL / 临时文件的覆盖边界、密钥轮换与 KMS 矩阵需对照 v26.3 文档复核。来源等级：官方文档（旧版本）+ 待验证

2 TLS / 传输加密 有

有。TLS 双向认证（节点证书 + 客户端证书），--insecure 仅限开发测试。来源等级：官方文档

3 审计 有（多为付费墙内）

有（多为付费墙内）。sql.log.user_audit / sql.log.admin_audit.enabled 等 cluster settings 存在（官方 skills 仓库的 CIS 审计样例报告可证）；具体自托管 / Cloud 各 tier 的能力边界待官方复核。来源等级：官方仓库资料 + 待验证

4 认证与权限 有

有。密码（SCRAM-SHA-256）、证书认证、RBAC 角色；OIDC/SSO、Kerberos 等多为 Enterprise / Cloud 付费层能力，具体矩阵待复核。来源等级：官方仓库资料 + 待验证

5 备份恢复 有（部分需 Enterprise）

有（部分需 Enterprise）。BACKUP / RESTORE SQL、增量备份、计划备份、PITR；全集群恢复需 enterprise license（Cockroach Labs 官方 university skill 明确）；恢复速度官方口径待复核；Cloud 提供托管备份（各 tier 保留期/能力待复核）。来源等级：官方仓库资料 + 待验证

6 可观测性 有

有。DB Console（:8080）、SQL Activity、statement diagnostics、Prometheus metrics 端点。但注意：pg_stat_statements 不可用（PG 生态监控工具链迁移时的明确缺口）。来源等级：官方文档 + 社区共识

7 连接模型 部分支持

部分支持。每个节点都是 SQL 网关，客户端应配置多节点地址或经 LB 分散连接；官方对接 PG 驱动生态（port 26257）；官方是否自带连接池（pgBouncer 式）未找到证据——未找到证据，待验证。来源等级：官方文档 + 待验证

8 事务与隔离级别 有

有。默认 Serializable；v23.2 起可选 READ COMMITTED（v26.3 的默认与语义细节待官方复核）。机制：MVCC + write intents + transaction record，多 Range 事务走 2PC，Parallel Commits 把提交关键路径压到约 1 轮共识 RTT。来源等级：官方文档 + 第三方技术资料

9 复制与一致性 有

有。每 Range 一个 Raft group + leaseholder 协调读写，默认强一致；另有 follower reads（AS OF SYSTEM TIME follower_read_timestamp()）提供有界陈旧读。来源等级：官方设计文档 / RFC + 第三方资料

10 扩展方式 有

有。横向 scale-out 在线扩容，加节点后 Range 自动 rebalance；节点纵向升级配置亦可。来源等级：官方文档 + 社区共识

11 兼容性 部分支持

部分支持。PostgreSQL wire protocol v3 + 多数 PG 语法/工具可用，但不是 PG 内核。v26.3 官方文档明确缺口：range types、events、drop primary key、XML functions、列级权限、XA、template 建库、FDW、session-scoped advisory locks（仅 transaction-scoped 支持）。来源等级：官方文档（v26.3）

12 许可证与商业模式 有（商业许可，非开源）

有（商业许可，非开源）。Apache 2.0（2017–2019）→ BSL（2019–2024）→ CockroachDB Software License（2024–今）；2024-11 起年收入 < $10M 组织免费 Enterprise；2026 起新版本源码私有。Cloud 按 RU/存储计费（Basic 层级含免费额度，第三方口径，待官方复核）；自托管商业授权价格不公开（询价）。来源等级：官方博客 + 第三方报道 + 待验证

13 中文资料丰富度 部分支持（偏少）

部分支持（偏少）（编辑判断）。官方文档以英文为主，中文社区实践帖远少于 OceanBase/TiDB。来源等级：编辑判断，待规模化采集验证

14 性能与延迟特征 有

有（用延迟换全球可用性；吞吐随节点线性扩展）。

  • 单行读写延迟毫秒级（跨地域更高），高于单机 DB；吞吐随节点数线性扩展 官方文档。
  • follower reads / 就近 leaseholder 降低读尾延迟 官方文档。
  • 热点行/高冲突事务是性能杀手，schema 设计需避免全局序列热点 社区共识。

19 云托管与 Serverless 有

20 数据接入与摄入 有

有（IMPORT（CSV/Parquet/Avro）；PG COPY 兼容）。

  • IMPORT FROM 可从 S3/GCS/HTTP 批量导入 CSV/Parquet/Avro 官方文档。
  • PG 协议兼容，COPY、pg_dump/pg_restore 可用 官方文档。
  • 大表 IMPORT 注意拆分与超时，并行度需实测 社区共识。

21 外部数据访问 部分支持

部分支持（IMPORT 读外部存储；无 FDW/外部表）。

  • 可从外部存储 IMPORT，但那是导入不是联邦查询 官方文档。
  • 无 postgres_fdw 等外部表机制 社区共识。
  • 跨库查询需求一般在应用层或用 CDC 同步后解决 社区共识。

22 CDC 与下游同步 有

有（CHANGEFEED 一等公民：Kafka/云存储/webhook）。

  • CHANGEFEED 可把行级变更推到 Kafka、云存储（Parquet/CSV）、webhook 官方文档。
  • 支持 Avro/JSON 信封，可做下游流处理 官方文档。
  • 大事务变更 feed 延迟与内存是已知调优点 社区共识。

23 TTL 与数据生命周期管理 部分支持

部分支持（无原生 TTL；靠 scheduled job 定时删）。

  • 无原生行级 TTL，需用 scheduled job 机制跑定时 DELETE 官方文档。
  • 大表定时删注意拆批，避免长事务拖慢 MVCC GC 社区共识。
  • 原生 TTL 的 feature request 长期 open，短期别指望 社区共识。

24 在线 DDL 与 Schema 演进 有

有（声明式在线 schema 变更，并发友好）。

  • schema 变更是在线声明式的，多语句可并发执行不阻塞读写 官方文档。
  • 大表加索引是后台分布式回填，前台无感 官方文档。
  • 极端场景下 schema 变更仍可能排队，变更期间避免混用 DDL+DML 大事务 社区共识。

25 多租户与资源隔离 部分支持

部分支持（admission control 有限；无租户资源组）。

  • admission control 做过载保护，但不是租户级 QoS 官方文档。
  • 多租户靠多集群/多 database 逻辑隔离 社区共识。

26 跨地域多活 有

有（多 region 生存目标，原生多活）。

  • REGIONAL BY ROW 等生存目标，数据放离用户近的 region 官方文档。
  • 多 region 写原生支持，follower 读降低跨区读延迟 官方文档。
  • 跨区事务延迟是物理上限，设计表时要分区裁剪 社区共识。

27 高可用架构与 RTO/RPO 有

有（Raft 自愈，RTO 秒级）。

  • Raft 多副本，节点故障自动选主，RTO 秒级 官方文档。
  • RPO=0（多数派提交），脑裂靠 Raft 任期防护 官方文档。
  • 多活架构下单节点故障业务几乎无感 社区共识。

28 行级安全与数据脱敏 未找到证据

未找到证据（RLS支持不完整，待官方确认）。

  • CockroachDB 曾实验行级安全相关能力，但官方文档中 RLS 的支持状态不明确 / 不完整 待验证
  • 当前行级隔离主要靠视图与应用层，或利用多租户 / 分区做隔离 社区共识
  • 无内置动态脱敏引擎的公开说明 待验证

29 JSON 与半结构化能力 有

有（JSONB 类型，PG 算子兼容）。

  • JSONB 类型，->/->>/@> 等 PG 兼容算子 官方文档。
  • GIN 索引支持弱于 PG，复杂 jsonb 查询性能注意 待验证。

30 全文检索能力 无

  • 全文场景需外挂 ES/Typesense 社区共识。

31 存储效率与压缩 有

有（Pebble LSM+Snappy 压缩）。

  • 存储引擎 Pebble（RocksDB 系）采用 LSM 结构，默认 Snappy 压缩，支持块级压缩配置。官方文档
  • 多副本（默认 3 副本）带来 3 倍存储放大，压缩可部分抵消但无法消除。社区实测
  • 备份与导入导出支持压缩，属运维层面能力。官方文档

32 开源协议与厂商锁定风险 部分支持

部分支持（曾从 Apache 2.0 转 BSL）。

  • CockroachDB 2019 年将核心从 Apache 2.0 转为 BSL（Business Source License），限制云厂商托管竞争，是明确的协议变更黑历史。官方文档

33 查询优化器与计划稳定性 有

1 Data-at-rest encryption / TDE Partially supported

Partially supported. On-disk data-file encryption has an in-engine mechanism (--enterprise-encryption startup flag, must be configured per store for multi-store setups; a storage-layer RFC shows file state recorded in COCKROACHDB_REGISTRY); backups can be encrypted with passphrase / KMS. But coverage boundaries for WAL / temp files, key rotation, and the KMS matrix need verification against v26.3 docs. Evidence level: official docs (older versions) + to-be-verified

2 TLS / transport encryption Supported

Supported. Mutual TLS (node certificates + client certificates); --insecure is for development/testing only. Evidence level: official docs

3 Auditing Supported

Supported (mostly behind a paywall). sql.log.user_audit / sql.log.admin_audit.enabled cluster settings exist (confirmed by a CIS audit sample in the official skills repo); exact capability boundaries across self-hosted / Cloud tiers pending official verification. Evidence level: official repo materials + to-be-verified

4 Authentication & authorization Supported

Supported. Passwords (SCRAM-SHA-256), certificate auth, RBAC roles; OIDC/SSO, Kerberos, etc. are mostly Enterprise / Cloud paid-tier capabilities — exact matrix pending verification. Evidence level: official repo materials + to-be-verified

5 Backup & recovery Supported

Supported (partially Enterprise-only). BACKUP / RESTORE SQL, incremental backups, scheduled backups, PITR; full-cluster restore requires an enterprise license (stated explicitly in Cockroach Labs' official university skill); restore-speed figures pending verification against official statements; Cloud offers managed backups (retention/capability per tier pending verification). Evidence level: official repo materials + to-be-verified

6 Observability Supported

Supported. DB Console (:8080), SQL Activity, statement diagnostics, Prometheus metrics endpoint. But note: pg_stat_statements is NOT available (an explicit gap when migrating the PG ecosystem monitoring toolchain). Evidence level: official docs + community consensus

7 Connection model Partially supported

Partially supported. Every node is an SQL gateway; clients should configure multiple node addresses or spread connections via an LB; official integration targets the PG driver ecosystem (port 26257); whether the official distribution ships a built-in connection pooler (pgBouncer-style) — no evidence found, to-be-verified. Evidence level: official docs + to-be-verified

8 Transactions & isolation levels Supported

Supported. Default is Serializable; READ COMMITTED became optional in v23.2 (v26.3 default and semantic details pending official verification). Mechanism: MVCC + write intents + transaction record; multi-Range transactions go through 2PC; Parallel Commits compresses the commit critical path to roughly 1 round of consensus RTT. Evidence level: official docs + third-party statement

9 Replication & consistency Supported

杀手特性

每个特性 = 它是什么 + 为什么是真本事 + 边缘真相。

  1. 跨地域/跨云的强一致分布式 SQL（multi-active 接入） 真本事：各地域节点都能接 SQL，Range 的 leaseholder 按负载/地域分布，配合 REGIONAL BY ROW 让行级数据贴着访问它的地域放；SURVIVE ZONE/REGION FAILURE 声明式表达容灾目标。 边缘真相：multi-active 是"接入多活"，不是"写本地完成"。跨地域写仍要等 Raft 多数派/所触及 Range 的共识；SURVIVE REGION FAILURE 直接把"至少一次跨地域 RTT"写进每一次健康日的写延迟。选型时必须把"容灾目标"翻译成"延迟预算"。
  2. 默认 Serializable 的跨节点 ACID 真本事：MVCC + HLC（无需 TrueTime 专用硬件）+ write intents + 跨 Range 2PC + Parallel Commits（约 1 RTT 提交），默认隔离级别就是最高档；2021 年 Jepsen 报告通过是正确性口碑的硬背书。 边缘真相：Serializable 的代价是热点冲突下 40001 / restart transaction 抛给应用——重试逻辑是应用的税，不是数据库的；HLC 的代价是时钟不确定性窗口和严格的 NTP 运维，时钟偏移超阈值（第三方资料称默认约 500ms，待官方复核）节点会自我保护。把"默认最强一致"读作"默认零心智负担"是误读。
  3. Range 自动 split / merge / rebalance（免手工分片） 真本事：KV keyspace 按 Range 分片，超阈值（第三方称约 512MB，待官方复核 v26.3 默认值）自动分裂，负载型拆分还能按 QPS 拆；小 Range 合并（merge queue 与 split 启发式联动，避免抖动），节点增减自动搬 Range。应用层基本告别分库分表。 边缘真相：拆分治得了"数据量大"，治不了"单 key 热"。顺序递增主键会把写入钉死在一个 Range/leaseholder 上——这时多数节点 CPU 空闲、总吞吐却卡住，是 CockroachDB 最经典的"看起来有劲使不出"现场。UUID/hash-sharded index 能打散，但牺牲顺序扫描局部性。
  4. PostgreSQL wire protocol 生态接入 真本事：psycopg2、SQLAlchemy、Prisma、Hibernate、ActiveRecord 等 PG 驱动/ORM 基本直连（port 26257），迁移的"接口成本"低。 边缘真相：协议兼容 ≠ 行为兼容。session-scoped advisory locks 不支持（Authentik 这类依赖它的应用直接跑不起来，上游 issue 2026-06 仍 open）、无触发器/存储过程（PL/pgSQL）、无 FDW、无 LISTEN/NOTIFY、无 SEQUENCE（用 UUID/unique_rowid()）。Storj 历史迁移（v19.2 时代）花了一个全职开发月处理兼容差异——pgwire 省的是"重写连接层"，不是"零改造成本"。
  5. 声明式多地域数据布局（REGIONAL BY ROW / GLOBAL） 真本事：行级地域亲和 + GLOBAL 表（读多写少的引用数据全地域放），是"全球一张表"场景里完成度最高的数据布局抽象之一；follower reads 让远地域读走本地副本、避开 WAN。 边缘真相：GLOBAL 表写要从主地域走，写放大的账要算；REGIONAL BY ROW 要求 schema 设计时就把"地域"建模进主键/分区键，事后补救等于重做数据建模；follower reads 是有界陈旧读，读到旧数据是 feature 不是 bug——用错地方就是线上事故。

先有固定题库基线，再看差异。以下是不宜塞进杀手特性、但选型时值得知道的"第二梯队"：

  • 向量检索（v24.3+）：PGvector 兼容函数 + DiskANN 索引，官方 2024-11 GA。差异点：TP workload 顺手做向量召回；但别把它当专用向量库——大规模 ANN 性能与生态（LangChain 等集成深度）待实测验证。来源等级：官方口径 + 待验证

  • Row-level TTL：行级自动过期删除，日志/事件类表的"自动清理"刚需。来源等级：官方文档，版本细节待复核
  • Continuum（2026-01 发布）：Cockroach Labs 新推出的"AI agent 舰队"产品，面向 AI workload 的数据基础设施；2026 年战略转向 AI 的信号。GA 状态与定价待验证，本档案不计入判决依据

Each feature = what it is + why it's genuinely strong + the edge-case truth.

  1. Cross-region / cross-cloud strongly consistent distributed SQL (multi-active access) Why it's genuinely strong: nodes in every region can serve SQL; each Range's leaseholder is distributed by load/region; with REGIONAL BY ROW, row-level data sits next to the region that accesses it; SURVIVE ZONE/REGION FAILURE declaratively expresses disaster-recovery goals. Edge-case truth: multi-active means "multi-active access," not "writes complete locally." Cross-region writes still wait for the Raft quorum / consensus of every Range touched; SURVIVE REGION FAILURE writes "at least one cross-region RTT" into every write's latency budget on every healthy day. In selection, "disaster-recovery goal" must be translated into "latency budget."
  2. ACID across nodes with Serializable by default Why it's genuinely strong: MVCC + HLC (no TrueTime dedicated hardware needed) + write intents + cross-Range 2PC + Parallel Commits (~1 RTT commit); the default isolation level is the strongest one; passing the 2021 Jepsen report is a hard endorsement of its correctness reputation. Edge-case truth: Serializable's price is that under hot contention, 40001 / restart-transaction is thrown to the application — retry logic is the application's tax, not the database's; HLC's price is the clock-uncertainty window and strict NTP operations — nodes protect themselves when clock skew exceeds the threshold (third-party materials say the default is ~500ms, pending official verification). Reading "strongest by default" as "zero cognitive load by default" is a misreading.
  3. Automatic Range split / merge / rebalance (no manual sharding) Why it's genuinely strong: the KV keyspace is sharded into Ranges; oversized Ranges split automatically (third parties say ~512MB, pending verification of the v26.3 default); load-based splits can split by QPS; small Ranges merge (the merge queue works with split heuristics to avoid flapping); Ranges move automatically when nodes are added or removed. The application layer can largely say goodbye to sharding. Edge-case truth: splitting cures "large data volume," not "single hot key." Sequential auto-increment primary keys pin all writes to a single Range/leaseholder — most nodes sit idle on CPU while total throughput is capped. This is CockroachDB's most classic "plenty of strength but nowhere to apply it" scene. UUID / hash-sharded indexes can scatter the load but sacrifice sequential-scan locality.
  4. PostgreSQL wire-protocol ecosystem access Why it's genuinely strong: PG drivers/ORMs like psycopg2, SQLAlchemy, Prisma, Hibernate, ActiveRecord basically connect directly (port 26257), so the "interface cost" of migration is low. Edge-case truth: protocol compatibility ≠ behavior compatibility. Session-scoped advisory locks are unsupported (apps that depend on them, like Authentik, won't run — the upstream issue was still open as of 2026-06), plus no triggers/stored procedures (PL/pgSQL), no FDW, no LISTEN/NOTIFY, no SEQUENCE (use UUID/unique_rowid()). Storj's historical migration (v19.2 era) took one full-time developer-month to handle compatibility differences — pgwire saves you "rewriting the connection layer," not "zero migration cost."
  5. Declarative multi-region data placement (REGIONAL BY ROW / GLOBAL) Why it's genuinely strong: row-level region affinity + GLOBAL tables (read-heavy reference data replicated in every region) is one of the most complete data-placement abstractions for the "one global table" scenario; follower reads let far-region reads use local replicas and skip the WAN. Edge-case truth: GLOBAL table writes go through the home region — do the write-amplification math; REGIONAL BY ROW requires "region" to be modeled into the primary/partition key at schema-design time — retrofitting later means redoing the data model; follower reads are bounded-staleness reads — reading stale data is a feature, not a bug — used in the wrong place it's a production incident.

深水区

深水区一（存储引擎）：Range 拆分救得了数据量，救不了单 key 热

  • 机制：Range 超容量/负载阈值由 leaseholder 选 split key、经 Raft 发起分裂；merge queue 定期扫描本 store 持有 lease 的 Range，与右邻合成假设合并 Range，若 split 队列会立刻再拆则不合并（天然防抖动）；小 Range（默认 <8MB 不参与合并判断的阈值，可按 zone 配）合并。
  • 推到边缘：顺序递增主键 → 新写入全部落到最右 Range → 该 Range 的 leaseholder 成为单点写瓶颈；Range 分裂对"单 key"无效（key 再热也只属于一个 Range）；此时集群 CPU 大片空闲但写吞吐封顶，看 Hot Ranges / SHOW RANGES 才能定位。缓解靠 UUID 主键或 hash-sharded index，代价是范围扫描变 scatter-gather。
  • 选型含义：凡是有"全局递增 ID"习惯的 MySQL/PG 迁移，第一件事就是改主键策略；热点压测必须按真实 key 分布打，不能只看均匀压测。
  • 来源：官方 range-merges tech note、design.md；社区运维总结（sanoy24）；HN 历史讨论（2019，历史社区观察）

深水区二（复制与一致性）：leaseholder 是延迟的指挥棒，follower reads 是陈旧读

  • 机制：强读走 leaseholder（本地读，无需 Raft）；写由 leaseholder 提案，经 Raft 多数派确认；follower reads 基于 closed timestamp 让 follower 副本 serving 有界陈旧读，避开 WAN 跳和 leaseholder 热点（但解决不了"单 key 写热"）。
  • 推到边缘：跨地域部署中，若某 Range 的 leaseholder 在远地域，每次强读/写都是一次 WAN RTT；SURVIVE REGION FAILURE 要求共识跨地域，写延迟下限 = 到最近必需副本的往返。节点故障时 lease 重新选举有秒级窗口（第三方笔记称约 4.5s 心跳超时量级，待官方复核），期间相关 Range 写不可用——这是"CP 系统"的正常表现，不是 bug。
  • 选型含义：多地域方案必须回答"leaseholder 在哪"和"读能不能接受陈旧"；延迟 SLA 要按"拓扑实测"签，不能按"单地域 benchmark"签。
  • 来源：官方 follower reads RFC（2020）、non-blocking txns 提案；cockroachlabs 官方 skills（multi-region）；Medium 第三方分析（2026-08）

深水区三（事务与时间）：Parallel Commits 压的是 RTT 次数，不是光速；HLC 的税是时钟

  • 机制：跨 Range 事务 2PC，Parallel Commits 把"写 intents（1 RTT）+ 提交 transaction record（1 RTT）"折叠，让事务在第一阶段返回后即可向客户端确认提交，关键路径约 1 RTT；HLC = 物理时钟 + 逻辑计数器，用不确定性窗口代替 TrueTime 硬件。
  • 推到边缘：① 单地域 2 RTT→1 RTT 是实打实的延迟减半；跨洋事务 1 RTT 仍是 100–300ms 量级（第三方估算，按拓扑实测），Parallel Commits 不消灭地理。② 时钟偏移超过 max-offset（第三方称默认 500ms，待官方复核）节点自我保护/拒绝服务——NTP 是生产前置条件，虚拟机时钟漂移是隐形杀手。③ 高冲突下事务在不确定性窗口内被 restart，应用看到 40001；重试必须由应用做，且"重试外部副作用"（发邮件、调支付）是应用自己的坑，数据库只保证"数据库内工作可重做"。
  • 选型含义：事务模型 POC 必须包含"跨地域事务延迟分布"和"热点冲突重试率"两项；任何在 commit 前做外部调用的代码，迁移过来都要重写。
  • 来源：官方设计文档；第三方工程手册（max-offset）；Medium 2026-08 分析（PG vs CRDB 地域故障）

深水区四（SQL 层/兼容）：pgwire 是"方言兼容"，缺口清单是迁移的真实工作量

  • 机制：自研 SQL 层实现 PG wire protocol v3 + 多数 PG 语法，非 PG 内核 fork。
  • 推到边缘（v26.3 官方兼容文档明确缺口）：range types、events、drop primary key、XML functions、列级权限、XA、template 建库、FDW、session-scoped advisory locks 不支持。另：SERIAL 行为差异、默认 INT8、自动 rowid 主键、PostGIS 等扩展生态缺失、pg_stat_statements 不可用（监控工具链迁移缺口）。历史案例：Storj 迁移花约 1 人月处理兼容/迁移脚本（v19.2 时代，仅作历史参考）；Authentik 因 session advisory locks 无法直接运行（2026-06 上游 issue 仍 open）。
  • 选型含义：PG 迁移必须逐项跑兼容矩阵，尤其是触发器、存储过程、advisory locks、FDW、扩展；"Django/Rails 能跑"不等于"你的 PG 能跑"。
  • 来源：官方 postgresql-compatibility（v26.3）；社区迁移案例

深水区五（运维/升级）：版本火车快，finalize 是单行道

  • 机制：滚动升级逐节点进行；全部节点换完二进制后显式 SET CLUSTER SETTING version finalize；finalize 前可用 cluster.preserve_downgrade_option 保住回退，finalize 后不可回退。
  • 推到边缘：一年多个大版本（v25.4→v26.1→v26.2→v26.3），升级是"日常操作"不是"年度项目"——跟不上的团队会长期停在旧大版本；finalize 后发现问题只能向前修不能向后退，升级前必须有完整备份 + 回滚预案（向前）。证书管理是持续吐槽点（社区运维手册单列"证书过期需全量重签发+重启"流程）。
  • 选型含义：把"升级演练"写进 SLA，把证书轮换写进 on-call 手册；Cloud Basic 自动跟随新稳定版（第三方称，待官方复核），要"版本 pin 住"得看 Standard/Advanced 的能力边界。
  • 来源：社区运维手册（rolling upgrade 实操）；rancher helm chart 文档（preserve_downgrade_option）

深水区六（成本/授权）：许可证三年三变，2026 年源码转私有是分水岭

  • 机制：Apache 2.0（2017–2019）→ BSL（2019–2024，限竞争性 DBaaS，旧版本到期转 Apache）→ CockroachDB Software License（2024–今，年收入 <$10M 免费 Enterprise）→ 2026 年新版本转私有仓库开发、公开仓库只留历史快照。
  • 推到边缘："自托管可移植" ≠ "自主可控"。BSL 时代至少还能看源码、到期转 Apache；2026 后新版本无源码可看、无社区可提核心 PR——线上遇到内核级 bug，你的选项只剩"等官方修/买支持"，和闭源商业数据库一致。收入口径（关联公司、$10M 线）、用途限制、审计条款必须在合同里抠字眼，不能按博客标题理解。
  • 选型含义：把 CockroachDB 当"商业数据库"做 TCO 和退出预案；需要源码级自主修复能力的团队（如信创/强监管），这条是硬门槛。
  • 来源：官方博客（licensing-update-2024、source-code-protection 2026）；SDTimes、The Register 报道

深水区七（成本/计费）：RU 是抽象货币，跨地域复制是隐形税

  • 机制：Cloud 按 RU（请求单元）+ 存储计费；RU 把 CPU/IO/网络抽象成统一货币。
  • 推到边缘：RU 抽象让预算难预测——同样的 SQL，索引选错、跨 Range fan-out、跨地域流量都会让 RU 膨胀；多地域写入在"计算+网络+存储"三处重复花钱；自托管躲开了 RU，但起步就是 3 节点 + 跨 AZ 流量 + 商业授权/运维人力。历史公开价格（2024 年第三方口径）已不适用，2026 年现价以官方为准，询价前不要按旧数字做预算。
  • 选型含义：POC 必须跑"计费影子测试"（同样 workload 在 Cloud 跑一周看账单），不能只看性能；自托管 vs Cloud 的 TCO 要按 3 年算，含人力。
  • 来源：TechTarget 2024（历史价，数字已删）；第三方部署指南（待官方复核）

深水区八（存储/性能）：LSM + MVCC 的债——tombstone、GC 与 fan-out

  • 机制：底层 Pebble（RocksDB 系 LSM），叠加 MVCC 多版本；Range 分裂/合并、rebalance 都是后台数据搬运。
  • 推到边缘：重 UPDATE/DELETE 产生 tombstone 与旧版本，GC/compaction 跟不上时读放大、磁盘水位上涨、p99 延迟毛刺；一次 SQL 扫大量 Range 触发 DistSQL fan-out，网络与内存放大；大删除后"删完了但磁盘没降、查询变慢"是社区反复出现的运维现场（2019 HN 讨论，历史观察）。长事务/长读会 pin 住 MVCC 版本，拖慢 GC——"一个忘了关的事务拖垮整库 GC"不是传说。
  • 选型含义：大批量删除/更新要有分批 + 观察 compaction/GC 水位的 SOP；慢查询排查先看"扫了多少 Range"。
  • 来源：社区运维总结；HN 历史讨论；官方设计文档

Deep Water 1 (Storage Engine): Range splits save you from data volume, not from a single hot key

  • Mechanism: when a Range exceeds capacity/load thresholds, the leaseholder picks a split key and initiates the split via Raft; the merge queue periodically scans Ranges for which the local store holds the lease, composes a hypothetical merged Range with the right neighbor, and skips the merge if the split queue would immediately split it again (natural anti-flapping); small Ranges (default <8MB threshold for exclusion from merge consideration, configurable per zone) merge.
  • At the edge: sequential auto-increment primary keys → all new writes land on the rightmost Range → that Range's leaseholder becomes a single-point write bottleneck; Range splitting does nothing for a "single hot key" (a hot key still belongs to exactly one Range); at this point cluster CPU is largely idle but write throughput is capped — only Hot Ranges / SHOW RANGES can pinpoint it. Mitigation relies on UUID primary keys or hash-sharded indexes, at the cost of turning range scans into scatter-gather.
  • Selection implication: any MySQL/PG migration with a "global auto-increment ID" habit must change its primary-key strategy first; hotspot load tests must use the real key distribution, not just uniform benchmarks.
  • Sources: official range-merges tech note, design.md; community ops summary (sanoy24); HN historical discussion (2019, historical community observation)

Deep Water 2 (Replication & Consistency): The leaseholder is the baton of latency; follower reads are stale reads

  • Mechanism: strong reads go through the leaseholder (local reads, no Raft needed); writes are proposed by the leaseholder and confirmed by a Raft quorum; follower reads use the closed timestamp to let follower replicas serve bounded-staleness reads, avoiding WAN hops and leaseholder hotspots (but they don't fix "single hot write key").
  • At the edge: in a cross-region deployment, if a Range's leaseholder sits in a far region, every strong read/write pays one WAN RTT; SURVIVE REGION FAILURE requires cross-region consensus, so the write-latency floor = the round trip to the nearest required replica. When a node fails, lease re-election has a seconds-level window (third-party notes say ~4.5s heartbeat-timeout scale, pending official verification) during which writes to the affected Ranges are unavailable — that's normal behavior for a CP system, not a bug.
  • Selection implication: a multi-region design must answer "where is the leaseholder" and "can reads tolerate staleness"; latency SLAs must be signed against "real-topology measurements," not "single-region benchmarks."
  • Sources: official follower reads RFC (2020), non-blocking txns proposal; Cockroach Labs official skills (multi-region); Medium third-party analysis (2026-08)

Deep Water 3 (Transactions & Time): Parallel Commits compresses RTT count, not physics; HLC's tax is clocks

  • Mechanism: cross-Range transactions use 2PC; Parallel Commits folds "write intents (1 RTT) + commit transaction record (1 RTT)" together, letting the transaction confirm the commit to the client after the first phase — critical path ~1 RTT; HLC = physical clock + logical counter, replacing TrueTime hardware with an uncertainty window.
  • At the edge: ① In a single region, 2 RTTs → 1 RTT is a genuine latency halving; for cross-ocean transactions 1 RTT is still 100–300ms scale (third-party estimate — measure your own topology); Parallel Commits doesn't eliminate geography. ② When clock skew exceeds max-offset (third parties say the default is 500ms, pending official verification), the node protects itself / refuses service — NTP is a production prerequisite, and VM clock drift is an invisible killer. ③ Under high contention, transactions get restarted inside the uncertainty window; the application sees 40001; retries must be done by the application, and "retrying external side effects" (sending email, calling payment) is the application's own pit — the database only guarantees that "work inside the database is redoable."
  • Selection implication: a transaction-model POC must include "cross-region transaction latency distribution" and "hotspot-conflict retry rate"; any code that does external calls before commit must be rewritten on migration.
  • Sources: official design docs; third-party engineering handbook (max-offset); Medium 2026-08 analysis (PG vs CRDB regional failure)

Deep Water 4 (SQL Layer / Compatibility): pgwire is "dialect compatibility"; the gap list is the migration's true workload

  • Mechanism: a self-built SQL layer implements PG wire protocol v3 + most PG syntax — not a PG kernel fork.
  • At the edge (v26.3 official compatibility docs list explicit gaps): range types, events, drop primary key, XML functions, column-level privileges, XA, template databases, FDW, session-scoped advisory locks are unsupported. Also: SERIAL behavior differences, default INT8, automatic rowid primary keys, missing extension ecosystem (PostGIS, etc.), pg_stat_statements unavailable (monitoring-toolchain migration gap). Historical cases: Storj's migration took ~1 person-month handling compatibility/migration scripts (v19.2 era, historical reference only); Authentik can't run directly due to session advisory locks (upstream issue still open as of 2026-06).
  • Selection implication: a PG migration must run the compatibility matrix item by item, especially triggers, stored procedures, advisory locks, FDW, extensions; "Django/Rails runs" does not mean "your PG runs."
  • Sources: official postgresql-compatibility (v26.3); community migration cases

Deep Water 5 (Operations / Upgrades): the release train is fast; finalize is a one-way street

  • Mechanism: rolling upgrades proceed node by node; after all nodes swap binaries, explicitly SET CLUSTER SETTING version to finalize; before finalize you can keep the rollback option via cluster.preserve_downgrade_option; after finalize there is no rollback.
  • At the edge: multiple majors per year (v25.4 → v26.1 → v26.2 → v26.3) make upgrades "routine operations," not "annual projects" — teams that can't keep up get stuck on old majors for a long time; after finalize, problems can only be fixed forward, never rolled back — so upgrades need a full backup + (forward) rollback plan. Certificate management is a standing complaint (community ops handbooks have a dedicated "expired certificates require full re-issuance + restart" procedure).
  • Selection implication: write "upgrade drills" into the SLA and certificate rotation into the on-call runbook; Cloud Basic auto-tracks new stable versions (third-party statement, pending official verification) — pinning a version depends on Standard/Advanced capability boundaries.
  • Sources: community ops handbooks (rolling-upgrade practice); Rancher helm chart docs (preserve_downgrade_option)

Deep Water 6 (Cost / Licensing): the license changed three times in three years; 2026's source-going-private is the watershed

  • Mechanism: Apache 2.0 (2017–2019) → BSL (2019–2024, restricted competitive DBaaS, old versions revert to Apache on expiry) → CockroachDB Software License (2024–present, free Enterprise under $10M revenue) → 2026: new versions developed in a private repo, public repo keeps only historical snapshots.
  • At the edge: "self-hostable" ≠ "self-controllable." In the BSL era you could at least read the source and it reverted to Apache on expiry; after 2026 there is no source to read for new versions and no community path to submit core PRs — when you hit a kernel-level bug in production, your only options are "wait for the vendor to fix it / buy support," exactly like a closed-source commercial database. Revenue definitions (affiliated companies, the $10M line), usage restrictions, and audit clauses must be read word by word in the contract — don't rely on blog headlines.
  • Selection implication: treat CockroachDB as a "commercial database" for TCO and exit-planning; teams that need source-level self-remediation (regulatory/strong-compliance scenarios) hit a hard barrier here.
  • Sources: official blog (licensing-update-2024, source-code-protection 2026); SDTimes, The Register coverage

Deep Water 7 (Cost / Billing): RU is abstract currency; cross-region replication is a hidden tax

  • Mechanism: Cloud bills by RU (Request Units) + storage; RU abstracts CPU/IO/network into a single currency.
  • At the edge: RU abstraction makes budgets hard to predict — the same SQL costs more RU with a wrong index choice, cross-Range fan-out, or cross-region traffic; multi-region writes pay three times over in "compute + network + storage"; self-hosting dodges RU, but starts at 3 nodes + cross-AZ traffic + commercial license/ops headcount. Third-party 2024 prices are already historical; 2026 current prices follow official figures — don't budget on old numbers before getting a quote.
  • Selection implication: the POC must run a "billing shadow test" (run the same workload on Cloud for a week and look at the bill), not just performance; self-hosted vs Cloud TCO must be computed over 3 years, headcount included.
  • Sources: TechTarget 2024 (historical pricing); 2026 third-party deployment guide (Basic $15 benefit/50M RU/10GiB, pending official verification)

Deep Water 8 (Storage / Performance): the debt of LSM + MVCC — tombstones, GC, and fan-out

  • Mechanism: Pebble (RocksDB-family LSM) underneath, with MVCC multi-versions on top; Range splits/merges and rebalances are all background data movement.
  • At the edge: heavy UPDATE/DELETE produces tombstones and old versions; when GC/compaction can't keep up, read amplification, rising disk watermarks, and p99 latency spikes follow; one SQL scanning many Ranges triggers DistSQL fan-out, amplifying network and memory; "deleted everything but the disk didn't shrink and queries got slower" is a recurring community ops scene (2019 HN discussion, historical observation). Long transactions/long reads pin MVCC versions and slow GC — "one forgotten-open transaction dragging down whole-cluster GC" is no legend.
  • Selection implication: bulk deletes/updates need batched execution + SOPs for watching compaction/GC watermarks; slow-query triage should first ask "how many Ranges did it scan."
  • Sources: community ops summaries; HN historical discussion; official design docs

判决

  • 一句话定位：为"全球多活 + 强一致"而生的分布式 SQL；单地域小库用它是大炮打蚊子，跨地域核心系统用它是同类里完成度最高的选择之一——前提是你接受它的许可证现实和延迟物理。
  • 适合谁：
    • 多地域/全球化业务的 OLTP 核心系统（用户和数据天然分区，如 SaaS、跨境、IoT 平台）
    • 金融/账务类对正确性零容忍、愿意为 Serializable 付延迟税的系统
    • 数据量持续增长、希望永远不做分库分表的团队
    • 需要原生 CDC 进湖仓（Kafka→Iceberg/Delta）的数据工程团队
    • 年收入 <$10M、想白嫖 Enterprise 能力的中小团队（以合同口径为准）
  • 不适合谁：
    • 单机 PG/MySQL 就能扛住的业务（延迟、运维、授权三重税白付）
    • 重度依赖 PG 触发器/存储过程/advisory locks/FDW/扩展生态，且不愿做兼容 POC 的团队
    • 需要源码级自主可控（信创/强监管）或对"闭源化"趋势敏感的组织
    • 预算敏感且 workload RU 难预测、又不想做计费影子测试的团队
    • 团队无专职 DBA/运维，又想"装完不管"（证书、NTP、升级、GC 都是活）
  • 迁移成本：
    • MySQL → 中高：无 MySQL 协议，走应用层改造；事务语义（Serializable vs REPEATABLE-READ）差异大；递增主键习惯必须改
    • PostgreSQL → 低-中：协议/驱动层摩擦小；但触发器、存储过程、advisory locks、FDW、扩展、pg_stat_statements 等缺口需逐项 POC；默认隔离级别差异要全回归
    • Oracle → 高：无 Oracle 兼容路线，不建议作为"去 O"目标
  • One-line positioning: a distributed SQL built for "global multi-active + strong consistency"; using it for a small single-region database is overkill, and for cross-region core systems it's among the most complete choices in its class — provided you accept its licensing reality and the physics of latency.
  • Who it's for:
    • OLTP core systems for multi-region/global businesses (users and data naturally partitioned, e.g. SaaS, cross-border, IoT platforms)
    • Finance/ledger systems with zero tolerance for incorrectness, willing to pay the Serializable latency tax
    • Teams with continuously growing data that want to never shard
    • Data-engineering teams needing native CDC into lakehouses (Kafka → Iceberg/Delta)
    • Small/medium teams under $10M revenue wanting free Enterprise capabilities (subject to contract wording)
  • Who it's not for:
    • Workloads a standalone PG/MySQL can handle (you'd pay the latency, ops, and licensing taxes for nothing)
    • Teams heavily dependent on PG triggers/stored procedures/advisory locks/FDW/extension ecosystem that won't run a compatibility POC
    • Organizations needing source-level self-controllability (domestic substitution / strong regulation) or sensitive to the "going closed-source" trend
    • Budget-sensitive teams whose workload RU is hard to predict and who won't run a billing shadow test
    • Teams without dedicated DBA/ops wanting "install and forget" (certificates, NTP, upgrades, GC are all ongoing work)
  • Migration cost:
    • MySQL → medium-high: no MySQL protocol — application-layer rework; transaction semantics differ greatly (Serializable vs REPEATABLE-READ); the auto-increment primary-key habit must change
    • PostgreSQL → low-medium: low protocol/driver-layer friction; but triggers, stored procedures, advisory locks, FDW, extensions, pg_stat_statements gaps need item-by-item POCs; default isolation-level differences need full regression
    • Oracle → high: no Oracle-compatibility path; not recommended as a "de-Oracle" target
