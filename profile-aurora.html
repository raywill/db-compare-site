档案：Amazon Aurora

关系型 OLTP #云原生 #存算分离 #全托管 #MySQL兼容 #PG兼容 #Serverless #GlobalDatabase #AWS锁定

AWS 的云原生关系型数据库：计算与存储分离、存储层 6 副本 quorum、MySQL / PostgreSQL 双协议兼容的**全托管**数据库，"不想运维数据库"的团队在 AWS 上的默认答案。

AWS's cloud-native relational database: compute-storage separation, a 6-copy quorum storage layer, fully managed with MySQL / PostgreSQL dual-protocol compatibility — the default answer for teams on AWS that "don't want to operate a database".

硬维度（14 项）

1 静态加密 / TDE 有

有官方文档。集群级 KMS AES-256，覆盖存储卷、自动备份、快照、副本；创建时开启，创建后不可修改（immutable，要加密旧库只能快照→加密复制→恢复→切换）。注意两点反直觉：MySQL 的 InnoDB 表空间级 TDE（ENCRYPTION='Y'）不支持（查证为无），keyring 插件全系不支持——加密是卷级的，不是表级的。新集群默认开启加密为社区说法，待验证。

2 TLS / 传输加密 有

有官方文档。TLS/SSL；Aurora MySQL 8.4 新集群默认强制 TLS（仅 1.2/1.3）；MySQL 侧 require_secure_transport、PG 侧 rds.force_ssl。

3 审计 有

有官方文档。Database Activity Streams（近实时活动流，KMS 加密，sync/async 两种模式，async 高负载可能丢日志）；Aurora MySQL 支持 MariaDB Audit Plugin（高级审计）；PG 支持 pgaudit 扩展；日志可导出 CloudWatch。

4 认证与权限 有

有官方文档。密码、IAM 数据库认证（token 15 分钟有效期）、Secrets Manager 集成、PG 支持 Kerberos/AD。上限是 rds_superuser，无 SUPER 权限：不能改 pg_hba.conf、不能 ALTER SYSTEM、不能建 C 语言函数、不能装非白名单扩展。

5 备份恢复 有

有官方文档。连续增量备份到 S3（对性能无影响）+ PITR 任意秒级恢复（保留期 1~35 天，恢复=建新集群）；手动快照；跨 Region 快照复制；克隆（copy-on-write）；Backtrack 仅 Aurora MySQL（建集群时启用，72 小时窗口）。

6 大版本升级 部分支持

部分支持（官方文档 + 社区实测）。三条路：原地升级（要停机窗口）、蓝绿部署（厂商口径切换 <1 分钟，2026-04 起支持 RDS Proxy 联动消 DNS 延迟）、快照恢复式升级。不可原地降级，in-place 升级无官方回滚（只能靠升级前快照恢复=丢数据，或蓝绿回切）；参数组族必须与目标版本匹配，否则升级失败或静默丢自定义参数；Aurora MySQL 8.4 新增自动升级 precheck。

7 可观测性 有

有官方文档。CloudWatch（Database Insights）、Performance Insights（7 天保留免费，超期按 vCPU 收费）、Enhanced Monitoring（走 CloudWatch Logs 计费）、慢查询日志（要手动在参数组开启并导出，产生日志费用）、DevOps Guru for RDS。

8 连接模型 每连接一个后端进程

每连接一个后端进程（MySQL 线程 / PG 进程），连接风暴靠 RDS Proxy 解官方文档：托管连接池、IAM 认证、Secrets Manager、failover 感知（不靠 DNS）。reader endpoint 是 DNS 轮询（TTL 5 秒），不是真负载均衡——长连接池不回收会钉死在个别 reader 上。

9 事务与隔离级别 继承引擎官方文档

继承引擎官方文档。MySQL：InnoDB，默认 REPEATABLE READ；PG：默认 READ COMMITTED，支持 SERIALIZABLE。写转发下 MySQL 仅支持 REPEATABLE READ；Limitless 跨分片事务有限制；XA 支持（PG 需 max_prepared_transactions > 0）。

10 复制与一致性 有，架构核心

有，架构核心（官方论文 + 官方文档）。存储层 6 副本跨 3 AZ，写 quorum 4/6、读 quorum 3/6；计算层只向存储层发 redo 日志（"log is the database"）；reader 共享同一存储卷，复制延迟为毫秒级厂商口径；Global Database 跨 Region 存储层异步物理复制（厂商口径典型 <1 秒）；MySQL 另有 binlog / Enhanced Binlog 逻辑复制选项。

11 扩展方式 纵向

纵向（实例规格；Serverless v2 0~256 ACU 自动）+ 横向读扩展（最多 15 副本）+ 存储自动扩容（10GB→256 TiB，只增不减）。写扩展靠 Aurora PostgreSQL Limitless（分片架构，router/shard 两层）。官方文档

12 兼容性 有

有（官方文档 + 社区共识）。MySQL 协议（3.x ~ MySQL 8.0.45；8.4 ~ 社区 8.4.7 LTS 且版本号对齐）、PG 协议（18.4 等）。JDBC / ORM / DMS / Debezium 等生态工具通用。PG 扩展为白名单制（SHOW rds.extensions），冷门扩展无自助安装通道。

13 许可证与商业模式 有

有（官方文档，闭源商业 + 厂商口径计费模型）。闭源商业，按量付费：计算（实例小时 / ACU-秒）+ 存储（GB-月）+ I/O（Standard 版按百万次）+ 备份/传输；Database Savings Plans / RI 可打折；无开源版。AWS 锁定是最大的商业现实：无他云、无自建，迁出=逻辑迁移。只写计费模型，不写绝对标价。

14 中文资料丰富度 有中文版但部分页面翻译滞后

中等社区共识。官方文档有中文版但部分页面翻译滞后；中文社区实践帖（CSDN/博客）不少，但深度调优、故障排查内容多为英文（re:Post、AWS Blog）。

1 Data-at-rest encryption / TDE Supported

Supported 官方文档. Cluster-level KMS AES-256, covering storage volumes, automated backups, snapshots, replicas; enabled at creation time and immutable afterward (to encrypt an existing cluster you must snapshot → copy with encryption → restore → cut over). Two counter-intuitive notes: MySQL InnoDB tablespace-level TDE (ENCRYPTION='Y') is unsupported (verified absent), and keyring plugins are unsupported across the board — encryption is at the volume level, not the table level. "New clusters have encryption on by default" is a community claim, 待验证.

2 TLS / transport encryption Supported

Supported 官方文档. TLS/SSL; Aurora MySQL 8.4 new clusters enforce TLS by default (1.2/1.3 only); require_secure_transport on the MySQL side, rds.force_ssl on the PG side.

3 Auditing Supported

Supported 官方文档. Database Activity Streams (near-real-time activity stream, KMS-encrypted, sync/async modes; async mode can drop logs under heavy load); Aurora MySQL supports the MariaDB Audit Plugin (advanced auditing); PG supports the pgaudit extension; logs can be exported to CloudWatch.

4 Authentication & authorization Supported

Supported 官方文档. Passwords, IAM database authentication (tokens valid for 15 minutes), Secrets Manager integration, PG supports Kerberos/AD. The ceiling is rds_superuser — no SUPER privilege: you cannot edit pg_hba.conf, cannot ALTER SYSTEM, cannot create C-language functions, cannot install non-whitelisted extensions.

5 Backup & recovery Supported

Supported 官方文档. Continuous incremental backup to S3 (zero performance impact) + PITR recovery to any second (retention 1–35 days, recovery = create a new cluster); manual snapshots; cross-Region snapshot copy; clone (copy-on-write); Backtrack only on Aurora MySQL (enabled at cluster creation, 72-hour window).

6 Major-version upgrades Partially supported

Partially supported (official docs + community-tested). Three paths: in-place upgrade (requires a maintenance window), blue/green deployment (vendor claim: switchover <1 minute; RDS Proxy integration to eliminate DNS lag since 2026-04), snapshot-restore upgrade. No in-place downgrade; in-place upgrades have no official rollback (only restoring from a pre-upgrade snapshot, which means data loss, or blue/green cutback); the parameter group family must match the target version or the upgrade fails or silently drops custom parameters; Aurora MySQL 8.4 added an automated upgrade precheck.

7 Observability Supported

Supported 官方文档. CloudWatch (Database Insights), Performance Insights (7-day retention free, beyond that billed per vCPU), Enhanced Monitoring (billed via CloudWatch Logs), slow query logs (must be manually enabled in the parameter group and exported, incurring log charges), DevOps Guru for RDS.

8 Connection model One backend proces

One backend process per connection (MySQL thread / PG process); connection storms are handled by RDS Proxy 官方文档: managed connection pooling, IAM authentication, Secrets Manager, failover-aware (not DNS-based). The reader endpoint is DNS round-robin (TTL 5 seconds), not true load balancing — connection pools that never recycle connections will pin to individual readers.

9 Transactions & isolation levels Inherited from the

Inherited from the engine 官方文档. MySQL: InnoDB, default REPEATABLE READ; PG: default READ COMMITTED, SERIALIZABLE supported. Under write forwarding, MySQL supports only REPEATABLE READ; Limitless cross-shard transactions have restrictions; XA supported (PG requires max_prepared_transactions > 0).

10 Replication & consistency Supported

Supported, architectural core (official paper + official docs). Storage layer: 6 copies across 3 AZs, write quorum 4/6, read quorum 3/6; the compute layer only sends redo logs to the storage layer ("log is the database"); readers share the same storage volume, replication lag in milliseconds 厂商口径; Global Database: cross-Region asynchronous physical replication at the storage layer (vendor claim: typically <1 second); MySQL additionally offers binlog / Enhanced Binlog logical replication options.

11 Scaling Vertical

Vertical (instance classes; Serverless v2 0–256 ACU automatic) + horizontal read scale-out (up to 15 replicas) + automatic storage expansion (10GB → 256 TiB, grow-only). Write scale-out via Aurora PostgreSQL Limitless (sharded architecture, router/shard two-tier). 官方文档

12 Compatibility MySQL protocol

MySQL protocol (3.x ~ MySQL 8.0.45; 8.4 ~ community 8.4.7 LTS with aligned version numbers), PG protocol (18.4, etc.). JDBC / ORM / DMS / Debezium ecosystem tools all work. PG extensions are whitelist-based (SHOW rds.extensions); obscure extensions have no self-service installation channel.

13 License & business model Closed-source comm

Closed-source commercial, pay-as-you-go: compute (instance-hours / ACU-seconds) + storage (GB-month) + I/O (Standard edition billed per million I/Os) + backup/transfer; Database Savings Plans / RIs can discount; no open-source edition. AWS lock-in is the biggest commercial reality: no other cloud, no self-hosted edition, leaving = logical migration.

14 Chinese-language resources Moderate

Moderate 社区共识. Official docs have a Chinese edition but some pages lag in translation; Chinese community practice posts (CSDN/blogs) are plentiful, but deep tuning and troubleshooting content is mostly in English (re:Post, AWS Blog).

杀手特性

  1. 存算分离 + 6 副本 quorum 存储层（"log is the database"） 真本事：计算层无本地持久化，跨过网络的只有 redo 日志；存储层 6 副本跨 3 AZ（写 4/6、读 3/6），单 AZ 故障写可用性不受影响；计算崩溃重启无需 redo 回放。这是 Aurora 故障切换能做到秒级、备份对性能零影响的根本原因（SIGMOD 2017 论文）。 边缘真相：见深水区一——"存储无限弹性"是错觉，单 writer 实例规格仍是写吞吐天花板；热点写入会让少数 10GB protection group 抖动，而存储层没有暴露给用户的分区级限流数字，排查只能靠指标推断。
  2. Serverless v2（2026-04 起改名 Aurora serverless）：0~256 ACU、按秒计费、可缩到 0 真本事：扩容秒级、连接不断；2024-11 起支持缩到 0 ACU 自动暂停，暂停期间计算费为 0，约 15 秒恢复厂商口径。波动/间歇负载和开发测试环境的"不用不花钱"终于名副其实。 边缘真相：见深水区六——"零费用"有三道关：默认最小 0.5 ACU 是地板价、暂停期间存储费照收、挂 RDS Proxy / 开逻辑复制 / 做 Global 主集群会阻止暂停。每天早上第一波流量要吃冷启动。
  3. Global Database：跨 Region 单写多读 + Region 级 DR 一体 真本事：存储层物理复制不经过引擎，主实例性能不受影响；厂商口径典型延迟 <1 秒；计划内 switchover 可做到 RPO=0（<30 秒）。从 Region 本地读延迟低，全球化读场景的天然方案。 边缘真相：见深水区四——计划外 failover 的 RPO = 当时的实际复制延迟，必须看 AuroraGlobalDBRPOLag 实时指标；跨 Region 传输费 + 复制 I/O 费另计；写永远只在主 Region，跨 Region 写转发只是"方便"，每条 DML 付一次跨 Region RTT。
  4. 克隆（Clone）：copy-on-write 分钟级复制整个集群 真本事：与源共享存储块，初始几乎不占额外存储；测试、压测、故障复现"复制一个生产库"从小时级变成分钟级。 边缘真相：创建便宜≠持有便宜——克隆体持续写入会累积差异存储与 I/O 费用；克隆是"快照式"一次性复制，不会自动跟随源更新，过期克隆上的测试结论可能失真。
  5. I/O-Optimized 计费模式：I/O 密集型负载的成本可预测性 真本事：取消按次 I/O 收费，I/O 费用占总支出超约 25%（厂商口径盈亏线）的负载切换后更划算，有案例总体节省可观。 边缘真相：代价是计算与存储单价上浮厂商口径；I/O 占比低、存储量大但访问少的库切过去反而亏；Standard→I/O-Optimized 30 天只能切一次，切错要等一个月。
  1. Disaggregated storage + 6-copy quorum layer ("log is the database") What it is: the compute layer has no local persistence; only redo logs cross the network; the storage layer holds 6 copies across 3 AZs (write 4/6, read 3/6), so a whole-AZ loss doesn't affect write availability; a crashed compute instance restarts with no redo replay. This is the fundamental reason Aurora failover is measured in seconds and backups have zero performance impact (SIGMOD 2017 paper). Edge truth: see Deep water 1 — "infinitely elastic storage" is an illusion; the single writer instance class is still the write-throughput ceiling; hot writes can make a few 10GB protection groups jitter, and the storage layer exposes no user-visible partition-level throttling numbers, so diagnosis relies on inferring from metrics.
  2. Serverless v2 (renamed Aurora Serverless in 2026-04): 0–256 ACU, per-second billing, can scale to 0 What it is: scaling in seconds with connections intact; since 2024-11 it can scale to 0 ACU and auto-pause, with zero compute cost while paused and ~15 seconds to resume 厂商口径. Fluctuating/intermittent workloads and dev/test environments finally get true "pay nothing when idle". Edge truth: see Deep water 6 — "zero cost" has three gates: the default 0.5 ACU minimum is a floor price, storage is still billed while paused, and attaching RDS Proxy / enabling logical replication / being the primary of a Global Database blocks auto-pause. The first wave of morning traffic eats a cold start.
  3. Global Database: cross-Region single-writer multi-reader + Region-level DR in one What it is: storage-layer physical replication bypasses the engine, so primary performance is unaffected; vendor-claimed typical lag <1 second; planned switchover can achieve RPO=0 (<30 seconds). Local reads in each Region with low latency — the natural solution for globalized read workloads. Edge truth: see Deep water 4 — for unplanned failover, RPO = the actual replication lag at that moment; you must watch the AuroraGlobalDBRPOLag metric in real time; cross-Region transfer + replicated I/O are billed separately; writes only ever happen in the primary Region — cross-Region write forwarding is "convenience", each DML paying one cross-Region RTT.
  4. Clone: copy-on-write, clone the whole cluster in minutes What it is: shares storage blocks with the source, consuming almost no extra storage initially; "copy a production database" for testing, load tests, or incident reproduction goes from hours to minutes. Edge truth: cheap to create ≠ cheap to keep — continued writes on the clone accumulate differential storage and I/O costs; a clone is a one-shot snapshot copy that never follows the source, so test conclusions on a stale clone can be misleading.
  5. I/O-Optimized billing: cost predictability for I/O-heavy workloads What it is: removes per-operation I/O charges; workloads where I/O exceeds ~25% of total spend (vendor-claimed breakeven) come out cheaper, with real-world cases showing substantial total savings. Edge truth: the tradeoff is higher compute and storage unit prices 厂商口径; databases with low I/O share but large, rarely-accessed storage do worse on it; Standard → I/O-Optimized switches are limited to once per 30 days — switch wrong and you wait a month.

深水区

深水区一：quorum 存储层——数学很美，热点很痛（domain：存储引擎）

  • 机制：数据切 10 GiB protection group，6 副本跨 3 AZ，写 4/6、读 3/6；计算层只发 redo 日志，从不写数据页（官方论文）。
  • 推到边缘：丢整个 AZ（2 副本）写不受影响；再坏 1 个节点（共 3 副本丢失）写 quorum 凑不齐→写不可用、读仍可用——这是设计目标，不是 bug。写入高度倾斜时压力集中在少数 protection group，社区基准测试观察到规律性性能抖动，AWS 官方调优指南建议主键轻量、外键检查移到应用层。存储层没有暴露分区级限流数字，热点症状是写延迟抖动而非明确报错待验证。
  • 选型含义：选 Aurora 是选"计算无状态、故障切换不搬数据"；但别把"自动扩展"理解成"无限"，单 writer 规格与写入热点模型必须先压测。
  • 来源：Verbitski et al. SIGMOD 2017 论文；AWS 官方文档；DZone 热点抖动基准

深水区二：写转发与读扩展——"15 副本"是 15 份计算，不是 15 份数据（domain：复制与读扩展）

  • 机制：reader 可接受写 SQL 并转发给 writer（Aurora MySQL 3.04+、PG 16.4+/15.8+/14.13+，官方文档）；reader endpoint 做 DNS 轮询分发。
  • 推到边缘：写转发硬限制多——MySQL 仅 REPEATABLE READ，两引擎均不支持 DDL / SAVEPOINT / XA / LOCK / TRUNCATE / COPY / 游标，PG 还不支持存储过程与 LISTEN/NOTIFY；转发会话占用 writer 连接池配额（MySQL 默认 10%、PG 默认 25%），突发写先触达的是这个配额。跨 Region 写转发每条 DML 付一次跨 Region RTT（官方博客实测 us-east-1↔us-east-2 每条 +12~15ms）。reader endpoint 是 DNS 轮询（TTL 5 秒）不是负载均衡，JVM 默认无限缓存 DNS、连接池长期持有连接都会导致"读不均"（官方博客）。
  • 选型含义：写转发是"偶发写"的便利功能，不是第二写入口，单 writer 本质不变；读一致性要求高的链路走 writer endpoint；长连接池必须配连接回收（ConnMaxLifetime）。
  • 来源：AWS 官方文档；官方博客

深水区三：故障切换——数据库 30 秒恢复，应用可能几分钟不可用（domain：高可用）

  • 机制：按 failover priority tier 提拔 reader 为 writer，共享存储无需拷贝数据；writer endpoint DNS（TTL 5 秒）切换；厂商口径通常 30 秒内完成，社区实测 30~60 秒端到端。已提交事务靠 4/6 quorum 不丢，未提交 in-flight 事务全丢。
  • 推到边缘：DNS 缓存是第一杀手——JVM 默认 DNS 缓存 30 秒~无限，不设 networkaddress.cache.ttl 会持续打旧 IP；社区压测显示一个 JVM 参数把应用恢复从约 5 秒降到约 100ms社区实测。无 reader 的集群故障时间拉长到分钟级（生产至少配 1 个 reader 是硬要求）。RDS Proxy 可把应用侧恢复压到秒级（AWS 内部基准：平均约 3 秒 vs 直连约 14~24 秒，厂商口径）。MySQL vs PG 的 failover 目标时间无公开可区分数字，不应作为引擎取舍依据待验证。
  • 选型含义：Aurora 的 RTO 本质是"控制面切换"，真正的 RTO 取决于应用侧重连工程；混沌演练要把客户端行为一起测。
  • 来源：AWS 官方文档；社区实测（re:Post）

深水区四：Global Database——RPO 必须绑定实时 lag 指标理解（domain：容灾）

  • 机制：1 主 Region + 最多 10 个从 Region（官方文档；上线初期为 5），存储层物理复制，厂商口径典型延迟 <1 秒。
  • 推到边缘：计划内 switchover 可 RPO=0（<30 秒）；计划外 failover 的数据丢失量 = 当时的实际复制延迟，必须用 AuroraGlobalDBRPOLag 度量而非默认 RPO=0（社区建议 lag >2s 持续 5 分钟告警）。灾难切换后旧主 Region 卷被替换、需从快照重建（小时级）——DR 演练必须用 switchover，用 failover 做演练会引入不必要的重建与数据丢失风险社区实测。从 Region 挂载会挤占主集群 reader 配额（每挂 1 个从集群，主 reader 配额减 1）。rds.global_db_rpo 参数可把从 Region 落后反压回主 Region 写路径，打开后主写延迟与从 Region 健康度耦合。
  • 选型含义：Global Database 是"单写多读 + Region 级 DR"，不要当多活；把 "~1s RPO" 写进 SLA 前先看 P99 lag；跨 Region 传输费 + 复制 I/O 费另计，多 Region 预算至少按单 Region ×2 起。
  • 来源：AWS 官方文档；社区 runbook

深水区五：I/O 计费——Aurora 第一成本深水区（domain：成本）

  • 机制：Standard 版除计算 + 存储外，读写 I/O 按百万次单独计费（询价/看账单）。
  • 推到边缘：全表扫描/缺索引、working set 装不进内存（Serverless v2 上限配太小是典型诱因）会导致读放大；社区真实账单案例（2026-06）：某 1.0 ACU 上限的小库 I/O 费占当月 Aurora 总账单 68%~88%社区实测。优化过的查询退化也会引爆 I/O 费。排查看 Cost Explorer 的 Aurora:StorageIOUsage 行项与 CloudWatch VolumeReadIOPs/VolumeWriteIOPs。
  • 选型含义：上 Aurora 第一件事是给 I/O 设账单告警；内存宁可配大一点，ACU 的钱比 I/O 惊魂账单便宜；I/O 占比超约 25% 就评估切 I/O-Optimized（但 30 天只能切一次，别切错）。
  • 来源：社区账单案例（2026-06，社区实测）；AWS 官方文档

深水区六：Serverless v2——"serverless"三道关（domain：成本/运维）

  • 机制：0~256 ACU，0.5 步长，按秒计费；0 ACU 自动暂停后约 15 秒恢复（厂商口径；暂停超 24 小时社区实测约 12~30 秒）。
  • 推到边缘："不用不花钱"三道关——①默认最小 0.5 ACU 是 24×7 的地板价；②暂停期间存储费照收；③挂 RDS Proxy、开逻辑复制/binlog 复制、做 Global 主集群会阻止自动暂停，实例卡在 0.5 ACU社区实测。扩容秒级但缩容按分钟级（防抖动）；恢复期间新连接排队/超时，有团队用定时 ping 保活规避冷启动社区实测。
  • 选型含义：开发/测试/间歇负载设 0 ACU 最划算；在线业务设 2~4 ACU 保底避开早高峰冷启动；"预置 writer + Serverless v2 reader"混搭是社区验证过的省钱组合。
  • 来源：AWS 官方文档；AWS Database Blog；社区实测

深水区七：版本滞后与升级之痛——托管的代价是"等 AWS 发版"（domain：兼容/版本）

  • 机制：Aurora MySQL 3.x 对应社区 8.0 的小版本长期滞后数月；Aurora PG 大版本落后社区数月到一年以上（官方发版日历 + 社区共识）。
  • 推到边缘：2026-05-21 是个转折点——Aurora MySQL 8.4 GA，对齐社区 8.4.7 且版本号与社区对齐，官方承诺大版本 12 个月内、小版本 3 个月内跟上厂商口径，此前"RDS MySQL 早有 8.4 而 Aurora 没有"被 re:Post 反复追问。大版本升级是运维最痛：MySQL 2→3 的 precheck 常因数据字典不一致等问题失败、升级后执行计划回退（优化器变化、query cache 移除、默认字符集变 utf8mb4）；PG 升级靠蓝绿部署但有隐藏前提（源库不能有活跃逻辑复制槽——文档未写，社区实测排查数小时；切换期间禁 DDL；切换后需 ANALYZE/REINDEX）；in-place 升级无回滚。
  • 选型含义：追新特性的团队选 Aurora 要接受"等发版"的节奏，RDS（非 Aurora）通常跟得更快；大版本升级走蓝绿部署 + 升级前逐项 precheck，把回滚路径（蓝绿回切）当必选项。
  • 来源：AWS What's New；AWS 官方文档；re:Post 社区实测

Deep water 1: the quorum storage layer — beautiful math, painful hotspots (domain: storage engine)

  • Mechanism: data is cut into 10 GiB protection groups, 6 copies across 3 AZs, write 4/6, read 3/6; the compute layer only emits redo logs and never writes data pages (official paper).
  • At the edge: losing a whole AZ (2 copies) doesn't affect writes; lose 1 more node (3 copies gone total) and the write quorum can't be formed → writes unavailable, reads still available — that's the design goal, not a bug. Highly skewed writes concentrate pressure on a few protection groups; community benchmarks observe regular performance jitter, and AWS's own tuning guide recommends lightweight primary keys and moving foreign-key checks to the application. The storage layer exposes no partition-level throttling numbers; hotspot symptoms show up as write-latency jitter rather than explicit errors 待验证.
  • Selection implication: choosing Aurora means choosing "stateless compute, failover without moving data"; but don't read "auto-scaling" as "unlimited" — the single-writer instance class and the write-hotspot model must be load-tested first.
  • Sources: Verbitski et al. SIGMOD 2017 paper; AWS official docs; DZone hotspot-jitter benchmark

Deep water 2: write forwarding & read scale-out — "15 replicas" is 15 copies of compute, not 15 copies of data (domain: replication & read scale-out)

  • Mechanism: readers can accept write SQL and forward it to the writer (Aurora MySQL 3.04+, PG 16.4+/15.8+/14.13+, official docs); the reader endpoint distributes via DNS round-robin.
  • At the edge: write forwarding has many hard limits — MySQL only REPEATABLE READ, neither engine supports DDL / SAVEPOINT / XA / LOCK / TRUNCATE / COPY / cursors, and PG additionally doesn't support stored procedures or LISTEN/NOTIFY; forwarded sessions consume writer connection-pool quota (MySQL default 10%, PG default 25%), so a write burst hits that quota first. Cross-Region write forwarding pays one cross-Region RTT per DML (official blog measured +12–15ms per statement between us-east-1 and us-east-2). The reader endpoint is DNS round-robin (TTL 5 seconds), not load balancing — JVMs caching DNS indefinitely by default and connection pools holding long-lived connections both cause "uneven reads" (official blog).
  • Selection implication: write forwarding is a convenience feature for "occasional writes", not a second write entrance — the single-writer nature doesn't change; latency-sensitive read paths should go through the writer endpoint; long-lived connection pools must be configured with connection recycling (ConnMaxLifetime).
  • Sources: AWS official docs; official blog

Deep water 3: failover — database recovers in 30 seconds, the application can be down for minutes (domain: high availability)

  • Mechanism: promote a reader to writer by failover priority tier; shared storage means no data copy; writer endpoint DNS (TTL 5 seconds) switches; vendor-claimed typically under 30 seconds, community-measured 30–60 seconds end to end. Committed transactions survive via the 4/6 quorum; all uncommitted in-flight transactions are lost.
  • At the edge: DNS caching is the #1 killer — JVMs cache DNS 30 seconds to indefinitely by default; without setting networkaddress.cache.ttl the app keeps hitting the old IP; one community benchmark showed a single JVM parameter dropping app recovery from ~5 seconds to ~100ms 社区实测. Clusters with no reader take minutes to fail over (at least 1 reader in production is a hard requirement). RDS Proxy can compress app-side recovery to seconds (AWS internal benchmark: ~3s average vs ~14–24s direct, vendor claim). There are no publicly distinguishable failover-time numbers between MySQL and PG — they must not be used to pick an engine 待验证.
  • Selection implication: Aurora's RTO is essentially a "control-plane switchover"; real RTO depends on client-side reconnection engineering; chaos drills must test client behavior together with the database.
  • Sources: AWS official docs; community tests (re:Post)

Deep water 4: Global Database — RPO must be understood bound to the real-time lag metric (domain: disaster recovery)

  • Mechanism: 1 primary Region + up to 10 secondary Regions (official docs; 5 at launch), storage-layer physical replication, vendor-claimed typical lag <1 second.
  • At the edge: planned switchover can achieve RPO=0 (<30 seconds); unplanned failover loses exactly the actual replication lag at that moment, which must be measured with AuroraGlobalDBRPOLag, not assumed to be 0 (community recommendation: alert when lag >2s sustained for 5 minutes). After a disaster failover, the old primary Region's volume is replaced and must be rebuilt from snapshot (hours) — DR drills must use switchover; using failover for drills introduces unnecessary rebuild and data-loss risk 社区实测. Each attached secondary Region consumes one reader slot on the primary cluster (one secondary = one fewer reader available). The rds.global_db_rpo parameter can back-pressure secondary lag into the primary Region's write path — once on, primary write latency is coupled to secondary health.
  • Selection implication: Global Database is "single-writer multi-reader + Region-level DR", not multi-active; before writing "~1s RPO" into an SLA, look at the P99 lag; cross-Region transfer + replicated I/O are billed separately — budget at least 2× a single Region.
  • Sources: AWS official docs; community runbooks

Deep water 5: I/O billing — Aurora's #1 cost deep water (domain: cost)

  • Mechanism: on the Standard edition, besides compute + storage, read/write I/O is billed separately per million operations (get a quote / check the bill).
  • At the edge: full table scans / missing indexes, or a working set that doesn't fit in memory (a classic trigger: Serverless v2 upper bound set too small) cause read amplification; a real community bill (2026-06): a small database capped at 1.0 ACU had I/O charges at 68%–88% of its total monthly Aurora bill 社区实测. A degraded previously-optimized query can detonate I/O costs too. Investigate via the Aurora:StorageIOUsage line item in Cost Explorer and the CloudWatch VolumeReadIOPs/VolumeWriteIOPs metrics.
  • Selection implication: the first thing after adopting Aurora is a billing alarm on I/O; size memory generously — ACU spend is cheaper than an I/O horror bill; once I/O exceeds ~25% of spend, evaluate switching to I/O-Optimized (but only one switch per 30 days — don't get it wrong).
  • Sources: community bill cases (2026-06, community-tested); AWS official docs

Deep water 6: Serverless v2 — the three gates of "serverless" (domain: cost/operations)

  • Mechanism: 0–256 ACU, 0.5-ACU steps, per-second billing; ~15 seconds to resume from a 0-ACU auto-pause (vendor claim; community-tested ~12–30 seconds after being paused more than 24 hours).
  • At the edge: "pay nothing when idle" has three gates — ① the default 0.5 ACU minimum is a 24×7 floor price; ② storage is still billed while paused; ③ attaching RDS Proxy, enabling logical replication/binlog replication, or being a Global Database primary blocks auto-pause, leaving the instance pinned at 0.5 ACU 社区实测. Scale-up is seconds, scale-down is minutes (jitter protection); new connections queue/time out during resume, and some teams ping on a schedule to keep instances warm and dodge cold starts 社区实测.
  • Selection implication: dev/test/intermittent workloads are cheapest at 0 ACU; online services should set a 2–4 ACU floor to dodge the morning-rush cold start; the "provisioned writer + Serverless v2 reader" mix is a community-validated cost-saving combination.
  • Sources: AWS official docs; AWS Database Blog; community tests

Deep water 7: version lag & upgrade pain — the price of managed is "waiting for AWS releases" (domain: compatibility/versions)

  • Mechanism: Aurora MySQL 3.x minor versions lag community 8.0 by months; Aurora PG major versions lag community by months to over a year (official release calendar + community consensus).
  • At the edge: 2026-05-21 was a turning point — Aurora MySQL 8.4 went GA, aligned with community 8.4.7 with matching version numbers, and AWS committed to major versions within 12 months and minor versions within 3 months 厂商口径; before that, "RDS MySQL has 8.4 but Aurora doesn't" was a recurring re:Post complaint. Major upgrades are the biggest ops pain: MySQL 2→3 prechecks commonly fail on data-dictionary inconsistencies and plans regress after upgrade (optimizer changes, query cache removal, default charset change to utf8mb4); PG upgrades rely on blue/green deployment but hide prerequisites (the source cluster must have no active logical replication slot — undocumented, community-tested, hours of debugging; no DDL during cutover; ANALYZE/REINDEX needed after cutover); in-place upgrades have no rollback.
  • Selection implication: teams chasing the newest features must accept the "wait for the release" rhythm on Aurora — plain RDS usually tracks faster; do major upgrades via blue/green + pre-upgrade precheck item by item, and treat the rollback path (blue/green cutback) as mandatory.
  • Sources: AWS What's New; AWS official docs; re:Post community tests

用户最买账的 5 点

  1. 故障切换快
    • 为什么是真的：共享存储免数据拷贝，提拔 reader + 切 DNS 即可；厂商口径通常 30 秒内，社区实测 30~60 秒端到端，显著快于传统主从重建。
    • 边缘与限度：快的是"数据库恢复"，应用恢复取决于 DNS 缓存与重连工程；无 reader 的集群故障时间拉长到分钟级；配 RDS Proxy 或 Advanced JDBC Wrapper 才能把应用侧也压到秒级。
  2. 运维省心
    • 为什么是真的：OS/引擎打补丁、备份、存储扩容全托管；小版本可自动升级；计算层无状态，实例坏了重建即可。
    • 边缘与限度：省的是"机器运维"，不是"数据库运维"——慢 SQL、索引、参数调优、版本升级规划一件不少；无 SUPER 权限意味着某些救火手段（如直接改系统表、装任意扩展）用不了，救火天花板比自建低。
  3. 读扩展容易
    • 为什么是真的：加 reader 不拷贝数据，分钟级上线，最多 15 个；reader endpoint 自动分发。
    • 边缘与限度：endpoint 是 DNS 轮询不是真负载均衡，长连接池不回收会读不均；PG 的 ReplicaLag 是 page-cache 语义，平稳期之外的延迟解读要小心；写扩展没有——单 writer 是硬天花板，写到头只能上 Limitless（PG only）或分库分表。
  4. Serverless 弹性
    • 为什么是真的：0~256 ACU 按秒计费，扩容连接不断；波动负载和开发环境是真的省。
    • 边缘与限度：见深水区六——地板价、存储费、阻止暂停的四种配置、冷启动；I/O-Optimized 下 ACU 单价更贵，选存储配置要连 ACU 单价一起算。
  5. MySQL / PG 兼容，迁移平滑
    • 为什么是真的：协议兼容，JDBC/ORM/DMS/Debezium 通用；从自建 MySQL/PG 迁过来应用层基本不用改。
    • 边缘与限度：兼容的是"协议与大部分语法"，不是"运维习惯"——MyISAM 表要转 InnoDB、压缩表要解压、keyring/TDE 要改 KMS 卷加密、SUPER 权限要降级、C 扩展/PAM 认证要重做（官方迁移限制清单）；版本滞后意味着社区新特性要等。
  1. Fast failover
    • Why it's real: shared storage means no data copy — promote a reader + flip DNS and you're done; vendor-claimed typically under 30 seconds, community-measured 30–60 seconds end to end, significantly faster than traditional primary-standby rebuilds.
    • Edges & limits: the fast part is "database recovery" — application recovery depends on DNS caching and reconnection engineering; reader-less clusters take minutes; RDS Proxy or the Advanced JDBC Wrapper is needed to compress the app side to seconds too.
  2. Worry-free operations
    • Why it's real: OS/engine patching, backups, storage expansion are all managed; minor versions can auto-upgrade; the stateless compute layer means a dead instance just gets rebuilt.
    • Edges & limits: what's managed is "machine operations", not "database operations" — slow SQL, indexes, parameter tuning, and upgrade planning all remain yours; no SUPER privilege means some firefighting tools (direct system-table edits, arbitrary extensions) are unavailable, so the self-hosted firefighting ceiling is higher.
  3. Easy read scale-out
    • Why it's real: adding a reader copies no data, comes up in minutes, up to 15 of them; the reader endpoint distributes automatically.
    • Edges & limits: the endpoint is DNS round-robin, not true load balancing — pools that never recycle connections read unevenly; PG's ReplicaLag is page-cache semantics, so lag readings outside steady state need care; there is no write scale-out — single writer is a hard ceiling, and once writes top out you either go Limitless (PG only) or shard manually.
  4. Serverless elasticity
    • Why it's real: 0–256 ACU billed per second, scaling without dropping connections; genuinely cheap for bursty workloads and dev environments.
    • Edges & limits: see Deep water 6 — floor price, storage charges, the four pause-blocking configurations, cold starts; ACU unit prices are higher under I/O-Optimized, so storage-config decisions must account for ACU unit pricing together.
  5. MySQL / PG compatibility, smooth migration
    • Why it's real: protocol compatibility, JDBC/ORM/DMS/Debezium all work; migrating from self-hosted MySQL/PG barely touches the application layer.
    • Edges & limits: what's compatible is "protocol and most syntax", not "ops habits" — MyISAM tables must become InnoDB, compressed tables must be uncompressed, keyring/TDE becomes KMS volume encryption, SUPER privileges must be downgraded, C extensions/PAM authentication must be redone (official migration limitation list); version lag means waiting for community features.

判决

  • 适合谁：已在 AWS 上的团队；不想运维数据库、愿意为托管付溢价的团队；读多写少、需要快速加读副本的业务；负载波动大/间歇性的业务（Serverless v2）；需要跨 Region 读就近 + Region 级 DR 的全球化业务（Global Database）；MySQL/PG 协议迁移上云。
  • 不适合谁：预算敏感的小库（同等规格 RDS 或自建更便宜，Aurora 存储层开销在小稳负载上不划算）；写密集到单 writer 成为瓶颈且不愿接受 Limitless 分片改造成本的业务；需要最新社区 MySQL/PG 特性"第一时间"上线的团队；重度依赖 PG 冷门扩展、SUPER 权限、自建插件的团队；多云/信创/出 AWS 部署要求。
  • 迁移成本：MySQL → 低（协议兼容，DMS/快照/XtraBackup 工具链成熟，注意 MyISAM/压缩表/TDE/keyring/SUPER 改造项）；PostgreSQL → 低（协议兼容，注意扩展白名单与 rds_superuser 降级）；Oracle → 高（无 Oracle 兼容模式，Babelfish 仅 PG 且 Limitless 不支持，走应用层改造或选 EDB 等）。
  • Good fit for: teams already on AWS; teams that don't want to operate databases and will pay a premium for managed; read-heavy workloads needing fast reader additions; bursty/intermittent workloads (Serverless v2); globalized businesses needing near-Region reads + Region-level DR (Global Database); MySQL/PG protocol migrations to the cloud.
  • Poor fit for: budget-sensitive small databases (RDS or self-hosted is cheaper at the same spec — Aurora's storage-layer overhead doesn't pay off on small steady workloads); write-heavy businesses hitting the single-writer ceiling that won't accept Limitless's sharding rework cost; teams needing community MySQL/PG features "day one"; teams heavily dependent on obscure PG extensions, SUPER privileges, or self-built plugins; multi-cloud / xìnchuàng (IT localization) / must-run-outside-AWS requirements.
  • Migration cost: MySQL → low (protocol-compatible, mature DMS/snapshot/XtraBackup tooling; watch the MyISAM/compressed-table/TDE/keyring/SUPER rework items); PostgreSQL → low (protocol-compatible; watch the extension whitelist and rds_superuser downgrade); Oracle → high (no Oracle compatibility mode, Babelfish is PG-only and unsupported on Limitless — go the application-rework route or pick EDB etc.).
