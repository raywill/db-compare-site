TiDB

关系型 OLTP #分布式 #MySQL兼容 #HTAP #存算分离 #开源 #云原生 #Raft

PingCAP 开源的分布式 NewSQL 数据库——"云原生的 MySQL 扩展方案"：让 MySQL 技术栈的团队不做分库分表、不搭 ETL，就拿到水平扩展和实时 HTAP，但要为架构的固定成本和运维复杂度付费。

PingCAP's open-source distributed NewSQL database — the "cloud-native MySQL scaling solution": it gives MySQL-based teams horizontal scaling and real-time HTAP without sharding or building ETL pipelines, but you pay for it in fixed architectural cost and operational complexity.

2 TLS / 传输加密 有

7 连接模型 有

8 事务与隔离级别 有

9 复制与一致性 有

有——Multi-Raft（每 Region 一个 Raft Group），默认 3 副本强一致；官方口径 RPO=0、RTO≤30 秒（故障自动切换，非备份恢复——厂商口径）。证据：官方口径。

47 热点数据更新能力 有

有（悲观锁内核重试加公平锁，同行串行）。

  • 并发控制原语：TiKV 层 latch 本地串行加分布式行锁；悲观事务模式（官方推荐的高冲突场景选择）下写冲突直接在内核加悲观锁串行，冲突语句由 TiDB 按最新数据内部重试（pessimistic-txn.max-retry-count 限次），应用只在超限时才看到错误 官方文档。
  • 公平锁：tidb_pessimistic_txn_fair_locking（v7.0 引入，新集群默认开启）解决同一行高并发下后到事务被持续饿死的问题，代价是冲突事务的平均延迟上升 官方文档。
  • 内存悲观锁（v6.0 引入）：悲观锁只存 Region leader 内存、不经 Raft 复制落盘，大幅降低加锁开销、提升悲观事务吞吐 官方文档。
  • 乐观模式：写冲突在 prewrite 阶段才发现，由 TiDB 内核按 tidb_retry_limit 自动重试整个事务，重试责任在内核而非驱动或应用 官方文档。
  • 内置热点缓解：PD 的 hot Region 调度可把热点 Region 的 leader 与副本在节点间打散；但单行热点仍卡在单个 Region leader 的 latch 串行上，Region 级打散解决不了单 key 瓶颈 官方文档。
  • 应用层模式：官方语境中的"热点"主要指 Region 写入热点，官方解法是在建表时用 SHARD_ROW_ID_BITS 预打散行 ID、把写入分散到多个 Region，配合 PD 的 hot Region 调度再平衡；严重冲突时还需缩小事务范围或拆分热点 key；代价是建模改造成本 官方文档。

1 Data-at-rest encryption / TDE Supported

Supported (must be enabled per component) — TiKV encryption at rest (v4.0+, AES-CTR on data files, master key via AWS KMS or a local file, data keys auto-rotated); TiFlash / PD / BR each have their own encryption support — "full coverage" requires per-component configuration. Evidence: official encryption-at-rest docs (v7.5).

2 TLS / transport encryption Supported

Supported — TLS. Evidence: official docs.

3 Auditing Partially supported

Partially supported — TiDB Server's built-in audit log (enable-audit switch, JSON-format logging of SQL/login events) exists per community deployment practices; no reliable official evidence found for fine-grained compliance auditing capabilities and the TiDB Cloud auditing boundary — this round does not conclude "full support." Evidence: community consensus (CSDN deployment practices), official docs pending re-verification.

4 Authentication & authorization Supported

47 Hotspot update handling Supported

Supported(Kernel-level retry of pessimistic locks plus fair locking; same-row serialization).

  • Locking primitive: local serialization via TiKV latches plus distributed row locks; in pessimistic transaction mode (the official choice for high-conflict workloads) write conflicts take pessimistic locks and serialize inside the kernel, and conflicting statements are retried internally by TiDB against the latest data (capped by pessimistic-txn.max-retry-count) — the application only sees an error past that limit 官方文档.
  • Fair locking: tidb_pessimistic_txn_fair_locking (introduced in v7.0, on by default in new clusters) fixes starvation of later transactions under same-row concurrency, at the cost of higher average latency for conflicting transactions 官方文档.
  • In-memory pessimistic locks (introduced in v6.0): pessimistic locks live only in the Region leader's memory, never persisted via Raft, greatly lowering lock-acquisition overhead and raising pessimistic-transaction throughput 官方文档.
  • Optimistic mode: write conflicts surface only at prewrite and are retried as whole transactions by the TiDB kernel per tidb_retry_limit — retry responsibility sits with the kernel, not the driver or the application 官方文档.
  • Built-in hotspot mitigation: PD's hot-Region scheduler disperses hot Regions' leaders and replicas across nodes; but a single-row hotspot still stalls on latch serialization at one Region leader — Region-level dispersal cannot fix a single-key bottleneck 官方文档.
  • Application patterns: in the official docs "hotspot" mainly means Region write hotspots, and the official remedy is SHARD_ROW_ID_BITS to pre-shard row IDs at table creation, spreading writes across Regions, complemented by PD's hot-Region rescheduling; severe conflicts still call for shrinking transaction scope or splitting hot keys; the cost is remodeling effort 官方文档.

招牌能力

写法要求：每个特性 = 它是什么 + 为什么是真本事 + 推到边缘会发生什么。

  1. 存算分离：无状态 SQL 层秒级扩容 真本事：TiDB Server 完全无状态，只做解析、优化、执行；计算和存储可独立扩缩——读压力大只加 TiDB 节点，写压力大只加 TiKV。这是与 OceanBase"一体化"架构最根本的分岔：云原生弹性场景下扩计算不需要搬数据。 边缘真相：秒级扩的是计算，存储扩容（加 TiKV）要靠 PD 做 Region 迁移重分布，吃 IO 和网络，赶上业务高峰等于"飞行中换引擎"；且 Region 迁移期间热点 Region 的 leader 切换会带来延迟毛刺。扩容快的是"加机器"，不是"数据就位"。
  2. TiFlash 实时 HTAP：行列双引擎 真本事：TiKV 行存跑 OLTP，TiFlash 列存跑 OLAP，通过 Raft Learner 实时复制同一份数据，优化器自动选路——同一套 SQL 接口同时服务交易和分析，省掉"T+1 ETL 到数仓"整条链路。得物等公司的典型用法：MySQL 分库分表做点查，TiDB 扛非分片查询和复杂分析。 边缘真相：见深水区四——Learner 复制是异步的，"强一致读"读到的是"某个已提交版本"而非"最新"；写入洪峰下 learner 落后，HTAP 查询的延迟直接放大；优化器选路可能选错引擎。HTAP 是 T+秒级，不是 T+0。
  3. Percolator 分布式事务：跨节点 ACID 真本事：基于 Google Percolator 论文的两阶段提交，跨 Region/跨节点事务原生 ACID，不需要应用层自己拼"最终一致"。这是它相对 MySQL 分库分表方案（跨分片无分布式事务）的代际优势。 边缘真相：见深水区二——2PC 的税是按"跨越的 Region 数"交的；单事务默认 100MB 上限、单行 6MB 上限是写死在架构里的（v6.5+ 改为会话内存配额，v8.0 bulk DML 绕过）；热点行上的分布式事务 = 锁等待放大器。事务模型设计不好，分布式事务比分库分表更慢。
  4. MySQL 协议兼容 + 迁移工具链 真本事：协议层兼容 MySQL 5.7，驱动、ORM、Navicat/DBeaver 即插即用；DM 做 MySQL→TiDB 全量+增量迁移，TiCDC 做反向/异构同步，Lightning/BR 管大批量导入导出。MySQL 团队迁移的心智成本是国产分布式库里最低的。 边缘真相：见深水区七——"95% 兼容"剩下的是存储过程、触发器、事件、全文索引、GIS、XA、CTAS 等（官方兼容性文档逐项列出不支持）；AUTO_INCREMENT 的语义与 MySQL 有微妙差异（批量分配、跨 TiDB 实例不保证单调），直接照搬 MySQL schema 会撞上写入热点。兼容的是"协议和常用语法"，不是"行为一致"。
  5. 全开源与全球化生态 真本事：Apache 2.0，内核 GitHub 全公开，TiKV 是 CNCF 毕业项目；DB-Engines 全球排名国产前列；中英文档、AskTUG 社区、TiDB Dashboard 可观测性工具链完整。出海、多云、不想被单一厂商绑定的团队，这是相对 OB/TDSQL 的结构性优势。 边缘真相：开源的是代码，不是运维能力——深水区问题（热点、TSO 瓶颈、TiCDC 延迟）最终都要靠读源码或买原厂支持解决；官方路线图脚注承认"不同订阅版本功能可能有所不同"，生产级 SLA 还是要付费。以及：社区版用户遇到内核级 bug，修得再快也要自己升级——升级本身就是个深水区（见吐槽清单）。

Writing rule: each feature = what it is + why it's genuinely good + what happens when pushed to the edge.

  1. Disaggregated compute and storage: second-level scaling of the stateless SQL layer The real strength: TiDB Server is fully stateless — it only parses, optimizes, and executes; compute and storage scale independently — add TiDB nodes when reads are heavy, TiKV nodes when writes are heavy. This is the most fundamental fork from OceanBase's "unified" architecture: scaling compute in cloud-native elastic scenarios requires no data movement. Edge truth: what's second-level is compute; storage scale-out (adding TiKV) relies on PD to migrate and redistribute Regions, consuming IO and network — doing it during peak hours is like "changing the engine mid-flight"; and leader switches on hot Regions during migration cause latency spikes. What's fast is "adding machines," not "data being in place".
  2. TiFlash real-time HTAP: dual row/column engines The real strength: TiKV's row store runs OLTP, TiFlash's columnar store runs OLAP, with the same data replicated in real time via Raft Learner and the optimizer routing automatically — one SQL interface serves both transactions and analytics, eliminating the entire "T+1 ETL to the warehouse" pipeline. The typical pattern at companies like Dewu (得物): sharded MySQL for point lookups, TiDB for non-sharded queries and complex analytics. Edge truth: see Deep Waters #4 — Learner replication is async; a "strongly consistent read" returns "some committed version," not "the latest"; under write bursts the learner lags and HTAP query latency blows up directly; the optimizer's routing can pick the wrong engine. HTAP is T+seconds, not T+0.
  3. Percolator distributed transactions: cross-node ACID The real strength: two-phase commit based on the Google Percolator paper gives natively ACID cross-Region/cross-node transactions — no need for the application layer to cobble together "eventual consistency." That's a generational advantage over MySQL sharding (which has no distributed transactions across shards). Edge truth: see Deep Waters #2 — the 2PC tax is paid per Region crossed; the 100MB default per-transaction limit and 6MB per-row limit are hard-wired into the architecture (v6.5+ switched to session memory quotas; v8.0 bulk DML bypasses it); distributed transactions on hot rows are lock-wait amplifiers. With a poorly designed transaction model, distributed transactions are slower than sharding.
  4. MySQL protocol compatibility + migration toolchain The real strength: protocol-level compatibility with MySQL 5.7 — drivers, ORMs, Navicat/DBeaver are plug-and-play; DM handles MySQL→TiDB full + incremental migration, TiCDC handles reverse/heterogeneous replication, Lightning/BR handle bulk import/export. The cognitive cost of migration for MySQL teams is the lowest among Chinese distributed databases. Edge truth: see Deep Waters #7 — the remainder of "95% compatibility" is stored procedures, triggers, events, full-text indexes, GIS, XA, CTAS, etc. (each listed as unsupported in the official compatibility docs); AUTO_INCREMENT semantics differ subtly from MySQL (batch allocation; not guaranteed monotonic across TiDB instances) — copying a MySQL schema verbatim runs straight into write hotspots. What's compatible is "the protocol and common syntax," not "behavioral parity."
  5. Fully open source with a global ecosystem The real strength: Apache 2.0, the kernel fully public on GitHub, TiKV a CNCF graduated project; top-ranked among Chinese databases globally on DB-Engines; complete Chinese/English docs, AskTUG community, and TiDB Dashboard observability toolchain. For teams expanding overseas, going multi-cloud, or unwilling to be locked into a single vendor, that's a structural advantage over OB/TDSQL. Edge truth: what's open-sourced is the code, not the operational capability — deep-waters problems (hotspots, TSO bottlenecks, TiCDC lag) ultimately require reading source code or buying vendor support; the official roadmap footnote admits "features may vary across subscription tiers," so production-grade SLA still costs money. And: when community-edition users hit a kernel-level bug, no matter how fast it's fixed, they must upgrade themselves — and upgrading is itself a deep water (see the complaint list).

客户最爱

内核 AUTO_RANDOM / SHARD_ROW_ID_BITS —— 热点打散，迁移第一课

一句话
自增主键在 TiDB 里会把全集群的写压到单个 Region、退化为单机写——AUTO_RANDOM 是官方给的打散机制，也是 MySQL 迁移者最普遍的坑、迁移 checklist 第一项。
Auto-increment primary keys in TiDB crush all cluster writes onto a single Region, degrading to single-node writes — AUTO_RANDOM is the official scattering mechanism and the most common pitfall for MySQL migrants, item one on the migration checklist.
窄场景
从 MySQL 迁过来的高并发写入 workload（订单、流水、秒杀）；主键是自增 ID 或时间戳单调递增的表。
High-concurrency write workloads migrated from MySQL (orders, ledgers, flash sales); tables with auto-increment IDs or monotonically increasing timestamp primary keys.
机制
TiDB 按 key range 把数据切成 Region 分散到 TiKV 节点。自增主键的新行 key 单调递增，永远落在最末一个 Region——整个集群的写吞吐退化为单个 TiKV 的写吞吐。AUTO_RANDOM 在事务提交时为键分配随机分片位，把插入均匀打散到各 Region；SHARD_ROW_ID_BITS 对隐式 rowid 表起同样作用。代价是主键不再单调，依赖 ID 单调性的业务逻辑要改。
TiDB splits data into Regions by key range across TiKV nodes. With auto-increment keys, new rows' keys increase monotonically and always land in the last Region — the whole cluster's write throughput degrades to a single TiKV's write throughput. AUTO_RANDOM assigns random shard bits to keys at transaction commit, scattering inserts evenly across Regions; SHARD_ROW_ID_BITS does the same for implicit-rowid tables. The cost: keys are no longer monotonic, so business logic depending on ID monotonicity must change.
生产验证
sql-lab 社区案例：促销期单台 TiKV CPU 100%、其余节点空闲，根因是自增主键热点，改为 AUTO_RANDOM 后打散解决——完整的"现象→根因→解法"生产记录（）。
A sql-lab community case: during a sale, one TiKV sat at 100% CPU while others idled — root cause was an auto-increment hotspot, fixed by switching to AUTO_RANDOM — a complete "symptom → root cause → fix" production record ().
竞品差距
CockroachDB 默认推荐 UUID 主键（随机），坑相对浅但用户仍需显式设计；YugabyteDB 默认 hash 分片打散，此坑较少；MySQL 单机无分片概念，迁移者带着"自增主键天经地义"的习惯过来。这是"MySQL 兼容"承诺下藏得最深的习惯税——兼容的是协议，不兼容的是单机时代的心智。
CockroachDB recommends UUID primary keys by default (random) — the pitfall is shallower but still needs explicit design; YugabyteDB shards by hash by default, so the pitfall is rarer; MySQL is single-node with no sharding concept, so migrants arrive with the "auto-increment is obviously right" habit. This is the deepest-hidden habit tax under the "MySQL compatible" promise — what's compatible is the protocol, not the single-node-era mindset.

内核 TiFlash 列存 MPP —— 真 HTAP

一句话
同一集群内行存（TiKV）与列存（TiFlash）物理隔离、Raft Learner 异步同步、优化器按代价自动路由——TP 与 AP 互不干扰的真 HTAP。
Row storage (TiKV) and columnar storage (TiFlash) are physically isolated inside one cluster, synced asynchronously via Raft Learner, with the optimizer routing by cost — real HTAP where TP and AP never fight.
窄场景
实时风控、运营看板、"交易库上的实时报表"——需要对分钟级新鲜数据做分析查询，但不能接受 ETL 到数仓的小时级延迟，也不想再运维一套 ClickHouse。
Real-time risk control, ops dashboards, "real-time reports on the trading database" — analytics over minute-fresh data without the hour-scale latency of ETL into a warehouse, and without operating a second ClickHouse.
机制
TiFlash 是独立的列存节点（与 TiKV 物理隔离、资源不争抢），通过 Raft Learner 机制异步复制行存数据并转为列式存储，延迟通常在秒到分钟级。查询时优化器按代价模型自动选择：点查/短事务走 TiKV 行存，大扫描/聚合下推到 TiFlash 做 MPP 并行。用户侧只写 SQL，不关心数据在哪份副本上。这是"真 HTAP"与"内存加速器"路线的区别：AlloyDB 的列存是存储层内存加速，TiDB 是独立 MPP 引擎。
TiFlash is an independent columnar node (physically isolated from TiKV, no resource contention) that asynchronously replicates row data via Raft Learner and converts it to columnar storage, typically seconds to minutes behind. At query time the optimizer picks by cost model: point reads/short transactions go to TiKV rows, big scans/aggregations are pushed down to TiFlash's MPP parallelism. Users just write SQL, never caring which copy holds the data. This is the difference between "real HTAP" and the "in-memory accelerator" route: AlloyDB's columnar store is a storage-layer memory accelerator, TiDB's is an independent MPP engine.
生产验证

For "one cluster, physical isolation, optimizer auto-routing" HTAP in open-source OLTP, TiDB is the most complete.

深水区

以下每条 = 机制 + 推到边缘会发生什么 + 选型含义。证据类型已标注。

深水区一：TSO——"免费"的全局时钟其实不免费

  • 机制：PD 的 TSO 服务分配全局单调递增时间戳（physical_ms << logical_bits | logical_counter）；每笔事务的 start_ts/commit_ts 都要找 PD 拿；TiDB 客户端用 TSFuture 异步批量预取，不在每次读写热路径上实时阻塞。
  • 推到边缘：
    • 官方调优文档承认：高频小事务场景下 TSO 会成为瓶颈——实测案例中 TSO wait 占 execute 时间超过 1/4（read-committed 隔离级别下每条语句都要取 TSO；v6.0 起 tidb_rc_read_check_ts 减少取 TSO 次数）。
    • 官方给出的缓解手段本身就是"降级"：tidb_low_resolution_tso（读缓存时间戳，可能读到几秒前的旧数据）、把小事务合并、tidb_tso_client_rpc_mode=PARALLEL/PARALLEL-FAST（v8.4+，用 2~4 倍 RPC 换延迟）。
    • PD 高可用靠内嵌 etcd 3 节点 Raft，leader 选举期间（约 3 秒，社区笔记口径）授时不可用；TiDB 拿不到 TSO 报 9001 PD server timeout（TiDB 后台 worker 100 秒拿不到 safepoint 即报错）。
    • 跨机房部署时 TSO RPC 延迟直接进账：官方实例中同机房 TSO wait 约 206µs，跨机房（同地区不同 AZ）涨到 3.12ms。
    • 官方路线图把"PD 路由功能微服务化（无状态、避免 PD 成为集群资源瓶颈）"列为未来方向——官方自己承认 PD 有成为瓶颈的风险。
  • 选型含义：POC 必须压"高频小事务"模型并看 Grafana 的 PD TSO Wait/RPC 面板；跨 AZ/跨机房部署要把 TSO 延迟算进 P99 预算；低精度 TSO 是用一致性换延迟的显式 trade-off，不是免费优化。
  • 来源：官方文档（performance-tuning-config.md、performance-tuning-methods.md、error-codes.md、tidb-roadmap.md）；社区共识（MVCC/TSO 技术解析）。

深水区二：Percolator 2PC 的税——按跨越的 Region 数交

  • 机制：乐观事务（默认）提交时做两阶段：prewrite 给所有 key 写 lock（带 start_ts），再拿 commit_ts 写主 key 提交、异步清其他 key 的锁；悲观事务（tidb_txn_mode='pessimistic'）写入时先加锁。
  • 推到边缘：
    • 硬性天花板（官方 transaction-overview.md）：单行 ≤6MB；单个事务默认 ≤100MB（txn-total-size-limit，最大可配 1TB），且事务内存放大可达 2~3 倍；v6.5 起改为计入会话内存由 tidb_mem_quota_query 控制；v8.0 起 tidb_dml_type="bulk" 的 DML 不受该限制——但这是"绕过"不是"消除"。
    • 超限直接报错：8004 事务过大、8005 Write Conflict, txnStartTS is stale；悲观事务下 SELECT FOR UPDATE 遇到写冲突不重试直接 8002 回滚，应用必须自己重做整个事务。
    • 单个事务持锁最长 max-txn-ttl 默认 1 小时，超时锁可能被其他事务清掉导致提交失败；长事务还会卡住 GC（默认 10 分钟）导致 MVCC 旧版本堆积、空间膨胀。
    • 热点行 + 分布式事务 = 灾难组合：秒杀扣库存这类场景，乐观事务冲突重试浪费整事务工作量，必须切悲观事务；而悲观锁等待又会拖慢整条链路。
  • 选型含义：ETL/批量写入必须拆批（官方 FAQ 原话：大事务会"卡住下面的 Raft 复制流程"）；POC 必须用真实事务模型（含热点行）压测，不要只测单表点查；从 MySQL 迁过来的"一个事务几十万行"写法是头号踩坑位。
  • 来源：官方文档（transaction-overview.md、error-codes.md、tidb-configuration-file.md、旧版 FAQ）。

深水区三：Region 热点——schema 写下的第一行就决定了上限

  • 机制：数据按 key range 切成 Region（v8.5 起默认 256MiB），Region 是 Raft 复制和调度的基本单位；AUTO_INCREMENT 递增 ID 让所有新写入打到"最后一个 Region"——尾部热点。
  • 推到边缘：
    • 官方文档（auto-increment.md）明确警告："使用 AUTO_INCREMENT 可能会给生产环境带热点问题，因此推荐使用 AUTO_RANDOM 代替"。AUTO_INCREMENT 在 TiDB 里是各 TiDB Server 批量缓存分配（默认 3 万一段），跨实例不保证单调——和 MySQL 的语义本来就不一样。
    • 打散手段都有代价：SHARD_ROW_ID_BITS 只对隐式 rowid 表有效，开太大 RPC 请求数放大、CPU/网络开销上升（官方文档原话）；AUTO_RANDOM（5bit 随机 + 59bit 自增）解决写入热点但 ID 不连续、不再"自增"；时间序主键（created_at 前缀）同样是尾部热点。
    • 社区实测（MySQL vs TiDB POC，2026-09）：单机 read-heavy 场景 MySQL TPS 领先 TiDB 58%~81%，结论"单机 Read-heavy：MySQL 压倒性领先；TiDB 为架构固定成本无解"——每次查询都要走 RPC + 多副本 + RocksDB，这是架构税，不是调优能抹掉的。
    • v8.5 把默认 Region 从 96MiB 提到 256MiB（官方性能报告：OLTP 插入 +27%、Analyze +45%——厂商口径，仅作架构演进参考，不作为判决依据），本质是"用更大的调度粒度换更低的管理成本"；但对小表多查询型业务，大 Region 反而可能聚合热点（官方博客建议这类场景调回小 Region）。
  • 选型含义：主键设计是 TiDB schema 设计的第一优先级，上线后再拆热点等于重构；POC 必须用"真实 ID 生成策略 + 真实写入分布"压测；数据量 <100GB 且读多写少的业务，单机 MySQL 可能更快更便宜——这是社区共识的"不适合"画像。
  • 来源：官方文档（auto-increment.md、troubleshoot-hot-spot-issues.md 引用）、官方 v8.5 性能解读、社区实测（MySQL vs TiDB POC）。

深水区四：TiFlash 的"实时"——Learner 复制的异步真相

  • 机制：TiFlash 是 TiKV 的只读副本，通过 Raft Learner 协议异步复制数据；读 TiFlash 时按 Raft log index 做一致性校验——只返回"已同步到的已提交版本"，保证"读到的是某个一致快照"，不保证"读到最新"。
  • 推到边缘：
    • 写入洪峰下 learner 落后是常态：TiFlash 读到的数据版本滞后于 TiKV，HTAP 查询的"实时性"退化为 T+秒甚至 T+分钟，而业务以为自己在做"实时分析"。
    • 优化器自动选路（走 TiKV 还是 TiFlash）可能选错：统计信息过期、代价估算偏差会导致 OLAP 查询走到 TiKV 全表扫，或点查走到 TiFlash；tidb_enforce_mpp 可强制但那是把优化器当摆设。
    • TiFlash 只读：任何写入都要先经过 TiKV，写放大路径上 TiFlash 只是"观众"；TiFlash 节点故障不影响 OLTP，但 HTAP 查询直接降级。
    • 资源隔离是"建议"不是"默认"：TiFlash 与 TiKV 混部时，大分析查询的 CPU/IO 会挤占 OLTP——官方建议独立部署 TiFlash 节点，等于 HTAP 要多付一套机器钱。
  • 选型含义：把 TiFlash 理解为"延迟秒级的实时数仓"，而不是"零延迟"；HTAP 场景 POC 必须同时压 OLTP 写入和 OLAP 查询，看 learner lag 指标；纯 OLAP 重查询场景，ClickHouse/Doris 的性价比通常更高社区共识。
  • 来源：官方架构（TiFlash Raft Learner 机制）、社区技术解析（TiFlash 一致性读取原理）；"混部资源争抢"为社区共识。

深水区五：写洪峰 → RocksDB write stall → 流控拒绝写入

  • 机制：每个 TiKV 有两个 RocksDB 实例（data/raft 存 Raft 日志，data/db 存真实数据）；写入先过 scheduler 做事务一致性检查，再进 raftstore（Store 线程复制 → Apply 线程落盘）。
  • 推到边缘：
    • 当 RocksDB compaction 跟不上写入（pending compaction bytes 堆积），触发 write stall——官方 troubleshooting 文档：v5.2 之前直接给客户端返回 ServerIsBusy 拒绝所有写（QPS 断崖）；v5.2 起改为流控机制：先延迟写请求，soft-pending-compaction-bytes-limit（默认 192GiB）开始拒绝部分写，hard-pending-compaction-bytes-limit（默认 1024GiB）拒绝全部写。
    • 这是 TiDB 版的"4030"：写入越猛，欠 compaction 的债越重，最终以"拒绝写入"的形式还。SATA SSD 上更容易触发（官方建议：磁盘吞吐到顶时要么换 NVMe，要么用更高压缩比算法拿 CPU 换磁盘）。
    • 跨机房再叠一层：Raft 多数派确认，写入要同步到至少 2 个数据中心；官方旧 FAQ 建议跨中心延迟 5ms 以下；同城双中心（<3ms）可双活承担写入，异地（20ms 专线）只能做灾备——写延迟与物理距离强相关，这是 Raft 写在架构里的税。
    • 社区实测（跨 IDC+GCP POC）：跨区后 TPS 下降，但"永远 0 Error"、无死锁无写冲突——乐观锁模型跨区是"降速不降正确性"，和 MySQL 主从跨区的"冲突靠人肉"形成对比。
  • 选型含义：写密集型业务必须做 compaction/流控指标监控（pending compaction bytes）和写入限流预案；磁盘选型直接决定写上限，SATA 在 TiDB 上是"能用但随时可能交税"；多活架构先看专线延迟再谈方案。
  • 来源：官方文档（tidb-troubleshooting-map.md 流控章节、performance-tuning-methods.md 写路径、旧版 FAQ 多活）、社区实测。

深水区六：DDL、GC 与升级——运维的三连坑

  • 机制：DDL 在线异步变更（多状态流转）；GC 默认每 10 分钟清理 MVCC 旧版本；升级 via TiUP 滚动重启。
  • 推到边缘：
    • DDL 历史上串行执行（单 DDL owner）；v6.2 起引入并发 DDL 框架，但 v6.2→v6.5 升级时 KV 队列改表队列曾导致升级卡住（官方升级 FAQ 有专门章节：插件加载、kill -9、DDL owner 变更都可能卡住升级）。
    • v6.3 引入元数据锁、v6.5 默认开启：有未提交事务的表上做 DDL 会被阻塞——"在线 DDL"不等于"随时 DDL"，业务高峰期的 ADD INDEX 可能排队到天荒地老。
    • information schema is changed（错误 8027 类场景）：TiDB Server 的 schema 版本落后时 SQL 直接报错，根因常是 TiDB 与 PD 间的网络抖动。
    • 长事务/卡住的 TiCDC 会拖住 GC safepoint：MVCC 旧版本删不掉，磁盘空间持续膨胀——"删了数据空间不释放"的经典困惑，根因往往是 GC 被某个慢消费者卡住。
    • 社区个案（得物升级实践，v5.3.3→v7.5.x）：v4.x 时代 TiKV 节点运行超过 2 年会自动重启；v6.5 以前 TiCDC 经常延迟/OOM；升级后 v7.5 优化器一度倾向全表扫描（215 亿行表走全表扫 60 秒超时，绑索引 0.4 秒），靠 tidb_opt_prefer_range_scan / SPM 绑定解决——"升级≠变快，执行计划可能先变差"。
    • 原地升级不支持回退、大版本跨度要递增升级且抖动翻倍；得物最终全部采用"迁移升级"（搭新集群 + TiCDC 同步），代价是双倍机器成本。
  • 选型含义：DDL 只在低峰做、做之前查长事务；升级先在测试环境完整演练、准备 SPM/绑定预案；GC 监控（safepoint 推进）是日常巡检项；把"升级窗口"写进年度运维预算。
  • 来源：官方文档（upgrade-tidb-using-tiup.md 升级 FAQ、tidb-troubleshooting-map.md DDL 章节、error-codes.md）；社区实测（得物升级实践，2025 年底）。

深水区七：MySQL 兼容的深水区——"95% 兼容"的剩下 5%

  • 官方兼容性文档（mysql-compatibility.md）明确列出不支持：存储过程/函数、触发器、事件、自定义函数、全文索引、GIS/空间类型、XA 语法、CREATE TABLE AS SELECT、SKIP LOCKED、降序索引、CHECK/CHECKSUM/REPAIR/OPTIMIZE TABLE、HANDLER、列级权限、LATERAL 派生表执行。
  • 推到边缘：
    • 传统系统（ERP/财务/电信计费）恰恰是存储过程+触发器+事件的重度用户——这类系统迁 TiDB 不是"改配置"而是"重写业务逻辑"，迁移成本从"低"直接跳到"高"。
    • 外键约束长期是实验特性（v6.x 引入），成熟度不及 MySQL——依赖外键做数据完整性的业务要重新评估。
    • 字符集仅支持 ascii/latin1/binary/utf8/utf8mb4/gbk/gb18030；lower_case_table_names 等行为有差异；SELECT ... FOR UPDATE 是乐观语义（冲突在提交时检查）而非 MySQL 的加锁语义——"语法一样，语义不同"是最贵的坑。
    • 反例：互联网业务（无存储过程、主键多为自增/雪花 ID）迁移确实平滑——兼容性的"坑度"完全取决于业务对 MySQL 偏门特性的依赖度。
  • 选型含义：迁移评估第一步是扫一遍"用了哪些 MySQL 独有特性"，而不是跑通几条 CRUD 就宣布兼容；POC 必须包含存储过程/触发器/全文检索等"有无"清单。
  • 来源：官方文档（mysql-compatibility.md）；社区共识（迁移指南、AskTUG 高频问题）。

Deep Waters #1: TSO — the "free" global clock isn't free

  • Mechanism: PD's TSO service hands out globally monotonic timestamps (physical_ms << logical_bits | logical_counter); every transaction's start_ts/commit_ts must be fetched from PD; the TiDB client uses TSFuture async batch prefetching so it doesn't block the read/write hot path in real time.
  • Pushed to the edge:
    • The official tuning docs admit: TSO becomes the bottleneck under high-frequency small transactions — in a measured case, TSO wait exceeded 1/4 of execute time (under read-committed isolation every statement fetches a TSO; since v6.0 tidb_rc_read_check_ts reduces TSO fetches).
    • The official mitigations are themselves "downgrades": tidb_low_resolution_tso (reads cached timestamps — may read seconds-old stale data), merging small transactions, tidb_tso_client_rpc_mode=PARALLEL/PARALLEL-FAST (v8.4+, trading 2–4x RPCs for lower latency).
    • PD high availability relies on an embedded etcd 3-node Raft; timestamping is unavailable during leader elections (~3 seconds, per community notes 社区共识); when TiDB can't get a TSO it raises 9001 PD server timeout (the TiDB background worker errors if it can't obtain a safepoint within 100 seconds).
    • Cross-datacenter deployments put TSO RPC latency straight onto the bill: in an official example, same-datacenter TSO wait was ~206µs, rising to 3.12ms across datacenters (different AZs in the same region).
    • The official roadmap lists "microservicizing PD's routing functions (stateless, avoiding PD becoming a cluster resource bottleneck)" as a future direction — the vendor itself admits PD risks becoming a bottleneck.
  • What it means for your decision: POCs must stress the "high-frequency small transaction" model and watch Grafana's PD TSO Wait/RPC dashboards; cross-AZ/cross-datacenter deployments must budget TSO latency into P99; low-resolution TSO is an explicit consistency-for-latency trade-off, not a free optimization.
  • Sources: official docs (performance-tuning-config.md, performance-tuning-methods.md, error-codes.md, tidb-roadmap.md); community consensus (MVCC/TSO technical analyses).

Deep Waters #2: the Percolator 2PC tax — paid per Region crossed

  • Mechanism: optimistic transactions (the default) do two phases at commit: prewrite writes locks on all keys (carrying start_ts), then fetch commit_ts to commit the primary key and asynchronously clear locks on the other keys; pessimistic transactions (tidb_txn_mode='pessimistic') lock on write.
  • Pushed to the edge:
    • Hard ceilings (official transaction-overview.md): 6MB max per row; 100MB default per transaction (txn-total-size-limit, configurable up to 1TB), with transaction memory amplification up to 2–3x; since v6.5 it's counted toward session memory governed by tidb_mem_quota_query; since v8.0, DML with tidb_dml_type="bulk" is exempt — but that's a "bypass," not an "elimination."
    • Exceeding the limit errors out directly: 8004 transaction too large, 8005 Write Conflict, txnStartTS is stale; under pessimistic transactions, SELECT FOR UPDATE hitting a write conflict doesn't retry — it rolls back with 8002 directly, and the application must redo the entire transaction itself.
    • A single transaction holds locks up to max-txn-ttl (default 1 hour); expired locks may be cleared by other transactions, failing the commit; long transactions also stall GC (default 10 minutes), causing MVCC old versions to pile up and space to bloat.
    • Hot rows + distributed transactions = a disastrous combination: in flash-sale inventory-deduction scenarios, optimistic-transaction conflict retries waste the whole transaction's work — you must switch to pessimistic transactions; but pessimistic lock waits then slow the whole pipeline.
  • What it means for your decision: ETL/bulk writes must be split into batches (official FAQ, verbatim: large transactions "stall the Raft replication pipeline underneath"); POCs must stress-test with realistic transaction models (including hot rows), not just single-table point lookups; the "hundreds of thousands of rows per transaction" pattern brought over from MySQL is the #1 trap.
  • Sources: official docs (transaction-overview.md, error-codes.md, tidb-configuration-file.md, the older FAQ).

Deep Waters #3: Region hotspots — the first line of the schema determines the ceiling

  • Mechanism: data is split into Regions by key range (256MiB default since v8.5); Regions are the basic unit of Raft replication and scheduling; AUTO_INCREMENT IDs funnel all new writes into the "last Region" — a tail hotspot.
  • Pushed to the edge:
    • The official docs (auto-increment.md) explicitly warn: "Using AUTO_INCREMENT may cause hotspot issues in production; AUTO_RANDOM is recommended instead." In TiDB, AUTO_INCREMENT is allocated by each TiDB Server in cached batches (30k per batch by default) and is not guaranteed monotonic across instances — semantically different from MySQL to begin with.
    • Every scattering technique has a cost: SHARD_ROW_ID_BITS only works on implicit-rowid tables, and setting it too large amplifies RPC counts and CPU/network overhead (official docs, verbatim); AUTO_RANDOM (5 random bits + 59 auto-increment bits) solves write hotspots but IDs are no longer sequential — no longer "auto-incrementing"; time-ordered PKs (created_at prefix) are tail hotspots too.
    • Community-tested (MySQL vs TiDB POC, 2026-09): in single-node read-heavy scenarios MySQL TPS led TiDB by 58%–81%, with the conclusion "Single-node read-heavy: MySQL leads overwhelmingly; TiDB's fixed architectural cost has no workaround" — every query goes through RPC + multi-replica + RocksDB; that's an architecture tax tuning can't erase.
    • v8.5 raised the default Region from 96MiB to 256MiB (official performance report: OLTP inserts +27%, Analyze +45% — vendor claim, cited for architecture-evolution reference only, not used as a verdict basis) — essentially "trading coarser scheduling granularity for lower management overhead"; but for small-table, query-heavy workloads, large Regions may instead concentrate hotspots (the official blog recommends smaller Regions for such workloads).
  • What it means for your decision: PK design is the #1 priority in TiDB schema design — breaking up hotspots after launch is effectively a rewrite; POCs must stress-test with a realistic ID-generation strategy + realistic write distribution; read-heavy workloads with <100GB of data may be faster and cheaper on single-node MySQL — the community-consensus "not suitable" profile.
  • Sources: official docs (auto-increment.md, troubleshoot-hot-spot-issues.md cited), official v8.5 performance analysis, community-tested (MySQL vs TiDB POC).

Deep Waters #4: TiFlash's "real-time" — the async truth of Learner replication

  • Mechanism: TiFlash is a read-only replica of TiKV that replicates data asynchronously via the Raft Learner protocol; reads on TiFlash are consistency-checked against the Raft log index — they return only "the synced committed version," guaranteeing "some consistent snapshot," not "the latest."
  • Pushed to the edge:
    • Learner lag under write bursts is the norm: the data version TiFlash reads lags behind TiKV, so HTAP queries' "real-timeness" degrades to T+seconds or even T+minutes — while the business believes it's doing "real-time analytics."
    • The optimizer's automatic routing (TiKV vs TiFlash) can pick wrong: stale statistics and cost-estimation bias send OLAP queries into TiKV full table scans, or point lookups into TiFlash; tidb_enforce_mpp can force it, but that's treating the optimizer as decoration.
    • TiFlash is read-only: all writes must go through TiKV first — on the write-amplification path TiFlash is merely a "spectator"; a TiFlash node failure doesn't affect OLTP, but HTAP queries degrade directly.
    • Resource isolation is a "recommendation," not the default: when TiFlash and TiKV are co-deployed, large analytical queries' CPU/IO crowds out OLTP — official guidance recommends dedicated TiFlash nodes, meaning HTAP costs an extra set of machines.
  • What it means for your decision: think of TiFlash as a "seconds-latency real-time warehouse," not "zero-latency"; HTAP POCs must stress OLTP writes and OLAP queries simultaneously and watch the learner lag metric; for pure OLAP heavy-query workloads, ClickHouse/Doris usually offer better price-performance 社区共识.
  • Sources: official architecture (TiFlash Raft Learner mechanics), community technical analyses (TiFlash consistent-read internals); "co-deployment resource contention" is community consensus.

Deep Waters #5: write bursts → RocksDB write stall → flow control rejects writes

  • Mechanism: each TiKV has two RocksDB instances (data/raft stores Raft logs, data/db stores real data); writes first pass the scheduler for transactional consistency checks, then enter raftstore (Store threads replicate → Apply threads persist).
  • Pushed to the edge:
    • When RocksDB compaction can't keep up with writes (pending compaction bytes pile up), write stall triggers — per the official troubleshooting docs: before v5.2, clients got ServerIsBusy, rejecting all writes (a QPS cliff); since v5.2, a flow-control mechanism instead: it first delays write requests, soft-pending-compaction-bytes-limit (default 192GiB) starts rejecting some writes, and hard-pending-compaction-bytes-limit (default 1024GiB) rejects all writes.
    • This is TiDB's version of "error 4030": the harder you write, the heavier the compaction debt — eventually repaid in the form of "rejected writes." More easily triggered on SATA SSDs (official advice: when disk throughput tops out, either switch to NVMe or trade CPU for disk with higher-compression-ratio algorithms).
    • Cross-datacenter adds another layer: Raft quorum acknowledgment means writes must sync to at least 2 datacenters; the old official FAQ recommends <5ms cross-datacenter latency; same-city dual datacenters (<3ms) can run active-active writes, while remote sites (20ms dedicated lines) can only do DR — write latency strongly correlates with physical distance; that's a tax Raft writes into the architecture.
    • Community-tested (cross-IDC+GCP POC): cross-region TPS drops, but "always 0 errors" — no deadlocks, no write conflicts — cross-region optimistic locking means "slower but still correct," in contrast to MySQL primary-replica cross-region, where "conflicts are resolved manually."
  • What it means for your decision: write-intensive workloads must monitor compaction/flow-control metrics (pending compaction bytes) and plan write throttling; disk choice directly determines the write ceiling — SATA on TiDB is "usable but may demand its tax at any time"; for active-active architectures, check dedicated-line latency before discussing the design.
  • Sources: official docs (tidb-troubleshooting-map.md flow-control section, performance-tuning-methods.md write path, the older FAQ on active-active), community-tested.

Deep Waters #6: DDL, GC, and upgrades — the triple ops pitfall

  • Mechanism: DDL is online and async (multi-state transitions); GC cleans MVCC old versions every 10 minutes by default; upgrades run via TiUP rolling restarts.
  • Pushed to the edge:
    • DDL historically executed serially (single DDL owner); v6.2 introduced a concurrent DDL framework, but the v6.2→v6.5 upgrade once stalled when the KV queue changed to a table queue (the official upgrade FAQ has a dedicated section: plugin loading, kill -9, and DDL owner changes can all stall upgrades).
    • v6.3 introduced metadata locks, enabled by default in v6.5: DDL on tables with uncommitted transactions gets blocked — "online DDL" ≠ "DDL anytime"; ADD INDEX during peak hours may queue indefinitely.
    • information schema is changed (error-8027-class scenarios): SQL errors out directly when a TiDB Server's schema version lags — the root cause is often network jitter between TiDB and PD.
    • Long transactions / stuck TiCDC drag the GC safepoint: MVCC old versions can't be deleted and disk space keeps bloating — the classic confusion of "deleted data but space not freed"; the root cause is often GC being stuck behind some slow consumer.
    • Community case (Dewu (得物) upgrade practice, v5.3.3→v7.5.x): in the v4.x era, TiKV nodes auto-restarted after running >2 years; before v6.5, TiCDC frequently lagged/OOMed; after upgrading, the v7.5 optimizer gravitated toward full table scans for a while (a 21.5-billion-row table took 60s to time out on a full scan vs 0.4s with a forced index) — fixed via tidb_opt_prefer_range_scan / SPM bindings: "upgrade ≠ faster; execution plans may regress first."
    • In-place upgrades don't support rollback, and large version jumps require incremental upgrades with doubled jitter; Dewu ultimately adopted "migration-based upgrades" exclusively (new cluster + TiCDC sync), at the cost of double the machines.
  • What it means for your decision: run DDL only off-peak and check for long transactions first; rehearse upgrades fully in test environments and prepare SPM/binding contingencies; GC monitoring (safepoint advancement) is a routine inspection item; write "upgrade windows" into the annual ops budget.
  • Sources: official docs (upgrade-tidb-using-tiup.md upgrade FAQ, tidb-troubleshooting-map.md DDL section, error-codes.md); community-tested (Dewu upgrade practice, late 2025).

Deep Waters #7: the deep waters of MySQL compatibility — the remaining 5% of "95% compatibility"

  • The official compatibility doc (mysql-compatibility.md) explicitly lists as unsupported: stored procedures/functions, triggers, events, UDFs, full-text indexes, GIS/spatial types, XA syntax, CREATE TABLE AS SELECT, SKIP LOCKED, descending indexes, CHECK/CHECKSUM/REPAIR/OPTIMIZE TABLE, HANDLER, column-level privileges, LATERAL derived-table execution.
  • Pushed to the edge:
    • Traditional systems (ERP/finance/telecom billing) are exactly the heavy users of stored procedures + triggers + events — migrating such systems to TiDB isn't "changing a config" but "rewriting business logic"; migration cost jumps straight from "low" to "high."
    • Foreign key constraints long an experimental feature (introduced in v6.x), less mature than MySQL — workloads relying on FKs for data integrity need re-evaluation.
    • Character sets limited to ascii/latin1/binary/utf8/utf8mb4/gbk/gb18030; lower_case_table_names and similar behave differently; SELECT ... FOR UPDATE has optimistic semantics (conflicts checked at commit) rather than MySQL's locking semantics — "same syntax, different semantics" is the most expensive trap.
    • Counterexample: internet businesses (no stored procedures, mostly auto-increment/Snowflake-ID PKs) do migrate smoothly — how treacherous compatibility is depends entirely on how much the workload depends on MySQL's exotic features.
  • What it means for your decision: step one of migration assessment is sweeping for "which MySQL-proprietary features are in use," rather than declaring compatibility after a few CRUD statements pass; POCs must include a presence/absence checklist for stored procedures/triggers/full-text search, etc.
  • Sources: official docs (mysql-compatibility.md); community consensus (migration guides, high-frequency AskTUG questions).

判决

  • 一句话定位：为 MySQL 生态准备的分布式"升级舱"——把分库分表和 ETL 的复杂度收进数据库内部，代价是架构固定成本、更高的硬件门槛和陡峭的运维学习曲线。
  • 适合谁：
    • MySQL 技术栈、数据量超过单机上限（TB 级起）又不想做分库分表的互联网业务；
    • 需要"交易 + 秒级分析"同库的 HTAP 场景（订单/风控/行为分析）；
    • 做多业务数据汇聚、复杂查询下放到 TiDB、点查留在 MySQL 的"双跑"架构；
    • 需要多云/出海、看重全开源不被厂商锁定的团队。
  • 不适合谁：
    • 数据量 <100GB 的小库——单机 MySQL 更快、更便宜、更省心；
    • 重度依赖存储过程/触发器/全文索引/GIS 的传统系统（迁移=重写）；
    • "去 O"替换 Oracle 的信创场景（无 Oracle 兼容）；
    • 团队无专职 DBA 又想"装完不管"；
    • 纯 OLAP 重查询（ClickHouse/Doris 性价比更高）。
  • 迁移成本：
    • MySQL → 低-中：协议兼容，DM 全量+增量成熟；存储过程/触发器需重写，自增主键建议改 AUTO_RANDOM，大事务拆批，复杂 SQL 回归测试。
    • PostgreSQL → 中高：无 PG 协议兼容，应用层改造为主。
    • Oracle → 高：无 Oracle 兼容模式，重度 Oracle 特性基本等于重构；"去 O"场景 TiDB 不在候选名单。
  • One-line positioning: a distributed "upgrade capsule" built for the MySQL ecosystem — it absorbs sharding and ETL complexity into the database itself, at the cost of fixed architectural overhead, a higher hardware bar, and a steep ops learning curve.
  • Good fit for:
    • Internet-scale businesses on the MySQL stack whose data volumes exceed single-node capacity (TB-scale and up) and who want to avoid sharding;
    • HTAP scenarios needing "transactions + second-level analytics" in one database (orders / risk control / behavioral analytics);
    • "Dual-run" architectures that consolidate multi-business data, push complex queries down to TiDB, and keep point lookups on MySQL;
    • Teams needing multi-cloud / overseas expansion that value full open source and no vendor lock-in.
  • Not a good fit for:
    • Small databases <100GB — single-node MySQL is faster, cheaper, and less hassle;
    • Legacy systems heavily dependent on stored procedures/triggers/full-text indexes/GIS (migration = rewrite);
    • "De-O" Oracle-replacement Xinchuang (信创) scenarios (no Oracle compatibility);
    • Teams with no dedicated DBA hoping to "install and forget";
    • Pure OLAP heavy-query workloads (ClickHouse/Doris offer better price-performance).
  • Migration cost:
    • MySQL → low-to-medium: protocol-compatible, DM full+incremental migration is mature; stored procedures/triggers need rewrites, auto-increment PKs should switch to AUTO_RANDOM, large transactions must be batched, complex SQL needs regression testing.
    • PostgreSQL → medium-to-high: no PG protocol compatibility; mostly application-layer rework.
    • Oracle → high: no Oracle compatibility mode; heavy Oracle features basically mean a rewrite; TiDB isn't on the shortlist for "de-O" scenarios.
