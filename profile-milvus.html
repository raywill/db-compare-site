Milvus

AI 数据库 #向量数据库 #分布式 #ANN #HNSW #混合检索 #开源 #RAG

Zilliz 开源的分布式向量数据库，为十亿级向量检索而生：索引类型矩阵（HNSW / IVF / DiskANN / 稀疏 / BM25）和存算分离架构是它的真本事；但它把复杂度拆成协调、消息队列、对象存储、segment、索引构建等多条链路——数据量尚未逼近 pgvector 边界时，这些能力只是额外的运维税。

Zilliz's open-source distributed vector database, built for billion-scale vector search: its index-type matrix (HNSW / IVF / DiskANN / sparse / BM25) and storage-compute separation are the real deal — but the complexity is split across coordination, message queues, object storage, segments, and index building. If your data volume hasn't pushed past pgvector's limits, those capabilities are just extra ops tax.

硬维度（47 项）

1 静态加密 / TDE 未找到证据

未找到证据——本轮未找到开源 Milvus 内核级 TDE（数据文件落盘加密）的可靠官方证据；数据实际落在对象存储、etcd、消息队列，可依赖 S3 / MinIO / 磁盘 / KMS 等基础设施层加密，但这不能称为 Milvus 的产品能力。证据：本轮官方文档检索无结果（待复核）。

2 TLS / 传输加密 有

有——支持客户端 TLS、双向 TLS（mTLS）及内部组件间 TLS。证据：官方文档（adminGuide/tls.md）。

3 审计 未找到证据

未找到证据——开源内核无合规级数据访问审计日志的可靠官方证据；注意边界：Zilliz Cloud 提供托管 Audit Logs（已 GA，开启后额外计费），Attu 仅记录其自身 UI / 服务端发起的写操作（存于 Attu SQLite），两者都不是开源内核能力。证据：本轮官方文档检索无结果 + Zilliz 官方博客（托管侧）。

4 认证与权限 有

有——用户名 / 密码认证 + RBAC（用户、角色、权限组）。证据：官方文档 + SDK 最佳实践。

5 备份恢复 有

有——milvus-backup 支持在线 collection / cluster 级备份与恢复；但：恢复索引可能需 --rebuild_index（索引重建计入 RTO）；恢复走 bulk insert；仅支持恢复到同版本或更高版本（2.2+ 的备份可恢复到 2.5 / 2.6 / 3.0.1+，3.0.0 不在支持列表）。证据：milvus-backup 官方 README（zilliztech）。

6 可观测性 有

有——Prometheus metrics、Grafana 看板、日志、Attu 管理 UI（拓扑 / 慢查询 / 任务队列）；支持 OpenTelemetry / Jaeger 链路追踪。注意 Attu 更偏管理 UI 而非完整诊断平台。证据：官方文档 + 社区实践。

7 连接模型 有

有——SDK 经 gRPC 连接无状态 Proxy（默认 19530 端口）；PyMilvus 的 MilvusClient 为统一入口；另有 RESTful API v2 / HTTP 接口；不是 SQL 连接模型，无连接池语义可比。证据：官方文档 + SDK 文档。

8 事务与隔离级别 不适用

不适用——Milvus 没有 SQL 意义的多语句 ACID 事务原语，batch insert 可能部分成功（第三方技术记录）；它提供的是四级可调读取一致性：Strong、Bounded Staleness（默认）、Session、Eventually，基于 GuaranteeTs 时间戳机制（Strong 读会等待 QueryNode 追上最新时间戳；Session 保证 read-your-writes；Eventually 跳过可见性等待）。证据：官方文档（tune_consistency.md、consistency.md）+ 第三方技术记录。

9 复制与一致性 部分支持

部分支持——协调与元数据走 etcd（Raft 强一致）；数据耐久性横跨消息队列（Pulsar / Kafka / Woodpecker / RocksMQ）与对象存储两条链路；查询侧 segment 多副本按需加载，四级读取一致性可调。没有"单一复制协议管全部数据"的传统模型，耐久性是链路问题不是单点问题。证据：官方架构文档 + 社区共识。

10 扩展方式 有

有——原生 scale-out；无状态 Proxy，Query / Data / Index（2.6 起索引构建收敛）/ 协调服务角色可独立扩展；存算分离，seal 后的 segment 沉到对象存储。注意：扩容不等于索引和 segment 立即就位（见深水区五）。证据：官方架构文档 + 社区共识。

11 兼容性 部分支持

部分支持——多语言 SDK（Python / Java / Go / Node.js / Rust / C++）、RESTful v2、LangChain / LlamaIndex 等 AI 生态集成成熟；但不兼容 SQL / PG wire 协议；2.x → 3.0 有 SDK major line、protobuf、schema 边界（Rust SDK 3.0 明确为 3.x 首个 major line，2.6.x 继续维护）。证据：官方文档 + SDK release notes。

47 热点数据更新能力 部分支持

部分支持（删插语义 LWW，热点更新触发压实风暴）。

  • 更新原语是 upsert（v2.3 起，需手动主键）：改一个标量字段也要整行重写——发删除墓碑再整行（含向量）重插；真正的列级原地更新（mutable columns）仍是 2026-07 的设计草案，未落地 待验证。
  • 同主键并发 upsert 无冲突报错，按时间戳后写覆盖（LWW 语义），无锁等待、无 abort，读-改-写不具原子性；一致性级别（Strong/Bounded/Session/Eventual）只决定读时间戳，不改变覆盖语义 厂商口径。
  • 衰减形态是压实风暴：同一批向量 ID 被反复更新时，某段更新比例越过约 20% 压实阈值即触发整段重写（含向量）并重建向量索引，持续的更新流变成永久的压实+索引风暴，只有大集群能扛 待验证。
  • 无已落地的内置热点缓解机制；墓碑靠后台压实清理是常规机制而非热点开关 社区共识。
  • 推荐模式：批量 upsert 替代逐条、高频变更的标量字段外置到 KV 存储再关联查询（官方设计草案承认用户已在用此外部方案）；代价是外部关联的复杂度与一致性级别调优（读后写需 Strong） 社区共识。

47 Hotspot update handling Partially supported

Partially supported (delete-plus-insert semantics with last-write-wins; hotspot updates trigger compaction storms).

  • The update primitive is upsert (since v2.3, requires a manual primary key): changing one scalar field rewrites the whole row — a delete tombstone is emitted and the full row (vectors included) is reinserted; true in-place column updates (mutable columns) remain a 2026-07 design draft, not shipped (to be verified).
  • Concurrent upserts on the same primary key raise no conflict error and follow last-write-wins by timestamp: no lock waits, no aborts, and read-modify-write is not atomic; the consistency level (Strong/Bounded/Session/Eventual) only selects the read timestamp and does not change the overwrite semantics 厂商口径.
  • The decay pattern is a compaction storm: when the same vector IDs are updated repeatedly, a segment whose update ratio crosses roughly the 20% compaction threshold is fully rewritten (vectors included) and its vector index rebuilt — a steady update stream becomes a permanent compaction-and-indexing storm that only a large cluster can absorb (to be verified).
  • There is no shipped built-in hotspot mitigation; tombstone cleanup by background compaction is routine housekeeping, not a hotspot switch 社区共识.
  • Recommended patterns: batched upserts instead of one-by-one, and keeping frequently-changing scalar fields in an external KV store joined at query time (the official design draft acknowledges users already work around it this way); the cost is the complexity of the external join and consistency-level tuning (read-after-write needs Strong) 社区共识.

  1. The full index spectrum: from FLAT to DiskANN Why it's real: the official index-selection guide covers FLAT (exact), IVF_FLAT / IVF_PQ / IVF_SQ8, the HNSW family (HNSW / HNSW_SQ / HNSW_PQ / HNSW_PRQ), SCANN, DiskANN, plus SPARSE_INVERTED_INDEX for sparse vectors; CPU / GPU / disk (NVMe) paths; AUTOINDEX lowers the entry barrier so newcomers don't have to read the index papers on day one.   2.   3. 深水区

以下每条 = 机制 + 推到边缘会发生什么 + 选型含义。证据类型已标注。

深水区一：向量索引算法——没有"最好"，只有"账单不同"

  • 机制：索引按 segment 独立构建，索引文件随 segment 落对象存储，查询时由 QueryNode 加载。HNSW 图索引：M（每节点连接数）、efConstruction（构建期搜索宽度）决定图质量与内存 / 构建时间，查询期 ef 决定召回 / 延迟。IVF：nlist（聚类中心数）、nprobe（扫描的中心数），nprobe 越大召回越高、延迟线性上涨。DiskANN：图放 SSD，内存只留压缩导航结构。FLAT：精确暴力搜索。
  • 推到边缘：
    • HNSW 内存约为原始向量的 1.5–2 倍（厂商 / 社区口径）：十亿级 768 维向量，单是索引内存就是 TB 级账单——这就是 DiskANN 和 IVF_PQ 存在的理由；mmap 能把部分压力转给磁盘，但换的是延迟。
    • segment 碎（小 segment 多）时，每个 segment 一份索引，索引总开销被放大；compaction 合并小 segment 既是空间优化也是索引成本优化。
    • IVF 的 nlist 选错，nprobe 怎么调都救不回来——聚类阶段的信息损失不可逆；索引参数在建索引时确定，改参数 = 重建索引 = 重交构建成本。
    • DiskANN 查询的尾延迟看 SSD：NVMe 换成普通云盘，P99 翻倍不止；构建时间也数倍于内存索引。
  • 选型含义：POC 必须用真实数据分布 + 真实 topK 做 recall@k / P99 网格实测；索引选型是"内存账单 vs 延迟 vs 构建成本"的三方谈判，没有银弹。
  • 来源：官方文档（index_selection.md，含 HNSW 调优示例 M=16 / efConstruction=200 / 查询期 ef）；社区成本优化指南（内存倍数口径已标注为厂商 / 社区口径）。

深水区二：删除与 compaction——"删了"不等于"没了"

  • 机制：Milvus 是 append-only 存储，只支持逻辑删除——delete 写入删除标记（delta log），查询时按时间戳过滤被标记实体；物理清除靠 compaction（DataCoord 触发、DataNode 执行）把未删除数据写入新 segment 并淘汰旧 segment。
  • 推到边缘：
    • 官方 release notes 原话：滥用删除会导致搜索性能暴跌、存储用量暴涨——每次查询都要先过一遍删除标记。
    • "删了数据空间不释放"的经典困惑：compaction 是有触发阈值和节奏的后台任务；做 GDPR"删除权"合规时，必须端到端验证物理清除真的发生，不能只看查询结果。
    • 更新 = 删除 + 插入：高频更新场景的删除标记堆积速度远超直觉；2026-07 的 mutable-columns 设计稿试图做列级更新（写入路径描述为"带 payload 的删除"），仍在设计阶段——GA 前不要当已发布能力用。
    • compaction 合并 segment 会触发 QueryCoord 的 target 更新与 segment handoff（先加载新 segment 再卸载旧 segment），不是完全无感的后台任务。
  • 选型含义：有高频删除 / 更新的业务，必须做 compaction 策略与删除标记堆积的压测；合规删除需求要验证到对象存储层。
  • 来源：官方 release notes（v2.0.0，逻辑删除警告）；compaction 设计文档；load-segment-pipeline 归档文档（handoff 流程）；mutable-columns 设计稿（2026-07，设计阶段）。

深水区三：标量过滤与混合检索——过滤写在哪，决定了你搜到什么

  • 机制：标量字段可建 INVERTED / BITMAP 等索引；hybrid_search 支持多路 ANN + RRF / 加权 rerank；过滤表达式（expr / filter）可与向量搜索组合；partition key 功能（启用时默认 64 分区）可做租户路由。
  • 推到边缘：
    • 过滤的执行位置改变候选空间：高选择性过滤（过滤后只剩几百条）时，ANN 图遍历的剪枝优势消失，FLAT 暴力扫反而更快更准——"索引越强越好"在此失效。
    • IVF + 过滤组合：nprobe 扫的是聚类中心，被过滤掉的向量不参与召回计算——过滤比例极高时有效 nprobe 被稀释，召回无声下跌；解法是调大 nprobe 或改用 HNSW / FLAT，代价是延迟 / 内存。
    • 多租户隔离（tenant_id 过滤）是典型的高基数低选择性过滤：必须用真实租户数据分布验证召回，不能拿均匀分布的 benchmark 当证据。
    • BM25 / analyzer 必须在建表时声明，事后无法追加——schema 设计时就要想清楚"以后要不要全文检索"，否则重建 collection + 重导数据。
  • 选型含义：混合检索的 POC 必须带上真实过滤表达式和真实数据倾斜一起测；只测纯向量 recall 的 benchmark 对 RAG 生产没有指导意义。
  • 来源：官方文档（index_selection.md、标量索引文档）；社区实践（2026-08 BM25 hybrid search 设计实测记录，基于 v2.5.0 + SDK 3.0.4 验证）。

深水区四：召回率调优——recall@k 是谈判桌，不是仪表盘

  • 机制：近似检索的本质是用精度换速度；可调旋钮分三层：索引构建参数（HNSW 的 M / efConstruction、IVF 的 nlist）、查询参数（HNSW 的 ef、IVF 的 nprobe）、数据面（segment 大小、compaction 程度）。
  • 推到边缘：
    • 构建参数改一次 = 索引重建一次：efConstruction 从 200 调到 400，构建时间翻倍不止，十亿级上就是一次以天计的窗口。
    • 查询参数是唯一"免费"的旋钮：ef / nprobe 在查询时可调，适合按业务分级（核心流量高召回、长尾流量低延迟）——但前提是 SDK / 网关真的透传了 search_params。
    • 官方文档的"推荐值"是起点不是终点：M=16 / efConstruction=200 这类默认值在 768 维文本向量上合理，在 2048 维图像向量上可能是另一个故事——维度、数据分布、topK 三者共同决定最优值，没有跨场景银弹。
    • 召回率必须和过滤一起谈（见深水区三）：单测 ANN recall 99% 的系统，加上生产过滤可能掉到 90% 以下——验收标准要写"带过滤的端到端 recall@k"，不是"裸 ANN recall"。
  • 选型含义：把"recall@k / nDCG + P95 / P99 + 真实 query set"写进验收标准；索引参数调优要留出重建窗口的预算。
  • 来源：官方文档（index_selection.md，HNSW 调优示例）；社区共识。

深水区五：十亿级扩展——"能扩展"和"扩展了就有数"之间隔着三条链路

  • 机制：Proxy / QueryNode / DataNode / 协调服务可独立扩展；segment 是最小调度单位，QueryCoord 负责 target 管理与 handoff；seal 后的数据沉对象存储。
  • 推到边缘：
    • 扩 QueryNode 不等于查询变快：新节点要先 load segment、加载索引，handoff 完成前新节点是"摆设"；扩容期的 segment 迁移吃网络和内存，高峰期扩容可能先抖再稳。
    • 写入侧：growing segment 靠 flush 密封，flush 落后则内存堆积；3.0 开发版曾出现 write buffer 等待慢 segment sync、insert QPS 掉到 0 的 issue（#48974，状态待最终核验）——持续写入的背压链路是生产第一杀手。
    • 外部依赖是扩展性的隐形天花板：etcd（元数据）、Pulsar / Kafka（消息）、对象存储任一环节到瓶颈，向量节点再多也白搭——"分布式"意味着瓶颈分析要横跨五个组件。
    • Standalone（单机 + MinIO / RocksMQ）与 Cluster 是两种运维物种：从 Standalone 切 Cluster 是换部署拓扑，不是改个配置。
  • 选型含义：十亿级 POC 必须压"持续写入 + 查询 + 扩容"三并发场景；监控要覆盖 MQ 积压、flush 落后、handoff 进度，而不仅是 QPS。
  • 来源：官方架构文档；load-segment-pipeline 归档文档；GitHub issue #48974（3.0 开发版，状态待核验）。

深水区六：一致性与可见性——"写入成功"和"搜得到"之间隔着 GuaranteeTs

  • 机制：写入先进 MQ（WAL），growing segment 在内存中可查，seal / flush 后落盘；查询的 GuaranteeTs 决定"等到多新"：Strong 等 QueryNode 的 service time 追上最新时间戳；Session 用本会话上次写入时间戳（read-your-writes）；Bounded（默认）允许有界陈旧；Eventually 跳过等待。Milvus Lite 只有 Strong 可选。
  • 推到边缘：
    • 默认 Bounded 下"刚写入搜不到"是 feature 不是 bug；切 Strong 能解，但 Strong 把整条 ingest → 可见链路的落后时间计入每次查询延迟——社区 50k QPS 实测 Strong 让 p95 翻倍。
    • 第三方集成可能吞掉你指定的 consistency_level（2026-08 semantic-router issue #2821：指定 Strong 未生效，后修复）——"可调"的前提是链路真的透传参数。
    • 强一致场景下，ingest 侧的任何落后（MQ 积压、segment 未及时 seal）都会直接变成查询延迟——可见性延迟是全链路问题，不只在查询侧。
  • 选型含义：RAG 的"写后即搜"需求要在 POC 里显式验证可见性延迟；一致性级别要写进 SDK 封装层，而不是依赖每个调用方自觉。
  • 来源：官方文档（tune_consistency.md、consistency.md；SDK 文档注明 Milvus Lite 限制）；社区 issue（semantic-router #2821，2026-08）；社区生产实践（Datadog 集成案例）。

Deep Waters 1: Vector index algorithms — no "best", only different bills

  • Mechanism: indexes are built independently per segment; index files land on object storage with their segments and are loaded by QueryNodes. HNSW graph index: M (connections per node) and efConstruction (build-time search width) determine graph quality vs. memory / build time; query-time ef determines recall / latency. IVF: nlist (cluster centers), nprobe (centers scanned) — larger nprobe means higher recall and linearly higher latency. DiskANN: graph on SSD, only compressed navigation structures in memory. FLAT: exact brute-force search.
  • At the edge:
    • HNSW memory is ~1.5–2× the raw vectors (vendor / community figure): at billion-scale 768-dim vectors, index memory alone is a TB-level bill — which is why DiskANN and IVF_PQ exist; mmap shifts some pressure to disk at the cost of latency.
    • Fragmented segments (many small ones) multiply index overhead since each segment carries its own index; compacting small segments is index-cost optimization as much as space optimization.
    • Pick nlist wrong for IVF and no nprobe tuning will save you — clustering-stage information loss is irreversible; index parameters are fixed at build time, changing them means rebuilding and paying build cost again.
    • DiskANN tail latency follows the SSD: swap NVMe for ordinary cloud disks and P99 more than doubles; build time is also multiples of in-memory indexes.
  • What it means: POCs must grid-test recall@k / P99 on real data distributions with real topK; index selection is a three-way negotiation between memory bill, latency, and build cost — no silver bullet.
  • Sources: official docs (index_selection.md, incl. the HNSW tuning example M=16 / efConstruction=200 / query-time ef); community cost-optimization guide (memory multiple labeled as vendor / community figure).

Deep Waters 2: Deletion and compaction — "deleted" doesn't mean "gone"

  • Mechanism: Milvus is append-only and supports logical deletion only — deletes write deletion markers (delta logs), and queries filter marked entities by timestamp; physical removal relies on compaction (triggered by DataCoord, executed by DataNode), which writes live data into new segments and retires old ones.
  • At the edge:
    • Official release notes, verbatim: abusing deletion tanks search performance and explodes storage usage — every query must first walk the deletion markers.
    • The classic "deleted data doesn't free space" confusion: compaction is a background task with trigger thresholds and its own cadence; for GDPR right-to-erasure compliance you must verify physical removal end to end, not just query results.
    • Update = delete + insert: deletion-marker pileup in high-update workloads is far faster than intuition suggests; the 2026-07 mutable-columns design draft proposes column-level updates (write path described as "a delete with a payload") but is still at design stage — don't treat it as shipped.
    • Compacting segments triggers QueryCoord target updates and segment handoff (load the new segment before unloading the old) — not a fully invisible background task.
  • What it means: workloads with heavy deletes / updates need compaction-strategy and marker-pileup load testing; compliance deletion must be verified down to the object-storage layer.
  • Sources: official v2.0.0 release notes (logical-deletion warning); compaction design docs; archived load-segment-pipeline doc (compaction / handoff flow); mutable-columns design draft (2026-07, design stage).

Deep Waters 3: Scalar filtering and hybrid search — where the filter runs decides what you find

  • Mechanism: scalar fields can carry INVERTED / BITMAP indexes; hybrid_search supports multi-path ANN with RRF / weighted reranking; filter expressions (expr / filter) compose with vector search; the partition-key feature (64 partitions by default when enabled) supports tenant routing.
  • At the edge:
    • Filter placement changes the candidate space: with highly selective filters (hundreds of candidates left), ANN graph traversal's pruning advantage evaporates and a FLAT brute-force scan is faster and more accurate — "stronger index is always better" fails here.
    • IVF + filtering: nprobe scans cluster centers, and filtered-out vectors don't count toward recall — with extreme filter ratios the effective nprobe is diluted and recall drops silently; the fix is larger nprobe or switching to HNSW / FLAT, paid for in latency / memory.
    • Multi-tenant isolation (tenant_id filters) is the classic high-cardinality, low-selectivity filter: recall must be validated on real tenant data distributions, never on uniform-distribution benchmarks.
    • BM25 / analyzers must be declared at table creation and can't be added later — schema design has to anticipate "will we ever need full-text search", or it's rebuild-collection + reimport.
  • What it means: hybrid-search POCs must test with real filter expressions and real data skew together; pure-vector-recall benchmarks say nothing about RAG production.
  • Sources: official docs (index_selection.md, scalar-index docs); community practice (2026-08 BM25 hybrid-search design record, verified on v2.5.0 + SDK 3.0.4).

Deep Waters 4: Recall tuning — recall@k is a negotiation table, not a dashboard

  • Mechanism: approximate retrieval trades accuracy for speed; the knobs come in three layers: index-build parameters (HNSW M / efConstruction, IVF nlist), query parameters (HNSW ef, IVF nprobe), and the data plane (segment size, compaction level).
  • At the edge:
    • Changing a build parameter once means rebuilding the index once: raising efConstruction from 200 to 400 more than doubles build time — at billion scale that's a multi-day window.
    • Query parameters are the only "free" knob: ef / nprobe tune at query time, enabling per-tier traffic (high recall for core traffic, low latency for the long tail) — provided the SDK / gateway actually forwards search_params.
    • The official docs' "recommended values" are starting points, not destinations: defaults like M=16 / efConstruction=200 that suit 768-dim text vectors may be a different story on 2048-dim image vectors — dimension, data distribution, and topK jointly determine the optimum; no cross-scenario silver bullet.
    • Recall must be discussed together with filtering (see Deep Waters 3): a system scoring 99% bare ANN recall can drop below 90% under production filters — acceptance criteria should read "end-to-end recall@k with filters", not "bare ANN recall".
  • What it means: write "recall@k / nDCG + P95 / P99 + real query set" into acceptance criteria; budget rebuild windows for index-parameter tuning.
  • Sources: official docs (index_selection.md, HNSW tuning example); community consensus.

Deep Waters 5: Billion-scale expansion — three links between "can scale" and "scaled and serving"

  • Mechanism: Proxy / QueryNode / DataNode / coordination scale independently; the segment is the smallest scheduling unit, with QueryCoord owning target management and handoff; sealed data sinks to object storage.
  • At the edge:
    • Adding QueryNodes doesn't make queries faster by itself: new nodes must first load segments and indexes; before handoff completes the new node is decoration; segment migration during scale-out eats network and memory, so scaling at peak can wobble before stabilizing.
    • On the write side: growing segments seal via flush, and lagging flush piles up memory; a 3.0 dev build once showed write buffers waiting on slow segment sync with insert QPS dropping to 0 (issue #48974, final status pending verification) — the sustained-write backpressure chain is production's #1 killer.
    • External dependencies are the invisible ceiling: if etcd (metadata), Pulsar / Kafka (messaging), or object storage bottlenecks, more vector nodes buy nothing — "distributed" means bottleneck analysis spans five components.
    • Standalone (single node + MinIO / RocksMQ) and Cluster are two different ops species: moving from Standalone to Cluster is a topology change, not a config tweak.
  • What it means: billion-scale POCs must load-test "sustained writes + queries + scale-out" concurrently; monitoring must cover MQ backlog, flush lag, and handoff progress — not just QPS.
  • Sources: official architecture docs; archived load-segment-pipeline doc; GitHub issue #48974 (3.0 dev build, status pending verification).

Deep Waters 6: Consistency and visibility — GuaranteeTs sits between "write succeeded" and "searchable"

  • Mechanism: writes enter the MQ (WAL) first, growing segments are queryable in memory, sealed / flushed data lands on disk; a query's GuaranteeTs decides "how new to wait for": Strong waits until QueryNodes' service time catches the latest timestamp; Session uses the session's last write timestamp (read-your-writes); Bounded (default) allows bounded staleness; Eventually skips the wait. Milvus Lite only offers Strong.
  • At the edge:
    • Under the default Bounded level, "just-written data isn't searchable" is a feature, not a bug; switching to Strong fixes it but folds the entire ingest → visibility lag into every query's latency — a community test at 50k QPS saw Strong double p95.
    • Third-party integrations may swallow your consistency_level (2026-08 semantic-router issue #2821: Strong specified but not honored, later fixed) — "tunable" requires the parameter to actually propagate.
    • Under strong consistency, any ingest-side lag (MQ backlog, unsealed segments) becomes query latency directly — visibility delay is a full-pipeline problem, not query-side only.
  • What it means: RAG "write-then-search" requirements need explicit visibility-latency validation in POCs; bake the consistency level into the SDK wrapper instead of relying on every caller to remember.
  • Sources: official docs (tune_consistency.md, consistency.md; SDK docs note the Milvus Lite limitation); community issue (semantic-router #2821, 2026-08); community production practice (Datadog integration case).

好的也要有深度。每条 = 为什么是真的 + 边缘与限度。

  1. 索引矩阵全，"选型不用换库"
    • 为什么是真的：从 FLAT 精确到 IVF_PQ 省内存、HNSW 高召回、DiskANN 超内存、稀疏 / BM25 全文，一套系统覆盖；AUTOINDEX 让新手不用第一天就读完索引论文。

  2. 横向扩展是架构原生能力
    • 为什么是真的：存算分离 + 无状态 Proxy + 角色独立扩展，segment 级调度；十亿级是设计目标不是口号。
    • 边缘与限度：扩容 ≠ 立即就位（handoff / 索引加载）；外部依赖（etcd / MQ / 对象存储）任一瓶颈则白扩；小规模用 Cluster 是"大炮打蚊子"，Standalone 到一定规模要换拓扑。
    • 来源：官方架构文档；社区共识。观察版本：2.6.x。
  3. 混合检索一次请求搞定
    • 为什么是真的：dense + sparse + 标量过滤 + RRF rerank 一次 hybrid_search 完成，省掉"调两次再融合"的应用层代码；BM25 function 写入时自动派生稀疏向量。
    • 边缘与限度：BM25 建表时定、事后加不上；过滤 + ANN 的召回互动必须实测（见深水区三）；RRF 的 k 参数本身也要调。

  4. SDK 与 AI 生态开箱即用
    • 为什么是真的：PyMilvus MilvusClient 统一入口，Java / Go / Node.js / Rust / C++ 全覆盖，RESTful v2；LangChain / LlamaIndex 等 RAG 生态集成成熟；Milvus Lite（pip install）本地就能跑通原型。

Depth on the good stuff too. Each = why it's true + edges and limits.

  1. Full index matrix — "no need to switch databases as you grow"
    • Why it's true: one system covers FLAT exact search through memory-saving IVF_PQ, high-recall HNSW, over-memory DiskANN, and sparse / BM25 full text; AUTOINDEX means newcomers don't read the index papers on day one.
    • Edges and limits: a full matrix means a large tuning surface means a large pitfall surface; per-segment index building amplifies index cost on small segments; changing an index parameter means rebuilding — picking wrong costs a rebuild window. And vendor / community "cut costs 80%" figures are specific-tuning-scenario claims, not general promises.
    • Source: official docs (index_selection.md); community cost-optimization guide. Observed version: 2.6.x.
  2. Horizontal scaling as native architecture
    • Why it's true: storage-compute separation + stateless Proxy + independently scalable roles, segment-level scheduling; billion-scale is a design target, not a slogan.
    • Edges and limits: scaling out ≠ immediately serving (handoff / index loading); any bottleneck in external dependencies (etcd / MQ / object storage) nullifies new nodes; running Cluster at small scale is overkill, and Standalone eventually needs a topology change.
    • Source: official architecture docs; community consensus. Observed version: 2.6.x.
  3. Hybrid search in a single request
    • Why it's true: dense + sparse + scalar filtering + RRF rerank complete in one hybrid_search, eliminating "query twice and fuse in app code"; the BM25 function auto-derives sparse vectors at write time.
    • Edges and limits: BM25 is fixed at table creation and can't be added later; filter × ANN recall interactions must be measured (see Deep Waters 3); RRF's k parameter needs tuning too.
    • Source: official docs; community testing (2026-08, v2.5.0). Observed version: 2.5+.
  4. SDKs and AI ecosystem work out of the box
    • Why it's true: PyMilvus MilvusClient as the unified entry point, full coverage of Java / Go / Node.js / Rust / C++, RESTful v2; mature RAG-ecosystem integrations (LangChain / LlamaIndex); Milvus Lite (pip install) runs a prototype locally.

    • Source: SDK docs; community issue (semantic-router #2821). Observed version: 2.6.x.
  5. Complete observability and tooling
    • Why it's true: Prometheus + Grafana, Attu management UI (topology / slow queries / task queue / backups), OpenTelemetry / Jaeger tracing — problems are locatable by the book.
    • Edges and limits: Attu is a management UI, not a diagnostics platform; deep-water problems (stuck handoff, lagging compaction) ultimately need log and source reading; many metrics ≠ knowing which to watch — MQ backlog / flush lag need dedicated alerts.
    • Source: official docs; community practice. Observed version: 2.6.x.

判决

  • 一句话定位：为十亿级向量检索而生的分布式系统——索引矩阵和横向扩展是真本事，但它把复杂度拆成协调、消息、对象存储、segment、索引构建等多条链路；数据量没逼近 pgvector 边界时，这些能力只是额外的运维税。
  • 适合谁：
    • 向量规模千万到十亿级、单机内存 / HNSW 压不住的 RAG / 搜索 / 推荐业务；
    • 需要 dense + sparse / BM25 + 标量过滤混合检索，且过滤 / 召回需要独立调优的场景；
    • 需要索引内存、查询、写入独立扩展，或已有 K8s / SRE 团队能 hold 住多组件分布式系统；
    • 愿意用 Zilliz Cloud 托管、把运维外包的团队。
  • 不适合谁：
    • 百万级小规模 RAG——pgvector / 单机方案更快、更便宜、更省心；
    • 团队已深度绑定 PG 且强依赖事务 / SQL / JOIN（Milvus 无 SQL、无多语句事务）；
    • 无专职平台 / SRE 团队、希望"装完不管"的团队；
    • 有合规级审计 / TDE 硬性要求且只能用开源自建版的场景（本轮未找到开源内核证据）。
  • 迁移成本：
    • pgvector → 中高：不止搬 embedding——schema、过滤表达式、索引参数、recall@k 基线要重建；无 SQL，访问层重写；迁移前必须用真实 query set 做 recall@k / nDCG / P95 / P99 对照，配双写 + 回滚预案。
    • Elasticsearch（向量场景）→ 中：BM25 / 全文能力可对接，但 ES 的 DSL / 分片习惯要重学；dense 向量部分需重建索引调优。
    • 自研 FAISS / ScaNN 服务 → 中低：索引算法概念相通，主要是把"自己管的索引进程"换成"分布式 segment / compaction / handoff"的心智；运维复杂度上升，但省掉自研调度。
  • One-liner: A distributed system built for billion-scale vector search — the index matrix and horizontal scaling are genuinely strong, but complexity is split across coordination, messaging, object storage, segments, and index building; below pgvector's limits, those capabilities are just extra ops tax.
  • Best for:
    • RAG / search / recommendation workloads at ten-million to billion vector scale, where single-node memory / HNSW can't hold;
    • Scenarios needing dense + sparse / BM25 + scalar-filter hybrid retrieval with independently tunable filtering and recall;
    • Teams needing index memory, query, and write to scale independently, or with K8s / SRE capacity to run a multi-component distributed system;
    • Teams happy to use Zilliz Cloud and outsource operations.
  • Not for:
    • Small-scale RAG in the low millions — pgvector / single-node options are faster, cheaper, and simpler;
    • Teams deeply invested in Postgres relying on transactions / SQL / JOINs (Milvus has no SQL, no multi-statement transactions);
    • Teams with no dedicated platform / SRE staff hoping to "install and forget";
    • Scenarios with hard compliance-audit / TDE requirements restricted to self-hosted open source (no open-source kernel evidence found this round).
  • Migration cost:
    • pgvector → medium-high: it's not just moving embeddings — schema, filter expressions, index parameters, and recall@k baselines must be rebuilt; no SQL means rewriting the access layer; compare recall@k / nDCG / P95 / P99 on a real query set before migrating, with dual-write + rollback plans.
    • Elasticsearch (vector use cases) → medium: BM25 / full-text capabilities map over, but ES DSL / sharding habits must be relearned; dense-vector indexes need rebuilding and tuning.
    • Self-built FAISS / ScaNN services → medium-low: index-algorithm concepts transfer; the main shift is from "index processes I manage" to distributed segment / compaction / handoff thinking; ops complexity rises, but self-built scheduling goes away.
