档案：Microsoft SQL Server

关系型 OLTP #商业闭源 #T-SQL #Windows生态 #AlwaysOn #按核授权 #纵向扩展 #Azure

微软的商业关系型数据库旗舰，Windows/.NET 生态的事实标准 OLTP 数据库；以 T-SQL、SSMS 工具链、Always On 高可用和纵深安全栈见长，授权复杂度与按核成本是选型时必须正面回答的问题。

Microsoft's flagship commercial relational database — the de facto standard OLTP database for the Windows/.NET ecosystem; known for T-SQL, the SSMS toolchain, Always On high availability, and a defense-in-depth security stack. Licensing complexity and per-core cost are questions any evaluation must answer head-on.

硬维度（46 项）

1 静态加密 / TDE 有

有。TDE 加密数据文件与事务日志文件；实例上任一库开启 TDE 则 tempdb 自动被加密；TDE 库的备份天然带加密。密钥管理：master 库证书/非对称密钥 → DMK → SMK 层级，可用 EKM 提供程序或 Azure Key Vault（BYOK）。另有 Always Encrypted（客户端列级加密，DBA 也看不到明文；secure enclave 支持密文上有限计算）、备份加密、动态数据掩码。证据：官方文档

2 TLS / 传输加密 有

有。支持 TLS 1.2/1.3，可强制加密连接（ForceEncryption）；2025 起默认 Encrypt=True、TDS 8.0 走 TLS 1.3（第三方资料，细节待验证）。证据：官方文档为主

3 审计 有

有。SQL Server Audit（服务器/数据库审计规范），可写文件、安全日志、应用日志；Azure SQL 可审计到 Log Analytics/Storage。证据：官方文档

4 认证与权限 有

有。Windows 认证（Kerberos/NTLM）、SQL Server 登录、2025 起 Entra ID（含 Azure Arc 托管标识）；服务器角色/数据库角色/架构级权限，另有行级安全（RLS）。证据：官方文档

5 备份恢复 有

有。原生 BACKUP/RESTORE：完整/差异/日志备份、压缩备份、加密备份、备份到 URL（Azure Blob）；日志链支持时间点恢复（PITR）。限制：备份只能还原到同版本或更新版本，不可降级还原。证据：官方文档

6 可观测性 有

有。DMV/DMF（sys.dm_os_wait_stats 等等待统计是 DBA 母语）、Extended Events、Query Store（2022 起新库默认开启）、SSMS；Azure Arc 提供最佳实践评估。证据：官方文档 + 社区共识

7 连接模型 有

有。TDS 协议；连接池在客户端驱动侧（ADO.NET 连接池），服务端按 worker 线程调度；版本按内存/CPU 上限约束并发能力。证据：官方文档 + 社区共识

8 事务与隔离级别 有

有。完整 ACID；默认 READ COMMITTED 是加锁读（读写互阻塞），RCSI/快照隔离需显式开启（代价是 tempdb 版本存储）；支持保存点；Windows 上支持 DTC 分布式事务。证据：官方文档

9 复制与一致性 有

有（见基本信息）。同步提交要求备库日志 hardening（落盘，非重做）才返回，主库提交延迟 = 网络 RTT 税；异步提交主库不等确认，允许备库落后。证据：官方文档

10 扩展方式 部分支持（纵向为主）

部分支持（纵向为主）。Enterprise 单实例 CPU/内存无上限（只受 OS 限制）；横向能力有限：可读副本（备库只读分流）、分布式 AG、手动分片。Standard 版单实例限 32 核/256GB 内存（2025 版官方口径）。证据：官方文档

11 兼容性 有

有。T-SQL 方言（与 Sybase 有历史渊源）；不兼容 MySQL/PG/Oracle 协议；SSMA 提供从 Oracle/MySQL/DB2 的迁移评估与转换。证据：官方文档

12 许可证与商业模式 有（商业闭源）

有（商业闭源）。Enterprise 仅按核；Standard 按核或 Server+CAL；Express/Developer 免费（Developer 禁生产）；Azure 上按 vCore/DTU/Serverless 计费，Arc 纳管支持 PAYG；Software Assurance 带来许可移动性与虚拟化权益。价格只询价，不引用标价（见文末授权核对清单）。证据：官方文档 + 第三方授权指南

1 Data-at-rest encryption / TDE Yes

Yes. TDE encrypts data files and transaction log files; if any database on the instance enables TDE, tempdb is automatically encrypted; backups of TDE-enabled databases are inherently encrypted. Key management: master-database certificate/asymmetric key → DMK → SMK hierarchy; EKM providers or Azure Key Vault (BYOK) supported. Also Always Encrypted (client-side column-level encryption — even DBAs can't see plaintext; secure enclave supports limited computation on ciphertext), backup encryption, dynamic data masking. Evidence: official docs

2 TLS / transport encryption Yes

Yes. Supports TLS 1.2/1.3, forced encrypted connections (ForceEncryption); since 2025, default Encrypt=True and TDS 8.0 over TLS 1.3 (third-party source; details to-be-verified). Evidence: primarily official docs

3 Auditing Yes

Yes. SQL Server Audit (server/database audit specifications), writable to files, security log, application log; Azure SQL can audit to Log Analytics/Storage. Evidence: official docs

4 Authentication & authorization Yes

Yes. Windows authentication (Kerberos/NTLM), SQL Server logins, Entra ID since 2025 (including Azure Arc managed identity); server roles / database roles / schema-level permissions, plus row-level security (RLS). Evidence: official docs

5 Backup & recovery Yes

Yes. Native BACKUP/RESTORE: full / differential / log backups, compressed backups, encrypted backups, backup to URL (Azure Blob); log chains support point-in-time recovery (PITR). Limitation: backups can only be restored to the same or newer version — no downgrade restores. Evidence: official docs

6 Observability Yes

Yes. DMV/DMF (wait statistics like sys.dm_os_wait_stats are every DBA's mother tongue), Extended Events, Query Store (enabled by default on new databases since 2022), SSMS; Azure Arc provides best-practices assessment. Evidence: official docs + community consensus

7 Connection model Yes

Yes. TDS protocol; connection pooling lives on the client driver side (ADO.NET connection pool); server schedules by worker thread; editions cap concurrency via memory/CPU limits. Evidence: official docs + community consensus

8 Transactions & isolation levels Yes

Yes. Full ACID; the default READ COMMITTED is locking reads (readers block writers), RCSI/snapshot isolation must be enabled explicitly (at the cost of tempdb version store); savepoints supported; DTC distributed transactions supported on Windows. Evidence: official docs

9 Replication & consistency Yes

Yes (see basic info). Synchronous commit requires the secondary to harden the log (durable write, not redo) before the primary returns — primary commit latency = network RTT tax; asynchronous commit doesn't wait for acknowledgment, allowing the secondary to lag. Evidence: official docs

10 Scaling Scale-up first

Scale-up first. Enterprise single instance has no CPU/memory ceiling (only OS limits); limited scale-out: readable replicas (secondary read offload), distributed AGs, manual sharding. Standard edition is limited to 32 cores / 256 GB RAM per instance (2025 edition, official statement). Evidence: official docs

11 Compatibility T-SQL dialect

T-SQL dialect (with historical Sybase roots); incompatible with MySQL/PG/Oracle protocols; SSMA provides migration assessment and conversion from Oracle/MySQL/DB2. Evidence: official docs

12 License & business model Commercial closed-

Commercial closed-source. Enterprise is per-core only; Standard is per-core or Server+CAL; Express/Developer are free (Developer forbidden in production); on Azure, billed by vCore/DTU/Serverless; Arc-managed instances support PAYG; Software Assurance brings license mobility and virtualization rights. 杀手特性

  1. Always Encrypted（含 secure enclave）：连 DBA 都看不到的列级加密 真本事：应用端驱动加密，密钥不出客户端，数据库内存里出现的是密文；enclave 允许在密文上做有限计算（模糊匹配、范围查询）。 边缘真相：要用它，应用必须改驱动/代码并管理列主密钥（CMK），运维复杂度从 DBA 侧转移到应用侧；enclave 需要 attestation，故障排查时"看不到明文"既是卖点也是排障地狱。适合的是"合规强制且应用可控"场景，不是"一键开启"。
  2. Query Store + 自动计划修正：执行计划的"飞行记录仪" 真本事：持久化保存计划历史与运行时统计，2022 起新库默认开；自动计划修正可在检测到回归时自动强制上一个好计划。 边缘真相：Query Store 本身有捕获与存储开销，高频 OLTP 要调捕获模式与保留期；自动修正只对"稳定可重复 workload"有效，ad-hoc 满天飞的系统里它帮不上忙。基线质量决定一切——没跑满一个业务周期的基线，修正就是瞎修正。
  3. 纵深安全栈：TDE + 审计 + RLS + 掩码 + Ledger 一套配齐 真本事：金融/政企合规要的"静态加密、传输加密、审计、行级权限、防篡改账本"全是第一方功能，不用拼第三方件，这是它相对开源库最硬的差异之一。 边缘真相：功能全不等于默认全开——TDE 证书过期会导致历史备份无法还原（真实事故类），审计写文件要规划存储，Ledger 有写入放大。安全栈的运维税是持续的，买之前先问团队有没有人懂证书生命周期管理。
  4. 2025 的 Optimized Locking（TID 锁 + LAQ）：不改代码的并发提升 真本事：锁在谓词判定之后再获取（Lock After Qualification），大幅减少锁内存与阻塞；Azure SQL 先验证过的技术下放到本地版。 边缘真相：这是 2025 新行为，老 DBA 的阻塞排障肌肉记忆（看 LCK_M_* 等）要更新；是否要求兼容级别 170 待验证。以及它缓解的是锁争用，不是烂 SQL——缺索引的全表扫描照样慢。
  5. 混合云故事：Arc 纳管 + Fabric 镜像 真本事：本地 SQL Server 可被 Azure Arc 统一纳管（清点、评估、PAYG 计费），数据可近实时镜像到 Fabric OneLake 做分析，OLTP 与分析解耦不写 ETL。 边缘真相：Arc 是 agent 依赖，容器里跑的 SQL Server 不支持 Arc 相关能力（官方明确）；Fabric 镜像是"分析加速器"不是"第二活库"，指望它当 DR 是误用。
  1. Always Encrypted (with secure enclave): column-level encryption even DBAs can't see Why it's real: encryption happens in the application driver; keys never leave the client; the database only ever sees ciphertext in memory; enclaves allow limited computation (fuzzy matching, range queries) on ciphertext. Edge truth: to use it, the application must change drivers/code and manage column master keys (CMK) — operational complexity moves from the DBA side to the application side; enclaves require attestation, and "can't see plaintext" is a selling point and a troubleshooting hell at once. This fits "compliance-mandated and application-controlled" scenarios — not "turn it on and forget".
  2. Query Store + automatic plan correction: the flight recorder for execution plans Why it's real: persistently stores plan history and runtime statistics, enabled by default on new databases since 2022; automatic plan correction can detect regressions and force the last good plan automatically. Edge truth: Query Store itself has capture and storage overhead — high-frequency OLTP workloads need to tune capture mode and retention; automatic correction only helps "stable, repeatable workloads" — systems full of ad-hoc queries get no help. Baseline quality decides everything: correcting against a baseline that hasn't covered a full business cycle is correcting blind.
  3. Defense-in-depth security stack: TDE + audit + RLS + masking + Ledger in one box Why it's real: everything finance/government compliance asks for — data-at-rest encryption, transport encryption, auditing, row-level permissions, tamper-evident ledger — is a first-party feature; no assembling third-party parts. This is one of its hardest differences vs. open-source databases. Edge truth: full feature list doesn't mean everything is on by default — an expired TDE certificate can make historical backups unrestorable (real accident class), file-based auditing needs storage planning, Ledger adds write amplification. The security stack's operational tax is ongoing; before buying, ask whether the team has anyone who understands certificate lifecycle management.
  4. 2025's Optimized Locking (TID locks + LAQ): concurrency gains without code changes Why it's real: locks are acquired after predicate qualification (Lock After Qualification), dramatically reducing lock memory and blocking; technology battle-tested on Azure SQL brought down to the on-prem edition. Edge truth: this is new 2025 behavior — veteran DBAs' blocking-troubleshooting muscle memory (watching LCK_M_* waits) needs updating; whether compatibility level 170 is required is to-be-verified. And it mitigates lock contention, not bad SQL — full table scans missing indexes are still slow.
  5. Hybrid cloud story: Arc management + Fabric mirroring Why it's real: on-prem SQL Server can be centrally managed by Azure Arc (inventory, assessment, PAYG billing), and data can be mirrored near-real-time into Fabric OneLake for analytics — OLTP and analytics decoupled without writing ETL. Edge truth: Arc is an agent dependency — SQL Server running in containers doesn't support Arc-related capabilities (officially stated); Fabric mirroring is an "analytics accelerator", not a "second live database" — relying on it as DR is misuse.

深水区

深水区一（授权与成本）：按核计费是把双刃剑，CAL 的"多路复用"不省钱

  • 机制：Enterprise 只按核卖，Standard 可选按核或 Server+CAL；有 SA 才允许"按虚机授权"和获得免费被动副本；Azure Hybrid Benefit 可把本地许可折抵到云上。
  • 推到边缘：
    • 虚机上 vCPU 在建虚机时随手给大，授权数虚胖 15–30% 是第三方审计里的常见发现——分配的核，不是用的核，决定账单。
    • CAL 模式下，应用经中间层连接不能减少 CAL 数量（多路复用规则），最终用户数照算；互联网应用基本只能选按核。
    • 被动副本"免费"的前提是 SA 在有效期内且副本真正被动（可读副本不算被动），很多团队的"高可用"最后在授权审计里变成"要补钱"。
    • Developer 版功能与 Enterprise 完全一致但禁生产——开发/测试环境误用生产许可是 SAM 审计重灾区。
  • 选型含义：询价前先做"计量边界核对清单"（见文末）；核心数/CAL 数/SA 状态三个变量任一个没对齐，报价单都失真。授权复杂度本身就是 TCO 的一部分。

深水区二（复制与容灾）：Always On 的自动故障转移比想象中苛刻

  • 机制：同步提交 = 主库等备库日志 hardening（落盘）才提交；自动故障转移要求：主备均为同步提交 + 自动故障转移模式 + 备库处于 SYNCHRONIZED + WSFC 仲裁正常 + 满足灵活故障转移策略。
  • 推到边缘：
    • 仲裁丢了，整个 AG 不会自动切——仲裁是比 AG 更大的单点，脑裂靠"多数派仲裁"防，但代价是少数派分区直接停写。2025 增强了仲裁丢失后的恢复逻辑官方文档，防止库卡在 Not Synchronizing，但这只是"恢复更快"，不是"不丢仲裁也能切"。
    • 异步提交的唯一故障转移方式是强制故障转移（可能丢数据），且只能手动——DR 演练时 DBA 必须亲手按按钮，RTO 里要算上"人"的时间。
    • 同步备库的 redo 队列是隐形杀手：备库重做跟不上时，故障转移时间被 redo 拖长，RPO=0 不等于 RTO 小。
    • Standard 版只有 Basic AG（2 节点、每组 1 个库），完整 AG 是 Enterprise 专属——"高可用"三个字在两个版本里不是一个东西。
  • 选型含义：AG 方案评审要画仲裁拓扑（见证放在哪），压测要测备库 redo 延迟，RTO 承诺要含"人肉决策"时间。

深水区三（存储与并发）：TempDB 是全实例的共享税，锁升级是隐形阻塞源

  • 机制：TempDB 被所有会话共享（排序、溢出、版本存储、临时表），分配页 PFS/GAM/SGAM 是全局串行点；单语句持锁超约 5000 个会触发锁升级（行锁→表锁）。
  • 推到边缘：
    • 高并发 OLTP 下 TempDB 分配页出现 PAGELATCH_EX 等待，经典解法是"文件数 = 逻辑 CPU 数（上限 8）+ 等大文件"；2022 起 tempdb 元数据优化与 GAM/SGAM 增强缓解了争用，但版本存储（RCSI/快照的代价）依然住在 TempDB——开了 RCSI 就要给 TempDB 留 IO 预算，这是拆东墙补西墙。
    • 一个批量 UPDATE 突然阻塞整张表的无关查询：大概率是锁升级过了 5000 阈值。NOLOCK 能绕开阻塞，但代价是脏读 + 页分裂导致的丢行/重行（正确性 bug，不只是"读到旧数据"）。
    • 2025 的 LAQ/TID 锁缓解锁争用，但改变的是"锁什么时候拿"，拿不拿、拿多少还是看执行计划。
  • 选型含义：TempDB 要独盘、预分配、等大文件三件套写进部署规范；RCSI 不是免费午餐，POC 时必须开着目标隔离级别压测。

深水区四（运维与升级）：升级是单向门，真正的风险在优化器

  • 机制：in-place 升级不支持降级；备份只能向上还原；兼容级别让"引擎升级"与"优化器行为变更"解耦——老库升级后保留旧兼容级别，新 CE（基数估计器）只在新级别生效。
  • 推到边缘：
    • 升级最大的坑不是引擎装不上，而是升了兼容级别后执行计划回归：新 CE 对关联谓词、相关列的估计方式变了，慢查询在升级后"凭空"出现。标准流程是：保持旧兼容级别升级 → 开 Query Store 跑满一个业务周期采基线 → 逐库升兼容级别 → 用 Query Store 找回归强制旧计划。跳过基线直接升级别，等于闭眼换引擎。
    • 大表统计信息自动更新阈值约 SQRT(1000×行数)：10 亿行表要 100 万行变更才触发，统计信息"算新鲜"但实际已漂移很远——升级前后都要查统计信息新鲜度。
    • side-by-side 是生产环境唯一推荐路径（可回退=切 DNS），in-place 留给测试环境；50 个实例的 in-place 是单向门叠 buff。
  • 选型含义：升级预算要按"引擎升级 + 兼容级别爬坡 + 计划回归治理"三段算，只算第一段的一定爆。

深水区五（兼容与迁移）：Azure SQL 的"95% 兼容"是迁移时最贵的 5%

  • 机制：Azure SQL Database 与本地引擎同源但 PaaS 化：无 SQL Agent（用 Elastic Jobs/自动化）、无跨库查询（用 elastic query）、无手动备份（平台自动备份+PITR）、无 Windows 认证/链接服务器/FILESTREAM；Managed Instance 接近 99%，SQL VM 则是 100% 本地版。
  • 推到边缘：
    • 迁移评估（DMA/SSMA）扫出来"不支持"最多的三件套：SQL Agent 作业、跨库三段式命名、CLR/链接服务器——恰好是老系统最爱用的。
    • 计费模型 DTU（打包）vs vCore（分开配）：DTU 简单但扩缩不灵活，vCore 灵活但选错 tier 账单难看；Serverless 自动暂停省的是闲置钱，代价是唤醒延迟， latency 敏感的生产库别碰。
    • 备份策略要重写：本地那套"全备+差异+日志自建保留策略"在 SQL DB 上不存在，RPO/RTO 改由平台 SLA 定义，合规审计要换口径。
  • 选型含义：上 Azure 不是"搬机器"，是"换运维模型"；POC 必须跑真实作业与跨库调用，不要只测单库 CRUD。

Deep Water 1 (Licensing & cost): per-core billing is a double-edged sword; CAL "multiplexing" doesn't save money

  • Mechanism: Enterprise is sold per-core only; Standard can be per-core or Server+CAL; only SA allows "licensing by VM" and free passive replicas; Azure Hybrid Benefit lets on-prem licenses offset cloud spend.
  • At the edge:
    • vCPUs sized generously when a VM is created inflate license counts 15–30% in third-party audit findings — allocated cores, not used cores, determine the bill.
    • Under CAL licensing, applications connecting through a middle tier do not reduce CAL counts (the multiplexing rule); end users are counted regardless; internet-facing applications basically must license per-core.
    • The "free" passive replica requires SA to be active and the replica to be genuinely passive (a readable replica doesn't count as passive) — many teams' "high availability" turns into "you owe money" at license audit time.
    • Developer edition is feature-identical to Enterprise but production-forbidden — misusing production licenses in dev/test environments is a SAM-audit disaster zone.
  • Selection implication: align the "metering boundary checklist" (at the end) before requesting a quote; if any of the three variables — core count, CAL count, SA status — is off, the quote is fiction. Licensing complexity itself is part of TCO.

Deep Water 2 (Replication & DR): Always On automatic failover is stricter than you think

  • Mechanism: synchronous commit = primary waits for secondary log hardening (durable write) before committing; automatic failover requires: both primary and secondary on synchronous commit + automatic failover mode + secondary in SYNCHRONIZED state + WSFC quorum healthy + flexible failover policy satisfied.
  • At the edge:
    • If quorum is lost, the whole AG won't fail over automatically — quorum is a bigger single point of failure than the AG itself; split-brain is prevented by "majority quorum", but the cost is that minority partitions go write-stopped. 2025 improved post-quorum-loss recovery logic 官方文档, preventing databases from getting stuck in Not Synchronizing — but that's "faster recovery", not "failover without quorum".
    • The only failover mode for asynchronous commit is forced failover (may lose data), and it's manual only — during DR drills the DBA must press the button by hand; budget "human decision time" into RTO.
    • The synchronous secondary's redo queue is the invisible killer: when the secondary can't keep up with redo, failover time stretches with redo; RPO=0 does not mean small RTO.
    • Standard edition only gets Basic AG (2 nodes, 1 database per group); the full AG is Enterprise-only — "high availability" isn't the same phrase in the two editions.
  • Selection implication: AG design reviews must draw the quorum topology (where the witness lives), stress tests must measure secondary redo lag, and RTO commitments must include "human decision" time.

Deep Water 3 (Storage & concurrency): TempDB is a whole-instance shared tax; lock escalation is an invisible blocking source

  • Mechanism: TempDB is shared by all sessions (sorts, spills, version store, temp tables); allocation pages PFS/GAM/SGAM are global serialization points; a single statement holding ~5,000+ locks triggers lock escalation (row locks → table lock).
  • At the edge:
    • Under high-concurrency OLTP, TempDB allocation pages show PAGELATCH_EX waits; the classic fix is "file count = number of logical CPUs (capped at 8) + equally sized files"; 2022's tempdb metadata optimization and GAM/SGAM enhancements eased contention, but the version store (the cost of RCSI/snapshot) still lives in TempDB — enabling RCSI means budgeting IO for TempDB; that's robbing Peter to pay Paul.
    • One batch UPDATE suddenly blocking unrelated queries on the whole table: most likely lock escalation crossing the ~5,000 threshold. NOLOCK dodges the blocking, but the cost is dirty reads plus page splits causing missing/repeated rows (a correctness bug, not just "reading stale data").
    • 2025's LAQ/TID locks mitigate lock contention, but they change "when the lock is taken" — whether and how many locks are taken still depends on the execution plan.
  • Selection implication: write the TempDB spec into deployment standards — dedicated disks, pre-sizing, equally sized files; RCSI is not a free lunch; POCs must stress-test under the target isolation level.

Deep Water 4 (Operations & upgrades): upgrade is a one-way door; the real risk is in the optimizer

  • Mechanism: in-place upgrades don't support downgrade; backups restore only upward; compatibility levels decouple "engine upgrade" from "optimizer behavior change" — old databases keep their old compatibility level after upgrade, and the new CE (cardinality estimator) only takes effect at the new level.
  • At the edge:
    • The biggest upgrade pitfall isn't the engine failing to install — it's plan regressions after raising the compatibility level: the new CE estimates join predicates and correlated columns differently, and slow queries appear "out of nowhere" post-upgrade. The standard flow: upgrade at the old compatibility level → run Query Store for a full business cycle to collect a baseline → raise compatibility level database by database → use Query Store to force old plans on regressions. Skipping the baseline and raising the level directly is swapping the engine blindfolded.
    • Large-table auto-update statistics threshold ≈ SQRT(1000 × rows): a 1-billion-row table needs 1M row changes to trigger; statistics "count as fresh" while actually drifting far — check statistics freshness before and after upgrade.
    • Side-by-side is the only recommended production path (rollback = flipping DNS); in-place stays in test environments; in-place across 50 instances is stacking one-way doors.
  • Selection implication: budget upgrades in three phases — "engine upgrade + compatibility-level climb + plan-regression remediation". Budgeting only the first phase guarantees overrun.

Deep Water 5 (Compatibility & migration): Azure SQL's "95% compatibility" hides the most expensive 5%

  • Mechanism: Azure SQL Database shares the same engine lineage but is PaaS-ified: no SQL Agent (use Elastic Jobs/automation), no cross-database queries (use elastic query), no manual backups (platform automatic backup + PITR), no Windows authentication/linked servers/FILESTREAM; Managed Instance is ~99%, and SQL VM is 100% the on-prem edition.
  • At the edge:
    • Migration assessment (DMA/SSMA) flags "unsupported" most often on three things: SQL Agent jobs, cross-database three-part naming, CLR/linked servers — exactly what legacy systems love most.
    • Billing models DTU (bundled) vs vCore (separately provisioned): DTU is simple but inflexible to scale, vCore is flexible but picking the wrong tier makes the bill ugly; Serverless auto-pause saves idle money at the cost of wake-up latency — latency-sensitive production databases should stay away.
    • Backup strategy must be rewritten: the on-prem "full + differential + log self-built retention" doesn't exist on SQL DB; RPO/RTO are defined by the platform SLA, and compliance audits must change caliber.
  • Selection implication: moving to Azure isn't "moving machines", it's "changing the operations model"; POCs must run real jobs and cross-database calls, not just single-database CRUD.

用户最买账的 5 点

  1. SSMS + T-SQL 生态：RDBMS 里最成熟的工具链
    • 为什么是真的：SSMS 的图形化执行计划、活动监视器、Profiler/Extended Events 链条完整；T-SQL 人才池是所有数据库里最深的，招 DBA 最容易。
    • 边缘与限度：SSMS 是 Windows only，跨平台靠 Azure Data Studio（功能弱一档）；人才池深但老龄化，新生代开发者更熟悉 PG/MySQL。生态强的另一面是锁定——SSIS/SSRS/SSAS 全家桶迁出去的成本极高。
  2. 查询优化器与 IQP（智能查询处理）："不改代码变快"的代表
    • 为什么是真的：自适应连接、批处理模式、参数敏感计划优化（2022+）等多代 IQP 积累，优化器是业界标杆；很多升级收益不需要改 SQL。
    • 边缘与限度：优化器的聪明建立在统计信息和"第一次编译的参数值"上——参数嗅探（为首个参数值编译的计划被后续调用复用）是 DBA 的经典噩梦；2022 的参数敏感计划优化与 2025 的可选参数计划优化是缓解，不是根治。
  3. Always On 高可用口碑
    • 为什么是真的：同步提交 RPO=0 是真同步（备库日志落盘确认），可读副本能分流报表，2012 年至今 10+ 年生产验证。
    • 边缘与限度：见深水区二——同步的代价是提交延迟=网络 RTT，跨城同步 AG 的写延迟是物理定律；仲裁、redo 队列、人肉决策都是 RTO 的组成部分。"RPO=0"不等于"故障无感知"，应用重连与 DNS 切换的时间要算进去。
  4. 安全合规栈开箱即用
    • 为什么是真的：TDE、Always Encrypted、审计、RLS、动态掩码、Ledger 全是第一方功能，等保/金融合规要的材料一次配齐，不用攒第三方件。
    • 边缘与限度：见杀手特性 3——证书生命周期、审计存储、Ledger 写放大都是持续运维税；功能"有"不等于"开"，POC 时要按合规清单逐项验证开启状态与开销。
  5. 向后兼容：30 年前的应用还能跑
    • 为什么是真的：兼容级别机制让老库平滑升级；T-SQL 方言稳定，企业里跑 10 年以上的存储过程是常态。
    • 边缘与限度：兼容是双刃剑——老兼容级别意味着用老 CE、错过新优化器，"能跑"不等于"跑得好"；技术债被兼容性掩盖，越往后还越贵。选型时要问：团队是"需要兼容"还是"在拿兼容当借口不重构"。
  1. SSMS + T-SQL ecosystem: the most mature toolchain among RDBMSs
    • Why it's real: SSMS's graphical execution plans, activity monitor, and the Profiler/Extended Events chain are complete; the T-SQL talent pool is the deepest of any database — hiring DBAs is easiest.
    • Edge and limits: SSMS is Windows-only; cross-platform relies on Azure Data Studio (one tier weaker); the deep talent pool is aging, and the new generation of developers knows PG/MySQL better. The flip side of a strong ecosystem is lock-in — migrating off the SSIS/SSRS/SSAS full stack is extremely expensive.
  2. Query optimizer and IQP (Intelligent Query Processing): the poster child of "faster without code changes"
    • Why it's real: multiple generations of IQP accumulation — adaptive joins, batch mode, parameter-sensitive plan optimization (2022+) — make it the industry benchmark optimizer; many upgrade gains require no SQL changes.
    • Edge and limits: the optimizer's intelligence rests on statistics and "the parameter value at first compile" — parameter sniffing (a plan compiled for the first parameter value being reused by later calls) is the classic DBA nightmare; 2022's parameter-sensitive plan optimization and 2025's optional parameter plan optimization are mitigations, not cures.
  3. Always On high-availability reputation
    • Why it's real: synchronous commit RPO=0 is genuine synchrony (secondary log-durable acknowledgment); readable replicas can offload reporting; 10+ years of production validation since 2012.
    • Edge and limits: see Deep Water 2 — the cost of synchrony is commit latency = network RTT; cross-city synchronous AG write latency is physics; quorum, redo queues, and human decisions are all components of RTO. "RPO=0" ≠ "failover is invisible" — application reconnection and DNS switchover time count.
  4. Out-of-the-box security/compliance stack
    • Why it's real: TDE, Always Encrypted, auditing, RLS, dynamic masking, Ledger are all first-party features — compliance materials for 等保 (China's MLPS cybersecurity standard) / finance land in one pass, no assembling third-party parts.
    • Edge and limits: see Killer Feature 3 — certificate lifecycle, audit storage, and Ledger write amplification are ongoing operational taxes; "feature exists" ≠ "feature is on"; POCs should verify each compliance checklist item's enabled state and overhead.
  5. Backward compatibility: 30-year-old applications still run
    • Why it's real: compatibility levels let old databases upgrade smoothly; the T-SQL dialect is stable; stored procedures running 10+ years are common in enterprises.
    • Edge and limits: compatibility cuts both ways — an old compatibility level means an old CE and missing the new optimizer; "it runs" ≠ "it runs well"; technical debt gets masked by compatibility, and the longer it accumulates, the more it costs to repay. Ask at selection time: does the team "need compatibility" or "use compatibility as an excuse not to refactor"?

判决

  • 适合谁：Windows/.NET 技术栈团队；需要 RPO=0 同步高可用 + 可读副本分流的企业 OLTP；强合规行业（金融/政企/医疗）要开箱即用安全审计栈；已有 SQL Server DBA 人才储备、SSIS/SSAS/Power BI 全家桶的组织；"去 Oracle"但不想换分布式架构的传统企业。
  • 不适合谁：成本敏感的初创团队（授权是持续税）；Linux-first/云原生多语言团队（Linux 版是二等公民）；需要横向 scale-out 写扩展的互联网高并发场景；无专职 DBA 又想"装完不管"的团队（TempDB/AG/授权三件套都要人养）。
  • 迁移成本：MySQL → 中（方言差异大，SSMA 可评估，无协议兼容）；PostgreSQL → 中（SQL 方言接近但 T-SQL 特性、窗口函数细节、过程语言都要改）；Oracle → 中高（PL/SQL→T-SQL 改造成本高，但授权费从 Oracle 降到 SQL Server 是经典降本路径，SSMA for Oracle 可辅助）。
  • Fits: Windows/.NET stack teams; enterprise OLTP needing RPO=0 synchronous HA + readable-replica offload; heavily regulated industries (finance/government/healthcare) wanting an out-of-the-box security-and-audit stack; organizations with SQL Server DBA talent and the SSIS/SSAS/Power BI full stack; traditional enterprises "leaving Oracle" without switching to a distributed architecture.
  • Doesn't fit: cost-sensitive startups (licensing is a continuing tax); Linux-first / cloud-native polyglot teams (the Linux edition is a second-class citizen); internet-scale high-concurrency scenarios needing horizontal scale-out write expansion; teams with no dedicated DBA hoping for "install and forget" (TempDB/AG/licensing all need tending).
  • Migration cost: MySQL → medium (large dialect differences; SSMA can assess; no protocol compatibility); PostgreSQL → medium (SQL dialects are close, but T-SQL features, window-function details, and procedural languages all need rework); Oracle → medium-high (PL/SQL→T-SQL rework is costly, but cutting license spend from Oracle to SQL Server is a classic cost-reduction path, with SSMA for Oracle to assist).

附录

询价前请先对齐以下每一项，否则报价单失真：

  1. 版本线：Enterprise（按核）还是 Standard（按核 / Server+CAL）——先定功能（AG 完整度、可读副本、安全特性），再定计费
  2. 核数口径：物理核还是 vCPU；虚机按虚机授权必须有 SA 或订阅；虚机 vCPU 是否虚胖（建虚机时随手给大是常见浪费）
  3. SA 状态：是否在有效期内——决定许可移动性、被动副本免费、版本升级权
  4. CAL 计数（如走 Server+CAL）：按用户还是按设备；经应用中间层不减少 CAL（多路复用规则）；互联网应用基本只能按核
  5. 高可用拓扑：被动副本是否"真被动"（可读=不免费）；仲裁见证的授权归属
  6. 非生产环境：开发/测试一律用免费 Developer 版，不要为非生产买 Enterprise
  7. 云路径：是否用 Azure Hybrid Benefit 折抵；Arc PAYG 按量是否比买断划算（波动型负载算三年 TCO）
  8. 历史包袱：老版本（2008–2014）是否在 ESU 续费，不如把 ESU 的钱折进升级预算

Align each of the following before requesting a quote, or the quote will be fiction:

  1. Edition line: Enterprise (per-core) or Standard (per-core / Server+CAL) — decide features first (AG completeness, readable replicas, security features), then billing
  2. Core-count metric: physical cores or vCPU; licensing a VM by VM requires SA or subscription; check whether VM vCPUs are bloated (casually oversizing at VM creation is common waste)
  3. SA status: whether it's active — decides license mobility, free passive replicas, upgrade rights
  4. CAL count (for Server+CAL): per-user or per-device; going through an application middle tier does not reduce CALs (the multiplexing rule); internet-facing applications are basically per-core only
  5. HA topology: whether the passive replica is "genuinely passive" (readable ≠ free); the witness's licensing ownership
  6. Non-production environments: use free Developer edition for all dev/test — never buy Enterprise for non-production
  7. Cloud path: whether to offset with Azure Hybrid Benefit; whether Arc PAYG beats buying outright (model 3-year TCO for fluctuating workloads)
  8. Legacy baggage: whether old versions (2008–2014) are renewing ESU — better to fold ESU money into the upgrade budget
